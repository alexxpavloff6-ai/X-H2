# A. LCD-линии: кто управляет флагом MOVDC и что такое `output+8`

Задача: найти всех писателей/читателей глобального флага MOVDC во всех блоках 0/1/2,
объяснить смысл флага, `source+8` / `output+8`, проверить сопутствующие изменения в той же
цепи и подтвердить поведение в Unicorn.

Все адреса — runtime VA (блок 1: X-H2 old база `0x29ae000`, new `0x29aa000`;
X-H2S `0x2cca000`; X-T5 `0x28eb000`). Файлы DAT — только чтение.

---

## 1. Кратко (что установлено)

1. **MOVDC — это лог-тег модуля** (`"MOVDC"`), а не имя структуры. Модуль занимает в блоке 1
   диапазон ~`0x3103ff8..0x312be60` (X-H2 new); в нём десятки функций и ~60 строк лога.
   Ключевые строки модуля: `MOVDC FREEZE`, `MOVDC NOTICE`, `MOVDC_DETCTRL`, `AftAbrt`,
   `NO_PLY`, `KEEP2!`, `MEMOVER!`, `C1BWind`, `C1BMask`, `C1BYCB/C1BYCR`, `C1AFea`,
   `C2AFcsN…`, `RRS_Fx/Fe1/Fe2`, `LOCK:%d %d`. Т.е. это модуль управления кадром/детекцией
   (окна/маски/АФ-признаки), который также пишет геометрию кадра в дескриптор.

2. **Флаг MOVDC — это снимок параметра камеры**, а не вычисляемое состояние:
   он копируется в структуру состояния MOVDC из блока параметров, где лежит по смещению
   **`+0x74`** от «текущей» копии параметров. Цепочка:
   `params.pending → memcpy → params.current (+0x74 = флаг) → apply-функции → state+0x43c/0x434 → MOVDC-функция`.

3. **Писателей флага всего два на прошивку** — это две функции «применения настроек»
   (apply1/apply2), и обе лишь **копируют** поле из блока параметров.

4. **Прямых писателей поля в самом блоке параметров нет ни в блоке 0, ни в 1, ни в 2**
   (проверено эмулятором по точной базе, а также поиском литералов). Значение приходит
   извне этого кода (другой процессор/API параметров) — см. §5, уровень «сильный кандидат».

5. **`output+8` — это stride (шаг строки в байтах)** дескриптора поверхности, а `source+8` —
   **текущее (прежнее) значение того же поля** того же дескриптора. MOVDC-функция пишет
   дескриптор `{height, width, stride}`; когда она берёт stride из геометрии, получается
   `2 × поле геометрии`; для 640×480 геометрия даёт поле `0x280 = 640`, т.е. **1280**.
   Старая версия (и новая при `flag == 0`) вместо этого наследует `p->[8] & ~1`;
   что унаследованное значение было неверным — не доказано (§6.3).

6. **Функциональное изменение ровно одно** — 3 инструкции guard'а внутри MOVDC-функции,
   одинаковые во всех трёх моделях. При `flag != 0` они **запрещают** брать stride из
   `source+8`, и тогда используется stride, вычисленный из геометрии (`2×640 = 1280`).
   При `flag == 0` обе версии наследуют `p->[8]`. Всё остальное в apply-функциях —
   перестановка регистров и переключение на **заглушки** (`ret`), т.е. функционально no-op.

7. **Unicorn-контроль** (реальные инструкции): при `flag=1` и текущем stride `640`
   старая версия пишет в дескриптор `stride=640`, новая — `1280`. При `flag=0` обе версии
   наследуют текущий stride (`640→640`, `1280→1280`); при текущем stride `1280` обе пишут
   `1280`. Совпадает по всем трём моделям.
   **Оговорка:** что унаследованный stride был *неверным* в дефектном режиме — не доказано
   (§6.3); дескриптор 640×480 и имена параметров модуля скорее указывают на кадр
   детекции/АФ, а не на изображение LCD (§5.4).

## 4. Что делает guard (точное поведение)

### 4.1 Старая версия (X-H2 old, 0x310808c–0x3108154)

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Ветка `flag==0` (`0x31083ac`) берёт `p->[0x10]` в `[sp+0x68]` и **прыгает в середину той же
записи** (`0x310811c`). Важно: `[sp+0x16c] = p->[8]>>1` вычисляется в `0x3108098–0x31080a8`
**до** проверки флага (`0x31080fc`) и **не зависит от флага** — только от `p != 0` и
`p->[0x10] != 0`. Поэтому в старой версии

> `out[8] = 2 * (p->[8]>>1) = p->[8] & ~1` **при обоих значениях флага**
> (если `p` и `p->[0x10]` ненулевые).

Геометрия (640) используется только если `p == 0` или `p->[0x10] == 0` (тогда присваивание
пропускается и в `[sp+0x16c]` остаётся значение, скопированное из геометрии, — то же и в
новой версии, см. VM-контроль в §7: `stride=1280` при `buf=0` у обеих версий).

### 4.2 Новая версия (X-H2 new, 0x3104200–0x31042d4)

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Итоговая семантика (согласуется с VM, `a19_vm_out.txt`):

| | `flag == 0` | `flag != 0` |
|---|---|---|
| старая | `out[8] = p->[8] & ~1` | `out[8] = p->[8] & ~1` |
| новая | `out[8] = p->[8] & ~1` | **`out[8] = 2*(geom) = 1280`** |

Т.е. старая версия **всегда наследует** stride дескриптора (`p->[8]`), а новая при
`flag != 0` **перестаёт наследовать** и принудительно берёт stride из геометрии;
при `flag == 0` поведение не изменилось. Меняется ровно одна ветка — `flag != 0`.

## 5. Смысл флага

### 5.1 Откуда он берётся (доказано)

Параметры камеры хранятся двумя копиями; `memcpy` переносит pending → current:

| Модель | memcpy (new) | pending → current | флаг = current+0x74 |
|---|---|---|---|
| X-H2 | `0x31015b4`: `mov w2,#0x168; adrp x1,#0x4c3b000; add x1,#0x90; adrp x0,#0x4c3b000; add x0,#0x1f8; bl memcpy` | `0x4c3b090 → 0x4c3b1f8` | `0x4c3b26c` ✔ |
| X-H2S | `0x341826c`: `mov w2,#0x170; … #0xe80 → #0xff0` | `0x4bb3e80 → 0x4bb3ff0` | `0x4bb4064` ✔ |
| X-T5 | `0x3043e9c`: `mov w2,#0x208; … #0x738 → #0x940` | `0x4ac2738 → 0x4ac2940` | `0x4ac29b4` ✔ |

Затем apply-функции копируют поле в состояние. X-H2 new (apply1, `0x3104614`):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

X-H2S: `0x341b134 ldr w2,[x0,#0x1ec] → 0x341b138 str w2,[x1,#0x434]`, дескриптор
`+0x1c8 → +0x480`. X-T5: `0x3047008 ldr w2,[x1,#0x284] → 0x304700c str w2,[x0,#0x43c]`,
дескриптор `+0x260 → +0x488`.

Соседние поля (X-H2 `+0x1e0/+0x1e8/+0x1ec/+0x1f0` → state `+0x438/+0x440/+0x444/+0x448`)
— это группа 32-битных параметров; `+0x1c0` — указатель на дескриптор кадра.
**Отдельного «enum-имени» у флага нет** — он адресуется как смещение в блоке параметров.

### 5.2 Кто пишет 0/1 (не найдено — важный отрицательный результат)

* Прямых `str` в поле параметров (`0x4c…26c`/`0x4c…064`/`0x4ac29b4`) **нет** ни в блоке 1
  (эмулятор по точной базе), ни в блоках 0 и 2.
* Отдельно проверен «косвенный» вариант из подсказки: `adrp+add` даёт базу структуры в
  регистр, база передаётся в callee, запись идёт по `[x0,#off]` — для поля флага таких
  записей нет: скан по точной базе структуры (X-H2 `0x4c3b088`/`0x4c3f088`, X-H2S
  `0x4bb3e78`, X-T5 `0x4ac2730`) в диапазоне `+0..+0x400` в блоках 0/1/2 находит только
  чтения, и все они — сами копирующие `ldr` в apply-функциях (плюс `ldrb [..,#0x2c4]`
  другого поля той же структуры).
* Писателей в состояние (`state+0x43c/0x434`) ровно два — apply1/apply2 (см. §3).
* Литеральных (`ldr xN,=addr`) ссылок на флаг и на поле-источник **нет**.
* Указателей на блок параметров в данных **нет** (`0x4c3b090/0x4c3b088/0x4c3b1f8`
  как u64 не встречаются).

Вывод: **значение флага формируется вне блоков 0–2** — его кладёт другой процессор/канал
параметров (или оно приходит из UI/настроек через API, который адресует параметры
переменным смещением). Статически в этих трёх блоках «кто ставит 1» не находится.

### 5.3 Как код использует флаг (доказано)

Флаг используется как селектор состояния, а не как счётчик:

1. **MOVDC-функция, режимы 9..11** (`0x4c2faf4 - 9 <= 2`):
   * `flag != 0` → **не** перезаписывать поле stride из `p->[8]` (новый guard); в
     `out[8]` идёт `2 × геометрия`;
   * `flag == 0` → поле stride = `p->[8]>>1`, `out[8] = p->[8] & ~1` (как в старой версии).
2. **apply2 (`0x3104b50`)**: `3104c5c: cmp w2,#0; 3104c60: ccmp x1,#0,#4,eq;
   3104c64: b.ne 0x3104c8c` (`w2` = флаг, `x1` = `p`). По ARM `ccmp` при **истинном**
   условии `eq` (флаг == 0) выполняет сравнение `x1` с 0, а при ложном — ставит `NZCV=4`
   (`Z=1`). Поэтому:
   * `flag == 0 && p != 0` → переход на `0x3104c8c`;
   * `flag != 0` или `p == 0` → сразу на `0x3104c68: bl #0x3103ff8` (MOVDC-функция).

   На `0x3104c8c`: `ldr x0,[x1,#0x10]; cbz x0,0x3104c68` → flush-заглушки
   (`0x155bde8`, `0x155bde0` — обе `ret`/`mov w0,#1; ret`) и `3104cb4: b #0x3104c68`.
   Т.е. **MOVDC-функция вызывается в любом случае**, различаются только заглушки.
3. **apply1 (`0x3104614`)**: `3104754: cmp w2,#0; 3104758: ccmp x1,#0,#4,eq;
   310475c: b.ne 0x31048d0` — по тому же правилу переход на `0x31048d0` происходит при
   **`flag == 0 && p != 0`**; там `ldr x0,[x1,#0x10]; cbz x0,0x3104760`, заглушки и
   `31048f8: b #0x3104760` (общая инициализация). Т.е. и здесь отличие только в заглушках.
4. **Обработчик смены режима (`0x3102434`, X-H2 new)**:
   `310247c: ldr w0,[flag]; 3102480: cmp w0,#0; 3102484: ccmp w19,#1,#4,ne;
   3102488: b.ne 0x310256c` — здесь `eq` заменён на `ne`, поэтому переход берётся при
   `flag != 0 && params.current+0x10 != 1`; позже
   `31024cc: ldr w0,[state+0x43c]; cmp w0,#1; b.ne` и при `flag == 1` — вызов
   зарегистрированного колбэка `*(0x4bc5808)`.

Направление ветвлений пп.2–3 дополнительно проверено в VM (`a21_branch_vm.py`, §7.2):
`flag=0, p!=0` → ветка; `flag!=0` (любой `p`) → прямо на вызов MOVDC-функции.

### 5.4 Интерпретация (уровень: сильный кандидат) и важное ограничение

Флаг — **снимок параметра «режим MOVDC/дисплея»** (условно `MOVDC_MODE`), который
ненулевой в специальном режиме, где кадр для MOVDC приходит из другого источника/буфера,
и поэтому текущий stride дескриптора нельзя переиспользовать. В коде нет строк/таблиц,
которые связывали бы его с CH/ES/1/8000/IMAGE DISP — эта связь следует только из того,
что **исправление функционально срабатывает лишь при `flag != 0`** (§4.2, §7), а симптом
проявлялся именно в наборе «CH HIGH SPEED BURST + электронный затвор + ≤1/8000 +
IMAGE DISP=CONTINUOUS». Прямого доказательства «флаг = IMAGE_DISP_CONTINUOUS» нет (в коде нет ни строки, ни
таблицы, связывающей значение с этой настройкой; проверка `==1` и нулевые/ненулевые ветки
не соответствуют перечислению IMAGE DISP). Поэтому такая привязка **не подтверждена** и
оставлена как гипотеза; таблицы `UI_SETP_*` (CONTINUOUS/BRACKET/SHUTTER/IMAGE_DISP),
по данным КОНТЕКСТА, не изменились.

**Ограничение: дескриптор скорее относится к кадру детекции/АФ, чем к изображению LCD.**
Против прямой привязки к LCD говорят:
* геометрия **640×480** (`0x1e0/0x280`) — типичный размер кадра для детектора/АФ, а не
  матрицы LCD (у X-H2 ~1.62 Мточки) и не live view (1920×1080);
* строки модуля — имена параметров детектора/АФ: `MOVDC_DETCTRL`, `C1BWind`, `C1BMask`,
  `C1BYCB/C1BYCR`, `C1AFea`, `C1AFeaW`, `C2AFcsN/C2AFcsD`, `C3ACsrM`, `RRS_Fx/Fe1/Fe2`;
* геттер геометрии `0x310379c` вызывается только из функций этого модуля
  (`0x3103c28`, `0x3103e28`, `0x3124e50`, `0x3124f38`, `0x3124f94` и helper `0x3103b10`),
  т.е. это «геометрия кадра детекции», а не общая геометрия дисплея;
* дескриптор пишется **по слоту** (`state+0x3a70 + idx*0x68`) и в общий `state+0x488`;
  потребителя в блоках 0–2 нет (см. §6.3).

Если это действительно только вход детектора, то неверный stride искажает вход АФ/трекинга,
а видимые горизонтальные линии на LCD — **вторичный эффект или отдельная связь** (например,
тот же буфер/кадр показывается в режиме CONTINUOUS, либо портится копия кадра, из которой
строится изображение). Уровень этой связи — **гипотеза**; признаков того, что именно этот
дескриптор выводится на экран, в блоках 0–2 не найдено. Если потребитель найдётся
(драйвер дисплея / колбэк `*(0x4bc5808)` / таблица `0x4bc5830`), связь можно будет усилить
или, наоборот, снять.

## 6. `source+8` и `output+8`: что это и как даёт горизонтальные линии

### 6.1 Дескриптор вывода

`p = *(state+0x488)` (X-H2/T5) или `*(state+0x480)` (X-H2S) — это **один и тот же объект**,
что и `source` в guard'е: `0x4c2fad8 + 0x488 = 0x4c2ff60` — ровно тот адрес, откуда
читается `p` в `3104200: ldr x0,[x0,#0xf60]`.

Структура (по коду MOVDC-функции и геттера геометрии):

| Смещение | Поле | Кто пишет/читает |
|---|---|---|
| `+0x00` | height | MOVDC: `out[0] = [sp+0x164]` |
| `+0x04` | width | MOVDC: `out[4] = [sp+0x168]` |
| `+0x08` | **stride в байтах** | MOVDC: `out[8] = 2*[sp+0x16c]` |
| `+0x10` | указатель на пиксели | проверяется `cbz` перед использованием |
| `+0x18` | размер (для flush) | `ldr w2,[x0,#0x18]` в apply-функциях |

`source+8` в guard'е — **текущее значение stride этого же дескриптора** (до перезаписи).
Т.е. старый код фактически «оставлял» прежний stride (менял только младший бит:
`2*(x>>1) = x & ~1`), а новый код при `flag!=0` заменяет его на `2 × геометрия`.

### 6.2 Геометрия и stride, который задаёт код

Геттер геометрии: MOVDC-функция вызывает 8-аргументный helper (`X-H2 new: 31040c0: bl #0x3103b10`
с `x1=sp+0x100, x2=sp+0xf0, x3=sp+0xe0, x4=sp+0x50`), который, в свою очередь, зовёт геттер
`0x310379c(2, sp+0xf0)`. Геттер пишет тройку:

```
31037e8..3103818 (ветка по режиму):
  str w?, [x19, #4]   ; width  = таблица режимов
  str w?, [x19]       ; height = таблица режимов
  mov w0,#0x280 ; str w0,[x19,#8]   ; stride-поле = 0x280 = 640
```

Для 640×480 та же тройка есть в `0x31039d0`: `str w0,[x20,#4] (0x280), str w1,[x20] (0x1e0),
str w0,[x20,#8] (0x280)`. Аналогичные последовательности подтверждены в X-H2S
(`0x341a45c`) и X-T5 (`0x3046324`) — константы те же: `0x1e0/0x280/0x280`.

Затем MOVDC-функция копирует `[sp+0xf0..]` в `[sp+0x164..]`. Если поле `[sp+0x16c]`
осталось геометрическим (`flag != 0` в новой версии, либо `p == 0`/`p->[0x10] == 0`), то
`out[8] = 2 × 640 = 1280` (16 бит/пиксель, ширина 640 ⇒ 1280 байт/строку). Если же поле
перезаписано из `p->[8]`, то `out[8] = p->[8] & ~1` — так ведёт себя старая версия всегда и
новая при `flag == 0`.

### 6.3 Механизм горизонтальных линий (гипотеза; арифметика проверена, «плохое» значение — нет)

Что **доказано**: при `flag != 0` новая версия перестаёт наследовать stride дескриптора и
принудительно ставит `2 × геометрия = 1280`; при `flag == 0` обе версии наследуют
`p->[8] & ~1` (VM, §7). Т.е. исправление меняет значение `out[8]` **только** в случае
`flag != 0` и только если `p->[8] & ~1 != 1280`.

Что **не доказано**: было ли унаследованное значение в дефектном режиме неверным. При
`flag == 0` значение 640 проходит без изменений и в старой, и в новой версии — сам по себе
факт «640 в дескрипторе» дефектом не является (для 8-битного кадра/другой поверхности это
может быть корректно). Поэтому формулировка «640 — плохой stride» **не подтверждена** и
здесь не используется.

Как неверный stride мог бы давать линии (условно): если фактический шаг поверхности —
1280 байт (640 px × 2 байта/px), а в дескриптор записан 640, то каждая следующая строка
начинается на полстроки раньше; изображение «складывается» из перекрывающихся половин
строк — визуально горизонтальные полосы/«разрыв строк». Это объяснение работает **только
при условии**, что унаследованный `p->[8]` не совпадал с фактическим шагом поверхности и
что эта поверхность так или иначе попадает на экран. Оба условия — **гипотеза**.

Проверено в VM (см. §7): при `cur_stride=640` old пишет 640, new — 1280; при
`cur_stride=1280` обе версии пишут 1280. Поэтому дефект мог проявляться только в режиме,
где `flag != 0` **и** дескриптор имел stride, отличный от `2 × геометрия`.

**Не доказано:** кто и когда ставит `p->[8]` в такое значение (это вне блоков 0–2; указатель
на дескриптор приходит из параметров: X-H2 `+0x1c0→state+0x488`, X-H2S `+0x1c8→state+0x480`,
X-T5 `+0x260→state+0x488`) и кто именно потребляет дескриптор (в блоках 0–2 больше нет
кода, разыменовывающего указатель; вероятно, драйвер дисплея/детектора в другом образе
или по колбэку `*(0x4bc5808)`).

## 7. VM-контроль (Unicorn, реальные инструкции)

Скрипт `a19_vm_stride.py`: эмулируется реальный участок MOVDC-функции — чтение `p`,
guard (new), запись `out[0..2]`. `bl/blr` заглушены (после них `x0=0`). Предзаполнение:
`state+0xab=1`, `mode=9`, `*(state+desc)=DESC`, `DESC+0x10≠0`, `*(state+slot)≠0`,
геометрия `480/640/640`; `DESC+8` = «текущий» stride.

| Модель | Версия | flag | текущий stride | out[0]=h | out[1]=w | **out[2]=stride** |
|---|---|---|---|---|---|---|
| X-H2 | old | 1 | 640 | 480 | 640 | **640** (наследует `p->[8]`) |
| X-H2 | new | 1 | 640 | 480 | 640 | **1280** (берёт геометрию) |
| X-H2 | old/new | 1 | 1280 | 480 | 640 | 1280 (значения совпадают) |
| X-H2 | old | 0 | 640 | 480 | 640 | 640 (наследует, как и new) |
| X-H2 | new | 0 | 640 | 480 | 640 | 640 (наследует, как и old) |
| X-H2S | old | 1 | 640 | 480 | 640 | **640** |
| X-H2S | new | 1 | 640 | 480 | 640 | **1280** |
| X-T5 | old | 1 | 640 | 480 | 640 | **640** |
| X-T5 | new | 1 | 640 | 480 | 640 | **1280** |

Полная матрица (24 прогона) — в `a19_vm_out.txt` и `доказательства.json → VM_unicorn`.

**Контроль (отрицательный):** если `p->[0x10] == 0` (пиксельного буфера нет), присваивание
`field = p->[8]>>1` пропускается и **обе** версии дают `stride=1280`. Это подтверждает, что
640 в таблице появляется именно из наследования `p->[8]`. Результат одинаков во всех трёх
моделях.

**Что это доказывает:** изменение меняет ровно одно решение — «брать ли stride из
дескриптора» — и меняет его только при `flag != 0`; при `flag == 0` обе версии идентичны.
Все прочие ветки не затронуты. **Что это не доказывает:** что унаследованное значение было
неверным в дефектном режиме (см. §6.3).

### 7.2 VM развилок `ccmp` в apply1/apply2 (`a21_branch_vm.py`)

Эмулируются только инструкции развилки (`cmp/ccmp/b.ne`), `p = x1`, `flag = w2`:

| Функция | flag | p | куда попали |
|---|---|---|---|
| apply1 `0x3104754` | 0 | !=0 | ветка `0x31048d0` (заглушки → `b 0x3104760`) |
| apply1 | 0 | ==0 | fall-through `0x3104760` |
| apply1 | !=0 | любой | fall-through `0x3104760` |
| apply2 `0x3104c5c` | 0 | !=0 | ветка `0x3104c8c` (заглушки → `b 0x3104c68`) |
| apply2 | 0 | ==0 | сразу `0x3104c68: bl MOVDC` |
| apply2 | !=0 | любой | сразу `0x3104c68: bl MOVDC` |

Т.е. ветка берётся при **`flag == 0 && p != 0`**, а MOVDC-функция в apply2 вызывается
**в любом случае** (ветка возвращается на `0x3104c68` через `b`).

## 8. Сопутствующие изменения в той же цепи (пункт 4 задачи)

Сравнение MOVDC-функции целиком (286 → 289 инструкций, `a12_func_diff.py`): **единственное
отличие — вставка 3 инструкций guard'а**. Больше в функции ничего не изменилось
(ни геометрия, ни запись дескриптора, ни вызовы, ни строки).

В apply-функциях (apply1/apply2) изменения одинаковы во всех трёх моделях
(`a18_apply_diff.py`):

1. `ldr w2` → `ldr w3` для полей после флага — чтобы сохранить значение флага в `w2`
   для нового теста (X-H2: `0x310472c/0x3104734/0x310473c/0x3104744`).
2. Новый тест `cmp w2,#0; ccmp x1,#0,#4,eq; b.ne …` (X-H2 `0x3104754–0x310475c`,
   X-H2S `0x341b164`, X-T5 `0x3047038`).
3. Новая ветка (`X-H2 0x31048d0`, X-H2S `0x341b2e0`, X-T5 `0x30471b4`), вызывающая
   flush-функции (`0x155bde8`/`0x155bde0` vs старые `0x1564db8`/`0x1564db0`); все четыре
   адреса — **заглушки** `ret` / `mov w0,#1; ret` (в блоке 0), поэтому изменение
   функционально no-op. Ветка берётся при `flag == 0 && p != 0` (§5.3, §7.2) и затем
   возвращается на общий путь (`b 0x3104760`).
4. apply2: тест `cmp/ccmp/b.ne` (`X-H2 0x3104c5c–0x3104c64`, X-H2S `0x341b654`,
   X-T5 `0x3047540`); MOVDC-функция по-прежнему вызывается **всегда** (`0x3104c68`), но
   при `flag == 0 && p != 0` перед этим исполняются flush-заглушки (`0x3104c8c…0x3104cb4`).
5. Новое чтение флага в apply1 (X-H2 `0x3104aec`, X-H2S `0x341b4e8`, X-T5 `0x30473d0`).

Других общих для трёх моделей изменений в этой цепи нет: набор строк модуля и таблицы
`UI_SETP_*` не менялись, геттер геометрии не менялся.

## 10. Что проверено и не дало результата

* Прямой поиск `str/strb/strh [..,#0xf14]` (old X-H2) — только чтения; **писатель через
  базу структуры был найден позже** (apply-функции), т.е. прежний вывод «писатель не найден»
  уточнён.
* Поиск писателей поля параметров (`0x4c3f26c`, `0x4c3b26c`, `0x4bb4064`, `0x4ac29b4`)
  в блоках 0/1/2 — **0 попаданий**.
* Поиск 8-байтовых литералов адресов флага/параметров — **0**.
* Поиск указателей на блок параметров в данных — **0**.
* Проверка, что таблицы `UI_SETP_CONTINUOUS/BRACKET/SHUTTER/IMAGE_DISP` не изменились —
  подтверждено ранее по КОНТЕКСТУ; в этой работе не пересматривалось.
* Версия «guard меняет бит чётности/выравнивание» — **опровергнута**: guard именно
  переключает источник stride (`p->[8]` vs геометрия), см. VM.
* Версия «при `flag == 0` обе версии берут геометрию (1280)» — **опровергнута VM**:
  при `flag == 0` обе версии наследуют `p->[8]` (640→640, 1280→1280). В старой версии
  `[sp+0x16c] = p->[8]>>1` присваивается *до* проверки флага (0x3108098–0x31080a8 vs
  0x31080fc), поэтому от флага не зависит; флаг лишь выбирает вход в запись дескриптора.
* Версия «`ccmp x1,#0,#4,eq` при `flag != 0` даёт Z=1 и переход на 0x3104c8c» —
  **опровергнута VM (`a21_branch_vm.py`)**: при истинном `eq` (флаг == 0) `ccmp`
  выполняет сравнение `x1` с 0, а при ложном ставит NZCV=4. Ветка берётся при
  `flag == 0 && p != 0`; в apply2 она возвращается на `bl MOVDC` (`b 0x3104c68`), т.е.
  MOVDC-функция вызывается всегда.
* Версия «верный/неверный stride 640» — **не доказана ни в одну сторону** (см. §6.3):
  при `flag == 0` 640 проходит без изменений в обеих версиях.
