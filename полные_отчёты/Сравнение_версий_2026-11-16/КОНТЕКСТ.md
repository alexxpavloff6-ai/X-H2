| X-H2S | `Firmware на прочиеFuji/FWUP0027.DAT` (7.30) | `Firmware на прочиеFuji/FWUP0027(new).DAT` (7.31) |
| X-T5  | `Firmware на прочиеFuji/FWUP0030.DAT` (4.31) | `Firmware на прочиеFuji/FWUP0030(new).DAT` (4.32) |

Корень проекта: `<корень проекта>`. Блоки FFLZ уже распакованы в
`Анализ_прошивки/Сравнение_версий_2026-11-16/blocks/` (см. `blocks/index.json`). Распаковывать заново не нужно.

Номера блоков в `fwcommon.load(model, state, idx)`:
- `0` — первый FFLZ (`0x300274`), база = u64 по смещению +8 (X-H2/X-T5 `0x1101000`, X-H2S `0x1421000`);
- `1` — второй, высокоуровневый ARM64 (X-H2/H2S `0x840274`, X-T5 `0x820274`), база: X-H2 old `0x29ae000`, new `0x29aa000`; X-H2S `0x2cca000`; X-T5 `0x28eb000`;
- `2` — низкоуровневый ARM64 (X-H2 `0xf40274`, остальные `0xf20274`), база 0 — адреса = смещения;
- `3` — Linux/initramfs, не изменился, не трогать.

Глобальные адреса вроде `0x4c2ff14` лежат вне блоков (RAM/BSS): их значения в DAT нет, искать надо код, который их пишет/читает.

## Инструменты

```python
import sys; sys.path.insert(0, r'<корень проекта>\Анализ_прошивки\Сравнение_версий_2026-11-16')
from fwcommon import *          # load, dis, insns, adrp_sites, adrp_refs, bl_callers, find_bytes, func_start, string_refs
```
- capstone и unicorn лежат в `Анализ_прошивки/инструменты` (fwcommon добавляет путь сам). Запуск: обычный `python` (не `-I`).
- `adrp_refs(b, addr)` разворачивает ADRP → (ADD…) → LDR/STR/ADD, т.е. находит и обращения через базу структуры
  (`adrp x0,page; add x0,x0,#0xad8; ldr w0,[x0,#0x43c]` = `page+0xf14`). Проверяйте результаты глазами.
- `func_start` — эвристика (ближайший `stp x29,x30,[sp,#-N]!`), может остановиться на вложенном прологе.
- Для VM-проверок — unicorn на оригинальных инструкциях, со стабами для `bl` и отрицательными контролями.
- Одиночные тяжёлые сканы целого блока занимают секунды–десятки секунд: кэшируйте результаты в своей папке.

## Что уже установлено (не перепроверять без причины)

Изменения одинаковы во всех трёх моделях, подтверждены в Unicorn.

1. **Видео 6.2K+ (зависание ~через минуту воспроизведения).** Блок 2. X-H2: start-code helper `0x8fdac4 → 0x8fda98`,
   подготовка кадровых записей `0x8fdc20 → 0x8fdcd8`, completion `0x8fdf68 → 0x8fe0d8`.
   X-H2S: `0x8f0d5c→0x8f0d30`, `0x8f0eb8→0x8f0f70`, `0x8f1200→0x8f1370`. X-T5: `0x8a2874→0x8a2848`, `0x8a29d0→0x8a2a88`, `0x8a2d18→0x8a2e88`.
   Исправлено: 4-байтовое поле длины больше не читается за границей фрагмента (случаи 3+1, 2+2, 1+3, 0 → ошибка);
   запись потока выросла `0x20 → 0x28`, добавлены `record+0x63c` (тег поколения кадра), `state+0x74` (ожидаемое поколение),
   статус переехал на `record+0x640`; completion не освобождает буфер текущего поколения. Модуль: строки `pm_dec`, `DEC_STA`, ProRes stream-read.
   **Не доказано:** почему «около минуты» и почему именно 6.2K+ (гипотеза: wrap кольцевого буфера зависит от битрейта).

2. **LCD, горизонтальные линии (CH HIGH SPEED BURST + электронный затвор + 1/8000 и быстрее + IMAGE DISP=CONTINUOUS).**
   Блок 1, функция со строкой `MOVDC` (`0x37d0178` в old X-H2). X-H2: `0x3107e84 → 0x3103ff8`, новая проверка `0x310420c–0x3104214`:
   `adrp x1,0x4c2f000; ldr w1,[x1,#0xf14]; cbnz w1,skip; ldr x1,[x0,#0x10]; cbz x1,skip; ldr w0,[x0,#8]; lsr w0,w0,#1; str w0,[sp,#field]`.
   Позже `output+8 = 2*field`. Старая версия всегда обновляла field из `source+8`; новая при `flag!=0` оставляет прежнее значение.
   Глобальный флаг: X-H2 old `0x4c33f14`, new `0x4c2ff14`; X-H2S `0x4ba8f0c`; X-T5 `0x4ab72c4` (адреса H2S/T5 — по прошлой сессии, проверьте old/new).
   Guard: X-H2S `0x341ac2c–0x341ac34`, X-T5 `0x3046af0–0x3046af8`.
   Прямой поиск `ldr/str [..,#0xf14]` в X-H2 нашёл только чтения в блоке 1 (old 10, new 12); **писатель флага не найден**.
   **Не доказано:** что означает флаг и как он связан с CH/ES/1/8000/CONTINUOUS; что такое `output+8` и кто его потребляет.
   Отброшено: условные вызовы `0x75a494/0x75a9b8` (смещения блока 1) — заглушки; таблицы `UI_SETP_*` CONTINUOUS/BRACKET/SHUTTER/IMAGE_DISP не изменились.

3. **ISO BKT / FILM SIMULATION BKT (изредка повреждённые снимки).** Блок 1. X-H2: функция подготовки кадра `0x2cecf2c → 0x2ce8f3c`,
   вставка `0x2ce98c0–0x2ce98d8`: `mov w0,#0x9155; movk w0,#1,lsl#16; bl property_getter; ubfiz w0,w0,#9,#16; str w0,[x19,#0x60]; cbz w24,..; str w0,[x22,#0x80]`.
   Старая версия поля не писала → в кадр шёл 0. Commit-copier: `commit+0x80 → per-frame+0x1f48` (X-H2), `→ per-frame+0x1050` (X-T5).
   В X-T5 значение используется в расчётах размеров image-buffer/resampling и адресов, не в ISO/экспозиции. `0x19155` — смещение в кэшированном blob параметров.
   **Не доказано:** что за параметр `0x19155`; почему дефект проявлялся именно в брекетинге (где одиночный кадр получает значение иначе).

4. **XF30mmF2.8 R LM WR Macro, ручная фокусировка при LINEAR с нестандартным углом.** Блок 1. X-H2: конструктор запроса `0x2df0818 → 0x2dec8a8`,
   проверка `0x2dec9b0–0x2dec9b8` (`cmp w21,#0x411; cset; str w0,[sp,#0xb0]`), потребитель `0x2ceb0e4 → 0x2ce70e4`.
   Операции `0x1e` и `0x20`: старое — `+0xa0 = property 0x1dba`, `+0x50 = 2*property_u8(0x1db3)`; новое для lens `0x411` — `0xe4`(228) и `0x118`(280),
   для остальных — `0` и `0x100`(256). X-H2S проверка `0x3107fe4–0x3107ff0`, X-T5 `0x2d2e048–0x2d2e054`.
   Ещё: новый helper `0x58a58c` (смещение блока 1 X-H2 new) работает с `0x205c = KEY_ND_FILTER`, `0x205e = KEY_TELE_CONVERTER`;
   generic-проверка `request+0x25` (нулевой байт пропускает lens-command presequence).
   UI-преобразования `UI_LENS_OP_SET_FOCUS_LINEAR_MOVE`, `UI_FOCUS_RING_PROPERTY_FIXED_STEP` не изменились.
   **Не доказано:** что `0x411` — именно XF30mm; цепь `output+0x50/+0xa0` → движение фокуса/кольцо; смысл `0x1dba`, `0x1db3`.
