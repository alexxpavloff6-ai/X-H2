# Задача E. Кто пишет свойство 0x2B9 (settings+0x144) и откуда значение 0x2C

Основная модель — **X-H2 5.33** (блоки 0/1/2 из `blocks/index.json`), проверки для **X-H2S 7.31** и **X-T5 4.32** — в §9.
Уровни: **[Д]** доказано (адреса/инструкции/VM), **[К]** сильный кандидат, **[Г]** гипотеза.
Скрипты — `*.py` в этой папке, сводка — `доказательства.json`, таблица имён — `id_names_2a0_2d3.json`,
результаты VM — `vm_blob_chain.json`.

---

## 0. Краткий ответ

1. **Запись `0x128c5d8: strb w19,[x0,#0x144]` — это ветка гигантского диспетчера установки свойств
   `0x11e6bf0(id, value, slot, w3, w4)`** (блок 0), а не отдельная функция: вход `0x11e6bf0`,
   выбор ветки — **таблица u32 `0x174289c`** (база `0x11e6c44`), `id 0x2B9 → ветка 0x128c558`. **[Д]**
2. Цепочка вызова: `0x11335c4(id,value,slot)` → `0x12aa680` → `0x11e6bf0` → `0x128c558`. **[Д]**
3. **Свойство 0x2B9 в блоке 0 — это НЕ режим съёмки.** Имя поля берётся прямо из строки лога его же
   ветки: `0x173af40 = "\t$BACKUP[%d]ubNetmaskSettingManual1octet8 %s(%d)->%s(%d)\r\n"` —
   **8-й октет маски сети №1** (сетевые настройки, ручной IP). Семейство 0x2A0…0x2D3 —
   это IPv6-адрес и три маски (см. §5). **[Д]**
4. Поэтому утверждение из `D_брекетинг/режим_0x2C.md` «`[ctx+0x3978]` = свойство 0x2B9» —
   **совпадение смещения `+0x144` в двух разных структурах**, а не одна и та же сущность. **[Д]** (опровержение)
5. Значение **0x2C для свойства 0x2B9 код прошивки не порождает**: нет ни литерала 0x2C рядом с
   установкой id 0x2B9, ни пары `{id 0x2B9, значение 0x2C}` в данных, ни значения по умолчанию.
   Это просто байт сетевой настройки (0x2C = 44), приходящий из слоя конфигурации. **[Д]** (отрицательный результат)
6. Реальный код режима 0x2C — это **32-битное поле `+0x144` структуры задания**, указатель на которую
   лежит в `[0x4daa6e8]` (менеджер `0x4daa6c0`); копия в `ctx+0x3978` — `0x30871a8/0x30871ac`. **[Д]**
   Писатель самого `[0x4daa6e8]` в блоках 0–2 не найден (см. §7.7) — указатель задаётся вне
   статически разобранного кода. **[Д]** (отрицательный результат)
7. **Что такое 0x2C: `MODE_RECORD_HDR`.** Резолвер `MODE_RECORD → строка` в блоке 0
   (X-H2 `0x1141ee0`) для `0x2C` возвращает строку `0x1641280 = "MODE_RECORD_HDR"`; для `0x2D` —
   `0x1641290 = "MODE_RECORD_MOTIONJPEG"`; `0x21..0x24` = `MODE_RECORD_PROGRAM / SHUTTER /
   APERTURE / MANUAL`. Подтверждено в X-H2S (`0x1461ee4 → 0x196b878`) и X-T5
   (`0x1142450 → 0x163f8b8`). **[Д]** (см. §7.6) — т.е. многокадровый путь `recfCalcRecifParam`
   при `0x2C` — это **HDR-композиция** (несколько экспозиций), а не ISO BKT.
8. Построитель `0x2ff1ed8`, на который указал воркер F, **не является** построителем этого job:
   его `+0x144` — булев флаг `0x2f80e38(...)` (0/1), а `+0x140` — 32-битное число, а не указатель
   буфера (см. §7.5). **[Д]** (опровержение)

## 3. Геттер — та же картина (контроль)

Геттер байтовых свойств `0x12d6bc8(id,default)` → `0x12aa788` — «читающий» диспетчер
с такой же структурой: таблица u32 `0x1745e70`, база `0x12aa7dc`; `id 0x2B9 → 0x12cd0c8`:

```
12cd0c8: ...
12cd0ec: ldrb w19,[x0,#0x144]     ; читает ровно тот же байт settings+0x144
```

То есть и запись, и чтение «свойства 0x2B9» сходятся на `settings+0x144`, и обе ветки логируют
одно и то же имя поля (`ubNetmaskSettingManual1octet8`). **[Д]**

## 4. Все пути установки, где id = 0x2B9 получается НЕ литералом

Проверено:
* **Литерала 0x2B9 нет ни при одном вызове сеттеров** (434 вызова `0x11335c4`: 338 с
  литеральным id, среди них 0x2B9 нет; 96 с нелитеральным id). Скан всех блоков на
  `mov w0,#0x2b9` даёт только: геттер-набор `0x12dd82c`, лог-цикл `0x128c600/0x128c614`,
  сброс `0x2c240ec`, маппер `0x1138388` — совпадает с D. **[Д]**

Найденные нелитеральные пути:

### 4.1. id из цикла «база + индекс»

`0x1316c1c` (`18_dyn_setter.py`): `add w20,w22,w19` → `mov w1,#0x1affffff` → `bl 0x11335c4` —
сброс диапазона последовательных id (`w22` — база, `w19` — смещение). Тот же приём в
`0x113a5d0` (`ldr w20,[x19,#8]` — id из таблицы/структуры) и др. — 96 таких мест.

### 4.2. Маппер «родительское свойство + индекс → id подполя» `0x11376d4`

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Полное отображение: родитель **0x2B1** («bManualSettingNetmask1Octet») + индекс
1…0x10 → **0x2B2…0x2C1** (`0x2B1+index`), т.е. 0x2B9 = «подполе 8» родителя 0x2B1.
Ровно то, что описано в задаче как «8 → 0x2b9», только это не произвольная нумерация
полей блока настроек, а **октеты маски сети**. **[Д]**

Вызывающих `0x11376d4` — 20 в блоке 0 и 13 в блоке 1 (блоки делят одно VA-пространство:
вызовы блока 1 идут на адрес блока 0). Литеральные родители: 0xC53, 0xC8C, 0x1EF, 0x200,
0x211, 0x254, 0x2D3, 0x2E4, 0x222, 0x233, 0xB93… **Ни один статический вызов не передаёт
w0 = 0x2B1** — ветка «8 → 0x2B9» достижима только с вычисленным родителем (например, из PTP-слоя). **[Д]** (отрицательный)

### 4.3. Код события 0x358 (пространство кодов блока 1)

Проверено независимо от D (`32_getter_and_event.py`):
диспетчер `0x2d3a500`, группа `0x300`, таблица s16 `0x33bd468` (база `0x2d3a94c`):

| код | offset | тело | id |
|---|---|---|---|
| 0x357 | 0x65 | `0x2d3aae0` | 0x2B8 |
| **0x358** | **0x67** | **`0x2d3aae8`: `mov w19,#0x2b9; b 0x2d3a958`** | **0x2B9** |
| 0x359 | 0x69 | `0x2d3aaf0` | 0x2BA |
| 0x35A | 0x12d | `0x2d3ae00` | 0 (default) |

Далее `orr w19,w19,#0x4000` (тип «set»), 16-байтовый payload `[x20]`/`[x20+8]` копируется в
`sp+0x30` и уходит в `0x2d3a41c(id, len=0x10, data, flag)`, которая кладёт id/длину в очередь
`0x4f76eb0+0x40/+0x4c`, данные — в `0x4f76f00`, и вызывает `0x2d3a1ac`/`0x2d3a144`.
**Это публикация уведомления (значение уходит наружу), а не вход значения** — 16-байтовый payload
согласуется с «октет/поле настройки + сопутствующие байты». **[Д]** для кода→id, **[К]** для семантики очереди.

Отправители кода 0x358 в блоке 1 (D, §9): `0x2b47ad8/ba8/cd8/da8/dc8`, `0x2b48068/088`,
`0x2b48364` — через `0x2c116ac` (только код, без payload). **[Д]** (перепроверено по адресам).

## 5. Что такое 0x2B9 на самом деле: домен и имена

Имена получены из строк-форматов лога в ветках сеттера (по одной строке на id),
`22_id_names3.py` → `id_names_2a0_2d3.json`:

```
0x2A0  $BACKUP[]bManualSettingIpAddress4Octet      (заголовок записи IP-адреса)
0x2A1  $BACKUP[]ubIpAddressSettingManual4octet1
 ...   ...                                         (16 октетов — похоже на IPv6)
0x2B0  $BACKUP[]ubIpAddressSettingManual4octet16
0x2B1  $BACKUP[]bManualSettingNetmask1Octet        (заголовок маски №1)
0x2B2  $BACKUP[]ubNetmaskSettingManual1octet1
 ...
0x2B9  $BACKUP[]ubNetmaskSettingManual1octet8      <<< НАШ id
 ...
0x2C1  $BACKUP[]ubNetmaskSettingManual1octet16
0x2C2  $BACKUP[]bManualSettingNetmask2Octet        (маска №2)
0x2C3..0x2D2  ubNetmaskSettingManual2octet1..16
0x2D3  $BACKUP[]bManualSettingNetmask3Octet        (маска №3)
```

То есть семейство 0x2A1…0x2D2 — **адрес IPv6 (16 октетов) и три 16-октетных маски**;
0x2B9 — восьмой октет первой маски, домен значения — **байт 0…255**. **[Д]**

Следствия для вопроса 4 задачи («домен 0x00..0x2D с именами режимов»):
для свойства 0x2B9 домена 0…0x2D не существует — это октет. Домен `0x00..0x2D` относится
**только** к полю `[ctx+0x3978]` (см. §7) и к нему имена из этой таблицы отношения не имеют. **[Д]**

## 6. Откуда значение 0x2C для свойства 0x2B9

Собрано всё, что могло бы породить 0x2C:

1. **Константа в коде.** Прямой скан пар «`mov wN,#0x2c` в пределах ±0x60 инструкций от вызова
   сеттера, у которого id = 0x2B9» — **0 совпадений** (`16_setter_calls.py`, `18_dyn_setter.py`);
   ни одного вызова сеттера с литеральным id 0x2B9 нет вообще, т.е. и пары нет.
   Скан «`mov wN,#0x2c` рядом с любым вызовом семейства сеттеров» даёт только `mov w0,#0x2c`
   в `0x1333740` — но это **значение режима** для другой ветки (см. §7.3), id там другой. **[Д]**
2. **Значение по умолчанию.** Таблица дефолтов настроек `0x1ac3cb8` (записи `{u16 id,u8 value,u8 pad}`,
   терминатор `0xfffe`, всего **143** записи, `27_defaults_table.py`) — id 0x2B9 в ней **нет**
   (все id < 0x10000, наша запись — сетевая, инициализируется отдельно). **[Д]**
3. **Таблицы {id,value}.** Нет (см. §4.4). **[Д]**
4. **Вычисление из других свойств.** Ветка 0x128c558 — чистый `strb` переданного значения,
   никаких арифметик. **[Д]**

**Вывод:** значение 0x2C для свойства 0x2B9 приходит **из слоя конфигурации** (ручной ввод
IP/маски в меню/приложении; 0x2C = 44 — допустимый октет), а прошивка только хранит его в
`settings+0x144` (слот 0 + тень) и уведомляет другую сторону событием 0x358.
Уровни: механизм хранения/уведомления — **[Д]**; «ручной ввод пользователя» — **[К]**
(UI-таблицу «пункт меню → байт» найти не удалось).

## 7. Где на самом деле живёт «код режима 0x2C» (ctx+0x3978)

### 7.1. Копия в ctx — [Д]

`0x308680c` (блок 1) — «заполнить RECF-контекст из структуры задания»; x0 = структура,
x1 = запрос. Фрагмент `0x30871a0..0x30871ac`:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Вызывающие `0x308680c`: `0x3089fd0`, `0x308a700`, `0x308af5c`, `0x308b0cc` (внутри
`0x3089ec8`/`0x308a1ec`), а структура задания берётся из **`[0x4daa6e8]`**
(`0x30172ac: adrp 0x4daa000; ldr x0,[x0,#0x6e8]; bl 0x3089ec8`), где `0x4daa6c0` — менеджер RECF.
Т.е. `[ctx+0x3978]` = `job+0x144`, 32-битное поле; `job+0x140` — **указатель на буфер вывода**
(`0x3086818: ldr x22,[x0,#0x140]; cbz → выход`). **[Д]**

### 7.2. Кто пишет `job+0x144` — не найдено (литерала 0x2C нет)

Все записи `[xN,#0x144]` в блоке 1 — **75** (`24_field144_writers.py`). Ни одна не пишет литерал
`0x2C`; значения берутся из чтений DB/структур (`ldr`, `ldrh`, getters `0x14920fc/0x1492110`).
В границах функции (эвристика `find_prologue`, окно до +0x200 после записи) не нашлось ни одной,
которая инициализировала бы `+0x140` как `str x`, — похоже, структура задания собирается по частям
(менеджер `0x4daa6c0` + аллокатор), и поле `+0x144` заполняется извне запроса.
**Конкретный писатель со значением 0x2C не найден** — **[Д]** (отрицательный; оговорка про эвристику границ).

### 7.3. Что 0x2C — это код режима, а не число кадров

* Функция-«оценщик режима» `0x1332f04` (блок 0) по коду команды `w19` (0x3002…0x3019) возвращает
  код режима в `w20`: 0x21/0x22/0x23/0x24 и **0x2C** (`0x1333730: ldr w0,[0x267c48c];
  cmp w0,#1; mov w0,#0x2c; csel w20,w20,w0,eq`), второй код — в `[x21]`.
  Это подтверждает, что 0x2C — код из того же перечисления, что 0x21…0x24. **[К]**
* `0x131cb44`: `cmp w0,#0x2c` → специальная ветка (читает свойство 0x876, сравнивает с 4). **[Д]** для кода.

### 7.4. Другая структура, которую нельзя путать с job — «зеркало настроек» из DB

В блоке 1 есть заполнитель `0x2de8ff4` (блок 1): `w19 = 9` (`0x2dead10`), и далее пачкой

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

где `0x14920fc(id)` (`b0`) — чтение байта из **базы настроек** `DB = [0x20bf458]`
(`0x1491e5c: adrp 0x20bf000; ldr x19,[x1,#0x458]; ldrb w0,[x19,w0,uxtw]`), а `DB = 0x27008000`
(жёстко, `0x1492504..0x149250c`), размер 0x7E0000, обнуляется при инициализации (`0x149206c`),
дефолты — только 143 `u16`-записи.

**VM-контроль** (Unicorn, `31_vm_blob_chain.py`, `vm_blob_chain.json`):

| проверка | вход | результат |
|---|---|---|
| A. `0x14920fc(id)` = `DB[id]` | id=0x2801C, DB=0x2C / 0x07; id=0x2801D | w0 = 0x2C / 0x07 / 0x2C — **совпадает** |
| B. `0x2debb38` (w19=9) кладёт `DB[0x2801C]` в `struct+0x144` | 0x2C,0x2D,0x21,0x00 | struct+0x144 = 0x2C,0x2D,0x21,0x00 |
| C. `0x30871a8` копирует `struct+0x144` в `ctx+0x3978` | 0x2C,0x2D,0x20 | ctx+0x3978 = 0x2C,0x2D,0x20 |

**НО:** это **другая структура**, чем job: у неё `+0x140` — байт (`strb`, `0x2debb14`),
а у job `+0x140` — 64-битный указатель (`ldr x1`). Поэтому цепочка «DB[0x2801C] → struct+0x144»
**не является** источником `ctx+0x3978`. Совпадение смещения `+0x144` — третье по счёту в этой
прошивке (после property 0x2B9 и job). **[Д]** для механизма зеркала, **[Д]** для отрицания связи.

**Кто пишет `DB[0x2801C]`:** сеттер DB `0x1492040(id,value)` — 678 вызовов, из них **376 с id,
прочитанным из памяти** (`33_setter_sources.py`), 206 — со значением из памяти; литерала
`0x2801C` (`movz wN,#0x801c; movk wN,#2`) в коде **нет** (0 совпадений, `30_verify.py`).
Инициализация DB — нулями + 143 дефолта, записи 0x2801C среди них нет. Значит значение приходит
по командному/настроечному каналу извне. **[К]**

### 7.5. Построитель `0x2ff1ed8` (кандидат воркера F) — это НЕ построитель job+0x144 режима

Воркер F указал на `0x2ff1ed8` как на построитель job, где `0x2ff2340: str w0,[x19,#0x144]`
и второй путь `0x2ff2518: ldr w0,[x19,#0x168]; 0x2ff251c: str w0,[x21,#0x144]`.
Разобрано (`44_src1c4.py`):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

То есть **`out+0x144` — не «откуда-то из rec+0x168», а поле `src+0x1C4`** (rec — лишь промежуточная
запись). `src` — это `x2` у вызывающего:

|---|---|---|---|---|
| `0x2fd229c` | `0x2fd1a18` | `0x38de1d8` | `0x38de3b0` | `0x38de500` |
| `0x2ff8ec8` | `0x2ff763c` | `0x38decc8` | `0x38de9c0` | `0x38deb10` |
| `0x2ff92f4` | `0x2ff763c` | `0x38decc8` | `0x38de9c0` | `0x38deb10` |

**Кто пишет `src+0x1C4` (и каким значением):**

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Сама `0x2f80e38` — **три сравнения и логическое И** (никаких таблиц/0x2C):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Значит `out+0x144` = **0 или 1** (флаг «src+0x98==4 и src+0x14==1 и src+0x58==1»), а не 0x2C.
`out+0x140` тоже 32-битный (`str w0`), тогда как у job, который читает `0x308680c`, `+0x140` —

`0x2ff1ed8`, — не тот job, чьё `+0x144` попадает в `ctx+0x3978`.** **[Д]** (опровержение гипотезы F)

Путь `rec+0x144` (F) — это байт записи слота `0x229a3a0+slot*0x2748+0x26c` (`0x1552874`),
т.е. ещё один булев/перечислимый признак, не режим 0..0x2D. **[Д]** для источника, **[К]** для смысла.

**Когда какой путь** (условия из вызывающих):
* путь A (`0x2fd229c`): если `src+0x141 ∈ {3,4}` → ветка `0x2fd2478` (без вызова);
  если `src+0x141 == 0` и `[0x38de304] == 1` → ветка `0x2fd2494`; иначе — вызов построителя. **[Д]**
* путь B (`0x2ff8ec8`/`0x2ff92f4`): вызов, если `w0 != 0` (флаг вызывающего) или
  `[0x38de0df1] == 1`, или `([0x38de0e09]-2) & 0xff <= 2` (значения 2..4);
  иначе вызов только при `[0x38de0de0] == 1`, иначе — пропуск (`0x2ff8f00`). **[Д]**

### 7.6. Имена режимов: резолвер `MODE_RECORD` (главный результат)

В блоке 0 есть длинная цепочка `cmp w0,#imm; b.eq body`, где каждое тело — `adrp/add` на строку.
Для X-H2 5.33 вход `0x1141ee0` (`46_mode_record_resolver.py`), проверено по строкам:

| код | тело (X-H2) | строка | имя |
|---|---|---|---|
| 0x21 | `0x11423bc` | `0x1641178` | `MODE_RECORD_PROGRAM` |
| 0x22 | `0x11423c8` | `0x1641190` | `MODE_RECORD_SHUTTER` |
| 0x23 | `0x11423d4` | `0x16411a8` | `MODE_RECORD_APERTURE` |
| 0x24 | `0x11423e0` | `0x16411c0` | `MODE_RECORD_MANUAL` |
| **0x2C** | **`0x1142440`** | **`0x1641280`** | **`MODE_RECORD_HDR`** |
| 0x2D | `0x114244c` | `0x1641290` | `MODE_RECORD_MOTIONJPEG` |
| 0x00 | `0x1142230` | `0x1640dd8` | `MODE_RECORD_AUTO` |

Кросс-модельная сверка (те же строки-имена, другие адреса):

| модель | резолвер (блок 0) | тело 0x2C | строка 0x2C |
|---|---|---|---|
| X-H2 5.33 | `0x1141ee0` | `0x1142440` | `0x1641280` `MODE_RECORD_HDR` |

ранней части цепочки.) **[Д]**

**Следствие:** `[ctx+0x3978]` — код `MODE_RECORD` (режим записи кадра), а `0x2C` = **HDR**.
Многокадровый путь `recfCalcRecifParam` при `0x2C` — это **HDR-композиция нескольких экспозиций**
(счётчик `[ctx+0x429c]` = 2/4/1 — число экспозиций/проходов), а не ISO BKT / FILM SIM BKT.
Это согласуется с «многокадровым still-режимом» из D, но конкретизирует его как HDR. **[Д]** для имён,
**[К]** для «число кадров = число экспозиций HDR».

## 10. Проверено и опровергнуто

1. «`[ctx+0x3978]` — копия свойства 0x2B9» — **опровергнуто**: 0x2B9 в блоке 0 =
   `ubNetmaskSettingManual1octet8` (сетевые настройки), `settings+0x144` — октет маски;
   в RECF копируется `job+0x144` другой структуры. Совпадение имён смещений — случайное. **[Д]**
2. «Значение 0x2C для свойства 0x2B9 задаётся прошивкой (константа/таблица/дефолт)» —
   **опровергнуто**: 0 совпадений по константам, 0 пар в данных, 0 записей в таблице дефолтов. **[Д]**
3. «Событие 0x358 передаёт значение свойства» — **уточнено**: код 0x358 действительно
   отображается в id 0x2B9 (таблица проверена), но 16-байтовый payload публикуется в очередь
   `0x4f76eb0/0x4f76f00` (`0x2d3a41c`) — это уведомление наружу; отправители `0x2b47xxx`
   передают только код. **[Д]** для отображения, **[К]** для семантики.
4. «Маппер `0x1137b0c` — произвольная нумерация полей блока настроек» — **уточнено**:
   это подполя родителя 0x2B1 (октеты маски); 8 → 0x2B9. **[Д]**
5. «Зеркало настроек `0x2de8ff4` питает `ctx+0x3978`» — **опровергнуто** по типу поля
   `+0x140` (байт vs указатель). **[Д]**
6. «UI-имена ISO_BKT/FILM_SIM/BKT дают код 0x2C» — **не найдено**; таблица `0x3216a90` —
   индексы пунктов меню. **[Д]** (отрицательный)
7. «Таблица `0x18b3xxx` — имена режимов» — **опровергнуто**: это коды действий кнопок. **[Д]**
8. «Построитель `0x2ff1ed8` (воркер F) заполняет job+0x144 режимом» — **опровергнуто**:
   его `out+0x144` = `src+0x1C4` = `0x2f80e38(src+0x58, src+0x98, src+0x14)` = булево
   `(w1==4 && w2==1 && w0==1)` (0/1), а `out+0x140` — 32-битное значение, тогда как у job
   `+0x140` — 8-байтовый указатель буфера. Это другая структура. **[Д]**
9. «`rec+0x168` — самостоятельный источник» — **уточнено**: `rec+0x168` пишется из `src+0x1C4`
   в `0x2ff23d4`, т.е. источник — поле `+0x1C4` входной структуры `src` (0x38de1d8 / 0x38decc8). **[Д]**
10. «0x2C — ISO BKT / FILM SIM BKT» — **опровергнуто**: резолвер `MODE_RECORD` даёт для 0x2C
    строку `MODE_RECORD_HDR` (X-H2 `0x1142440→0x1641280`, H2S `0x1461ee4→0x196b878`,
    T5 `0x1142450→0x163f8b8`), 0x2D = `MODE_RECORD_MOTIONJPEG`. **[Д]**
11. «Поле режима в T5 — на `+0x3978`» — **опровергнуто**: в T5 оно на `+0x39C0`
    (`0x2d132dc`), а `#0x3978` в T5 только читается (3 обращения), записей нет. **[Д]**

## 11. Что осталось (для следующего шага)

1. Найти писателя `job+0x144` со значением 0x2C: писатель `[0x4daa6e8]` в блоках 0–2 не найден
   (§7.7) — вероятно, структура job приходит извне (очередь/межпроцессорный канал); искать
   приёмник командного канала и/или инициализатор вне образа.
2. X-T5: поле режима найдено (`ctx+0x39C0`), но записи 0x2C в образе нет — искать, откуда T5
   получает HDR-режим (другой образ/ядро/общая память) либо подтвердить, что путь мёртв.
3. Имена режимов **найдены** (резолвер `MODE_RECORD`, §7.6): 0x2C = HDR, 0x2D = MOTIONJPEG,
   0x21..0x24 = PROGRAM/SHUTTER/APERTURE/MANUAL. Осталось при желании добрать остальные
   значения домена (0x00..0x20) из того же резолвера — это механическая работа.
4. Построитель F (`0x2ff1ed8`) проверен и отброшен для режима: его `+0x144` — булев флаг
   `0x2f80e38()`, `+0x140` — не указатель. Если F продолжает идти от него, стоит искать
   **другой** построитель, у которого `+0x140` пишется как `str x?` (указатель буфера),
   и только там смотреть `+0x144`.
