# Кто пишет свойство 0x2B9 (код режима 0x2C) и счётчик [ctx+0x429c]

Продолжение `режим_0x2C.md`: там найдено, что `[ctx+0x3978]` — копия байтового
свойства **0x2B9**, а `0x2C` — единственный код, включающий многокадровый цикл
в `recfCalcRecifParam`. Здесь — поиск писателей значения и счётчика.

Основная модель X-H2 5.33; проверки для X-H2S 7.31 / X-T5 4.32 — в конце.
Уровни: **[Д]** доказано, **[К]** сильный кандидат, **[Г]** гипотеза.
Скрипты: `44_prop2b9_sites.py`, `45_enum_table.py`, `46_ui_name_table.py`,
`47_vm_prop_chain.py`.

## 1. API свойств и как значение попадает в [ctx+0x3978]

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Копирование в RECF-контекст (см. `режим_0x2C.md`): `0x30871a8 ldr w1,[x19,#0x144]`
→ `0x30871ac str w1,[x0,#0x3978]`.

**VM-контроль** (`47_vm_prop_chain.py`) подтверждает всю цепочку:

```
settings+0x144 = 0x2C -> ctx+0x3978 = 0x2C -> ветка 0x2dd216c (многокадровая)
settings+0x144 = 0x21 -> ctx+0x3978 = 0x21 -> ветка 0x2dd1fa4 (общая)
settings+0x144 = 0x00 -> ctx+0x3978 = 0x00 -> ветка 0x2dd1fa4 (общая)
```

## 2. Писателя константы 0x2C нет — значение приходит извне

Проверено (все модели, old/new, блоки 0/1/2):

* `mov w0,#0x2b9` (movz) встречается только в: геттере-наборе `0x12dd82c`,
  «читай-логируй» цикле `0x128c5fc/0x128c614`, сбросе `0x2c240ec`, табличном
  маппере `0x1138388` и (в 5.30 то же). Ни в одном месте рядом нет
  `mov wN,#0x2c`.
* Прямой скан пар «`mov wN,#0x2c` в пределах ±6 инструкций от `mov w0,#0x2b9`»
  по всем блокам/моделям версий old/new — **0 совпадений**
  (`44_prop2b9_sites.py`, `45_enum_table.py`). Значит **0x2C не является
  константой прошивки** для этого свойства: код приходит извне (приложение/ПК)
  через API установки свойств, а прошивка только хранит его в таблице настроек.
* Строковых таблиц «значение → имя режима» для этого свойства не найдено.

## 3. Счётчик [ctx+0x429c] = 2/3: писателей тоже не найдено

* Сеттер `0x2dd0598`: `add x0,x0,#4,lsl#12; strh w1,[x0,#0x29c]; ret`.
* Все вызовы в блоке 1: `0x2e694ac` и `0x2e6dab0` — оба с `w1 = 0`
  (инициализация перед настройкой). Прочие записи в `+0x29c`:
  `0x2e0d3b8` и `0x2e0fca4` — `strh wzr` (0).
* Записей **2** или **3** в `[ctx+0x429c]` в блоках 0/1 не найдено; значит число
  проходов (4/1/2 при 2/3/прочее) задаётся либо из блока 2/приложения, либо
  большим копированием структуры, которое не попало в скан.
* Следствие: типовой случай — счётчик 0 → **2 прохода**; 4 и 1 требуют внешней
  записи 2/3.

## 4. UI-имена режимов существуют, но не связаны с 0x2B9 напрямую

В блоке 1 есть таблица `{u64 указатель на строку, u64 индекс}`, база ≈ `0x3216a90`
(`46_ui_name_table.py`): `UI_MENUCOM_ITEM_BRACKET` = индекс **0x3F**,
`UI_MENUCOM_ITEM_MULTI_EXPO` = **0x40**, `UI_MENUCOM_ITEM_DRIVE_MODE` = **0x4C**,
`UI_MENUCOM_ITEM_ISO_BKT` = **0x5A**, `UI_MENUCOM_ITEM_CLARITY` = **0x3B**,
`UI_MENUCOM_ITEM_PRE_SHOOT` = **0x4E**, `UI_MENUCOM_ITEM_SELFTIMER` = **0x4F**.
Это **индексы пунктов меню**, а не id свойств; таблицы, связывающей 0x2B9
с этими именами, найти не удалось (в таблице индексы 0x39…0x5B, а id свойств —
0x2A6…0x2BA). То есть режимы ISO BKT / BRACKET / MULTI EXPO в прошивке есть,
но их коды для свойства 0x2B9 задаются приложением.

## 5. Вывод

| вопрос | ответ | уровень |
|---|---|---|
| кто пишет `[ctx+0x3978]` | копия `settings+0x144` (свойство 0x2B9); цепочка подтверждена VM | **[Д]** |
| какой код события даёт 0x2B9 | **событие 0x358** в диспетчере `0x2d3a500` (группа 0x300, jump-таблица `0x33BD468`, тело `0x2d3aae8`) | **[Д]** (см. §8) |
| откуда ЗНАЧЕНИЕ 0x2C | из хранилища настроек блока 0 (сеттер `0x128c5d8`), куда его кладёт UI/ПК; событие 0x358 из блока 1 (`0x2c116ac`) — **уведомление без payload** (см. §9) | **[К]** |
| кто отправляет 0x358 | блок 1, обработчики `0x2b47ad8/ba8/cd8/da8/dc8`, `0x2b48068/088`, `0x2b48364` (через `0x2c116ac`; читают глобалы `[0x244eb20]`/`[0x244ebd4]`) | **[Д]** |
| кто пишет счётчик 2/3 | не найдено в блоках 0/1; сеттер `0x2dd0598` вызывается только с 0 | **[Д]** (отрицательный результат) |
| что такое 0x2C | код режима из внешнего enum (домен ≤ 0x2D), трактуется RECF как «многокадровый still-режим» | **[К]** для поведения, **[Г]** для имени |
| есть ли среди кодов ISO BKT / FSIM BKT | UI-имена таких режимов есть (`ISO_BKT` индекс 0x5A, `BRACKET` 0x3F), но привязки кода 0x2C к ним в прошивке нет | **[Г]** |

**Итог (уточнён):** значение 0x2C не «просто внешнее» — оно **транспортируется в payload
события 0x358**, которое диспетчер `0x2d3a500` переводит в id свойства 0x2B9.
Прошивка не порождает это значение и не хранит таблицу «id → значение»; производитель
события (кто кладёт 0x2C в payload) находится вне разобранного кода (очередь/IPC).
Чтобы назвать режим, нужно найти отправителя события 0x358 (см. §7).

## 6. Проверено и не подтвердилось

* «В прошивке есть константа 0x2C для свойства 0x2B9» — **нет** (0 совпадений
  по всем блокам/версиям).
* «Счётчик 2/3 пишется сеттером 0x2dd0598 из числа кадров брекетинга» — **нет**:
  сеттер вызывается только с 0; 2/3 в блоках 0/1 не пишутся.
* «Таблица UI_MENUCOM_ITEM_* задаёт коды свойства 0x2B9» — **нет**: в таблице
  индексы пунктов меню, а не id свойств.
* Блок 2 ссылок на `mov w0,#0x2b9` не содержит.

## 8. Код события 0x358 → свойство 0x2B9 (разбор switch 0x2d3a500)

### 8.1 Диспетчер и jump-таблица

Функция `0x2d3a500(code, payload_ptr)` (X-H2 5.33, блок 1) — обработчик команд/событий.
Группа выбирается по `code & 0xff00`; для группы `0x300`:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Декодирование таблицы (`49_switch_table.py`): каждое тело — `mov w19,#id; b 0x2d3a958`
(`0x2d3a958: orr w19,w19,#0x4000`). Результат для нужного участка:

| код события | id свойства | тело |
|---|---|---|
| 0x34B..0x361 | 0x2AC..0x2C0 (подряд; 0x35A/0x35B — default) | 0x2d3aa80…0x2d3ab20 |
| **0x358** | **0x2B9** | **0x2d3aae8** |
| 0x357 | 0x2B8 | 0x2d3aae0 |
| 0x359 | 0x2BA | 0x2d3aaf0 |

Полная таблица группы 0x300 — в `switch_table.txt` (172 кода). Семейство id
`0x2AC..0x2C0` соответствует кодам `0x34B..0x361` (шаг 1: id = code − 0x9F).

### 8.2 Путь установки значения

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

`0x2d3a41c(id, len, data, flag)` кладёт id/длину в очередь (`0x4f76eb0+0x40/+0x4c`),
копирует данные в `0x4f76f00` (`memcpy 0x14c9564`) и вызывает обработчик `0x2d3a1ac`.
**Значение свойства берётся из payload события**, а не из таблицы прошивки.

### 8.3 Вызывающие диспетчера (источник события)

* `0x2c351c8` — внутри функции `0x2c35124(code, flag)`: диспетчер команд/уведомлений
  (`mov w0,w19; bl 0x2d3a500`, при `w20 != 0` — ветка с payload).
* `0x2d3bdd4` — цикл «дослать накопившиеся коды»: массив кодов `0x3e230c8`,
  счётчик `[0x39081f8]` (глобалы, о которых говорил координатор).
* `0x2d3be10` — служебный код `0x60a`.
* `0x2ea8b28` — ещё один вызов.

Есть и «очередь с задержкой»: `[0x39081f4] > 0`, коды складываются в `0x3e230c8`
(`0x2d3a568..0x2d3a5cc`), затем досылаются циклом `0x2d3bdd4`. Это подтверждает:
код 0x358 приходит **извне** (IPC/очередь событий), а не вычисляется в RECF.

### 8.4 Блок 0: отображение «индекс поля → id свойства»

Функция около `0x1137b0c` (X-H2 5.33, блок 0) по индексу `w1` возвращает id:

```
w1=1 -> 0x2a1 ; 2 -> 0x2a2? ; 3 -> 0x2b4 ; 4 -> 0x2b5 ; 5 -> 0x2b? ;
6 -> 0x2b7 ; 7 -> 0x2b8 ; 8 -> 0x2b9 ; 9 -> … ; 0xb -> 0x2ab ; 0xc -> 0x2ac ;
0xd -> 0x2ad ; 0xe -> 0x2ae ; 0xf -> 0x2af ; 0x10 -> 0x2b0
```

(`0x1138364..0x11383a4` — участок, где 8 → 0x2b9). Это внутренний **дескриптор полей
блока настроек**: семейство `0x2A1..0x2C0` = последовательные поля записи настроек,
и 0x2B9 — поле №8 в этой нумерации. Имён полей в коде нет; они задаются приложением.

## 9. Отправитель события 0x358 (блок 1) и два пространства имён

### 9.1 Где отправляется 0x358

Все `mov w0,#0x358` (X-H2 5.33, `53_event_sender.py`):

* **блок 1, как код события** — 8 мест, все через `bl 0x2c116ac`:
  `0x2b47ad8`, `0x2b47ba8`, `0x2b47cd8`, `0x2b47da8`, `0x2b47dc8`,
  `0x2b48068`, `0x2b48088`, `0x2b48364`.
* **блок 0, как id свойства** — `0x12de18c` (`bl 0x12d6bc8; strb w0,[x20,#0x1da]`),
  `0x12dfcb0` — т.е. в блоке 0 **0x358 — это свойство** (поле `settings+0x1da`),
  к нашему коду отношения не имеет. Ещё `0x12952a0/0x12952b4` — только логирование.

Функции-отправители (`0x2b47xxx`) — обработчики изменения состояния привода/брекетинга:
перед отправкой они читают глобалы **`[0x244eb20]`** (сравнения `==8`, `0xd..0x12`)
и **`[0x244ebd4]`** (сравнения `&~2 ==0xb/0xc`, `==2`, `0xb..0xe`), а также
перечитывают/пишут свойство `0x979` (`0x11335ec` get, `0x1135930` set).
Эти глобалы — режимное состояние (drive/bracket), их пишут десятки мест в блоке 1
(`0x2a25a80`, `0x2c3dfa0`, `0x2e97ca4`, `0x2fbc320`, `0x30ab57c` и др.).

### 9.2 Что делает 0x2c116ac — уведомление, а не установка значения

```
2c116ac: w19 = code
2c116bc: if [0x26a30a8+0x18000+0x25fc] != 1 -> 0x2c35238(code); ret
2c116e8..: проверяет «занятость» через 0x12e82f8(0x11..0x15,0x2a,0x20,0x2b,0x29)
           и при освобождении -> 0x2c35238(code)
```

Аргумент — **только код** (payload не передаётся). Далее `0x2c35238(code)` — локальный
диспетчер команд: он логирует (`0x33a0b68 "初期化(0)"`, `0x33a0b90 "\t# OSD画面表示設定 : %s"`),
обрабатывает коды `< 0x9ff`, особый код `0x60a`, и в конце вызывает
**`0x2c35124(code, flag)`** (`0x2c35460`), а тот — `0x2d3a500` (наш диспетчер).
То есть 0x358 — это **уведомление «настройка изменилась / перечитай»**, а не передача
значения: 16-байтовый payload в `0x2d3a500` используется только когда `x20 != 0`
(путь `0x2d3ae44`), а здесь x20 = 0.

### 9.3 Следствие: откуда берётся 0x2C

* `[x20+0x144]` (свойство 0x2B9) заполняется в блоке 0 **чтением из хранилища**
  (`0x12d6bc8`), а хранилище обновляет сеттер `0x128c5d8` (`strb w19,[settings+0x144]`).
* Событие 0x358 из блока 1 лишь заставляет перечитать/синхронизировать это поле
  (payload отсутствует). Значение 0x2C приходит в сеттер блока 0 **из выбора
  пользователя/ПК** (пункт меню drive/bracket) — таблицу «пункт → 0x2C» найти
  не удалось; пары «id 0x2B9 + 0x2C» в коде нет.
* Пространства имён: в блоке 1 коды событий `0x3xx` (диспетчер `0x2d3a500`), в блоке 0
  id свойств (`0x358` — другое свойство, `settings+0x1da`). Соответствие
  `code = id + 0x9F` действует **только** для семейства `0x2AC..0x2C0`
  (коды `0x34B..0x361`), т.е. это табличное кодирование, а не общее правило.

**Уровни:** отправка 0x358 из `0x2b47xxx` и путь `0x2c116ac → 0x2c35238 → 0x2c35124 →
0x2d3a500` — **[Д]**; что 0x358 — уведомление без значения, а 0x2C задаётся в блоке 0
из UI — **[К]**; конкретный режим (ISO BKT/FSIM BKT) — **[Г]**.
