# Код режима 0x2C ([ctx+0x3978]) в цепи RECF/RECCF

Задача: выяснить, что означает код `0x2C`, с которым сравнивается поле `[ctx+0x3978]`
перед вызовом подготовки кадра `0x2ce8f3c`/второго прохода `0x2ceabb8`, и как с ним
связан счётчик кадров `[ctx+0x429c]` = 1/2/4.

Основная модель — X-H2 5.33; проверки для X-H2S 7.31 и X-T5 4.32 — те же адреса
по смыслу (указаны отдельно). Уровни: **[Д]** доказано, **[К]** сильный кандидат,
**[Г]** гипотеза. Скрипты: `37_mode3978.py`, `38/39_mode_domain*.py`,
`40_mode_source.py`, `41_mode_dispatcher.py`, `42_settings_builder.py`, `43_vm_mode.py`.

## 1. Откуда берётся поле [ctx+0x3978] — это 8-битное свойство 0x2B9

Цепочка (X-H2 5.33):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

То есть `[ctx+0x3978]` — **не константа режима внутри RECF, а копия байтового
свойства 0x2B9** (блок настроек: соседние 0x2AE…0x2BA → смещения 0x13A…0x145).
Свойство читается с умолчанием 0 (`mov w1,#0` перед вызовом), т.е. это параметр
конфигурации камеры/задания, а не код, жёстко прошитый в RECF.

Проверено, что свойство 0x2B9 используется во всех трёх моделях (block 0/1,
old и new): X-H2 `0x128c600/0x12dd82c` (b0), `0x2c240ec` (b1); H2S `0x15aacbc/0x15fbe20`
(b0), `0x2e7e8e8/0x2e89624` (b1); T5 `0x11fa3dc/0x12dffe0` (b0), `0x2bcaf80/0x2bdb208` (b1).

**Кто пишет значение (продолжение — `писатель_0x2B9.md`):** в прошивке **нет**
константы 0x2C для этого свойства — скан всех блоков/версий не нашёл ни одной пары
«`mov w0,#0x2b9` + `mov wN,#0x2c`». Значение приходит **в payload события 0x358**:
диспетчер `0x2d3a500` переводит код 0x358 в id `0x2B9` (jump-таблица `0x33BD468`,
база `0x2d3a94c`, тело `0x2d3aae8`), затем 16-байтовый payload копируется
(`[x20]`,`[x20+8]` → `sp+0x30`) и передаётся в `0x2d3a41c(id, len=0x10, payload)`.
Хранится значение в таблице настроек (`0x128c5d8: strb w19,[settings+0x144]`),
сброс — `0x2c240ec` (`mov w1,#0x1affffff; bl 0x11335c4`). Счётчик `[ctx+0x429c]` = 2/3
в блоках 0/1 также не пишется (сеттер `0x2dd0598` вызывается только с 0).
VM-контроль цепочки: `settings+0x144=0x2C → ctx+0x3978=0x2C → ветка 0x2dd216c`
(`47_vm_prop_chain.py`).

**Отправитель события 0x358 (продолжение — `писатель_0x2B9.md` §9):** блок 1,
обработчики изменения состояния привода/брекетинга `0x2b47ad8/ba8/cd8/da8/dc8`,
`0x2b48068/088`, `0x2b48364` — `mov w0,#0x358; bl 0x2c116ac`; они читают глобалы
`[0x244eb20]` (==8, 0xd..0x12) и `[0x244ebd4]` (&~2==0xb/0xc, ==2, 0xb..0xe) и
перечитывают свойство 0x979. `0x2c116ac` — **уведомление без payload** (аргумент
только код), далее `0x2c35238 → 0x2c35124 → 0x2d3a500`. Поэтому значение 0x2C
в событии не передаётся: оно уже лежит в хранилище блока 0 (сеттер `0x128c5d8`),
куда его кладёт выбор пользователя/ПК. Два пространства имён: код события 0x358
(блок 1) и свойство 0x358 (блок 0, `settings+0x1da`) — разные вещи.




## 2. Домен значений и кто с ним что делает

Строгий скан `39_mode_domain2.py` (чтение `[xN,#0x3978]` → `cmp` тем же регистром в
пределах 4 инструкций): **294 сравнения**, значения:

```
0x00..0x03, 0x06, 0x07, 0x09, 0x0A, 0x0C, 0x0F, 0x12, 0x14, 0x17, 0x18,
0x1D(35), 0x1E, 0x1F, 0x20(42), 0x21..0x24, 0x26, 0x28, 0x2C(78), 0x2D(73)
```
(в скобках — число сравнений). То есть поле — байтовый код с «тяжёлыми» кластерами
`0x1D/0x20`, `0x21..0x24` и `0x2C/0x2D`.

Писатели поля в блоке 1 (7 мест, `37_mode3978.py`):

| адрес | что пишет |
|---|---|
| `0x2e18340/0x2e1834c/0x2e18358` | 0x21 / 0x22 / 0x23 / 0x24 — по полю `[ctx+0x397c]` ∈ {1,2,3} |
| `0x2e5c3f8`, `0x2e5c500` | 0x21, если поле было 0 (инициализация) |
| `0x2e96014` | `[settings+0x7d0]` (другая структура) |
| `0x30871ac` | `[settings+0x144]` = свойство **0x2B9** (главный путь) |

Функции, ветвящиеся по `0x2C` (`39_mode_domain2.py`, `40_mode_source.py`):
`0x2dd1ec0` (recfCalcRecifParam — подготовка кадра), `0x2dd1bb0`, `0x2dd18d0`
(recfSetRecfOffsetCcdrw/_CHG), `0x2dcc9ac`, `0x2dd0d30` и др.
По `0x2D`: `0x2dceb54` (**recfSetRecifImg()**), `0x2dd0d30`, `0x2dd0f38`.

Функция-«диспетчер» с наибольшим числом разных сравнений (`41_mode_dispatcher.py`) —
`0x2e4dde8`: значения `{0,1,2,3,7,0xA,0x12,0x18,0x1D,0x1E,0x1F,0x20,0x24,0x26,0x28,
0x2C,0x2D}`, строки — `Maker_WideDRangeMode() : Illegal ResultDRange`,
`Maker_WideDRangeManual/Auto` (динамический диапазон/DR), рядом `0x2e51024` —
`Maker_MovieFrameTypes`. То есть код участвует и в still-RECIF, и в кино, и в DR-логике.

## 3. Что делает 0x2C: включает многокадровый (многопроходный) путь

X-H2 5.33, функция `0x2dd1ec0` (recfCalcRecifParam), перед циклом кадров:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

**VM-контроль** (`43_vm_mode.py`, эмуляция оригинальных инструкций, ctx в памяти):

```
A) [ctx+0x3978] : 0x2C -> ветка 0x2dd216c (многокадровая)
                  0x2D, 0x20, 0x00 -> общая ветка 0x2dd1fa4
B) [ctx+0x429c] : 0/1/4 -> 2 прохода;  2 -> 4;  3 -> 1
```

То есть **код 0x2C — единственный, при котором RECIF-расчёт вообще заходит в цикл
по нескольким кадрам**; остальные коды идут одиночным путём.

Дополнительно: в `0x2dd0d30` при `0x2C` не подставляется значение 3
(`ldr w0,[x21,#0x3978]; cmp w0,#0x2c; mov w0,#3; csel w23,w23,w0,ne`) — код 0x2C
меняет и этот параметр; в DR-функции `0x2e4dde8` он входит в набор допустимых
кодов DR-режима.

## 4. Счётчик [ctx+0x429c] = 1/2/4

* Поле — u16 по смещению `ctx+0x429c` (доступ через `ctx+0x4000` + `0x29c`).
* Сеттер — `0x2dd0598`: `add x0,x0,#4,lsl#12; strh w1,[x0,#0x29c]; ret`
  (рядом такие же сеттеры `0x2dd0574` → `+0x2cc`, `0x2dd058c` → `+0x29e`,
  `0x2dd05b4` → `+0x22c`).
* Вызывающие сеттера в блоке 1: `0x2e694ac` и `0x2e6dab0`, оба пишут **0**
  (инициализация перед заданием). Другие записи в `+0x29c` — `0x2e0d3b8`/`0x2e0fca4`
  (`strh wzr`). В найденном коде блока 1 значения **2 и 3 не выставляются** — они
  приходят извне (блок 0/приложение) или из путей, не попавших в скан.
* Поэтому для «обычного» запуска счётчик равен 0 → **2 прохода**; 4 прохода — только
  при явно записанной 2; 1 проход — при 3.
* Число 1/2/4 **не совпадает** с типичным числом кадров ISO BKT/FSIM BKT (обычно 3),
  что ослабляет прямую связь «0x2C = брекетинг».

## 5. Что такое 0x2D (для контраста)

Предикаты `0x2dd0ee8`, `0x2dd0f7c`, `0x2dd0fa0` (используются в вызывающем коде
подготовки кадра) работают только при `[ctx+0x3978] == 0x2D` и проверяют подтип
`[ctx+0x399c]`:

```
0x2dd0ee8: if mode != 0x2D -> 0; else [ctx+0x399c] в 7..9
0x2dd0f7c: if mode != 0x2D -> 0; else [ctx+0x399c] == 0xA
0x2dd0fa0: if mode != 0x2D -> 0; else [ctx+0x399c] == 0xB
```

Рядом — строки `Maker_MovieFrameTypes` (`0x2e51024`) и `recfSetRecifImg()`
(`0x2dceb54`, ветвление по `0x2D`). **[К]** 0x2D — «кино/серийная запись» с подтипом
(кадровый тип/кодек) в `[ctx+0x399c]`, 0x2C — многокадровый still-путь.

## 6. Итог и сопоставление с брекетингом

| вопрос | вывод | уровень |
|---|---|---|
| что такое `[ctx+0x3978]` | копия байтового свойства **0x2B9** (настройки камеры) в RECF-контекст (`0x30871ac` ← `[settings+0x144]`) | **[Д]** |
| что такое 0x2C | код, при котором recfCalcRecifParam включает **многокадровый цикл** (VM) и меняет параметр в `0x2dd0d30`; в одиночных кодах путь не выполняется | **[Д]** для поведения, **[Г]** для имени режима |
| что за счётчик 1/2/4 | `[ctx+0x429c]`: 0/1/4 → 2 прохода, 2 → 4, 3 → 1; сеттер `0x2dd0598`; инициализируется 0 | **[Д]** |
| 0x2D | кино/серийный режим с подтипом в `[ctx+0x399c]` {7..9,0xA,0xB}; строки `Maker_MovieFrameTypes`, `recfSetRecifImg` | **[К]** |
| 0x2C = ISO BKT / FILM SIM BKT? | **не доказано.** Счётчик даёт 1/2/4, а не 3; строк BKT/BRACKET в цепи нет; 0x2C встречается и в DR-логике (`Maker_WideDRangeMode`), и в `recfSetIqRecInfo` | **[Г]** |

Наиболее правдоподобно: **0x2C — «многокадровый still-режим» из свойства 0x2B9**
(серия/композит: BKT, Clarity, multi-frame NR/DR — что именно, по коду не различить),
а 2/4 прохода — число изображений/проходов конвейера, задаваемое снаружи. Чтобы
отличить ISO BKT/FSIM BKT от других многокадровых режимов, нужно найти, кто пишет
`[ctx+0x429c]` = 2 или 3 и кто выставляет свойство 0x2B9 = 0x2C (поиск в блоке 0,
PTP-обработчиках и UI-таблицах) — это осталось за пределами текущего разбора.

## 7. Проверено и не подтвердилось

* «0x2C — строковый/именованный режим в коде RECF» — **нет**: строковых имён
  (`BKT`, `BRACKET`, `ISO_BKT`, `FSIM`) в достижимой цепи нет; поле приходит из
  свойства 0x2B9.
* «Счётчик — число кадров брекетинга (3)» — **нет**: значения 4/1/2 и 2/4/1 в VM,
  ни одно не равно 3, и в блоке 1 нет записи 2/3 в `+0x29c`.
* «0x2C — только still-путь» — **частично**: он же встречается в DR-функции
  `0x2e4dde8` и в `recfSetIqRecInfo`; но многокадровое ветвление доказано только
  в `recfCalcRecifParam`.
