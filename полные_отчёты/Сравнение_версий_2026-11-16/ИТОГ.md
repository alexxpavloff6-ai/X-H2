# Итог: исправления X-H2 5.33 / X-H2S 7.31 / X-T5 4.32 — разбор слабых мест (2026-11-16)

Оркестрация: координатор Claude Opus 5.5 (high), воркеры DeepSeek Harness `dsh-tui` с `deepseek-flash` (DeepSeek-V4.1-Flash), effort high
(`dsh-flash-high.patch.yml`). Ключевые утверждения воркеров выборочно перепроверены координатором по коду (`fwcommon.py`).
Подробности, скрипты и `доказательства.json` — в папках `A_…`–`D_…`. Камерные тесты не выполнялись; DAT не изменялись.

Уровни: **Д** — доказано кодом/VM; **К** — сильный кандидат; **Г** — гипотеза.

## 1. Видео 6.2K+ — `C_видео_6K/отчёт.md`

- **Д.** Исправлен путь воспроизведения **H.265**: helper переводит 4-байтовые BE-поля длины NAL в старт-коды `00 00 00 01`
  (`PMFRM_SetStartCodeSlice2forAdvance`). Кольцо чтения 192 МиБ = 3 сегмента × 64 МиБ (`0x3C999000/0x40999000/0x44999000`).
- **Д (Unicorn, 3 модели).** Если граница сегмента режет поле длины (1–3 байта в первом сегменте), старый код читает мусор из
  `state+0x62c` → `FrameSizeError` и запись старт-кода по неверному адресу / «дикий» указатель. Новый собирает поле 1+3/2+2/3+1,
  при остатке 0 — `PreSizeError`; в completion добавлена диагностика `PMFRM_AfterDataReadForH265:FinFrameDataSizeError`.
  Очередь: 2 записи, шаг `0x20→0x28`, тег поколения сверяется с `ST+0x74`.
- **Опровергнуто.** «Минута = время оборота кольца»: при битрейтах 6.2K кольцо оборачивается за 0.3–8 с; случайное попадание
  разреза в поле длины слишком редко. Ветвлений по разрешению рядом с патчем нет.
- **Не доказано.** Почему около минуты и почему 6.2K+: реальные размеры чанков приходят от внешнего сервиса, нужен рантайм-лог.

## 2. LCD, горизонтальные линии — `A_LCD_MOVDC/отчёт.md`

- **Д.** Флаг guard (X-H2 `0x4c2ff14`, X-H2S `0x4ba8f0c`, X-T5 `0x4ab72c4`) — поле состояния `+0x43c/+0x434`, которое
  пишут ровно две apply-функции на прошивку, копируя `params.current+0x74` (после `memcpy pending→current`).
  В блоках 0–2 нет кода, который формирует само значение 0/1 — оно приходит извне.
- **Д (Unicorn).** `output+8` — stride дескриптора `{height,width,stride}`. Старая версия всегда наследовала текущий stride дескриптора
  (`p->[8] & ~1`); новая при `flag≠0` берёт его из геометрии (`2×640 = 1280`). В MOVDC-функции это единственное изменение (3 инструкции).
  В apply-функциях добавлены ветки, которые вызывают `0x155bde0/0x155bde8` `(2, ptr, size)` — в образе блока 0 это заглушки
  (**Г:** возможно, обслуживание кэша, подменяемое при загрузке).
- **Г.** Связь с LCD-линиями понижена: геометрия 640×480 и строки модуля (`MOVDC_DETCTRL`, `C1AFea`, `C1BWind/Mask`)
  указывают скорее на кадр детекции/АФ, потребителя дескриптора в блоках 0–2 нет. Что флаг означает CH/ES/1/8000/CONTINUOUS — не доказано.

## 3. ISO BKT / FILM SIMULATION BKT — `D_брекетинг/отчёт.md`

- **Д.** `0x19155` — нижняя граница тройки параметра **CSDROB** (`[OFFSET] CSDROB 設定値 :%d`, `0x33aeb98`) в блоке OFFSET/уровня чёрного
  тракта RAW (рядом FGNOB, UCGNOB, UCNROB, GNAOB, ROB, «黒レベル»). Не ISO и не экспозиция.
- **Д.** Вставка (`+0x984` от входа функции, одинакова в 3 моделях) **безусловно** пишет `params+0x60 = lo<<9`.
  `memset(params,0,0x68)` перед вызовом (`0x2dd1f80`) → в старой прошивке там был 0 (версия «мусор от прошлого кадра» опровергнута).
  Потребитель — второй проход `0x2ceabb8`: `commit+0x88 = lo24<<9 + ((params+0x60 − lo24<<9)·k)/256` (`0x2cec060–0x2cec0a0`),
  т.е. остаточное смещение уровня считалось от 0 вместо границы CSDROB.
- **Поправка к прошлой сессии.** Запись `commit+0x80` и копировщик в `per-frame+0x1f48/+0x1050` работают только при `blob[0xa8].7`,
  который ставится временно в одном месте (`0x2fb0b90`) вокруг служебной выгрузки — к обычной съёмке это не относится.
- **Г.** Связь именно с брекетингом не найдена: в предках (глубина 4, движок RECF/RECCF «S2») нет строк BKT/BRACKET;
  единственное режимное ветвление — `[ctx+0x3978]==0x2C` и счётчик кадров 1/2/4. Ключ — смысл кода режима `0x2C`.
  Механизм «неверное смещение уровня чёрного → испорченный кадр» — **К**.
- **Код режима `0x2C`** (`D_брекетинг/режим_0x2C.md`). **Д:** `[ctx+0x3978]` копируется из блока настроек (`0x30871ac` ← `[settings+0x144]`),
  младший байт — свойство `0x2B9` (`0x12dd82c`, умолчание 0); копия 32-битная, поэтому при сравнении с `0x2C` соседние байты
  (свойства `0x2BA…`) должны быть 0. **Д (VM):** только при `0x2C` функция `recfCalcRecifParam` (`0x2dd1f9c`) входит в многокадровый цикл;
  проходов: счётчик `[ctx+0x429c]` = 2 → 4, = 3 → 1, иначе (в т.ч. 0 по умолчанию) → 2. Значения 2/3 в блоке 1 не выставляются.
  `0x2D` — отдельное семейство (кино/серия, подтип `[ctx+0x399c]`). **Г:** что `0x2C` = ISO BKT / FILM SIMULATION BKT —
  строк BKT в цепи нет, число проходов 1/2/4 не совпадает с 3 кадрами брекетинга; кандидаты — любой «одна экспозиция → несколько проявок» режим.
- **ОТВЕТ: `0x2C` = `MODE_RECORD_HDR`** (воркер F, `F_режим_съёмки/отчёт.md`, `enums.txt`; проверено координатором).
  **Д:** функция-резолвер имени режима в блоке 0 сопоставляет `0x2C` строке `MODE_RECORD_HDR` во всех трёх моделях
  (X-H2 `0x114203c`, X-H2S `0x1461ae0`, X-T5 `0x114204c`). **К:** `[ctx+0x3978]` — код `MODE_RECORD`: прямые писатели кладут
  `0x21..0x24` = PROGRAM/SHUTTER/APERTURE/MANUAL по селектору P/S/A/M (`0x2e18340`), дефолт `0x21`; набор значений из 294 сравнений D
  совпадает с enum (`0x1D` ADV_TURNING_PANORAMA, `0x1F` ADV_MULTI_EXPO, `0x20` ADV_FILTER, `0x2D` MOTIONJPEG — D независимо отнёс `0x2D` к кино).
  Значит многокадровая ветка `recfCalcRecifParam` при `0x2C` — это **режим HDR** (композит из нескольких кадров), а не брекетинг.
  Прямой записи `0x2C` в код нет: значение приходит копией из `job+0x144` или из still-параметров `+0x7d0` (заполняются UI-командой, диспетчер `0x1343b84`).
  Писателя `[0x4daa6e8]` (указатель на job) в блоках 0–2 нет — задание приходит извне (**К**, воркер E). X-T5: поле режима RECF —
  `ctx+0x39C0` (`0x2d132dc`, подтип `+0x39C4`); X-H2S: доп. прямой путь `0x31771dc` (`ctx+0x3978 = src+0x14`).
  Следствие для исправления брекетинга: патч CSDROB общий для пути подготовки кадра, связь именно с ISO BKT / FILM SIM BKT по-прежнему не доказана.
- **ОПРОВЕРЖЕНО (воркер E, `E_сеттер_0x2B9/отчёт.md`; проверено координатором):** свойство `0x2B9` — `ubNetmaskSettingManual1octet8`
  (строка лога `0x173af40` в ветке сеттера), октет маски сети. Связь `[ctx+0x3978]` со свойством `0x2B9` ложная: совпало лишь смещение `+0x144`
  в разных структурах. Реальный источник — 32-битное поле `job+0x144` структуры задания из `[0x4daa6e8]` (копирование `0x30871a8/0x30871ac`).
  Пункт ниже про `0x2B9`/событие `0x358` к режиму `0x2C` не относится и оставлен как история проверки.
- ~~**Кто ставит `0x2B9`**~~ (`D_брекетинг/писатель_0x2B9.md`). **Д:** константы `0x2C` для `0x2B9` в коде нет. Хранилище — блок 0 (`0x128c5d8`,
  `strb [base+slot*0x12768+0x1000+0x144]`, прямых вызовов нет). Событие `0x358` → свойство `0x2B9` (jump-таблица `0x33BD468`, case `0x58` → `0x2d3aae8`;
  семейство кодов `0x34B..0x361` → id `0x2AC..0x2C0`, id = code − `0x9F`). Отправители события — 8 мест в блоке 1 (`0x2b47ad8…0x2b48364`) через
  `0x2c116ac(code)`: это **уведомление без данных** («перечитай настройку»), значение в нём не передаётся. Отправители проверяют глобалы
  `[0x244eb20]` (507 чтений, `==8`, `0xd..0x12`) и `[0x244ebd4]`; прямых записей в них не найдено. **Г:** таблица «пункт меню → 0x2C» не найдена,
  режим съёмки для `0x2C` не установлен.

## 4. XF30mm Macro — `B_объектив_0x411/отчёт.md`

- **Д (Unicorn, 3 модели).** Новый флаг `request+0x50 = (lens == 0x411)` в двух конструкторах запроса переключает источник «шага» и
  «значения» MF-операций; старый источник — свойства `0x1db3/0x1dba` (писателя в коде нет, приходят извне; в новой прошивке удалены).
- **Поправка к прошлой сессии.** Реализация **не одинакова**: X-H2/X-H2S — константы `out+0xa0 = 0xe4 (228)`, шаг `0x8c` → `out+0x50 = 280`
  (остальные объективы 0 / 256); X-T5 — читает свойства `0x205a/0x205e` для `0x411` и `0x2059/0x205c` для остальных.
  Поэтому прежнее сопоставление `0x205c = KEY_ND_FILTER`, `0x205e = KEY_TELE_CONVERTER` вероятно ошибочно.
- **К.** `0x411` = XF30mmF2.8 R LM WR Macro: таблицы названий объективов в прошивке нет. 228/280 — не углы кольца (UI: 90/180/270/360),
  вероятно параметры пересчёта поворота в перемещение фокуса.
- **Не доведено.** Цепь до команды объективу: последние адресаты — `dest+0x448+0x20` (`0x2de613c`) и глобал `0x4bd535c` → объект `0x4b0b148`.
- Helper `0x58a58c` — отдельная правка, `0x411` не проверяет; `request+0x25` не менялась.
