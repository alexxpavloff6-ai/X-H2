# Задача F: глобалы `[0x244eb20]` и `[0x244ebd4]` — что это, кто пишет, и как связано с кодом режима `0x2C`

Основная модель — **X-H2 5.33** (блок 1, если не указано иное). Подтверждение в X-H2S 7.31 и X-T5 4.32 —
по тем же идиомам кода (адреса указаны). Уровни: **[Д]** доказано (инструкции/VM), **[К]** сильный
кандидат, **[Г]** гипотеза. Скрипты и артефакты — в конце. Предыдущие результаты (`D_брекетинг/режим_0x2C.md`,
`писатель_0x2B9.md`) не перепроверялись, кроме тех мест, где это было нужно для ответа.

## 0. Краткий ответ

| вопрос | ответ | уровень |
|---|---|---|
| что такое `[0x244eb20]` | **не отдельный глобал, а ПЕРВОЕ ПОЛЕ структуры** `S` = `0x244eb20`, размер **0x2940** (10.5 КБ), RAM-блок состояния рекордера/съёмки; инициализируется `memset(S,0,0x2940)` в `0x2ba99a8`…`0x2ba9a10` с установкой 4 указателей vtable по `+0x760` и `+0x1c00` | **[Д]** |
| что такое `[0x244ebd4]` | поле `S+0xb4` (u32), младший байт кода подрежима (значения 2, 3, 0xb, 0xc, 0xb..0xe) | **[Д]** для адреса, **[Г]** для имени |
| кто пишет `S+0` / `S+4` / `S+0x10` / `S+0xb0` / `S+0xb4` | **прямых писателей нет ни в блоке 0, ни в блоке 1** (все шесть образов, включая 5.30/H2S/T5). Пишутся только vtable-указатели (`+0x760…+0x778`, `+0x1c00…+0x1c18`), счётчик `+0x3e4` и `memset` при инициализации. Структура ведёт себя как **чужой/разделяемый блок состояния** (заполняется вне разобранного кода) | **[Д]** (отрицательный результат), **[Г]** (как заполняется) |
| что означают значения `S+0` = 8 и 0xd..0x12 | в прошивке есть три готовых enum-таблицы (MODE_RECORD 0..0x68, MODE_CONTINUOUS 0..0xE, DRIVEMODE_BKUP 0..0x1A). Ни одна не даёт связной группы «8 + 0xd..0x12»; ближе всего DRIVEMODE_BKUP (`0xd..0x12` = AE_BKT_NUM_4..1/BKT/FOCUS_BKT), но `8` там = AE_BKT_NUM_9. | что означают `S+0xb4` = 2, 0xb..0xe | известно только использование: `(v & ~2) == 0xc` (т.е. v ∈ {0xc,0xe}), `v ∈ {2,3}`, `v ∈ {0xb,0xc,0xe}`; в таблицах enum'ов такие же значения есть у DRIVEMODE_BKUP (0xb..0xe = AE_BKT_NUM_6..3) и MODE_CONTINUOUS (0xb..0xe = FOCUS_BKT, PIXEL_SHIFT, MEGA, NUM) — однозначно не сопоставляется | **[Г]** |
| свойство `0x979` | X-H2: id `0x979` → поле настроек **`settings+0x5a0`** (тот же offset в X-H2S для id `0x978`; в X-T5 id `0x9ff` → `+0x64c`). Значения — **{0,1,2,3}**, проверяются таблицей enum `0x1bd3ab8` (у `0x979` запись `0x175fd50`: 0,1,2,3, стоп-запись 0xffff). Debug-метка поля в логгере бэкапа — `bPlayResize` | **[Д]** адрес/домен, **[К]** метка |
| отправляется ли `0x358` при `S+0` = 8 / 0xd..0x12 | **да, но другим путём**: эти значения (и `mode` = 4/6/7/0x15, и `S+8` = 1/0x100000001) направляют в ветку, где перед `0x358` выполняется предкоманда `0x19F`/`0x1A0`; иначе `0x358` отправляется «напрямую» (`0x2b47cd8`). Сам код `0x358` отправляется практически всегда при входе в обработчик (при `0x2a02384()==0x55`) | **[Д]** (VM) |
| может ли `0x2B9` стать `0x2C` в этой ситуации | **прошивка это значение не пишет** — обработчики только уведомляют «перечитай свойство»; запись `0x2B9` идёт через property-ядро из UI/внешнего слоя. Значит `0x2B9 = 0x2C` возможно только если оно уже такое в хранилище; в проверяемых ветках `0x2C` не появляется (там 8 и 0xd..0x12). Косвенно: в enum MODE_RECORD код `0x2C` = **`MODE_RECORD_HDR`**, `0x2D` = `MODE_RECORD_MOTIONJPEG` — это ровно те два кода, которые D нашёл в `[ctx+0x3978]`, и оба многокадровые | **[Д]** для «не пишет», **[К]/[Г]** для HDR |

## 1. Структура `S = 0x244eb20`: идентификация

### 1.1 Это база структуры, а не одиночный глобал

Скан страницы `ADRP 0x244e000` по блоку 1 X-H2 5.33 даёт **290** пар `adrp+add`, из них
`add #0xb20` — **256** (и ещё `add #0xb4c` = `S+0x2c` — 29). Распределение (скрипт `04_page_adds.py`):

```
+0x0b20 -> 0x244eb20  n=256   <- база S
+0x0b4c -> 0x244eb4c  n= 29   <- S+0x2c (строковый буфер)
+0x0808 -> 0x244e808  n= 4    (другая структура)
+0x00a8/0x05f8/0x0800/0x085d — единичные, другие объекты
```

В блоке 0 — те же 5 пар `+0xb20` и 20 пар других иммедиатов.

Прямое подтверждение, что `0x244eb20` — **начало** объекта, а не поле:

* `0x2ba99bc–0x2ba99d0` (b1): `adrp x19,0x244e000; add x19,x19,#0xb20; mov w2,#0x2940;
  mov w1,#0; mov x0,x19; bl 0x14c9754` → **`memset(S, 0, 0x2940)`**; значит размер 0x2940,
  и `S` — самостоятельный объект.
* сразу после memset в него ставятся 4 указателя, каждый **дважды** — в `+0x760…+0x778`
  и в `+0x1c00…+0x1c18`:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

  То есть `S` — объект с **двумя одинаковыми наборами «виртуальных» указателей** (активный и
  «теневой»), т.е. классический C++-подобный синглтон состояния. Те же 8 записей есть в блоке 0
  (`0x1315ca0…0x1315cd4`, там же `str x0,[x19,#0x1c00]`) — блок 0 и блок 1 работают с одним объектом.
* `0x1316a34` (b0): `add x0,0x244e000,#0xb20; str x0,[x19,#0x58]` — указатель на `S` кладётся
  в объект-владелец (`x19+0x58`), рядом с другими указателями (`+0x50`, `+0x60`, `+0x68`…).
* `0x1141020`/`0x1141628` (b0): `add x21,#0xb20` и `bl 0x15e2ec0` c второй базой `0x260da08` —
  **побайтовое сравнение** `S` с «теневым» блоком `0x260da08` (функция типа `memcmp`), т.е. `S`
  периодически сверяется с эталоном/копией.

### 1.2 Карта полей (X-H2 5.33; чтения — мой счёт, окно 40 инструкций)

| смещение | размер | чтений | записей | что видно в коде |
|---|---|---|---|---|
| `+0x000` (`0x244eb20`) | u32 | 249 (275 при прямых `ldr w,[x,#0xb20]`) | **0** | частое поле-«режим»: сравнения `==8`, `0xd..0x12`, `(v&~2)==1` (т.е. 1/3), `==4/6/7/0x15` |
| `+0x004` (`0x244eb24`) | u32 | 6 | 0 | классификатор `≤6`, маска `0x25` = {0,2,5} и `0x48` = {3,6} (`0x29faf98`) |
| `+0x008` (`0x244eb28`) | u64 | 47 | 0 | сравнивается с `1` и `0x100000001` → **два u32-флага** в `+8/+0xc` |
| `+0x010` (`0x244eb30`) | u32 | 31 | 0 | «флаг/счётчик», в обработчиках `cbz` = «нет состояния» |
| `+0x014`,`+0x018` | u32 | 8+8 | 0 | редко читаются |
| `+0x02c` (`0x244eb4c`) | char[] | 29 обращений через `add #0xb4c` | 0 | **имя файла**: `strcpy` в `sp+0x20`, `strlen`, добавление `".RAF"` (`0x31ab7a0`) и проверка существования `0x2ec0ef0` (`0x29fb004–0x29fb034`) |
| `+0x0b0` (`0x244ebd0`) | u32 | 36 | 0 | счётчик/флаг рядом с `+0xb4` |
| `+0x0b4` (`0x244ebd4`) | u32 | 15 | **0** | код подрежима (см. §3.3) |
| `+0x0b8`,`+0x0bc` | u32 | 1+1 | 0 | — |
| `+0x0c0…+0xc4` | байты | 2…3 | 0 | — |
| `+0x3d6` | u16 | **85** | 0 | самое частое поле после `+0`; смысл не установлен |
| `+0x3e4` | u16 | 10 | **3** (`0x2c10fa0/fb8/fcc`, `strh`) | единственное «живое» числовое поле, инкремент/декремент (`+1`, `-1`, `ldr w0,[x0,#0x86c]; strh`) |
| `+0x760…+0x778`, `+0x1c00…+0x1c18` | u64×4 ×2 | — | 8+8 | vtable-указатели (`0x2ba99dc…`, `0x1315ca0…`) |

Т.е. `[0x244eb20]` = `S->mode` (u32), `[0x244ebd4]` = `S->sub` (u32, `S+0xb4`). Значения из задачи
(507/15 чтений) — это счёт с другим окном/включая `ldr w,[x,#0xb20]` — совпадает по порядку величины.

### 1.3 Кросс-модельные адреса (те же поля, проверено идиомами)

| модель | `S` (=`mode` при `+0`) | `sub` (`+0xb4`) | сайты-идиомы (`&~2==0xc`, `sub 0xd/cmp 5`) |
|---|---|---|---|
| X-H2 5.30 | `0x2452b20` | `0x2452bd4` | `0x2b4ba88`, `0x2b4bac8`, `0x2b4bb14` |
| X-H2 5.33 | **`0x244eb20`** | **`0x244ebd4`** | `0x2b47a88`, `0x2b47ac8`, `0x2b47b14` |
| X-H2S 7.30/7.31 | `0x276eb88` | `0x276ec3c` | `0x2e65cac`, `0x2e65cec`, `0x2e65d38` |
| X-T5 4.31/4.32 | `0x23bd360` | `0x23bd414` | `0x2a8c8b4`, `0x2a8c8f4`, `0x2a8c940` |

Разность `sub - mode` = `0xb4` во **всех** моделях — лишнее подтверждение, что это одна и та же структура
с одинаковой раскладкой полей `+0`/`+0xb4`, а не совпадение. Сдвиг X-H2 5.30 → 5.33 ровно `-0x4000`
(вся страница `0x2452000` → `0x244e000`).

## 2. Писатели `[0x244eb20]` / `[0x244ebd4]`: отрицательный результат и что проверено

**Прямых записей в `S+0`, `S+4`, `S+8`, `S+0x10`, `S+0xb0`, `S+0xb4` в коде X-H2 5.33 (блоки 0 и 1)
НЕТ.** Проверено (скрипты `01`, `02`, `11`, `18`, `21`, `22`, `23`):

1. **ADRP 0x244e000 + ADD #0xb20 + LDR/STR с 12-битным смещением** (в т.ч. прямой `ldr w0,[x8,#0xb20]`):
   275 чтений `+0`, **0 записей**; отдельный проход по полям `+0xb0…+0xc4` — только чтения.
2. **Трассировка `add`-цепочек внутри функции** (окно 60 инструкций, `add` любой глубины,
   `stp/str/strh/strb`): записи только в `+0x760`, `+0x768`, `+0x770`, `+0x778`, `+0x1c00…+0x1c18`
   (инициализатор) и `+0x3e4` (счётчик).
3. **Отрицательные смещения** (компилятор мог собрать `adrp 0x244f000; str w0,[x8,#-0x4e0]`):
   просканированы страницы `0x244c000..0x2453000` с любыми `±imm` у `add` и `ldr/str`
   (`ldur/stur` тоже) — снова 0 записей в поля режима.
4. **Копирование базы через `mov`/`orr`** (частый приём: `mov x19,x0`) — учтено в `18`, `21`, `23`.
5. **Передача базы в callee**: указатель на `S` трассируется через спил в стек
   (`str x0,[sp,#off]` → `ldr xN,[sp,#off]`) и передачу в `x0..x7`; найдено 4 callee:
   `0x15e2ec0` (memcmp с `0x260da08`), `0x2c19774`, `0x2c1f144` (обе — чтение/логирование),
   `0x14c9754` (memset при инициализации). **Ни один не пишет поля режима.**
6. **Блок 2** (низкоуровневый ARM64): `ADRP` на страницу `0x244e000` вообще нет ни в одной модели,
   т.е. блок 2 к этой структуре по этим адресам не обращается.
7. **Другие версии/модели**: для 5.30 (`0x2452b20`), H2S (`0x276eb88`), T5 (`0x23bd360`) картина та же
   (совпадающие идиомы чтения, ни одной записи в поле режима).

Единственные записи в `S`, которые удалось найти:

* `memset(S,0,0x2940)` + 8 vtable-указателей — `0x2ba99a8`…`0x2ba9a10` (b1) и `0x1315ca0`…`0x1315cd4` (b0);
* `strh` в `S+0x3e4` (счётчик) — `0x2c10fa0`, `0x2c10fb8`, `0x2c10fcc`;
* `0x1316a34`: `str x0,[x19,#0x58]` — сохранение **самого указателя** на `S` в объекте-владельце.

**Вывод.** `S` — объект, который прошивка только читает (плюс одна ветка обновляет счётчик `+0x3e4`).
Значения `mode`/`sub` приходят извне разобранного кода: либо заполняются по указателю,
хранящемуся в объекте `x19+0x58` (его писатели ищутся уже в другом пространстве имён),
либо структура заполняется другим агентом/через IPC. Уровень: **[Д]** — «прямых писателей в блоках 0/1
нет»; **[Г]** — «заполняется извне». **Точный writer не найден** — это главный незакрытый пункт задачи.

## 3. Смысл значений `S+0` и `S+0xb4`

### 3.1 Что делает код с `S+0` (`mode`)

Сводка по читателям (`20_field_cmps.py`, `26_moderecord_hypo.py`):

* `(mode & ~2) == 1` → mode ∈ **{1, 3}** — «обычный одиночный» путь (так в `0x2b47840`,
  `0x2b47878–0x2b47890`, и в ~200 других функциях тот же идиом `cmp #1 / cmp #3`);
* `mode == 8` и `mode ∈ 0xd..0x12` — «особые» режимы (обработчики `0x2b47xxx`);
* `mode ∈ {4, 6, 7, 0x15}` — отдельный case-блок (вход `0x2b47a14`/`0x2b47c14`);
* `mode` сравнивается с `2`, `0x14`, `0x16` и др. в других местах (см. `field_cmps.txt`).

### 3.2 Enum-таблицы, которые есть в прошивке (b0 X-H2 5.33) — полные расшифровки в `enums.txt`

1. **`MODE_RECORD_*`** — резолвер `0x1141ee0` (105 значений): `0=AUTO`, `1=SR_AUTO`,
   `2..4=EXR_FULL/MIX/DOUBLE`, `5..0x1c` — SP-сюжеты, `0x1d=ADV_TURNING_PANORAMA`,
   `0x1e=ADV_3D2`, `0x1f=ADV_MULTI_EXPO`, `0x20=ADV_FILTER`, `0x21=P`, `0x22=S`, `0x23=A`, `0x24=M`,
   `0x25=SIMPLE_MANUAL`, `0x26..0x28=SYNC_*`, **`0x2c=HDR`**, **`0x2d=MOTIONJPEG`**, `0x2e=MAX`, …
   Это enum **режима съёмки/положения диска REC** (SP/P/S/A/M/ADV/HDR).
2. **`MODE_CONTINUOUS_*`** — резолвер `0x11427a8` (15 значений): `0=OFF`, `1=ON`, `2=PRE`,
   `3=FACE_BRACKET`, `4=CYCLE`, `5=AE_BRACKET`, `6=FSIM_BRACKET`, `7=DRANGE_BRACKET`,
   `8=BEFORE_AFTER`, `9=ISO_BRACKET`, `0xa=WB_BRACKET`, `0xb=FOCUS_BRACKET`, `0xc=PIXEL_SHIFT`,
   `0xd=MEGA`, `0xe=NUM`. Это enum **режима привода/серийной съёмки**.
3. **`BKUP_DOTLCD_POWOFF_DRIVEMODE_*`** — резолвер `0x116bcc8` (27 значений): `0=MULTI`, `1=PRE`,
   `2=CONT_SH`, `3=CONT_H`, `4=CONT_M`, `5=CONT_L`, `6=CONT`, `7=AE_BKT`, `8=AE_BKT_NUM_9`,
   `9..0xf=AE_BKT_NUM_8..2`, `0x10=AE_BKT_NUM_1`, `0x11=BKT`, `0x12=FOCUS_BKT`,
   `0x13=BKT_UNABLE`, `0x14=SINGLE`, `0x15=COLOR_MODE`, `0x16=DR_BKT`, `0x17=WB_BKT`,
   `0x18=ISO_BKT`, `0x19=MOVIE`, `0x1a=PIXEL_SHIFT`.

### 3.3 Сопоставление с наблюдаемыми значениями

| поле | значения в проверках | что подходит | вывод |
|---|---|---|---|
| `S+0` | `8`, `0xd..0x12`, `{1,3}`, `{4,6,7,0x15}`, `2`, `0x14` | DRIVEMODE_BKUP: `0xd..0x12` = AE_BKT_NUM_4..1 + BKT + FOCUS_BKT (связная группа «AE-брекетинг и фокус-брекетинг»), но `8` = AE_BKT_NUM_9 выбивается; MODE_CONTINUOUS: `8`=BEFORE_AFTER, `0xd`=MEGA, `0xe..0x12` вне домена; MODE_RECORD: `8`=SP_LANDSCAPE, `0xd`=SP_NIGHTSCAPE_HAND… — тоже не группа | **[Г]**: точное имя не установлено; наиболее правдоподобно — «режим привода/брекетинга» из семейства DRIVEMODE |
| `S+4` | `≤6`; маски `{0,2,5}` и `{3,6}`; `{1,4}` → ложь | MODE_CONTINUOUS-подобный enum 0..6: `{0,2,5}` = OFF/PRE/AE_BKT, `{3,6}` = FACE_BKT/FSIM_BKT | **[Г]** |
| `S+0xb4` | `2`, `3`, `0xb`, `0xc`, `0xd?`, `0xe`; проверки `(v&~2)==0xc`, `v∈{2,3}`, `v∈{0xb,0xc,0xe}` | ни один из трёх enum не даёт согласованной семантики | **[Г]** |

Все три enum-таблицы выгружены целиком (`enums.txt`), так что при появлении внешней информации
(что за код 8 и 0xd..0x12) имя восстанавливается однозначно.

Дополнительно установлено, что `S+0` **не** используется как индекс таблицы имён
(скрипт `35_table_index.py`, 0 совпадений) — имена полей в коде не хранятся.

## 4. Свойство `0x979`: id, поле настроек, значения

### 4.1 Id → поле настроек (новый результат, property-ядро)

Ядро доступа к свойствам: `0x12aa788(id, default, slot, …, …)` (b0 X-H2 5.33) — по `id` берёт
jump-таблицу `0x1745e70` (`s32`, `target = 0x12aa7dc + off*4`), в каждом case читает/пишет
`settings = 0x2624a88 + slot*0x12768`. Декодировано (`27_prop_to_offset.py`):

| id | поле настроек | как читается |
|---|---|---|
| **`0x979`** | **`+0x5a0`** | `12c61b4: ldrb w19,[x0,#0x5a0]` |
| `0x90a` | `+0x59f` | `12c618c: ldrb w19,[x0,#0x59f]` |
| `0x2b9` | `+0x1144` | `12cd0ec: ldrb w19,[x0,#0x144]` после `add x0,x0,#1,lsl#12` |
| `0x358` | `+0x11da` | `12ceab4: ldrb w19,[x0,#0x1da]` (после `+0x1000`) |
| `0x0d` | `+0x202` | `12aa9dc: ldrb w19,[x0,#0x202]` |

Кросс-модельно (`29`, ручная проверка): X-H2S `0x978` → тот же `settings+0x5a0`
(`1585cf4: strb w19,[x0,#0x5a0]`); X-T5 `0x9ff` → `settings+0x64c` при базе `0x257c888` и шаге
`0xab4c` (`12c65d8: ldrb w19,[x0,#0x64c]`). Для X-T5 `0x2b9` → `settings+0x329`, `0x358` → `+0x880`.

### 4.2 Значения `0x979` — {0,1,2,3}

Функция `0x12e67ac(id, value, mode, flag)` (обёртка `0x1135930`) по таблице `0x1bd3ab8`
(`u64`-массив «id → массив 16-байтных записей») ищет `value` в списке допустимых значений:

```
0x979 -> 0x175fd50:  записи {0}, {1}, {2}, {3}, затем стоп {0xffff,0xffff,0xffff,0xffff}
```

То есть домен `0x979` = **{0,1,2,3}**, и вызов `check(0x979, get(0x979), 1, 0)` в обработчиках — это
фактически «нормализация/проверка значения» (возвращает значение, если оно в таблице, иначе 0 и
выставляет флаг ошибки `[0x204f408]`). В обработчиках результат сравнивается с **1, 2, 3**.

### 4.3 Как называется поле

В логгере бэкапа настроек (b0, `0x1264xxx…0x1268xxx`) чтение `settings+0x5a0` сопровождается
форматом `"\t$BACKUP[%d]bPlayResize %s(%d)->%s(%d)\r\n"` (`0x1267658`/`0x1267668`, `0x17322d0`) —
единственная debug-метка для этого offset. В X-T5 поле `settings+0x64c` тоже логируется как
`bPlayResize` (`0x126fd48`/`0x126fd58`). Уровень **[К]**: метка согласована в двух моделях, но
«playResize» плохо вяжется с контекстом режима съёмки — возможно, метка устарела или поле
переиспользовано. Поэтому в отчёте оно фигурирует в первую очередь как **«свойство `0x979`
(X-H2) = поле настроек `+0x5a0`»**.

Замечание: в блоке 0 есть ещё два места с `mov w0,#0x979` (`0x126765c/0x1267670`) — это тот же
логгер (число лишь передаётся в itoa-подобную функцию, которая первый аргумент игнорирует), поэтому
«0x979» там не свойство, а артефакт вызова.

## 5. Обработчики `0x2b478b0` и соседние: когда шлётся `0x358` и что ещё меняется

### 5.1 Четыре функции и таблица указателей

Все 8 сайтов `mov w0,#0x358; bl 0x2c116ac` лежат в четырёх функциях (b1 X-H2 5.33):

| функция | адреса отправки `0x358` | прочее |
|---|---|---|
| **A** `0x2b47840` | `0x2b47ad8`, `0x2b47ba8` | шлёт также `0x301`, `0x35b`, `0x3a3`, `0x602`; читает свойство `0x90a` (get) и `0x979` (4×(get+check)) |
| **B** `0x2b47bb8` | `0x2b47cd8`, `0x2b47da8`, `0x2b47dc8` | те же `0x301/0x35b/0x3a3/0x602` в других ветвях; `0x979` ×4 |
| **C** `0x2b47dd8` | `0x2b48068`, `0x2b48088` | `0x300`, `0x359`, `0x35a`, `0x301`, `0x35b`, `0x3a3`, `0x602`, `0xa04`, `0xa05`, `0xa50`, `0xa3e`, `0x4a9`, `0x4a3`; `0x90a`, `0x979` |
| **D** `0x2b481ec` | `0x2b48364` | как C (`0xa04`, `0x359`, `0x301`, `0x35b`, `0x3a3`, `0x602`, …) |

Все четыре вызываются косвенно: прямых `bl` на них нет; указатель на `0x2b47dd8` лежит в таблице
`0x32439c0` (там же `0x2b47840`, `0x2b47bb8`, `0x2b480a8`, `0x2b48148`, …, `0x2b48cc4` — 16 обработчиков).
Таблицу в блоках 0/1/2 никто не адресует напрямую — диспетчеризация идёт через указатели/`blr`
(как и предупреждает задание).

### 5.2 Полная логика ветвления (дизассемблер + VM)

Вход (функция B, `0x2b47bb8`):

```
busy = 0x12e82f8(0x29)
if (busy != 0) goto FALLBACK
if ([S+0x10] == 0) goto FALLBACK
if ((mode & ~2) == 1) goto FALLBACK        // mode ∈ {1,3}
case mode:
  0x15: if (S+8 == 1 || S+8 == 0x100000001) goto FALLBACK
  4,6,7: goto FALLBACK
then:
  if (u16[0x244f1a4] == 0x16) goto FALLBACK
  if (u16[0x244eef6] != 0 && [ctx+0x26ac] == 1) goto FALLBACK
  if ((sub & ~2) == 0xc) goto CHECK_MODE      // sub ∈ {0xc,0xe}
  p = check(0x979, get(0x979)); if (p == 0) goto FALLBACK
  if (sub ∈ {0xb,0xc,0xe}) goto CHECK_MODE
  p = check(...); if (p != 1) goto CHECK_MODE
  goto FALLBACK
CHECK_MODE:
  if (sub-2 <= 1)  { p=check(...); if (p != 2) goto C2; goto FALLBACK }   // sub ∈ {2,3}
  if (sub == 2)    { p=check(...); if (p != 3) goto C3; goto FALLBACK }
C2/C3:
  if (mode == 8) goto FALLBACK
  if (mode-0xd <= 5) goto FALLBACK            // mode ∈ {0xd..0x12}
  bl 0x130cd44;  SEND 0x358 @0x2b47cd8; return -1
FALLBACK:                                      // 0x2b47bec
  bl 0x130cd44; busy = 0x12e82f8(0x29)
  if (busy == 0) { 0x2c151d8(); /* шлёт команду 0x19F */ }
  else           { 0x2c15200(); /* шлёт команду 0x1A0 */ }
  if (0x2a02384() == 0x55) SEND 0x358 @0x2b47da8/0x2b47dc8
```

`0x2c151d8`/`0x2c15200` — обёртки над `0x12e863c(0x19f/0x1a0, 0,0,0,0)`, т.е. перед повторным
чтением свойства `0x2B9` прошивка посылает одну из двух команд (`0x19F` при свободном состоянии,
`0x1A0` при занятом). `0x2a02384` — запрос состояния UI/экрана (читает `[ctx+…+0x8d8]` и сравнивает
с `0x1a4/0x1a5/0x1a6/0x1b4`), возвращает `0x55` в «разрешённом» состоянии.

### 5.3 VM-контроль (Unicorn, оригинальные инструкции)

Скрипты `31`, `32`, `33`, `36`, `37`: эмуляция функции B при разных `(mode, sub, p, busy, aux)`,
`bl` перехватываются заглушками. Матрица `matrix_358.json` (busy=0, aux=0x55):

| sub \ p | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| 0,1,4..0x0a,0x0d,0x0f,0x10 | pre_19F | pre_19F | direct | direct |
| 2 | pre_19F | pre_19F | pre_19F | pre_19F |
| 3 | pre_19F | pre_19F | pre_19F | **direct** |
| 0xb | pre_19F | **direct** | direct | direct |
| 0xc | **direct** | direct | direct | direct |
| 0xe | **direct** | direct | direct | direct |

* `direct` = `0x358` без предкоманды (`0x2b47cd8`);
* `pre_19F` = перед `0x358` команда `0x19F` (`0x2b47dc8`); при `busy != 0` — `0x1A0` (`0x2b47da8`).

Для `mode` = 8, 0xd..0x12, 4, 0x15 — всегда `pre_19F` (значения `S+8` для `0x15` тоже влияют).
Для `mode` = 1/3 обработчик уходит в FALLBACK сразу — там тоже возможна отправка `0x358`
(через `0x2c151d8`/`0x2a02384`), т.е. **`0x358` — «уведомление о перечитывании», а не сигнал
«особого режима»**; особые значения лишь выбирают предварительную команду и набор побочных кодов.

Итог: **событие `0x358` (перечитать свойство `0x2B9`) отправляется при любом вызове обработчика,
если `0x2a02384()==0x55`; значения `S+0` (8, 0xd..0x12), `S+0xb4` (2, 0xb..0xe) и свойства `0x979`
(0..3) определяют, будет ли перед этим послана команда `0x19F`/`0x1A0` и какие ещё коды
(0x301/0x359/0x35a/0x35b/0x3a3/0x602/0xa04/0xa05/…) уйдут.** Уровень **[Д]** (дизассемблер + VM).

## 6. Связь с режимом `0x2C` (свойство `0x2B9`)

1. `[0x244eb20]` и `[0x244ebd4]` **не являются** свойством `0x2B9` и не являются его копией:
   это поля `S+0`/`S+0xb4` объекта состояния. Копия свойства `0x2B9` живёт по другому адресу —
   `settings+0x1144` (X-H2) → `[ctx+0x3978]` (см. `D_брекетинг/режим_0x2C.md`).
2. Обработчики `0x2b47840/…` **не пишут** `0x2B9` (и вообще ничего не пишут в `S`): они шлют
   уведомление `0x358` (без payload), которое диспетчер `0x2d3a500` сопоставляет с id свойства `0x2B9`
   (jump-таблица `0x33BD468` у D). Т.е. они **заставляют перечитать** уже лежащее в хранилище значение.
3. Значение `0x2C` в эти обработчики не попадает: проверяются `8` и `0xd..0x12` (для `S+0`),
   `2/3/0xb..0xe` (для `S+0xb4`), `0..3` (для `0x979`). **В ситуации, когда перечитывается `0x2B9`,
   прошивка не превращает его в `0x2C`** — она просто перечитывает то, что лежит в хранилище;
   `0x2C` приходит от UI/ПК через property-сеттер блока 0 (`0x128c5d8`, см. D) или из внешнего слоя.
4. Полезное косвенное совпадение: в enum `MODE_RECORD` (`enums.txt`) **`0x2C = MODE_RECORD_HDR`**,
   `0x2D = MODE_RECORD_MOTIONJPEG`, `0x21..0x24 = P/S/A/M`, `0x1d..0x20 = ADV_*`. Ровно этот набор
   значений D наблюдал в 294 сравнениях `[ctx+0x3978]` (максимум `0x2D`, кластеры `0x1D/0x20`,
   `0x21..0x24`, `0x2C/0x2D`). Если свойство `0x2B9` — это `MODE_RECORD` (enum режима съёмки),
   то код `0x2C` = **HDR**, а «многокадровый цикл», который D нашёл в `recfCalcRecifParam` при
   `0x2C`, — это как раз многокадровый HDR-композит. Уровень **[К]** (совпадение домена и семантики
   HDR/многокадровости), но прямой привязки «id 0x2B9 → резолвер MODE_RECORD» в коде нет.

## 7. Проверено и опровергнуто

* «`[0x244eb20]` — одиночный глобал» — **нет**, это база структуры `S` (memset 0x2940, vtable-указатели,
  сравнение с тенью `0x260da08`).
* «Писатель `[0x244eb20]`/`[0x244ebd4]` есть в блоке 1» — **не найден**: ни прямых `str`, ни через
  `add`-базу, ни через отрицательные смещения, ни через передачу в callee (6 независимых сканов,
  все модели/версии).
* «`S+0` — это `MODE_RECORD`/`MODE_CONTINUOUS`/`DRIVEMODE`» — **ни одна таблица не подтверждается
  однозначно**; сравнений `S+0` с константами `0x1d/0x20/0x21..0x24/0x2c/0x2d` в коде **нет**
  (`26_moderecord_hypo.py`, 0 совпадений), поэтому `S+0 ≠ MODE_RECORD` как минимум по способу
  использования.
* «`S+0` индексирует таблицу имён» — **нет** (0 совпадений, `35_table_index.py`).
* «Свойство `0x979` — это имя режима» — **нет**: это поле настроек `+0x5a0` с доменом {0,1,2,3};
  debug-метка `bPlayResize`.
* «`0x358` шлётся только при `S+0`∈{8,0xd..0x12}» — **нет**: шлётся практически всегда (при
  `0x2a02384()==0x55`), а эти значения выбирают ветку с предкомандой `0x19F`/`0x1A0`.
* «Таблица обработчиков `0x32439b0` используется напрямую» — в блоках 0/1/2 ссылок на неё нет
  (только косвенная диспетчеризация), поэтому вызывающий контекст обработчиков статически не
  восстановлен.

## 8. Что осталось (и где искать)

1. **Писатель `S+0`/`S+0xb4`**: искать в блоке 3 (Linux/оболочка) и в IPC-слое; либо по указателю
   `[obj+0x58]` (объект-владелец инициализируется в `0x1316a34`, b0) — найти код, который делает
   `ldr xN,[obj,#0x58]; str ...` (в блоках 0/1 такого нет).
2. **Имя `S+0`**: нужен внешний источник соответствия кодов (8, 0xd..0x12) — например, меню камеры
   или лог другой подсистемы; из трёх таблиц в `enums.txt` имя выбирается механически.
3. **Проверка гипотезы «`0x2B9` = MODE_RECORD»**: найти код UI, который выставляет `0x2B9` при
   повороте диска REC (значения `0x21..0x24`, `0x2c`), и сравнить с `MODE_RECORD`-константами.
