# Задача F (новая постановка): откуда берётся `[ctx+0x3978]` — поле `job+0x144` — и какие значения оно получает

Основная модель — **X-H2 5.33**; подтверждения для X-H2S 7.31 и X-T5 4.32 — по тексту.
Уровни: **[Д]** доказано (инструкции/цепочка), **[К]** сильный кандидат, **[Г]** гипотеза.

## 0-бис. Итог F3: прямые писатели `[ctx+0x3978]` — их всего 10, и ни один не пишет `0x2C`

Полный скан всех записей `[xN,#0x3978]` (скрипт `51_all_3978_writes.py`) даёт в X-H2 5.33
**3 записи в блоке 0 и 7 в блоке 1** — и ни одна не кладёт `0x2C`:

| блок | адрес | что пишется |
|---|---|---|
| b1 | `0x2e18340` / `0x2e1834c` / `0x2e18358` | `0x23` / `0x22` / `0x24` — по `[ctx+0x397c]` = {1, 2, 3}; иначе `0x21` (`csel`); функция `0x2e17f74`, обработчик параметра **`0x115f`** |
| b1 | `0x2e5c3f8`, `0x2e5c500` | `0x21`, если поле было 0 (дефолт), функции `0x2e5c210` / `0x2e5c4fc` |
| b1 | `0x2e96014` | ← `[src+0x7d0]` (still/RAW-путь, функция `0x2e957ac`) |
| b1 | `0x30871ac` | ← `job+0x144` (путь задания, функция `0x308680c`) — это ведёт воркер E |
| b0 | `0x14dd48c`, `0x14e04ac` | `0x21` (дефолт) |
| b0 | `0x13434d0` | `w3` (из стека, значение не установлено) |

**Ключевой вывод.** Значения `0x21…0x24` — это ровно `MODE_RECORD_PROGRAM/SHUTTER/APERTURE/MANUAL`
(`0x21=P, 0x22=S, 0x23=A, 0x24=M`, см. `enums.txt`), а обработчик `0x2e17f74` ставит их по
`[ctx+0x397c] ∈ {1,2,3}` (P/S/A/M-селектор). Значит `[ctx+0x3978]` живёт в пространстве имён
**MODE_RECORD**, и единственное значение этого enum, которое D видел в RECF как «особое»,
**`0x2C` = `MODE_RECORD_HDR`** → **`[ctx+0x3978] = 0x2C` в режиме HDR** (уровень **[К]**: прямого
`mov w0,#0x2c; str …, #0x3978` нет; `0x2C` может прийти только через одну из двух копий —
`src+0x7d0` still-пути или `job+0x144`, — и попадает туда из UI/команды).

Дополнительно (пункт 2 задания): `0x2e5c3f8` — **дефолт** (`0x21`, когда режим ещё 0), а не
кино/live view; `0x2e18340` — обработчик параметра `0x115f`, ставящий P/S/A/M по `[ctx+0x397c]`.
То есть «кино/live view» здесь нет: это режимы съёмки P/S/A/M.

Порядок (пункт 3): две копии пишут в **разные базы** — job-путь в `x22+0x1c94000+0x3978`, где
`x22=[job+0x140]` (`0x3086e20–0x3086e40`), still-путь — в статический буфер `0x3a54010`
(или `[obj+0x1068]`), который затем сравнивается `memcmp` (`0x2e9ab64`). RECF-код получает контекст
через `[x20]` (`0x2dda830`, `0x2ddfc74`), и численно свести его к одной из баз без runtime не удалось;
но обе ветки — копии, прямых записей «режима» в RECF-контекст в коде нет.

Про `src+0x7d0` (главная задача пункта 1): источник — большая структура still-параметров
(поля `+0x4cc`, `+0x780`, `+0x7d0`, `+0xa20…+0xa3c`, `+0x1344` и т.д.), которую заполняет
**диспетчер UI-команд** `0x1343b84` (b0): в case для `+0x7d0` значение берётся из payload команды
(`0x13454b0: memcpy(sp+0xf8, x21, w23); 0x13454c8: ldr w0,[sp,#0xfc]; 0x13454cc: str w0,[x19,#0x7d0]`).
То есть поле приходит извне (UI/ПК) и само по себе не вычисляется прошивкой; его домен задаётся
отправителем команды.

> **Важно.** Исходная посылка («свойство `0x2B9` — это режим съёмки, а `[ctx+0x3978]` — его копия»)
> **опровергнута**. Воркер E установил, что `settings+0x144`/`0x1144` — это октет маски сети
> (`ubNetmaskSettingManual1octet8`). Мои независимые данные это подтверждают (см. §1). Поэтому вся
> ветка `0x2B9` → событие `0x358` → отправители `0x2b47xxx` → глобалы `0x244eb20/0x244ebd4` к режиму
> `0x2C` **не относится**; её разбор вынесен в приложение (побочный результат).

## 1. Почему старая цепочка неверна (и моё подтверждение)

* Мой разбор ядра свойств (скрипт `27_prop_to_offset.py`) даёт: id свойства `0x2B9` → поле
  `settings+0x1144` (`12cd0ec: ldrb w19,[x0,#0x144]` после `add x0,x0,#1,lsl#12`). Попытка найти
  debug-имя этого поля (`28_field_names.py`) дала строку
  `"\t$BACKUP[%d]ubNetmaskSettingManual1octet8 %s(%d)->%s(%d)"` — я тогда отбросил её как
  «промах эвристики», но именно она совпадает с выводом воркера E: **`0x2B9` — октет маски сети**.
  Совпадало только смещение `+0x144` в разных структурах.
* Следствие: события `0x358`, отправители `0x2b47840/0x2b47bb8/0x2b47dd8/0x2b481ec` и глобалы
  `0x244eb20`/`0x244ebd4` — это отдельная подсистема (обновление/перечитывание сетевых и UI-настроек),
  к RECF-режиму отношения не имеет. Её разбор — в приложении (побочный результат).
* Реальная связь `[ctx+0x3978]` с заданием — ниже.

## 2. Реальная цепочка: `job+0x144` → `[ctx+0x3978]`

### 2.1 Копирование (X-H2 5.33)

Функция `0x308680c` (b1) — «копирование задания в RECF-контекст». Аргументы: `x0 = job`, `x1 = приёмник`.
Поля `job` читаются последовательно и пишутся в приёмник со смещением `+0x38xx`; наш участок:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

X-H2S 7.31 — идентичный порядок: `33a0734 ldr x1,[x19,#0x140]` → `[x0,#0x3974]`,
`33a073c ldr w1,[x19,#0x144]` → `33a0740 str w1,[x0,#0x3978]`.
X-T5 4.32: запись `str w?,[#,0x3978]` в этом виде не найдена (у T5 другая раскладка RECF-контекста),
но поле `job+0x144` у T5 существует и заполняется (§5).

### 2.2 Карта полей, которые RECF получает из задания (X-H2 5.33)

`job+0xd0…+0xf8` (u32/u16/u8) → `ctx+0x38e4…+0x3914`;
`job+0xf8…+0x100` (u8/u16) → `ctx+0x3914…+0x392c`;
`job+0x108…+0x134` (u32) → `ctx+0x393c…+0x3970`;
`job+0x140` (u64) → `ctx+0x3974` (нижние 32 бита);
`job+0x144` (u32) → **`ctx+0x3978`**.

То есть `[ctx+0x3978]` — это ровно одно u32-поле задания, а не свойство и не кэш настроек.

### 2.3 Что такое `job` и где он живёт

* Менеджер заданий: **`0x4daa6c0`** (RAM). Поля: `+0x18`/`+0x20` — указатели-объекты,
  `+0x28` — **указатель на активное задание** (`[0x4daa6e8]`), `+0x6c0` — состояние,
  `+0x6d8`/`+0x6e0` — колбэк и объект синхронизации.
* Загрузки `[0x4daa6e8]` в b1 (X-H2 5.33) — всего 4, все в менеджере `0x3017xxx`:
  `30172b0` → `0x3089ec8(job, …)`, `30172d0` → `0x30891f8(job, …)`, `301732c` → `0x308a1ec(job, …)`,
  `3017624` → `0x303750c(…, job, …)`. Через эти API задание и наполняется.
* «Сброс/публикация» задания: `0x30173c4` — `memset`(`0x1533ee0`) локального буфера `0x90`,
  `memcpy(job → тень 0x4bb5478, 0x190)` (`0x1533ebc`), `memcmp(job, тень, 0x190)` (`0x15e2ec0`),
  обнуление полей `+0x12c…+0x150` и событие `0x3097d70`. Т.е. задание имеет размер ≈ `0x190` и
  «теневая копия» для сравнения — приём, который D уже видел для структуры `0x244eb20`.

## 3. Кто и чем заполняет `job+0x144`

### 3.1 «Строитель задания» `0x2ff1ed8` (b1 X-H2 5.33)

`0x2ff1ed8(w0=slot/lens, w1=флаг, x2=params, x3, x4, x5=job)` — заполняет задание:

```
+0x118 = 0x15510fc(w22)              +0x11c = 0x30815fc(w22)
+0x120 = [x20+0x58]                  +0x124 = 0x154e444(w22)
+0x128 = 0x1553f60(w22)              +0x12c = [x20+0x154]
+0x130 = [x20+0x158]                 +0x134 = 0x155201c(w22)
+0x138 = 0x302dd78(w22,[x20+0x154])  +0x13c = 0x155448c(w22)
+0x140 = 0x1544c6c(w22)              +0x144 = 0x1552874(w22)   <== НАШЕ
+0x148 = 0x1554ff8(w22)              +0x14c = [x20+0x190]
+0x150 = [x20+0x3c]
```

(все `0x15xxxxx` — это адреса **блока 0**, т.е. вызовы через общий код.)

### 3.2 `0x1552874` → `ldrb [slotrec+0x26c]`

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*
* База записей — **`0x229a3a0`**, шаг **`0x2748`**, число записей 2 (индекс `[0x226f500]`, `0..1`;
  см. `0x155b95c`). Это слот-записи настроек (у каждой — свой набор аксессоров
  `0x155aa00…0x155ad00` с маской уведомления `0x15589b8`).
* Поле — **байт `+0x26c`**; сеттер — `0x155ac14` (`str w1,[x0,#0x26c]` + уведомление
  `0x15589b8(маска 0x1008000000000000)`).
* Вызовов сеттера всего 2: `0x14ed510` (копирование поле-в-поле между записями, «копия настроек»)
  и `0x1552914` (обёртка `0x15528c8`, вызываемая из `0x1557d14` — тоже копирование из другой записи).

### 3.3 Домен `slotrec+0x26c`

* Читатели байта и их сравнения (b1 X-H2 5.33, скрипт `46_read26c.py`):
  `0x2e4ee00` {0,1}, `0x2e4f8a0` {1}, `0x2e5136c` {0,1}, `0x2f0a438` {6}, `0x2f0ad64` {7},
  `0x2fb36ac` {1}, `0x3007bb0` {1}, `0x30ac9bc` {1}; в b0 — `0x14be344` {0}.
  Итого наблюдаемый домен — **{0, 1, 6, 7}**, т.е. малое перечисление.
* Писатели `+0x26c` (все сайты — `45`/`47`): в b1 их 27, среди них
  `0x2e4dde8` (DR/multi-frame-диспетчер: пишет `100` и `0`), `0x2e51024`
  (`Maker_MovieFrameTypes`: `100`), `0x2f08e1c`, `0x2e54040`, `0x2e95d24` и др.
  **Ни один писатель не кладёт `0x2C`** (константы в окрестности записей: 0, 1, 2, 100 и адреса/ид
  параметров вида `0x5da1`, `0x5b96`).
* `0x2C` (44) в качестве значения для `+0x26c` не встречается ни разу.

### 3.4 Вывод по значению `job+0x144`

`job+0x144` = байт из слота настроек, с наблюдаемым доменом `{0,1,6,7}`.
Значит:
* для «обычного кадра», ISO BKT и FILM SIM BKT это поле, скорее всего, остаётся в этом малом
  домене (0/1), т.к. оно не связано с типом брекетинга;
* `0x2C` через этот путь **не приходит** — [К], отрицательный результат.

## 4. Что означает `0x2C` в RECF (код остаётся, но сценарий не подтверждён)

В X-H2 5.33 (b1) `0x2e4dde8` — функция подготовки кадровых параметров — читает `[ctx+0x3978]`
(скопированное `job+0x144`) и ветвится:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Это ровно то поведение, которое описал D (`режим_0x2C.md`): при `0x2C` многокадровый путь
отключает чтение счётчика. **Но** если `job+0x144` принимает только 0/1/6/7, ветка `0x2C`
на практике не срабатывает — либо `0x2C` приходит из другого источника (другой набор полей
задания/другой контекст), либо это унаследованный код.

Проверено и опровергнуто (в этой части):
* «`[ctx+0x3978]` = свойство `0x2B9`» — **нет** (0x2B9 = маска сети, §1).
* «`job+0x144` = код режима съёмки (P/S/A/M/HDR/…)» — **не подтверждается**: производитель — байт
  слота настроек с доменом {0,1,6,7}; констант `0x1d..0x24/0x2c/0x2d` в писателях нет.
* «В ISO BKT / FSIM BKT `job+0x144` = 0x2C» — **нет данных**; тип брекетинга в этой цепочке не
  участвует.

## 5. Кросс-модельные отличия (важно для дальнейшего поиска)

| модель | копия в `ctx+0x3978` | производитель `job+0x144` |
|---|---|---|
| X-H2 5.33 | `0x30871a8`/`0x30871ac` (`ldr w1,[x19,#0x144]`) | `0x2ff1ed8` → `0x1552874` → `0x155ac0c` = `ldrb [0x229a3a0 + slot*0x2748 + 0x26c]` |
| X-H2S 7.31 | `0x33a073c`/`0x33a0740` (порядок полей тот же: `+0x12c→0x3968`, `+0x134→0x3970`, `+0x140→0x3974`, `+0x144→0x3978`) | в одном из строителей — **чтение аппаратного регистра**: `0x302b3d0 bl 0x5de38` с адресом `0xffd02144` → `str w0,[x19,#0x144]` (и `0xffd02140` → `+0x140`). Кроме того, в H2S есть отдельная функция `0x3177xxx`, которая пишет `ctx+0x3978` значениями **1/2/3** и из `[x20+0x14]` |
| X-T5 4.32 | отдельная копия в `0x3978` не найдена | `0x2fb399c` → `0x1542cac` → `0x1558338` = `ldr w0,[0x2222248 + slot*0x2778 + 0xdc]`; плюс варианты с чтением регистров (`0x5dd50`) |

Т.е. в X-H2 `job+0x144` — настройка из слота, в X-H2S — в одном из путей аппаратный регистр,
в X-T5 — поле слота `+0xdc`. Единая семантика по трём моделям не подтверждается, и это ещё один
аргумент, что `0x2C` — не «код режима съёмки», а служебное значение конкретного пути.

## 6. Что осталось (следующие шаги)

1. **Логический писатель `slotrec+0x26c`**: сеттер `0x155ac14` вызывается только из «копирования
   записей» (`0x14ed510`, `0x1557d14`). Нужно найти источник копии (вероятно, запись настроек
   `0x2624a88+slot*0x12768` или таблица дефолтов) и UI-команду, которая меняет это поле; там будет
   имя и полный домен значений.
2. **Брекетинг**: тип брекетинга (ISO BKT / FSIM BKT / AE BKT / …) искать не в `job+0x144`, а в
   других полях задания (`job+0x13c`, `+0x148`, `+0x14c`, `+0x150`, `+0x34…`) и в UI-таблицах
   `MODE_CONTINUOUS_*` (значения: `0=OFF,1=ON,2=PRE,3=FACE_BRACKET,4=CYCLE,5=AE_BRACKET,
   6=FSIM_BRACKET,7=DRANGE_BRACKET,8=BEFORE_AFTER,9=ISO_BRACKET,0xa=WB_BRACKET,0xb=FOCUS_BRACKET,
   0xc=PIXEL_SHIFT,0xd=MEGA`) — полная расшифровка в `enums.txt`.
3. **VM-проверка RECF**: подать в `[ctx+0x3978]` значения 0/1/6/7 и 0x2C и посмотреть, какая ветка
   `0x2e4dde8`/`recfCalcRecifParam` реально срабатывает при каждом — это отделит «код есть» от
   «сценарий есть».

## Приложение. Побочный результат: структура `0x244eb20`/`0x244ebd4` (к режиму `0x2C` не относится)

Полный разбор — в `отчёт_побочный_структура_0x244eb20.md`; кратко:

* `0x244eb20` — **база структуры `S`** размером `0x2940` (не одиночный глобал): `memset(S,0,0x2940)`
  в `0x2ba99d0` + установка 4 указателей в `+0x760…+0x778` и `+0x1c00…+0x1c18` (`0x2ba99dc…0x2ba9a10`);
  сравнение с тенью `0x260da08` (`0x15e2ec0`); указатель на `S` хранится в объекте `+0x58`
  (`0x1316a34`, блок 0).
* `[0x244eb20]` = `S+0` (u32, «режим»), `[0x244ebd4]` = `S+0xb4` (u32, «подрежим»); `S+0x2c` —
  строковый буфер (имя файла, к нему добавляется «.RAF»), `S+0x3e4` — счётчик.
* **Писателей `S+0/S+4/S+0x10/S+0xb0/S+0xb4` в блоках 0/1 нет** (6 независимых сканов: прямые
  `str`, `add`-цепочки, отрицательные смещения, `mov`-копии, передача в callee, блок 2) — только
  vtable-указатели и счётчик `+0x3e4`. Значения приходят извне разобранного кода.
* Кросс-модельно: X-H2 5.30 `0x2452b20/0x2452bd4`, X-H2S 7.31 `0x276eb88/0x276ec3c`,
  X-T5 4.32 `0x23bd360/0x23bd414` (разность `sub-mode` = `0xb4` во всех моделях).
* Обработчики `0x2b47840/0x2b47bb8/0x2b47dd8/0x2b481ec` шлют `0x358` (уведомление «перечитай»)
  практически всегда при `0x2a02384()==0x55`; `S+0` = 8 / `0xd..0x12` и `S+0xb4` = 2/0xb..0xe
  выбирают лишь предварительную команду `0x19F`/`0x1A0` (VM: `matrix_358.json`).
