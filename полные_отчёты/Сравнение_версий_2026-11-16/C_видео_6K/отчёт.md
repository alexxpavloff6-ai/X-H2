# Задача C. Видео 6.2K+ — почему зависание примерно через минуту

Отчёт по статическому анализу прошивок X-H2 5.30→5.33, X-H2S 7.30→7.31, X-T5 4.31→4.32.
Все выводы получены повторяемыми скриптами из этой папки (см. §10) и VM-контролем на Unicorn
(§8). Уровни доказательности: **доказано** / **сильный кандидат** / **гипотеза**.

Кратко:

* Найдена структура потока **ST** (pm_dec/DEC_STA) и её геометрия: кольцо **192 МиБ**
  (`0xC000000`) из трёх сегментов по **64 МиБ** (`0x4000000`) по адресам
  `0x3C999000`, `0x40999000`, `0x44999000`; указатель записи `ST+0x38`, остаток
  сегмента `ST+0x18`, смещение в сегменте `ST+0x30`, смещение в чанке `ST+0x2c`,
  размер чанка `ST+0x28`, указатель чанка `ST+0x20`.
* Кадр-чанк пишется в кольцо как **две «половины»** `[len1][payload1][len2][payload2]`
  (4-байтовые big-endian длины). Если чанк не влезает в остаток сегмента, prepare
  режет его: первая часть — в конец сегмента, вторая — в начало следующего.
* Исправленная `PMFRM_SetStartCodeSlice2forAdvance` читает 4-байтовое поле `len1`,
  которое при d=1..3 **разрезано границей сегмента**. Старая версия читала 4 байта
  подряд из слота записи (`state+0x62c`), т.е. подставляла мусор вместо байтов из
  второго сегмента → неверная длина → `FrameSizeError` и **запись start code
  `00 00 00 01` по неверному адресу**; при d=0/1 старый код уходил по «дикому»
  указателю (в VM — недопустимое чтение, в прошивке — чтение чужой памяти).
  Новая версия собирает поле из d байт слота и 4−d байт второго сегмента (d=1,2,3),
  а d=0 объявляет новой ошибкой `PreSizeError`. **Доказано в VM на всех трёх моделях.**
* Дополнительно в completion появился тег **поколения кадра**: запись потока выросла
  `0x20 → 0x28`, в запись добавлено поле `record+0x63c` (номер/поколение кадра),
  статус переехал `record+0x1c → record+0x20`, а completion сверяет тег с
  `ST+0x74` (ожидаемое поколение) — иначе не трогает запись.
* Гипотеза «зависание ≈ через минуту **пропорционально битрейту** из-за обёртки
  кольцевого буфера» в простой форме **не подтверждается**: 192 МиБ при битрейтах
  6.2K/8K заполняются за **0.8–8 с**, а не за минуту; вероятность случайного
  попадания в «окно» 1–3 байта на границе 64 МиБ ≈ `3/2^26` на чанк. Минутный
  масштаб должен иметь другой механизм (см. §6).
* Ветвления по разрешению рядом с патчем **нет** (проверено). Различие 4K/FHD
  объясняется не проверкой разрешения, а тем, что helper вообще вызывается только
  для «незавершённого» чанка (когда чанк не влез в сегмент) и только в режиме
  `mode != 3`; у 4K/FHD (ProRes/однослайсовые кадры) этот путь, судя по коду, либо
  не задействован, либо не попадает в разрез поля — это **сильный кандидат**, а не
  доказательство (§7).
* Других изменений логики в модуле, кроме трёх функций и нового диагностического
  сообщения H265, не найдено; остальные отличия блока 2 — перекомпоновка/сдвиг и
  чужие модули (пример: `playWlanB_*` со сдвигом полей структуры на +0x10).

## 1. Что именно исправлено: три функции и их адреса

Адреса — виртуальные адреса блока 2 (`base = 0`, т.е. адрес = смещение в блоке;
дамп `blocks/X-H2_5.30_b2_0xf40274.bin` и т.д.). Функция helper в обеих версиях
начинается по одному адресу, но её тело переписано; prepare и completion сдвинуты
вместе с последующим кодом.

| Функция | X-H2 old → new | X-H2S old → new | X-T5 old → new |
|---|---|---|---|
| `PMFRM_SetStartCodeSlice2forAdvance` (helper) | `0x8fda98` (тело 0x8fda98–0x8fdbdb, далее автомат 0x8fdbdc) → `0x8fda98` (тело 0x8fda98–0x8fdc93, автомат 0x8fdc94) | `0x8f0d30` → `0x8f0d30` | `0x8a2848` → `0x8a2848` |
| подготовка записей (prepare) | `0x8fdc20 → 0x8fdcd8` (+0xb8) | `0x8f0eb8 → 0x8f0f70` (+0xb8) | `0x8a29d0 → 0x8a2a88` (+0xb8) |
| завершение чтения (completion) | `0x8fdf68 → 0x8fe0d8` (+0x170) | `0x8f1200 → 0x8f1370` (+0x170) | `0x8a2d18 → 0x8a2e88` (+0x170) |
| код после completion | сдвиг +0x1b4 (проверено: 4096-байтное окно совпадает, кроме 9–12 слов — вызовы в переехавшие модули) | +0x1b4 | +0x1b4 |

Строки-якоря (новые сообщения, все три модели):

| Строка | X-H2 | X-H2S | X-T5 | Ссылка в коде (add) |
|---|---|---|---|---|
| `PMFRM_SetStartCodeSlice2forAdvance:PreSizeError` (новая) | `0x9cb018` | `0x9bdf70` | `0x96f058` | H2 `0x8fdb90`, H2S `0x8f0e28`, T5 `0x8a2940` |
| `PMFRM:PMFRM_SetStartCodeSlice2forAdvance:FrameSizeError` | `0x9cb048` (старая — `0x9cb018`) | `0x9bdfa0` | `0x96f088` | H2 `0x8fdc4c`, H2S `0x8f0ee4`, T5 `0x8a29fc` |
| `PMFRM_AfterDataReadForH265:FinFrameDataSizeError` (новая) | `0x9cb080` | `0x9bdfd8` | `0x96f0d8` | H2 `0x8fe47c`, H2S `0x8f1714`, T5 `0x8a322c` |

(`PMFRM_AfterDataReadForH265`) — именно он относится к 8K/6.2K HEVC.

## 2. Структура потока ST (pm_dec/DEC_STA) и геометрия кольца

Код обращается к глобальной структуре как `ADRP xN, <page>; ADD xN, xN, #base;
LDR/STR [xN, #field]`. `ST = page + base`; поля ниже даны относительно `ST`.

| Модель | page (64-бит) | base | ST |
|---|---|---|---|
| X-H2 | `0xFFFFFFFFFFFD3000` (−0x2d000) | `0x838` | `0xFFFFFFFFFFFD3838` |
| X-H2S | `0xFFFFFFFFFFFD2000` (−0x2e000) | `0xc58` | `0xFFFFFFFFFFFD2C58` |
| X-T5 | `0xFFFFFFFFFFFD3000` (−0x2d000) | `0x8d0` | `0xFFFFFFFFFFFD38D0` |

Поля ST (одинаковые смещения у всех трёх моделей — проверено `c2_state_map.py`):

| Поле | Смысл (по коду) | Кто пишет/читает |
|---|---|---|
| `ST+0x04` | число «незавершённых» записей (0/1/2) | prepare, completion |
| `ST+0x0c` | счётчик кадров (растёт по кадру) | prepare (`0x8fde08` и аналоги) |
| `ST+0x18` | остаток байт в текущем сегменте | init `0xC000000`, сброс `0x4000000` |
| `ST+0x20` | указатель данных кадра от сервиса `0x7af35000` | `0x8fd20c` (H2) |
| `ST+0x28` | размер чанка кадра (от сервиса) | `0x8fd20c` |
| `ST+0x2c` | сколько байт чанка уже скопировано | prepare/completion |
| `ST+0x30` | смещение записи внутри сегмента (для split) | prepare/completion |
| `ST+0x38` | указатель записи в кольце (абсолютный) | init и completion |
| `ST+0x54` | «группа кадров» (`ldrsb`) — период выравнивания счётчика кадров | prepare (`0x8fdcb8` old) |
| `ST+0x618` | выравнивание до 64 байт (padding) | prepare/completion |
| `ST+0x61c` | дополнительное смещение/выравнивание первого поля | prepare/completion |
| `ST+0x600/0x604/0x614` | индекс/режим таблицы кадров | `0x8fe5ec`-путь |
| `ST+0x60 …` | массив дескрипторов «патчей», шаг `0x18`, очищается `memset(…,0x5a0)` → **60 записей** | prepare (`0x8fdccc` old / `0x8fdd84` new) |
| `ST+0x620 …` | массив записей кадра: old шаг `0x20`, new шаг `0x28`; **две** записи (entry0/entry1) | prepare/completion |

Про «две записи»: функция-автомат (old `0x8fdbdc`, new `0x8fdc94`) сравнивает
запрошенный статус только с двумя полями — `ST+0x63c` (entry0+0x1c) и `ST+0x65c`
(entry1+0x1c); в новой версии это `ST+0x640` и `ST+0x668` (шаг 0x28). Значит
очередь кадров — двойная (double buffering), а массив дескрипторов `ST+0x60`
(60×0x18) — очередь отложенных «патчей» начала слайса.

Инициализация (X-H2 old; у H2S/T5 те же константы по другим адресам):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*
`0x8fd814`: при `0x8d6448()!=0` (режим 1/2) `ST+0x18 = 0x4000000` (64 МиБ) —
длина сегмента после первого «чтения».
Таблица указателей (`c4_buffer_refs.py`): `0x9cb060=0x3C999000`,
`0x9cb068=0x40999000`, `0x9cb070=0x44999000` (в new — `0x9cb0c8/0x9cb0d0/0x9cb0d8`).
Итого кольцо `0x3C999000 … 0x48999000` = **192 МиБ**, три сегмента по 64 МиБ.

Проверка указателя записи в completion (old `0x8fdf74–0x8fdfa8`, new
`0x8fe0e4–0x8fe118`): допустимы окна `[0x3C999000, +0x4000000)` и
`[0x40999000, +0x4000000)`; иначе логируется ошибка. Сброс кольца
(old `0x8fe1d8–0x8fe208`, new `0x8fe374–0x8fe3a4`): если
`ST+0x38 >= 0x44999000+0x4000000`, то `ST+0x38 = 0x3C999000`.

**Вывод (доказано):** буфер — 192 МиБ, сегменты по 64 МиБ; «фрагмент» в
исправленном helper — это остаток сегмента, а не фиксированный маленький блок;
число записей очереди кадров — 2, дескрипторов патчей — 60.

## 3. Данные кадра: две «половины» и поле длины

Функция `0x8d694c` (H2) разбирает чанк: `v=BE32(ptr)`; успех, если `v+4 == size`
(одна половина) **или** `v==1` (уже start code); иначе читает следующее поле по
`ptr+4+v` и требует `v + 8 + v2 == size`. Т.е. чанк устроен как
`[len1][payload1][len2][payload2]`, big-endian длины (это же видно из
`0x8fda98` и из `PreSizeError`-проверки). Start code в потоке — `00 00 00 01`
(пишется байтами `0,0,0,1` в old `0x8fdb84–0x8fdbd4`, new `0x8fdc08–0x8fdc90`).

## 4. Разрез кадра на два фрагмента (wrap) — где именно

prepare (old `0x8fdc20`, new `0x8fdcd8`) для каждого кадра от сервиса
(`0x8fd20c`: `ST+0x20`=ptr, `ST+0x28`=размер) считает:

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*
В ветке разреза (`old 0x8fde38`, `new 0x8fdf4c`) код:
`ST+0x30 += остаток; ST+0x2c += остаток; ST+0x18 = 0` — фиксирует, что чанк
продолжится в следующем сегменте, и заводит дескриптор патча. Первое поле
длины (`len1`) при этом может оказаться **разрезанным**: если чанк начинается
в последних 1–3 байтах сегмента, то d = `ST+0x2c` ∈ {1,2,3} байт `len1` лежат
в старом сегменте, остальные — в новом. Именно этот случай и правит патч.

Признак «поле разрезано» в prepare: `old 0x8fdd18: cmp w0,#3` (если
`ST+0x2c <= 3` — заводится дескриптор с числом байт в первом фрагменте;
`new 0x8fde60: cmp w0,#3`).

## 5. Что именно изменилось в helper (old vs new)

Старая версия (X-H2 `0x8fda98`):

*(листинг инструкций не публикуется — это фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Новая версия (`0x8fda98`) добавляет диспетчер по d = `w3` (сколько байт `len1`
доступно в первом фрагменте) **до** чтения поля:

```
8fdab4: cmp w3,#3 ; b.ls 0x8fdb0c
  w3>3: чтение 4 байт из [x0] (поле целиком в сегменте 1)
  w3==3: 0x8fdb44: [x0],[x0+1],[x0+2] + [x2][0]        (3+1)
  w3==2: 0x8fdb68: [x0],[x0+1]       + [x2][0],[x2][1] (2+2)
  w3==1: 0x8fdb20: [x0]              + [x2][0..2]      (1+3)
  w3==0: 0x8fdb8c → bl 0x8bb6ac (0x9cb018 PreSizeError), затем пересборка от x2+4
8fdadc-8fdae8: w4'=v+4; если w4'=total — выход без патча;
                если d <= w4' — второе поле в сегменте 2: x2+(v+4-d) (0x8fdba4)
                иначе — в сегменте 1: x1+(v+4) (0x8fdaf0), обход с границей d
8fdbf8-8fdc04: проверка len2+4+len1+4 == total
8fdc48: при несовпадении — строка 0x9cb048 FrameSizeError
8fdc58-8fdc90: запись 00 00 00 01 (0,0,0,1) по 4 указателям
```

Ключевое: `x0` — это **4-байтовый слот сохранённой длины** (`state+0x62c`,
куда ранее скопированы байты из буфера), `x1` — начало чанка в сегменте 1,
`x2` — начало следующего сегмента. Старый код при d=1..3 читал из слота все
4 байта, хотя валидны только d из них; новые байты нужно брать из `x2`.

## 6. Как старая ошибка приводила к зависанию

Доказанное в VM (см. §8):

1. **Неверное значение `len1`** → проверка `len2+4+len1+4 == total` не проходит →
   логируется `FrameSizeError`.
2. **Патч пишется по неверному адресу.** Адрес второго поля вычисляется из
   неверного `len1`: `x2 + (len1+4-d)`; в VM при d=2 мусор `0xAAAA` дал запись
   `00 00 00 01` по адресу `x2+0xAAAC` (вместо `x2+0x102`) — т.е. **порча
   посторонних данных в буфере**; нужное поле осталось непропатченным.
3. При d=0/1 в VM старый код уходил по «дикому» указателю (`x1+(len1+4)` /
   `x2+(len1+4-d)`), возникало **недопустимое чтение** (`UC_ERR_READ_UNMAPPED`).
   В прошивке это либо чтение случайной памяти, либо data abort — зависит от
   карты, но в любом случае поведение неопределённое.
4. Потребитель потока (декодер/писатель) ждёт кадр, у которого **нет start code**
   на границе слайса и в который записан мусор → кадр не декодируется/не
   отправляется; в самом модуле pm_dec **нет блокирующего ожидания** (в трёх
   функциях нет циклов ожидания события/семафора) — встаёт внешний потребитель.
   Это **сильный кандидат** на механизм зависания (прямого `while` в модуле нет).

Дополнительно патч добавляет **тег поколения кадра** (`record+0x63c` ← счётчик
кадров в prepare; completion сверяет с `ST+0x74`). Без этой проверки старая
версия могла применять «патч» к записи, которая уже относится к другому
поколению/другому буферу, — то есть портить/освобождать буфер, который ещё
читается. Это второй **сильный кандидат** на причину «залипания» чтения:
потребитель не получает завершения, потому что буфер уже «свободен»/переписан.

## 7. Гипотеза «зависание ≈ 1 минута зависит от битрейта»

Проверка арифметикой (сегмент 64 МиБ = 536.9 Мбит; кольцо 192 МиБ = 1610 Мбит):

| Битрейт | 64 МиБ сегмент | 192 МиБ кольцо |
|---|---|---|
| 2.0 Гбит/с (6.2K ProRes HQ) | 0.27 с | 0.81 с |
| 1.5 Гбит/с (6.2K ProRes 422) | 0.36 с | 1.07 с |
| 400 Мбит/с (8K HEVC) | 1.34 с | 4.0 с |
| 200 Мбит/с (6.2K HEVC) | 2.68 с | 8.1 с |
| 100 Мбит/с (4K HEVC) | 5.37 с | 16.1 с |
| 8.9 Мбит/с | 60 с | 180 с |

**Вывод: в простой форме гипотеза не подтверждается.** При любом реальном
битрейте 6.2K/8K кольцо оборачивается за секунды, а не за минуту; чтобы
получить минуту на сегмент, нужен битрейт ≈ 8.9 Мбит/с, что для 6.2K
нереально. Кроме того, «опасное окно» — это 1–3 байта из 64 МиБ: при
равномерном распределении начала чанка вероятность `≈ 3/2^26 ≈ 4.5·10⁻⁸` на
чанк, т.е. при 30 к/с — раз в ~10⁷ секунд. Случайная модель не даёт ни минуты,
ни секунд.

Значит, наблюдаемая минута — это **не** первый обход кольца. Проверенные
варианты, которые остаются (гипотезы, требуют рантайм-данных):

* **детерминированная фаза**: кадры/слайсы выровнены по 64 байта, сегмент —
  кратен 64, поэтому фаза «попадания» фиксирована на (кодек, разрешение,
  размер кадра). Тогда попадание либо в первом же сегменте, либо никогда;
  «через минуту» может означать смену фазы при смене размера кадра (VBR) —
  надо поймать лог `FrameSizeError` по времени;
* **период поколений/GOP**: completion сверяет `ST+0x74` с тегом записи; при
  каждом несовпадении запись не трогается, а очередь всего из 2 записей —
  исчерпание очереди даёт остановку через ~2 периода поколений (30–60 с —
  правдоподобно, но не доказано);
* **файловый сегмент** (разрез файла/индекса): для 6.2K HEVC 200 Мбит/с 4 ГиБ —
  ~172 с, для 8K ~86 с; для 6.2K ProRes 2 Гбит/с 4 ГиБ — ~17 с. Ни один из
  вариантов не даёт ровно минуту без знания реального битрейта.

**Что проверено и опровергнуто:** (а) версия «первая обёртка кольца
пропорциональна битрейту» — опровергнута арифметикой; (б) версия «есть проверка
разрешения рядом с патчем» — опровергнута (см. §7.1); (в) версия «старый код
испорчен и при d>=4» — опровергнута VM (контрольный сценарий old/plain
корректен).

### 7.1 Почему 4K/FHD не страдают

Проверено `c8_key_addrs.py`/`c2_state_map.py`: рядом с helper/prepare/completion
**нет ни одного сравнения с шириной/высотой кадра** и нет ветвления по
разрешению. Есть только:

* ветвление по режиму: `0x8d6128()` возвращает `[−0x24000+0x85c] == 3`;
  при `mode != 3` работает completion `0x8fdf68` и буфер `0x3C999000`
  (`0x8fe540: cbz w0 → completion`); при `mode == 3` — другой обработчик
  (`0x8fd564`) и другой буфер `0x100001000` (`0x8fd09c–0x8fd0a8`);
* ветвление по числу байт до границы (d) и по кодекам (ProRes-поток
  `MOV_IF_Prores_SendStreamReadComp` и новая диагностика `…ForH265`).

Поэтому различие 4K/FHD vs 6.2K/8K — не «проверка разрешения», а геометрия:
helper вызывается только когда чанк не влез в сегмент (незавершённая запись),
и опасен только разрез поля `len1` (d=1..3). У 4K/FHD (меньше кадр, ProRes/
однослайсовая упаковка, другой режим) этот путь либо не активируется, либо
поле не попадает в разрез. Уровень: **гипотеза/сильный кандидат**; прямой
проверки в прошивке нет.

## 8. VM-контроли (Unicorn, реальные инструкции из блоков)

Скрипт `c6_vm_helper.py`: эмулируется сама функция helper из old/new блока 2
всех трёх моделей; память — слот `state+0x62c`, «сегмент 1» (0x10000000),
«сегмент 2» (0x10002000); логгер `bl` перехватывается. Сценарий: чанк
`total=0x1234`, `len1=0x100`, `len2=0x112C`; при d=2 слот содержит 2 валидных
байта `len1` и 2 байта мусора `0xAA`, остальные 2 байта — в начале сегмента 2;
второе поле — по адресу `сегмент2 + (len1+4-d) = x2+0x102`.

| Модель | вариант | сценарий | fault | лог | поле пропатчено | мусор тронут |
|---|---|---|---|---|---|---|
| X-H2 | old | d=2 | нет | `…:FrameSizeError` | **нет** | **да** (`x2+0xAAAC`) |
| X-H2 | old | d=3 | нет | `…:FrameSizeError` | нет | нет |
| X-H2 | old | d=1 | **UC_ERR_READ_UNMAPPED** | — | нет | — |
| X-H2 | old | d=0 | **UC_ERR_READ_UNMAPPED** | — | нет | — |
| X-H2 | old | plain (d=total) | нет | — | да | — |
| X-H2 | new | d=2 | нет | — | **да** | нет |
| X-H2 | new | d=1 | нет | — | да | нет |
| X-H2 | new | d=3 | нет | — | да | нет |
| X-H2 | new | d=0 | нет | `PreSizeError` + `FrameSizeError` | нет (невалидный случай) | нет |
| X-H2 | new | plain | нет | — | да | — |
| X-H2S | old/new | все | **то же самое** (old: ошибка/дикий указатель; new: d=1,2,3 корректно) | | | |
| X-T5 | old/new | все | **то же самое** | | | |

Сырые результаты: `c6_vm_results.json`. Контрольные точки (отрицательный
контроль): сценарий `plain` проходит и в old, и в new без ошибок — значит
различие old/new действительно только в разрезанном поле.

## 9. Другие изменения в модуле (old/new, нормализация сдвига)

Скрипты: `c5_module_diff.py` (нормализация PC-относительных полей: BL/B,
b.cond, cbz/cbnz, tbz/tbnz, adr/adrp, ldr literal, а также ADD сразу после
ADRP — иначе перекомпоновка чужих модулей даёт тысячи ложных «различий»),
`c7_module_check.py` (проверка по участкам с известным сдвигом),
`c8_key_addrs.py` (точные адреса строк/инициализации).

Результат:

* Логика изменена **только** в трёх функциях (§1). Проверены два окна кода
  модуля (скрипт `c5_module_diff.py`, нормализация PC-относительных полей):
  * **до helper** (X-H2 `0x8f9c00–0x8fda98`): 4006 слов, 119 расхождений — все
    до одного являются обращениями к **другой** структуре, сдвинутой на `+0x10`
    (`0x420→0x430`, `0xe98→0xea8`, `0x380→0x390`, `0x388→0x398`); у X-H2S
    `0x8f0000–0x8f0d30` — 15 расхождений того же типа (`0x118→0x128`,
    `0xda0→0xdb0`), у X-T5 `0x8a1000–0x8a2848` — 47 (`0xab0→0xac0`,
    `0xdd8→0xde8`). Поля самой ST не сдвинулись.
  * **после completion** (X-H2 `0x8ff000–0x900000`, сдвиг `0x1b4`): 1024 слова,
    12 расхождений — это немедленные смещения на код/данные модуля
    (`add x1,x1,#0xe08 → #0xfbc`, ровно `+0x1b4`) и на соседнюю структуру
    (`0xb88→0xb98`), т.е. релокация, а не логика. У X-H2S — 33 на 1360 слов,
    у X-T5 — 40 на 1664 слова.
* Вызовы в **другие** модули переехали (пример: `bl 0xfffffffffc451534 →
  0xfffffffffc44c564`) и при сравнении не учитываются (нормализация).
* В completion добавлена проверка H265: при `ST+0x2c > 0` после завершения
  чтения логируется `PMFRM_AfterDataReadForH265:FinFrameDataSizeError`
  (new `0x8fe3dc–0x8fe3e4`, ссылка `0x8fe47c`).
* В блоке 2 есть **чужие** изменения, к pm_dec не относящиеся: например,
  функции `playWlanB_*` (`0x8eff74`) со сдвигом полей своей структуры на
  `+0x10` (`0x988→0x998`, `0x420→0x430`); в окрестностях ST-кода также
  встречается сдвиг `0xe98→0xea8` у другой структуры (не ST: поля ST
  `0x618/0x61c/0x638/0x63c/0x640` не сдвинулись). Это отдельная правка
  (или перекомпоновка) — в рамках задачи C на выводы не влияет, но
  заслуживает отдельного разбора.
* Таблица строк модуля перестроена (вставлены две новые строки, §1) —
  поэтому все адреса строк сдвинулись; это не логика.

## 11. Уровни доказательности (сводка)

**Доказано (код + VM):**
1. Поле `len1` читается через границу сегмента; old читает 4 байта слота
   (мусор при d=1..3) → неверная длина → `FrameSizeError`, запись start code
   по неверному адресу (VM: порча `x2+0xAAAC`), при d=0/1 — дикий указатель;
   new собирает 1+3/2+2/3+1 из двух сегментов и корректно патчит поле;
   d=0 → `PreSizeError`.
2. Геометрия: кольцо 192 МиБ, сегменты 64 МиБ, базы
   `0x3C999000/0x40999000/0x44999000`, `ST+0x38`/`ST+0x18`, init `0xC000000`
   и сброс `0x4000000`, сброс кольца по `0x48999000`.
3. Очередь: 2 записи кадра (шаг `0x20→0x28`), 60 дескрипторов `0x18`;
   статус `record+0x1c → record+0x20`, добавлен `record+0x1c` — тег поколения,
   и `ST+0x74` — ожидаемое поколение.
4. В модуле нет блокирующего ожидания в трёх функциях; зависание — у внешнего
   потребителя.
5. Других изменений логики в pm_dec нет (кроме нового сообщения H265).

**Сильный кандидат:**
6. Зависание = следствие испорченного/непропатченного start code (декодер не
   получает кадр) и/или раннего освобождения буфера без проверки поколения.
7. Различие 4K/FHD vs 6.2K+ — геометрия чанков/слайсов и режим `mode==3`, а не
   проверка разрешения.

**Гипотеза (не подтверждена статикой):**
8. «≈1 минута» — период поколений/GOP или файлового сегмента; версия
   «обёртка кольца пропорционально битрейту» арифметически опровергнута.

## 12. Ограничения

* Данные кадров (размеры чанков, `ST+0x44/0x54`, `ST+0x74`) приходят из
  другого модуля/сервиса (`0x7af35000`, `[x+0x18]→0xf58/0xf70`), в блоках
  DAT их значений нет — реальные размеры кадров 6.2K/8K и реальный битрейт
  статически не получить.
* Поэтому минута не выведена из кода; для её объяснения нужен рантайм-лог
  (модуль пишет `FrameSizeError`/`PreSizeError` через строковый логгер
  `0x8bb6ac` — это видно в UART/журнале) с временными метками и размером
  кадра, либо трассировка `ST+0x38/0x18/0x2c` по кадрам.
* VM-контроль ограничен helper'ом; prepare/completion не эмулировались
  целиком (нужны заглушки внешних сервисов 0x7af35000, 0x97d148 и т.п.).
