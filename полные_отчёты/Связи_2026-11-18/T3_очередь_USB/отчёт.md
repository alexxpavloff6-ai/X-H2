# T3. Маршрут USB-записи свойства до общего сеттера

## Главные выводы

1. `0x2BDFBCC` — синхронный диспетчер кодов событий, а не приёмник сообщения из очереди ThreadX. Его ветвь `0x1F` читает идентификатор и значение по `0x26B7998/0x26B799C`, вызывает `0x2C88E98`, затем `0x2BBCB18()`.
2. PTP-путь записи свойства найден отдельно от события `0x1F`: код свойства читается по `0x26C0DF4`, а диспетчер `0x2C13E4C` направляет `D195`, `D18E` и `D199` в разные обработчики.
3. Для `D195` обработчик `0x2C0B970` читает 16-разрядное значение из текущего PTP-буфера через `0x1320800`, проверяет и преобразует его для внутреннего `id=0x108`, затем формирует событие `0xF8` через `0x2BDFBA4` и `0x12E863C`.
4. Таблица преобразования для `id=0x108` допускает PTP-значения `1..5` и переводит их в набор внутренних значений `0..4` (в порядке `1→4`, `2→3`, `3→1`, `4→2`, `5→0`); `6` отсутствует и попадает в ветвь ошибки `0x80000080`.
5. `D199` направляется в обработчик внутреннего `id=0x5F5`; его таблица не содержит PTP-значения `0`, поэтому проверка также завершается внутренней ошибкой `0x80000080`. `D18E` использует таблицу разрешённых строк: учитываются флаг строки и значение запроса; при отсутствии совпадения передаётся та же ошибка.
6. Обёртка `0x2BDFBA4` задаёт аргументы `0x12E863C` как событие `0xF8`, идентификатор, преобразованное значение, `0xF001`, `0`. Шина записывает идентификатор и значение в `0x26B7984/0x26B7988`; функция `0x2A49BC0` копирует сообщение в область предыдущего сообщения, читает текущие поля и вызывает общий сеттер.
7. Наблюдённый PTP-ответ `0x201C` для трёх отказов согласуется с найденными ветвями проверки, но перевод внутреннего кода `0x80000080` именно в ответ `0x201C` в этом проходе не прослежен.
8. Инструкция `add #0x10, lsl #12` прибавляет `0x10000`: база `0x26A70A8` становится `0x26B70A8`, а поля `0x2BDFBCC` находятся по `0x26B7998/0x26B799C`. Копия длиной `0x14` из `0x26B7980` в `0x26B7994` переносит эти слова в область предыдущего сообщения.
9. Преобразование чтения `GetDevicePropValue` для зерна 6/7 и размера слота в этом проходе не найдено. Эмуляцию Unicorn не запускал: путь записи и таблицы проверки удалось восстановить статически.

## Повторная проверка адреса и копирования

В поправке координатора верно пересчитан адрес: `add x?,x?,#0x10,lsl #12` прибавляет `0x10 × 0x1000 = 0x10000`. По фактическому дизассемблированию `0x2BDFC64–0x2BDFC74` база равна `0x26A7000 + 0xA8 + 0x10000 = 0x26B70A8`; загрузки по `+0x8F0/+0x8F4` дают `0x26B7998/0x26B799C`. Выражение `0x26A70A8 + 0x10000 + 0x8F0` также равно `0x26B7998`.

В то же время обнаружено копирование отдельной структуры в соседней области `0x26B7000`:

| Вызов memcpy | Назначение | Источник | Длина | Что следует дальше |
|---|---:|---:|---:|---|
| `0x2A4A694` из функции `0x2A4A678` | `0x26B7994` | `0x26B7980` | `0x14` | `0x2BDFBCC(1)`, затем возврат |
| `0x2A49BDC` из функции `0x2A49BC0` | `0x26B7994` | `0x26B7980` | `0x14` | общий сеттер получает идентификатор/значение из `0x26B7984/0x26B7988` |
| `0x2A4E9F0` из функции `0x2A4E9D0` | `0x26B7994` | `0x26B7980` | `0x14` | общий сеттер получает идентификатор/значение из `0x26B7984/0x26B7988` |

В копии длиной `0x14` поля `0x26B7998/0x26B799C` являются третьим и четвёртым словами структуры назначения (`0x26B7994 + 4/+8`). Именно их читает ветвь `0x1F` функции `0x2BDFBCC`. Функции `0x2A49BC0` и `0x2A4E9D0` берут для общего сеттера текущий идентификатор/значение из `0x26B7984/0x26B7988` (`+0x8DC/+0x8E0`) — второе и третье слова шины `0x12E863C`.

В блоке 1 найдено 1179 прямых вызовов `0x12E863C`; в диапазонах `0x2A40000–0x2A60000` и `0x2BD0000–0x2C00000` — 54 и 12. Единственный прямой вызов с непосредственно заданным событием `0x1F` — `0x2BA9B14`: `w1` загружается из `0x26A700AC`, `w2=w3=w4=0`; этот короткий путь не читает PTP-буфер. Он не является найденным отправителем записи свойства. Обработчики PTP приходят к той же шине через обёртку `0x2BDFBA4`, задающую событие `0xF8`.

## Схема, подтверждённая кодом

```text
PTP-код свойства читается из [0x26C0DF4]
  → 0x2C13E4C выбирает обработчик по таблице 0x33A2CAC
  → D195: 0x2C0B970; D18E: 0x2C0BD78; D199: 0x2C0B9F0
  → значение PTP читается из текущего буфера через 0x1320800
  → проверка/перевод через 0x1135944 и 0x1135930 (для D18E — отдельная таблица)
  → 0x2BDFBA4(id, value) формирует событие 0xF8
  → 0x12E863C(0xF8, id, value, 0xF001, 0)
  → слова записываются в 0x26B7980..0x26B7990 и передаются в 0x133CACC
  → 0x2A49BC0 копирует сообщение 0x26B7980 → 0x26B7994, читает текущие поля 0x26B7984/0x26B7988 и вызывает 0x2C88E98
```

Диспетчер `0x2C13E4C` загружает код текущего PTP-свойства по адресу `0x26A7000 + 0xA8 + 0x18000 + 0x1D4C = 0x26C0DF4` (промежуточная база `0x26BF0A8`). Индексы таблицы ветвлений для D195, D18E и D199 равны соответственно `0x194`, `0x18D` и `0x198`; они ведут к указанным обработчикам. Функция `0x1320800` читает два байта из буфера, на который указывает поле `0x25D99E0`.

Для D195 ветка таблицы ведёт в `0x2C0B970`, где значение из буфера передаётся как `id=0x108` в `0x2C0B844`. Общая таблица `0x1BD5AB8 + 8·id` сопоставляет входное значение с внутренним номером строки. Для `id=0x108` входы `1,2,3,4,5` дают строки `4,3,1,2,0`; вход `6` не найден. При успешной проверке значение преобразуется `0x1135930` и обёртка передаёт его в `0x2BDFBA4`.

Путь D199 ведёт в обработчик `0x2C0B9F0` с внутренним `id=0x5F5`; вход `0` отсутствует в столбце таблицы, по которому выполняется проверка. D18E направляется в `0x2C0BD78`, который перебирает строки таблицы `0x18BBCF0`, проверяя признак строки по `+0x14` и входное значение по `+0x18`. При отсутствии подходящей строки обработчик передаёт `0x80000080` в `0x2C05748`.

Ветка `0x1F` функции `0x2BDFBCC` — синхронный маршрут чтения предыдущего сообщения: она читает `0x26B7998/0x26B799C`, то есть третье и четвёртое слова копии в `0x26B7994`. PTP-обработчики передают событие `0xF8` через ту же шину сообщений. Верхний диспетчер, связывающий эту цепочку с кодом операции `0x1016`, и регистрацию перехода от `0x133CACC` к `0x2A49BC0` в этом проходе отдельно не восстановил.

### Связанные вызовы и условия

В `0x2A4BD04` выполняется проверка и разветвление:

- `0x2BDF9C4(1,0x8031)` — предварительная проверка;
- сравнение текущего свойства `0x26C0DF4` с D18D и D263;
- при совпадении вызывается `0x2BDFBCC(0x5F)`, затем `0x2BDFBCC(2)`;
- иначе, если поле `0x26C0E60` равно нулю, записывается `0x43` по адресу `0x3BF47B8` и вызывается `0x2BDFBCC(0x1F)`;
- если поле ненулевое, вызывается событие `2`.

В соседней функции `0x2A4BDA8` выполняются `0x2BDF9C4(0x1F,0x8031)`, затем события `0x5F` и `2`. Они также не записывают `+0x8F0/+0x8F4` непосредственно.

Функция `0x12E863C` записывает пять слов «событие, идентификатор, значение, аргумент 3, аргумент 4» по адресам `0x26B7980…0x26B7990` и при выполнении условий передаёт их в `0x133CACC`. PTP-обёртка `0x2BDFBA4` вызывает её с событием `0xF8`, идентификатором и преобразованным значением. Потребитель `0x2A49BC0` копирует структуру в `0x26B7994`, читает из исходной шины поля `0x26B7984/0x26B7988` и вызывает общий сеттер; ветвь `0x1F` в `0x2BDFBCC` обращается к копии.

## Три наблюдённых отказа `0x201C`

| Запрос | Проверка в найденном пути | Внутренний результат |
|---|---|---|
| D195 = 6 | обработчик `0x2C0B970`, `id=0x108`; значение отсутствует среди допустимых входов таблицы | `0x2C0B844` вызывает `0x2C05748(0x80000080)` |
| D18E, размер слота с RAW | `0x2C0BD78` ищет совпадение среди разрешённых строк таблицы `0x18BBCF0` | если активной совпадающей строки нет, вызывает `0x2C05748(0x80000080)` |
| D199 = 0, WB слота | обработчик `0x2C0B9F0`, `id=0x5F5`; вход `0` отсутствует в проверяемом столбце таблицы | `0x2C0B844` вызывает `0x2C05748(0x80000080)` |

Все три пути сходятся на внутреннем коде `0x80000080`, что объясняет общий характер отказа на уровне проверки/обработки значения. Связь этого внутреннего кода с наблюдённым ответом PTP `0x201C` через последующий обработчик ответа пока не прослежена. Для D18E таблица явно учитывает флаг допустимости строки, однако какая именно строка соответствует наблюдённому размеру RAW-слота, отдельно не установлено.

## GetDevicePropValue

Предыдущий анализ установил модель чтения зерна по паре `GRAIN`/`GRAIN_SIZE` и соответствие USB-кодов 6/7 случаю `GRAIN=2`; размер слота связан с `PIXEL`/`ASPECT`. Обработчик GetDevicePropValue, который собирает эти значения в USB-коды, здесь не найден; адреса сборки и возврата ответа остаются неизвестными.

## План дальнейшей проверки в Unicorn

Для маршрута записи эмуляция не требуется: ветви выбора свойства, чтение буфера, таблицы допустимых значений и отправка события `0xF8` восстановлены статически. Если понадобится подтвердить конечный ответ `0x201C`, в Unicorn следует запускать найденный PTP-обработчик с отображёнными таблицами и текущим указателем `0x25D99E0`, а перехватывать `0x2C05748` и путь формирования ответа. Для GetDevicePropValue сначала нужно найти его отдельный обработчик и источник значений.

## Уровни достоверности

- **Д** — дизассемблирование блоков 0 и 1: диспетчер `0x2C13E4C`, переходы таблицы для D195/D18E/D199, чтение PTP-буфера, таблицы преобразования, вызов `0x2BDFBA4` и запись шины `0x12E863C`; отдельно проверены поля ветви `0x1F` в `0x2BDFBCC`.
- **К** — связь отправки сообщения функцией `0x12E863C` с потребителем `0x2A49BC0`: адреса источника и копии совпадают с читаемыми полями, но регистрация перехода через `0x133CACC` не восстановлена.
- **Г** — точное соответствие внутреннего отказа `0x80000080` ответу PTP `0x201C`, причина недопуска конкретного RAW-размера и маршрут GetDevicePropValue.

## Что это даёт для будущих доработок прошивки

Для записи свойства найдено преобразование PTP-значения, проверка допустимости и передача внутренних идентификатора/значения через сообщение `0xF8`; ветвь события `0x1F` читает предыдущую копию сообщения. Перед будущими изменениями следует отдельно проверить точное отображение внутреннего отказа `0x80000080` в ответ `0x201C`, затем восстановить маршрут GetDevicePropValue и его сборку кодов 6/7.
