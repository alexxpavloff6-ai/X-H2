# X-H2 5.30: путь параметров AF от настроек до кода

## Главные выводы

1. В блоке 1 видны ветви, которые принимают изменения и сохраняют их, а также общий геттер `0x2C93FD4`. Для большинства перечисленных параметров после геттера найдено чтение для ответа/отображения, но не доказанный вход алгоритма автофокуса.
2. Ветка распознавания объектов `0x2C89528` переводит выбор QMENU в `DETECT_SUBJECT (0x620)`, обновляет статусы `0x624/0x625` и при значениях, кроме внутреннего `6`, записывает `0` в `FACEDETECT (0x618)`. Это явная связь настроек в коде (Д).
3. `FACEDETECT (0x618)` и `DETECT_SUBJECT (0x620)` дополнительно читаются в `0x2BD5114` и переносятся в производные поля `0xACD/0xADF`; это синхронизация состояния, не поиск лиц/объектов (Д).
4. Чтения `0x618`, `0x61C`, `0x5BE` и `0x622` в `0x2BF...` относятся к выдаче/сериализации значения: после геттера идёт перевод через `0x1135930` и запись в буфер ответа. Их нельзя считать доказательством потребления алгоритмом AF (Д).
5. Для AF-C Set виден путь выбора до трёх обработчиков `0x12F0BD4/0x12F0C6C/0x12F0D04`: они записывают переданные значения в три глобальных поля последнего состояния и при условиях вызывают форматирование уведомления. Прямой записи этих обработчиков в API записи или доказанного вызова алгоритма AF нет (Д для записей/вызовов; К для назначения полей как состояния уведомления).
6. Значения `TARGET_CHASE/SPEED/PRIORITY` кодируются раздельно по шести наборам; D233 упаковывает три выбранных параметра в одну строку. В `0x2BF8784` значения последнего набора (`0x715/0x71C/0x723`) и в `0x2BF8848` два значения (`0x716/0x71D`) переводятся и собираются в строковый буфер. Это подтверждает сериализацию; единая структура входа алгоритма AF не обнаружена.
7. Перевод целевых параметров проходит через общую функцию `0x1135930` с таблицей конкретного id. В видимых сериализаторах есть перевод id и упаковка байтов, но нет отдельного умножения/масштаба для этих параметров. Точные таблицы значений и их физический смысл из этих функций не выводятся.
8. Имена `UI_AUTO_FOCUS_AF_C`, `UI_REC_AUTO_FOCUS_PRE_AF`, `UI_FOCUS_AF_AREA_SELECT`, `UI_PERFORMANCE_AF_SPEED_UP`, `UI_TARGET_*` и `TSK_TRACKING` найдены в строковых таблицах. Это подсказки для терминологии; имя задачи `TSK_TRACKING` не связано доказанной ссылкой с найденными читателями. Метки `PDAF/CDAF` в проверенных строках не обнаружены.
9. Для LCD-флага отдельно известен путь через запись `0x4C` к сервисному модулю, но связь этого пакета с настройками AF не показана. Для параметров AF в блоках 0–2 не найден доказанный переход через `0x14CF124`, геттер записи `0x14CF354` или службу вызовов; последующее использование алгоритмом автофокуса остаётся границей (Г).

## Объём и способ

Читались задание T2, общий контекст, отчёт S2, его `результат.json`, итоги рецепта/съёмки, блоки X-H2 5.30 и строковые каталоги. Кодовые адреса ниже – адреса времени исполнения из `fwcommon.py`; блок 1 загружен через `load('X-H2','old',1)`, блок 0 – индекс 0. Камера не использовалась. Посторонние файлы не менялись.

Для точных прямых вызовов `BL 0x2C93FD4` искались идентификаторы, переданные в `w0`; отдельно проверялись ветви центрального сеттера, прямые вызовы `0x11335EC`/`0x1135930` и пути `TARGET_*`. Отсутствие читателя ниже означает «не найден в проверенных статических ссылках», а не доказательство отсутствия всех косвенных/динамических потребителей.

Обозначения: **Д** – непосредственно видно в коде/таблице; **К** – сильное толкование по потоку вызовов и именам; **Г** – гипотеза или неразобранная граница.

### Сборка параметров AF-C

В `0x2C90F24–0x2C91048` находится часть ветви центрального сеттера для тройки D233. Она выделяет младший байт, байт 1 и байт 2 из упакованного значения, затем пишет три отдельных внутренних id через `0x2C88E98`: `0x715`, `0x71C`, `0x723` в соответствующем пути. Вызовы вокруг ветвей соседних индексов аналогично работают с `0x716/0x71D` и другими элементами семейств.

Для выбранного AF-C Set `0x2C90F9C` сохраняет `0x70D`, вызывает три обёртки чтения семейства (`0x1338C70`, `0x1338C9C`, `0x1338CC8`), а затем обновляющие функции. Внутри каждой обёртки виден запрос контекстного id через `0x1139F50/64/78` и перевод соответствующего `TARGET_*` через `0x1135930`. В ветвях смены отдельных значений вызываются парные помощники `0x1338CF4/0x1338D08/0x1338D1C` и `0x12F0BD4/0x12F0C6C/0x12F0D04`.

Отдельно от применения, `0x2BF8784` преобразует три поля выбранного отображаемого набора в символы для строки, затем вызывает `0x2BF6704`, который кладёт строку в ответный буфер. `0x2BF8848` формирует таблицу/строку для значений `0x716` и `0x71D`. Точные коэффициенты/таблицы, которыми контекстный индекс выбирает набор, полностью не разобраны; видимый перевод – общая таблица на внутренний id, отдельного численного масштаба в этих путях нет.

**Вывод:** кандидат на единый объект в функции, который передаёт три параметра непосредственно алгоритму AF, в проверенном коде не найден. Доказана обработка отдельных свойств и сборка строки ответа, а также запуск внутренних обновляющих функций при смене набора. Конкретный смысл этих обновлений требует продолжения анализа адресов `0x12F0BD4/0x12F0C6C/0x12F0D04` и вызываемых ими модулей.

## Подсистемы и границы блоков

- В блоке 1 есть подписи меню `UI_MENUCOM_ITEM_FACEDETECT_AND_EYEAF`, `UI_MENUCOM_ITEM_DETECT_SUBJECT`, `UI_MENUCOM_ITEM_FOCUS`, `UI_MENUCOM_ITEM_AFCCUS`, а также `UI_TARGET_CHASE/SPEED/PRIORITY` и `UI_TARGET_*_LV*`. Они подтверждают словарь меню и параметров.
- Строки `UI_AUTO_FOCUS_AF_C`, `UI_REC_AUTO_FOCUS_PRE_AF`, `UI_FOCUS_AF_AREA_SELECT`, `UI_PERFORMANCE_AF_SPEED_UP` в блоках 0/1 обозначают предполагаемые узлы интерфейса/настроек. Это не таблица задач и не имена функций для установленных кодовых адресов.
- `TSK_TRACKING` встречается в словаре строк блока 0; найденная ссылка `0x118A0D0` ведёт в цепочку таблицы строк/переходов, а не даёт доказанной связи с AF-потребителями. Отдельные имена PDAF/CDAF в проверенных строках не найдены. Поэтому называю подтверждённые узлы интерфейсом настроек и обновляющими обработчиками AF-C; конкретная задача ThreadX автофокуса неизвестна.
- Основные читатели/обработчики расположены в блоках 0 и 1, которые связаны внутренними вызовами. Для целевых параметров нет установленного пути через mailbox/RPC к companion M4. Из предыдущего разбора сервисного модуля известен общий случай RPC за пределами установленной базы кода, но перенос AF-параметров через него не найден. Код M4 и фактическое поведение автофокуса не подтверждены этим разбором.

## Проверка гипотезы о канале AF через оценщик и записи

### Условные таблицы

Цепочка для LCD-флага подтверждается как `0x2FE35D4 → 0x30256EC → 0x30308A0 → 0x2F84C48 → 0x2F85F3C → 0x3456B20`. `0x30256EC` передаёт шесть скалярных значений от помощников чтения полей режима; сама таблица индексируется категорией выдержки и типом затвора. В таблице `0x3456B20` 246 ячеек (`41 × 6`, по 4 байта), значения только `0/1/2`. Идентификаторов `0x8C0`, `0x6FB`, `0x618`, `0x61C`, `0x620`, `0x70D`, `0x710–0x723`, `0x1E2`, `0x5BA–0x5BE` в ней нет; таблица содержит результаты условий, а не список чтений параметров (**Д**).

У соседней таблицы `0x3456EF8` 41 ячейка со значениями только `0/1`; к ней обращается помощник `0x2F85F70`. Это соседний вариант проверки: `0x2F84C14` выбирает его, когда второй вход равен `1`, а `0x2FE5FB8` также вызывает `0x2F85F70` после чтения категории из `0x154CF6C`. В собственно цепочке `0x30308A0 → 0x2F84C48` используется `0x2F85F3C` и таблица `0x3456B20`, а не `0x3456EF8`. В обеих таблицах нет значений-идентификаторов настроек; прямых чтений перечисленных идентификаторов AF в коде этих двух помощников также не видно (**Д**).

### Проверка API записи и чтения

В вызове `0x14CF124` первый аргумент — номер записи, второй — её описание. Для записи `0x4C` в блоке 1 учтено 86 прямых вызовов; полный вызов `0x311B788` из построителя `0x311B6B8` передаёт номер `0x4C` и пакет размером `0x158`. Именно в этот пакет построитель параметров `0x2FE38E4` переносит результат LCD-оценщика по смещению `+0x64`. Это доказывает путь LCD-флага через сервисную запись, но не путь параметров AF (**Д** для записи и смещения; **Г** для связи с AF).

Сопоставление функций, которые читают перечисленные идентификаторов AF или вызывают AF-C-обработчики, с прямыми вызовами API не выявило общей функции. Обработчики `0x12F0BD4/0x12F0C6C/0x12F0D04`, обёртки чтения `0x1338C70/0x1338C9C/0x1338CC8` и известные читатели идентификаторов AF не вызывают `0x14CF124` или `0x14CF354` (**Д**, в пределах прямых вызовов и найденных ссылок).

Адреса получения записи в исходной гипотезе требуют поправки. `0x14C6384` в блоке 0 — безусловный переход `B 0x14C62B4`, а не вход функции чтения записи; прямых вызовов `BL 0x14C6384` в блоках 0–2 нет. `0x14C648C` — инструкция `mov w4, #0x18` внутри функции, а ближайший вызов там — `BL 0x14C5774` по адресу `0x14C64A0`, не диспетчер `0x4A458`. Подтверждённое чтение записи `0x4C` находится в `0x31053F8`: `mov w0, #0x4C; BL 0x14CF354`. Сам `0x14CF354` обращается к резолверу `0x5460C`. Проверенный общий RPC-обёртка `0x14CF45C` вызывает диспетчер `0x4A458` по адресу `0x14CF4C8`; по разбору Q3 этот диспетчер расположен в загрузчике сервисного модуля, а не в блоке 2. Обработчик сервиса записи остаётся за границей имеющихся блоков (**Д** для адресов и вызовов; **Г** для конечного потребителя).

### Что фактически делают три обработчика AF-C

| Обработчик | Значение на входе | Запись в пределах функции | Дополнительный путь |
|---|---|---|---|
| `0x12F0BD4` | Значение от `0x1338C70` для семейства `TARGET_CHASE` | Читает прежнее значение и записывает новое в `0x2680474` | При смене значения и разрешающих флагах отображает старое/новое значения через `0x11469B4` и передаёт сообщение форматировщику `0x133CACC` (**Д** для вызовов; **К** для назначения `TARGET_CHASE`) |
| `0x12F0C6C` | Значение от `0x1338C9C` для `TARGET_SPEED` | Читает прежнее и записывает новое в `0x2680478` | Аналогичное сообщение через преобразователь `0x1146A28` и формат `0x18C1318` (**Д**/**К**) |
| `0x12F0D04` | Значение от `0x1338CC8` для `TARGET_PRIORITY` | Читает прежнее и записывает новое в `0x268047C` | Аналогичное сообщение через преобразователь `0x1146A74` и формат `0x18C1338` (**Д**/**К**) |

Во всех трёх функциях есть одинаковые проверки флагов и сравнение с прежним значением; во всех ветвях новое значение в итоге записывается в соответствующее поле. Прямые ссылки на `0x2680474/0x2680478/0x268047C` в блоке 0 ведут только к чтению и записи внутри соответствующего обработчика. Поэтому эти поля выглядят как локальная память о последнем уведомлённом значении, а не подтверждённый вход алгоритма слежения (**К**).

`0x133CACC` разбирает формат и значения аргументов, затем передаёт строку в `0x133C73C`. Последняя функция проверяет разрешение вывода, синхронизирует доступ и добавляет текст в общий кольцевой буфер сообщений. В этих ветках нет вызова `0x14CF124`, `0x14CF354` или `0x4A458`; значит прослеженный выход обработчиков — уведомление/журналирование, не найденный канал доставки в механизм автофокуса (**Д** для последовательности вызовов и записи строки; **К** для назначения буфера как журнала).

### Итоговая граница

- LCD-флаг: контекст съёмки → оценщик и таблица → пакет записи `0x4C` → сервисный модуль. Код записи/конечного потребителя находится за разобранной границей; маршрут подтверждён только для LCD-флага.
- Параметры AF-C: выбранные `TARGET_*` → чтение активного значения обёрткой `0x1338...` → запись значения в одно из полей `0x2680474/478/47C` и возможное сообщение в кольцевой журнал. От этих полей до потребителя автофокуса связь не найдена.
- Для остальных настроек AF из списка таблицы условий и найденные вызовы API не подтверждают такой же маршрут. Это не исключает, что часть данных находится в непрозрачном пакете сервисной записи или передаётся косвенно; конкретное поле и получатель не установлены (**Г**).

## Что это даёт для будущих доработок прошивки

1. Для изменения только того, что камера отдаёт по USB, следует отличать сериализаторы `0x2BF...` от обработчиков поведения. Изменение этих сериализаторов поменяет ответное представление, но не доказанно изменит работу AF.
2. Для изменения взаимного исключения распознавания лиц и объектов проверяемая точка – ветвь `0x2C89528`; следует сохранять проверки статусов `0x624/0x625` и видеорежима.
3. Для AF-C Set точки записи выбора и семейства находятся в `0x2C90F9C` и ветвях D233; обёртки `0x1338C70/9C/CC8` читают выбранные `TARGET_*`. Три обработчика `0x12F...` только обновляют последние значения и журналируют изменения; их потребитель автофокуса пока не установлен.
4. Перед выводами о PDAF/CDAF, задаче AF или M4 нужно найти код потребителя за локальными полями `0x2680474/478/47C`; для записи `0x4C` следующий рубеж — разобрать сервисный модуль вне блоков 0–2. Имеющихся строк и названий меню для этих выводов недостаточно.
