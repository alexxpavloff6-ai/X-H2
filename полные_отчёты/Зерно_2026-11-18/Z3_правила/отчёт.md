# Сочетания настроек рецепта в X-H2 5.30

## Краткие выводы

1. В 5.30 есть крупный обработчик проверки состояния свойств от `0x2C9B038`; его ветви обращаются к идентификаторам `UI_SETP_*` и возвращают разные состояния. Это подтверждает проверку доступности/применимости на уровне прошивки, хотя не каждая ветвь однозначно именована по назначению. **Д/К.**
2. Для монохромной тонировки есть прямая связь с выбранной имитацией плёнки: `BLACK_TONE` (`0x6A2`) читает `FILM_SIM` (`0x68E`), а `BLACK_TONE_MOVIE` (`0x6A3`) – `FILM_SIM_MOVIE` (`0x691`). После преобразования значений проверяются диапазоны, согласующиеся с чёрно-белыми режимами; сепия в эти диапазоны не входит. **Д** для связи и сравнений; **К** для семантической расшифровки диапазонов.
3. Ветка `BLACK_TONE_RG` (`0x6A4`) содержит дополнительные условия по режиму/контексту съёмки, включая сравнения с `0xD031`, `0xD274` и `0x80AD`. Их точный смысл без таблицы символов не установлен. **Д** для сравнений; **Г** для предметного толкования.
4. В исследованном оценщике не найдено однозначной проверки «WB Kelvin разрешён только при WB=Kelvin», а также прямых правил для `Color`, `DRANGE` и тонов через `DRANGE_P`. Это не доказывает отсутствия таких правил в других ветвях или подсистемах.
5. Для сборки параметров проявки `0x2C93FD4` читает объект по адресу `0x22A3000` (поля `0x22A3564…0x22A35C0`) и применяет преобразования значений. В частности, значение, возвращаемое как параметр `0x929`, при поле `0x22A3568 == 0x641` или `0xFFFFFFFF` подменяется на `0x64`; соседние поля `0x22A3568` и `0x22A356C` также участвуют в вычислении параметра `0x92B`. **Д** для операций; **К** для отождествления этих полей с Dynamic Range / Dynamic Range Priority.
6. В обработчике RAW-параметров `0x93F` получается преобразованием поля `0x22A359C`, а `0x940` – поля `0x22A35A0`. Это кандидаты на значения рядом с флагом «WB как снято» и режимом WB, но код сам по себе не доказывает, что `0x93F` – именно позиция 10 D185. **Д** для чтения/преобразования; **К** для смыслового соответствия.
7. В `fujicli` позиция 10 профиля названа `white_balance_as_shot`; при WB «как снято» она превращается в `0x01`, при любом другом WB – в `0x02`. Это правило инструмента формирования профиля, а не доказательство, что камера сама переключает WB по такой же формуле.
8. Камеру не использовал. Работал только с блоками прошивки, таблицей карты банка и локальными исходниками `fujicli`.

## Сверка с правилами fujicli

| Правило fujicli | Результат проверки по прошивке 5.30 |
|---|---|
| Монохромные температура/тон только при чёрно-белых имитациях | Для `BLACK_TONE`/`BLACK_TONE_MOVIE` найдены связки с `FILM_SIM`/`FILM_SIM_MOVIE` и тесты диапазонов. Явную идентификацию отдельного поля монохромной температуры здесь не нашёл. |
| WB temperature только при WB=Temperature | Отдельные состояния `WB` и `WB_KELVIN` присутствуют; прямой совместный тест в найденной ветви не установлен. |
| Color не действует для ч/б и сепии | В просмотренных фрагментах связи `UI_SETP_COLOR` с `FILM_SIM` не установлено. |
| DR и тона доступны только при DR Priority=Off | Есть вычисление RAW-значений по двум соседним полям, вероятно DR и priority; прямого общего условия доступности DR/Highlight/Shadow по `DRANGE_P` не установлено. |
| Размер изображения не применяется к RAW | В просмотренных адресах прямого условия для пары Image Size / Image Quality не найдено. |
| Auto DR сохраняет значение DR кадра | В getter есть специальное преобразование поля `0x22A3568 == -1` в `0x64` для параметра `0x929`. Это согласуется с «не отправлять Auto как отдельный DR», но семантическая связь остаётся кандидатом. |

## Дополнительные проверки прошивки, не отражённые в правилах fujicli

В ветках `BLACK_TONE_RG` видны проверки рабочего режима/контекста (`0xD031`, `0xD274`, `0x80AD`) и дополнительные проверки выбора. `fujicli` описывает смысловые ограничения по имитации плёнки, но не эти контекстные состояния меню. По одним константам нельзя утверждать, что они являются дополнительным правилом самого рецепта: это может быть состояние UI, режим передачи или условие доступности свойства.

## Ограничения вывода

- `0x2C9B038` и `0x2C93FD4` — адреса функций, установленные по таблицам переходов, прямым вызовам и инструкциям ARM64 в распакованном блоке 1 версии 5.30.
- Точные имена некоторых внутренних параметров не содержатся в коде; связь с названиями `fujicli` отмечена уровнем К, если она выведена по соседству/порядку полей.
- Уровень Д означает доказанную операцию или ветвление машинного кода, а не подтверждённую камеру экспериментом. Эксперименты на камере не выполнялись.

## Что это даёт для будущих доработок прошивки

Для чёрно-белой тонировки уже видна точка проверки и две разные ветви для фото и видео; при изменении набора имитаций плёнки можно проверять именно значения после `0x1135930`, а не коды USB напрямую. Для DR и WB известны кандидатные поля общего объекта и места нормализации, но до вмешательства в код нужно установить соответствие полей `0x22A3568…0x22A35C0` позициям D185 и значениям таблицы `0x1BD5AB8 + 8·id`. Правила `fujicli` следует воспринимать как ограничения построения/проверки профиля; они сами по себе не доказывают, что камера отвергает запись свойства.
