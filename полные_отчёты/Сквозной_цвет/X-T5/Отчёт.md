# X-T5 4.31: Classic Chrome и «Цвет» от кодов к заданию обработчику

## Что именно доказано

Использован `Firmware на прочиеFuji/FWUP0030.DAT`, SHA-256 `790d6deecf26766188b0e506e40645e6b816addfeba39a52334349405421724e`. Исходный DAT только читался; скрипт сравнивает хеш при начале и после эксперимента. Камера не подключалась. Оригинальные инструкции ARM64 выполнялись в Unicorn; адреса — **модельная** карта распакованных FFLZ, не доказанное фактическое расположение на камере. Исходный встроенный шаблон из DAT `0xc0274`, длина `0xc6c00`, размещён по модельному `0x27008000`, указатель записан в `0x2066d90`. Это не индивидуальные настройки устройства.

Главный результат: найдены и исполнены собственные узлы X-T5, в том числе **непрерывная последовательность вызовов конвертера и настоящего сохранителя MODE**. Остальная модель соединяет реальные фрагменты с явным ручным переносом значений; это не непрерывная трасса от физической кнопки к кадру. Важное различие моделей: аналог интересующего поля X-H2 `+0x39b8` в X-T5 находится по **`+0x3a00`**. Механическое применение старого смещения неверно.

## Имитация: код → состояние → кадр → параметры

* В собственном словаре записи `UI_SETP_FILM_SIM=1699` и `UI_FILM_SIM_CLASSIC_CHROME=14`; адреса записей и строк приведены в JSON. Таблица указателей `0x1bb1a30` по ID 1699 указывает на исходную таблицу `0x1759c70`, запись 14 в ней содержит представление 3 со значением 13.
* По адресу `0x132a978` сравниваются слова `0x2003300` и `0x2001080`. При значениях `(14,0)` исходная ветвь переходит на `0x132ae38`; непрерывно исполняются `mov w3,3; mov w2,0; mov w0,1699`, затем BL `0x1135948` → конвертер `0x12e48b0` и BL **сохранитель** `0x12ed180`. При нулевых синтетических глобальных флагах итог `0x25bcccc=13`, флаг ошибки `0x20007ec=0`; остановка до следующей инструкции `0x132ae4c`. Равенство `(14,14)` до границы `0x132a990` оставляет заранее заданное значение состояния нетронутым. Имена и происхождение сравниваемых глобальных слов не установлены.
* Для каждого опыта отдельно участок `0x132ae38..0x132ae4c` действительно выполняет оба вызова для UI-кодов 0, 14, 18, 17 и сохраняет соответственно 0, 13, 18, 22. Это не доказательство, что данный фрагмент вызывается физическим действием пользователя.
* Значение состояния **вручную** передаётся исследовательской программой в исходный сеттер `0x1559350`: `str w1,[x0,#0xc0]`. Затем непрерывный участок `0x2d955e8..0x2d955f8` вызывает исходный getter `0x1559348`, функцию `0x14ec8ac` (в этой сборке `ret`) и записывает полученное слово в `params+0x3a00`. Фрагмент вызван с `x21=frame`, `x20=params`. Для Classic Chrome оба поля равны 13.
* Статически обнаружен вызывающий сеттер код `0x2ef90b4` → `0x154a658` → `0x1559350`, где аргумент задаётся через промежуточную подготовку `0x2f54574`. **Связь сохранителя MODE с этой подготовкой не доказана**. Прямого выполнения от состояния до формирования кадра нет.
* Исполненный участок `0x2d2ede4..0x2d2edec` копирует `params+0x3a00` в промежуточное `+0x20`; `0x2e75160..0x2e7516c` читает его и вызывает `0x2e73f2c`, формируя `context+0x130`. Для Classic Chrome там 8. Соседний участок построителя и последующие вычисления здесь выполнялись отдельно с заранее заданным контекстом, а не как один полный вызов построителя.

## «Цвет»: словарь, исходная таблица, исполняемые преобразования

В словаре `UI_SETP_STILLCOLOR=1742`, а девять записей `UI_STILLCOLOR_*` имеют коды 0…8. Указатель на таблицу ID 1742 ведёт к `0x176eb80`: каждая запись содержит четыре 32-битных представления; десятая — терминатор из `0xffff`. Исходный конвертер `0x12e48b0` выполнен для каждого кода со входным представлением 0 и выходными представлениями 3 и 4, с очисткой и проверкой флага ошибки. В представлении 3 возвращаются 0…8; знаковое представление 4 даёт +40…−40 с шагом 10. Условное соответствие делениям −4…+4 получено делением последнего значения на 10, как в прежнем исследовании шкалы; **фактический текст экрана и доступность девяти позиций этой камеры независимо не наблюдались**.

После конвертации код вручную помещён в синтетическую входную запись `+0x50`. Оригинальные `0x2d9e76c..0x2d9e774` копируют его в `params+0x39fc`; `0x2d2edb0..0x2d2edb8` — в промежуточное `+0x0c`. Участок `0x2e751c8..0x2e751dc` вызывает `0x2e743b8` и записывает индекс `context+0x13c`. В использованном контексте `context+0x12c=1`, `context+0x100=0`, функция возвращает 8−код. ## Селектор, расчёт и виртуальная передача

В синтетическом контексте дополнительно заданы `+0x124=18`, `+0x128=18`, `+0x10c=8`, `+0x17c=2`, остальные обнулены, кроме перечисленных выше полей. Селектор `0x2e5f410` для Classic Chrome возвращает 6. Исходный сборщик `0x2e57910..0x2e57928` вызывает расчёт `0x2e5f7dc` и формирует четыре коэффициента; упаковщик `0x2e57f0c` и передатчик `0x2e57f38` затем выполняются с маской `0x80`. Все выходы передаются через общую синтетическую RAM. Упаковка сохраняет верхние биты выходных 16-битных полей; в данных опытах они изначально нулевые.

Например, Цвет 0: упакованные половинки `[885,8182,859,8180]`; виртуальные 32-битные записи `0xff96c634=0x1ff60375`, `0xff96c638=0x1ff4035b`. Цвет +2: `0x1ff403ce`, `0x1ff203b2`; Цвет −4: `0x1ff802c1`, `0x1ff602ac`. При нулевой маске запись этой пары отсутствует. В JSON сохранены адрес, размер, PC инструкции записи и все 36 опытов. Адреса MMIO отображены на искусственную память — это не запись в аппаратный регистр и не проверка вычисления пикселей.

Контроли с той же шкалой и нейтральным окружением, при Цвет 0:

| Имитация | UI → MODE → цветовой код | Селектор | Четыре коэффициента |
|---|---|---:|---|
| STANDARD | 0 → 0 → 0 | 1 | 1141, −12, 1520, 78 |
| CLASSIC CHROME | 14 → 13 → 8 | 6 | 885, −10, 859, −12 |
| ETERNA | 18 → 18 → 9 | 7 | 887, 49, 893, 101 |
| REALA | 17 → 22 → 13 | 16 | 1074, −21, 1471, 141 |

На каждом из четырёх режимов выполнены все девять значений. Эти числа описывают лишь конкретный шаблон и входы, не готовый JPEG и не все режимы камеры.

## Воспроизведение и границы

Из корня проекта: `python "Анализ_прошивки/Сквозной_цвет/X-T5/исследовать.py"`. Скрипт использует локальные Unicorn/Capstone и общие существующие декодер DAT и извлекатель словаря; создаёт `результаты.json` и `фрагменты.asm` исключительно в этом каталоге. Каждый вызов контролирует конечный PC; во всех опытах исходные инструкции не патчатся. Файл JSON содержит сырьевые строки обеих таблиц, словари с адресами, хеши распаковок, входы и результаты. Вторая репрезентация столбцов таблиц не интерпретируется без доказательств.

Не доказаны реальное нажатие и вывод экрана, происхождение сравниваемых UI-глобалов, автоматический мост MODE-состояние → кадр, происхождение исходной записи цвета, полная цепочка вызовов и все необходимые ветви построителя, доступность имитаций в меню, реальное обращение к устройству, калибровка конкретной камеры и конечный визуальный результат. Исполненные отдельные участки нельзя выдавать за одну непрерывную аппаратную трассу.
