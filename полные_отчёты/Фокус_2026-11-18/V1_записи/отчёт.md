# V1: назначение пяти активных записей хранилища X-H2 5.30

## Краткие выводы

1. Записи `0x88`, `0x4F`, `0x8B`, `0x03` и `0x02` – не сплошные байтовые журналы одного назначения: отправители строят пакеты с кодом события, типом, длиной и указателем на данные. Это видно по полям, которые передаются в `0x14CF124` (Д).
2. Размер элемента при регистрации: `0x88` – `0x48`, `0x4F` – `0x38`, `0x8B` – `0x48`, `0x03` – `0x50`, `0x02` – `0x1D0` байт. У всех регистраций по 48 элементов; предел полезных данных меньше размера элемента на служебные 8 байт (Д по регистрационным дескрипторам и коду API).
3. `0x88` регистрируется в потоке `lenscom` (`0x13E6420`, строковая метка в конфигурации), который публикует 112 уведомлений. Это сильная улика связи с обменом с объективом, но конкретные параметры автофокуса в пакетах пока не названы (Д/К).
4. `0x8B` регистрируется в потоке с меткой `biscom` (`0x13FCAB0`); найдено 51 публикация. Значение сокращения и роль потока по доступным строкам не восстановлены (Д для метки, К для назначения).
5. `0x4F` имеет 88 публикаций и читающий цикл `0x15669E0`. Читатель выбирает сообщения через `0x14CF354`, передаёт их обработчикам и разводит по кодам. Функция чтения подтверждена, но названия конечных обработчиков и смысл событий пока не установлены (Д/К).
6. `0x03` обслуживается задачей с меткой `reccont`: её инициализатор `0x2D5A998` создаёт чтение через `0x14CE004`, а цикл `0x2D67134` получает записи `0x03` через `0x14CF354`. В пакетах есть пустые уведомления и короткие структуры с полями из входных данных (Д).
7. `0x02` зарегистрирован функцией `0x2E89120` и имеет 28 отправителей в блоке 1, однако прямого читающего вызова не найдено. Связь со съёмочным трактом остаётся кандидатом, конечный получатель не установлен (К).
8. В этих пяти потоках не удалось доказать перенос конкретных настроек `UI_SETP_FOCUS_MODE` (`0x8C0`), `UI_SETP_FOCUS` (`0x6FB`), экспозиции, фактического затвора, серийной съёмки или верхнего дисплея. Имена/номера событий сами по себе этого не доказывают.

Уровни: **Д** – вывод прямо следует из кода или строковых меток; **К** – сильное, но неполное толкование; **Г** – гипотеза.

## Разбор по записям

### `0x88` – поток `lenscom`

Инициализатор `0x13E6420` в блоке 0 вызывается из последовательности `0x14E2634`. Он регистрирует 48 элементов размером `0x48`, затем запускает поток с текстовой меткой `lenscom` (строка по адресу `0x19123C8`) и обработчиком в области `0x13EB4DC`. Данные в каждом сообщении доступны в пределах `0x40` байт.

Публикации используют общую форму: `u16` код, байт состояния из `0x14CE514`, байт типа `0x88`, длина, указатель на содержимое. Пример `0x13E683C` публикует код `0x18DE`, размер `0x38`; часть данных берётся из `[x19]`, `[x19+4]`, `[x19+8]`, некоторые биты упаковываются в заголовок. Другие кодировщики вызывают `0x14D2704`, затем дополняют пакет полями аргументов и константами. Это единая оболочка формата, но наборы данных собирают разные функции.

Статических вызовов чтения или подписки по ID `0x88` не найдено. Метка указывает на объективную связь, однако граница проходит до конкретного получателя и его алгоритма. В частности, по этим публикациям нельзя назвать поле AF-C или утверждать, что передаются выдержка, экспозиция, серия либо дисплей.

### `0x4F` – отдельная очередь событий

Функция `0x1576AA8` регистрирует 48 элементов по `0x38` байт. Она вызывается из кода запуска около `0x157FFEC`; название потока по этому коду не установлено. В блоке 0 найдено 88 вызовов публикации. Короткие отправители создают пакет, где `x0` – код события, `0x14CE514` даёт байт состояния, в поле типа записывается `0x4F`, затем задаются длина и адрес данных. Например, `0x156E95C` передаёт одно 32-битное значение с кодом `0x1726`.

Читатель `0x15669E0` получает ID `0x4F` через `0x14CF354` с индексом `-1`, затем подаёт сообщение в маршрутизаторы и обработчики. Кодовые ветви проверяют категории, вычисленные из диапазонов сообщений. Это доказывает очередь событий и диспетчеризацию, но не предметную роль каждого события. Никаких подписчиков `0x14CF45C` для `0x4F` каталог не показывает.

### `0x8B` – поток `biscom`

Функция `0x13FCAB0` регистрирует запись и запускает поток с меткой `biscom` (строка по адресу `0x196B138`); найденные публикации используют тип `0x8B`. Оболочка сообщений похожа на `0x88`, но коды другие (`0x19AF–0x19DF`), а размеры данных в рассмотренных примерах достигают `0x38` байт. В примере `0x13FCB7C` два входных значения копируются в 16-байтовую область данных. Другие функции кодируют поля структур через `0x14D2704` и битовые вставки.

Прямых читателей/подписчиков по постоянному ID не найдено. Строка `biscom` – единственная установленная текстовая подсказка; расширять её расшифровку или называть конечное устройство без подтверждения нельзя.

### `0x03` – обработчик `reccont`

Инициализатор `0x2D5A998` регистрирует 48 элементов по `0x50`, затем настраивает обработчик `0x2D67134` с меткой `reccont` (строка по адресу `0x33C4B10`). Для публикаций встречается стандартная оболочка API: код события, байт состояния, тип `3`, длина и адрес данных. Так, `0x2D380E8` копирует слово `[x0]` в сообщение `0x205` длиной 4; `0x2D380D4` собирает сообщение `0x204` из трёх слов длиной 12; `0x2D38134` переносит последовательность полей структуры в событие `0x206` длиной `0x2C`. Пустые события также встречаются и служат уведомлениями без полезной части.

Цикл `0x2D67134` запрашивает запись 3 с индексом `-1`, затем проходит по функции обработки, вызывает `0x2D9A060` и `0x2D5B36C`, а для сравнения пары полей использует `0x2E00D18`. Это прямое подтверждение маршрута сообщений внутри съёмочного контура. Содержание сравниваемых значений и действия конечного обработчика по одному разбору этой очереди не назначены.

### `0x02` – возможный поток съёмочного тракта

В блоке 1 функция `0x2E89120` регистрирует 48 элементов размером `0x1D0`. 28 найденных отправителей строят тип 2. У коротких функций оболочка содержит код события, байт состояния и нулевую длину; например, `0x2E891C8` отправляет `0x1101`, а соседние функции – `0x1103` и `0x1105`. В других местах (`0x2D39058`, `0x2D3C724`, `0x2D3C93C`) оболочка передаёт размер и указатель на данные, полученные от вызывающего кода.

В каталоге прямых читателей ID `0x02` нет, как нет и прямой ссылки на регистратор `0x2E89120`. Поэтому регистрация могла идти через косвенный вызов, однако конкретный потребитель статически не найден. Контекст указывает на область съёмочного тракта, что даёт кандидата подсистемы, но не доказывает применение записи для выдержки, экспозиции или серийной съёмки.

## Отдельно о фокусе, экспозиции, затворе, серии и дисплее

По проверенным прямым маршрутам нет доказанной карты от этих пяти записей к настройкам `UI_SETP_FOCUS_MODE` (`0x8C0`), `UI_SETP_FOCUS` (`0x6FB`), `UI_SETP_AFC_SET_CALL` (`0x70D`), к фактическим полям затвора/выдержки или к состоянию дисплея. Для `0x88` подтверждена связь с объективным потоком, но это не раскрывает семантику конкретных байтов. Для `0x4F` числовые коды принадлежат маршруту сообщений; для `0x03` и `0x02` часть полей переносится, но конечное действие остаётся за границей разбора.

Ни одна из найденных функций не даёт основания называть эти данные параметрами выдержки или серии. Отдельно от данной выборки остаётся уже известная запись `0x4C`: её поле `+0x64` переносит флаг в MOVDC, но она не входит в предмет этого задания.

## Границы вывода

- Каталог и прямые вызовы взяты из `U2_каталог_записей/результат.json`; разбор выполнен для блоков 0–1 5.30. Статический поиск не исключает обращения по динамическому ID и косвенные переходы.
- Строки `lenscom`, `biscom`, `reccont` доказывают только текстовые метки потоков. Название не заменяет разбор кода, который отправляет и принимает данные.
- Не расшифрованы внутренние коды событий и конечные получатели отдельных пакетов. Для `0x02` читатель не найден; для `0x88` и `0x8B` по прямым API-вызовам читателей нет.
- Камера не использовалась; опыт на ней для выполнения этого статического задания не требовался.

## Что это даёт для будущих доработок прошивки

Пять ID теперь разбиты на четыре канала с установленными метками потоков и один неразрешённый поток событий. Для поиска живого обмена наиболее полезны точки регистрации `0x13E6420`, `0x13FCAB0`, `0x2D5A998`, чтения `0x15669E0` и `0x2D67134`, а также общий API публикации `0x14CF124`. Перехват полезной части вместе с кодом события позволит сопоставить сообщения с действиями камеры; до этого этапа изменять пакеты по одному только ID или соседству адресов нельзя.

Артефакты: `результат.json`, `analyze_v1.py`.
