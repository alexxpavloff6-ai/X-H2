# Матрица → AF → объектив: четыре самостоятельные трассы

## Результат

Найдена **не сквозная физическая цепь**, а более узкая прямая связь внутри AF: код в зарегистрированной точке входа задачи `paf` при определённой, не восстановленной здесь ветви вызывает обёртку формирования сообщения; та передаёт код и данные общей функции отправки с идентификатором одной из двух задач `paf_sub`. Входы `paf_sub0`/`paf_sub1` запрашивают сообщение с соответствующим ID, передают его 16-битный код общему диспетчеру; выбранная ветвь вызывает следующий обработчик. Это не просто совпадение строк: есть конкретные инструкции, сопоставленные ID, код и условное исполнение. Фактическая очередь, её реализация и доставка на устройстве не выполнялись и не доказаны. Источник данных матрицы, назначение обрабатываемых структур и команда мотору остаются неизвестными.

| Модель | Участок `paf`: вызов обёртки | Обёртка → отправитель | Код, ID sub0/sub1 | Входы sub0 / sub1 | Диспетчер → следующий обработчик |
|---|---|---|---|---|---|
| X-H2 5.30 | `0x3135d8c` | `0x313754c` → `0x3137340`; нижний вызов `0x14cf124` | `0x17e2`, `0x93` / `0x94` | `0x31372b0` / `0x31372f8` | `0x31367b0` → `0x314530c` |
| X-H2S 7.30 | `0x3447fd8` | `0x3449798` → `0x344958c`; `0x17eecb8` | `0x17e1`, `0x93` / `0x94` | `0x34494fc` / `0x3449544` | `0x34489fc` → `0x34573e0` |
| X-T5 4.31 | `0x307521c` | `0x30769dc` → `0x30767d0`; `0x14c6f88` | `0x17e4`, `0x93` / `0x94` | `0x3076740` / `0x3076788` | `0x3075c40` → `0x308479c` |
| X100VI 1.31 | `0x335d370` | `0x335f258` → `0x335f034`; `0x159b220` | `0x183a`, `0xb6` / `0xb7` | `0x335efa4` / `0x335efec` | `0x335e058` → `0x336d8a0` |

Адреса — модельные адреса распакованных блоков, не смещения DAT и не экспериментально проверенная карта работающей камеры. Входы `paf` и `paf_sub` сопоставлены с ранее независимо подготовленными описателями задач в [карте четырёх камер](../../Сравнение_камер/Карта_задач_четырёх_камер.md). Участок вызова лежит внутри тела, начинающегося с зарегистрированного `paf`; достижимость конкретной ветви из реального состояния не установлена. Поиск прямых `BL` к показанным обёрткам в двух распакованных блоках каждой модели дал по одному кандидату — указанный вызов; поиск не покрывает косвенные вызовы и может включать данные, похожие на инструкции.

## Что делают инструкции

В ветви перед вызовом обёртки все четыре прошивки записывают `1` в поле структуры, копируют несколько её 64-битных полей, затем передают адрес функции, указатель на локальные 24 байта и `w2=1`. Обёртка добавляет указатель функции к этим 24 байтам, передаёт вниз код из таблицы и длину `0x20`. Общий подготовитель выбирает ID: базовый плюс `(w3 != 0)`; сохраняет 16-битный код, результат ещё одного вызова, ID, длину и указатель на локальные данные, затем вызывает нижнюю функцию с ID и адресом сообщения. Сравнение относительных инструкций выявило одинаковую схему для всех четырёх, но **числа сообщений между моделями различаются** и не являются универсальным протоколом.

В исследованной вызывающей ветви непосредственно выше вызова реально установлено `w20=1`, следовательно подготовка выбирает `sub1`; эксперимент с `w20=0` — дополнительная искусственная проверка общего механизма, а не утверждение, что этот конкретный путь выбирает `sub0`. Приёмная сторона вызывает соответствующую функцию ожидания с ID и `0xffffffff`, загружает `ldrh` из буфера и вызывает диспетчер с кодом и указателем на отдельный контекст. Диспетчер по коду выбирает следующий обработчик и передаёт адрес `контекст+8`. После этого в коде предусмотрен условный косвенный вызов указателя из контекста, но он здесь не выполнялся.

В отдельном опыте следующий обработчик действительно исполнен до первого `BL`, а затем его первый вызываемый фрагмент — до ещё одного `BL`. Одинаковые для четырёх камер искусственные данные: `x0=0x70002000`, по этому адресу u64-указатель `0x70001000`, по `0x70001018` лежит u32 `0x12345678`, по `0x70001020` — u32 `0x9abcdef0`. Исполнены чтения указателя, затем поля `+0x20`, затем поля `+0x18`; первый вызов получает `(w0,w1)=(0x12345678,0x9abcdef0)`. Его оригинальный код меняет аргументы местами и вызывает следующую функцию с `(0x9abcdef0,0x12345678)`; она **не исполнялась**. Кроме сохранения регистров в искусственный стек других чтений до этой границы нет. Семантика полей и источник структуры неизвестны.

| Модель | Первый BL обработчика → исполненная функция | Второй BL → вход, где остановлено | PC неуспешного чтения при нулевом указателе |
|---|---|---|---|
| X-H2 | `0x3145338` → `0x313f0d4` | `0x313f0e8` → `0x1542080` | `0x3145330` |
| X-H2S | `0x345740c` → `0x34512fc` | `0x3451310` → `0x18619f4` | `0x3457404` |
| X-T5 | `0x30847c8` → `0x307e564` | `0x307e578` → `0x1537e4c` | `0x30847c0` |
| X100VI | `0x336d8cc` → `0x3367408` | `0x336741c` → `0x16092e0` | `0x336d8c4` |

Контроль перестановкой значений обоих полей меняет соответствующие аргументы вызовов; отрицательный контроль с нулевым внутренним указателем на всех моделях приводит к ошибке чтения адреса `0x20` до первого вызова. Это свойство изолированной VM с незамапленной нулевой страницей, а не утверждение о реакции камеры. Исполнение начато с искусственного аргумента, **не** с полученного выше контекста, содержимое которого не восстановлено.

В первом qword сформированной нагрузки обнаружен адрес оригинального кода. Его начало отдельно исполнено с искусственным стеком до вызова: X-H2 `0x3134f4c` → `0x3134f04` с `w0=0x17da`; X-H2S `0x3447198` → `0x3447150` с `w0=0x17d9`; X-T5 `0x30743dc` → `0x3074394` с `w0=0x17dc`; X100VI `0x335c7fc` → `0x335c7b4` с `w0=0x1831`. Во всех четырёх `x1=x2=0`. Адреса действительно указывают на фрагменты инструкций, а не только на похожие значения; они не доказывают, что указатель действительно попадает в контекст и вызывается после доставки сообщения. Тела этих вызываемых функций не исполнялись.

## Контрольный эксперимент и подмены

[Скрипт](исследовать.py) по отдельности распаковывает оригинальные блоки каждого DAT в память и исполняет оригинальные AArch64 инструкции Unicorn. Для каждого корпуса проведены два опыта: принудительный `w20=0` и `w20=1`; в 24 байта источника помещены синтетические `10 11 ... 27` hex. Начало выбрано непосредственно у подготовки аргументов вызова, то есть более ранние инструкции тела `paf` и условия ветвления не исполнялись. Значение неизвестной функции при формировании заголовка искусственно подменено на `0x2a`. Нижняя функция отправки перехвачена на входе, её тело не выполнялось: сохранены сформированные заголовок и 32 байта данных, включая настоящий кодовый указатель, подготовленный инструкциями прошивки. Значение `0x2a` не означает идентификатор реальной задачи.

Приёмная сторона запускается **в отдельной VM**, с нулевой искусственной памятью контекста; функция ожидания перехвачена, вместо реальной доставки скрипт вручную записывает только первые два байта полученного заголовка в ожидаемый буфер и подставляет успешный возврат. Данные, callback и прочие поля сообщения в контекст не переносятся: механизм их доставки не исследован. В этом опыте обработчик перехвачен на входе; независимое дальнейшее исполнение с искусственной структурой описано выше. Указатель на локальные данные отправителя не является доказательством времени их жизни при настоящей межзадачной передаче.

В [результатах JSON](результаты.json) сохранены точные машинные байты и дизассемблирование подготовителя, обёртки, обоих входов и первых инструкций диспетчера, трассы ключевых PC, содержимое буферов, проверенные входные и выходные хеши, хеши и базы FFLZ. Кодовые указатели и адреса в трассах относятся к модели; все регистры и оперативная память, кроме явно описанных, — искусственные.

## Незакрытые стрелки

1. **Матрица → вход `paf`**: происхождение полей структуры, роль сенсора, фактические кадры и ветвление до вызова не установлены.
2. **Подготовленное сообщение → реальная доставка/контекст**: реализация функций отправки и ожидания, копирование полезной нагрузки, очереди, синхронизация и обратный вызов не исследованы. Переход между VM — явная ручная подмена.
3. **Следующий обработчик → результат AF**: структура и семантика входных полей, весь расчёт и данные не восстановлены; последняя граница независимого исполнения — вход второго вызываемого фрагмента из таблицы выше, тело не исполнялось.
4. **AF → объектив**: не выявлена прямая связь с обработчиками `lenscom`/`lensdata`, приводом или протоколом объектива. Наличие этих имён в каталогах не доказывает маршрут. У X100VI объектив встроен; отсутствие `lenscom` в использованном каталоге не доказывает отсутствия управления фокусировкой. Связи с внешними ZIP объективов не получены, поэтому сравнение байтов ZIP и утверждения о протоколе не делались.
5. **Физическое выполнение**: реальная камера не участвовала; скорость, фокус, точность и результат оптического движения не измерены.
