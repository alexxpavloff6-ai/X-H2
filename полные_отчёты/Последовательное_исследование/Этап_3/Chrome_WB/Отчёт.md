# Color Chrome и баланс белого: четыре собственных писателя

## Что установлено и чего это не означает

На X-H2 5.30, X-H2S 7.30, X-T5 4.31 и X100VI 1.31 **отдельно исполнены собственные машинные инструкции каждой модели**. При искусственных входах `Chrome=2`, `Blue=2`, `WB mode=13`, сдвиг `(1, −5)`, поле температуры `5750`, `gate=2` все четыре писателя дали объект с `(64, 64)`, `WB=0x0ff0`, температурой `5750` и сдвигом `(20, −100)`; собственные построители сериализовали эти значения. Это совпадает с численными метаданными 0296 X-H2, но **не доказывает физический путь UI → параметры → EXIF**, достижимость такого состояния в живой камере или влияние на пиксели. Особенно нельзя выводить, что три другие камеры производили 0296.

[Метаданные 0296](../../../Проявка_0296/Метаданные/Отчёт.md) сообщают об интерпретации ExifTool: оба Chrome — Strong, WB — Kelvin 5750 K, FineTune `(20, −100)`; реальные значения экрана WB не проверены. [Ранее для X-H2](../../../Контрольные_снимки/Рецепт_прошивка/Отчёт.md) найдены UI-таблицы: Kelvin UI 6 → внутренний 13, R P1 → 1, B M5 → −5, оба HARD → 2. Это отдельное статическое наблюдение по X-H2, не исполненная цепочка передачи этих значений в найденные здесь поля. Интерпретации тегов взяты из [ExifTool FujiFilm](https://exiftool.org/TagNames/FujiFilm.html): 0/32/64 — Off/Weak/Strong, `0x0ff0` — Kelvin, FineTune — два знаковых 32-битных числа с примечанием о делении на 20 для новых камер. Названия UI, внутренние коды и численные теги нельзя отождествлять только по совпадению.

## Адреса и модельные смещения

Адреса — виртуальные адреса распакованной прошивки, не позиции внутри DAT; смещения — от начала искусственной структуры параметров. Начало WB-фрагмента — непосредственно перед вызовом переводчика режима; он также исполняет соседние преобразователи и формирует флаг наличия сдвига. Chrome — фрагмент основного писателя, конец указан в JSON; ветки могут выходить за линейный диапазон.

| Модель | WB-фрагмент | Chrome-фрагмент | gate | Chrome / Blue | WB mode | WB shift 0 / 1 | обычная температура |
|---|---:|---:|---:|---:|---:|---:|---:|
| X-H2 | `02e52ca4` | `02e531d0` | `3978` | `3f10 / 3f14` | `39a4` | `39a8 / 39ac` | `3a94` |
| X-H2S | `03169f88` | `0316a4b4` | `391c` | `3ebc / 3ec0` | `3948` | `394c / 3950` | `3a40` |
| X-T5 | `02d90eec` | `02d91410` | `39c0` | `3f48 / 3f4c` | `39ec` | `39f0 / 39f4` | `3ad0` |
| X100VI | `03060e24` | `03061370` | `3fa8` | `4538 / 453c` | `3fd4` | `3fd8 / 3fdc` | `40c0` |

Входы Chrome, mode, shift и gate — 32-битные, температура — 16-битная. X100VI использует адресацию `+0x4000` плюс непосредственное смещение, а не X-H2-смещения. X-T5 и X100VI дополнительно вызывают собственную функцию проверки gate перед каждой записью Chrome; результаты ниже относятся к `gate=2` и не обобщаются на другие gate.

Функции перевода WB mode / температуры / отдельной компоненты сдвига соответственно: X-H2 `02e50e00 / 02e513b4 / 02e515bc`; X-H2S `031680f0 / 0316869c / 031688a4`; X-T5 `02d8ef38 / 02d8f53c / 02d8f774`; X100VI `0305eee0 / 0305f4e8 / 0305f728`. У всех четыре исходных поля объекта для этой проверки: `+98` (16-битный режим), `+9e` (16-битная температура), `+a4` и `+a8` (signed32 сдвиг); флаг сдвига `+a0`. Значения Chrome — signed32 `+4c` и `+50`. Считанные в каждой модели дескрипторы группы 2 отдельно подтверждают привязку полей к тегам `1002`, `1005`, `100a`, `1048`, `104e`; полные исходные байты дескрипторов и адреса — в JSON.

## Исполнение и сериализация

В опытах нулевой объект соединён исследователем с двумя фрагментами и затем вручную передан собственным предикату и построителю модели. Для каждого тега выполняется предикат. При `gate=2`, режиме 13 и прочих указанных ниже входах все пять предикатов дали 1 во всех моделях. Записи — элементы искусственного каталога TIFF, не JPEG. Указатель `0x100a` относится к началу искусственного буфера построителя, а не к файлу.

| Входы Chrome / Blue | Поля объекта / численные значения тегов |
|---|---|
| `0 / 0` | `0 / 0` |
| `2 / 2` | `64 / 64` |
| `1 / 2` | `32 / 64` |
| `2 / 1` | `64 / 32` |
| `3 / 3` | `0 / 0` |

Последняя строка — контроль этого входа, не утверждение, что код 3 допустим в меню. Для случая 2/2 каждая модель вернула записи:

```text
02 10 03 00 01 00 00 00 f0 0f 00 00  # 1002, SHORT 1, 0x0ff0
05 10 03 00 01 00 00 00 76 16 00 00  # 1005, SHORT 1, 5750
48 10 09 00 01 00 00 00 40 00 00 00  # 1048, SLONG 1, 64
4e 10 09 00 01 00 00 00 40 00 00 00  # 104e, SLONG 1, 64
```

`100a` — тип 9, количество 2, данные находятся отдельно: `14 00 00 00 9c ff ff ff` = `(20, −100)`. Сама 12-байтная запись у X-H2 и X-H2S заканчивается указателем `24 05 00 00`, у X-T5 — `30 05 00 00`, у X100VI — `00 05 00 00`: это различия смещения данных внутри искусственного каталога, не различия значений. При сдвиге `(0,0)` восемь байтов данных — нули. Длина полного искусственного каталога соответственно `3598 / 3598 / 3618 / 3538`; равенство пяти полей не означает равенства каталогов.

В обоих каналах отдельно проверены внутренние signed32 `−10…10`: `−9…9` дают ровно вход × 20; крайние проверенные `−10` и `10` дают 0. Для рецептурной пары это `(1,−5) → (20,−100)`; 20 — не доказанное значение UI. При mode 0 получены объектный режим 0 и температура 0, предикат `1005=0`, и тег температуры отсутствует, хотя введённое поле всё ещё равно 5750; `100a` остаётся. Это показывает зависимость, а не универсальное правило для всех режимов.

При mode 13 и обычной ветви функция температуры берёт 16-битное поле из таблицы выше. Также исследованы альтернативные источники: при discriminator 10 и selector 2/3 функции всех моделей выбирают искусственно заданные 5200/5300 вместо 5750. Смещения discriminator / selector / альтернативных трёх полей: X-H2 `396c / 429c / 4160,4162,4164`; X-H2S `390c / 424c / 4114,4116,4118`; X-T5 `39b4 / 4418 / 42d0,42d2,42d4`; X100VI `3f9c / 4a50 / 48e8,48ea,48ec`. Физический смысл переключателя не установлен.

## Метод и недоказанные пути

* Каждый DAT прочитан и проверен по SHA-256 до и после, оба собственных блока распакованы, сопоставлены в Unicorn по виртуальным адресам и исполнены без патчей и заглушек. Для X100VI блок B перекрывает A, как в предыдущих работах. Остальная отображённая память — искусственные нули; стек, параметры, объект и выходной буфер синтетические. Все вызовы стартуют вручную; переходы внутри исполняемых фрагментов реальные.
* Предикат и построитель реально вызваны, но объект из писателей передан в них исследователем; штатный владелец объекта, полный вызывающий участок и дальнейшая упаковка в реальный JPEG не исполнены. Не установлено, что реальные UI-конвертеры заполняют именно эти поля во всех режимах и на всех моделях.
* Связь экранных пунктов Strong, Kelvin 5750, R+1/B−5 с найденными параметрами — согласованная гипотеза, не прямое наблюдение экрана и пути к EXIF. Не исследованы остальные WB-режимы, все дополнительные ветки gate, калибровка, RGB-коэффициенты и обработка пикселей. Смещение WB — не коэффициенты `WBRed/Green/Blue`.
* При временном пропуске инструкций вычисления флага `+a0` предикат `100a` давал 0; итоговые опыты включают эти инструкции. Следовательно нельзя делать вывод об отсутствии тега по объекту без этого флага. Условия предиката вне проверенных состояний не исчерпаны.
