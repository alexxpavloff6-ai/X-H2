# A53: программатор MOVDC и писатель guard-флага (блоки 0–2, X-H2 5.30/5.33)

Дата: 2026-11-16. Продолжение G2. Только чтение блоков/DAT.
Уровни: **Д** — доказано байтами/дизассемблером; **К** — сильный кандидат; **Г** — гипотеза.

---

## 0. Итог

1. **Ветка 1 (MOVDC через указатель) — пусто (Д).** Во всех блоках 0–3 обеих версий **нет ни одного**
   `u32`/`u64`, попадающего в окно таблицы карты регистров (`0x385E000..0x385E400` в 5.33,
   `0x3862000..0x3862400` в 5.30), и нет указателей на её записи (`0x385E14C + k*0x18`).
   Таблицу не адресует ни `ADRP+ADD/LDR` (прошлая задача), ни указатель из данных. Значит
   **программатора MOVDC в ThreadX-приложении нет** и по указательной ветке.
2. **Ветка 2 (флаг) — писатель найден, но он не «решает режим» (Д/К).**
   Guard-флаг `0x4C2FF14` пишется **только** в двух местах 5.33:
   `0x3104728` и `0x3104C40` — `str w2,[x0,#0x43c]` (x0 = `0x4C2FAD8`), причём
   `w2 = [0x4C3B088 + 0x1E4]` = **`current_params + 0x74`** (`0x4C3B26C`).
   `current_params` (`0x4C3B1F8`) получается `memcpy` (0x168 байт) из `pending_params` (`0x4C3B090`)
   в `0x31015B4`. **Прямых записей в `pending+0x74` (`0x4C3B104`) нет ни в одном блоке** — всё поле
   приходит в составе 168-байтного блока, который заполняется вызовом `0x14C6384(id=0x4C, buf=0x4C3B090)`
   в `0x3101504`. То есть флаг — **сохранённое поле записи/настройки**, читаемое на apply, а не
   решение режима внутри кадрового пути (К).
3. **Важное предупреждение:** пространство id этого геттера **не совпадает** с нумерацией UI_SETP.
   По словарю UI_SETP в блоке 0 (0x1654ED0, номер = индекс−1) `id=0x4C` = `UI_SETP_BT_SHOOTINGGRIP_DEVICE_ADDRESS_15`
   (индекс 77) — к MOVDC/съёмке отношения не имеет (Д). Искать «режим» через UI_SETP по id 0x4C нельзя.

## 2. Ветка 2: писатель guard-флага `0x4C2FF14`

### 2.1. Структуры и копирование (Д)

`0x31015B4` (5.33, block1) — функция `memcpy(pending → current)`:

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Итог адресов:

| Сущность | 5.33 | 5.30 (+0x4000) |
|---|---|---|
| `pending_params` | `0x4C3B090` | `0x4C3F090` |
| `pending+0x74` (**поле флага**) | `0x4C3B104` | `0x4C3F104` |
| `current_params` | `0x4C3B1F8` | `0x4C3F1F8` |
| `current+0x74` | `0x4C3B26C` | `0x4C3F26C` |
| `state_params` (флаг) | `0x4C2FAD8 (+0x43C)` = `0x4C2FF14` | `0x4C33F14` |

### 2.2. Кто пишет флаг (Д) — `52_записи_флага.py`, `53_писатели_флага.py`

Трекер абсолютных записей по `ADRP+ADD` (блоки 0,1,2, обе версии) даёт **ровно два** писателя:

| 5.33 | 5.30 | Инструкция | Источник |
|---|---|---|---|
| `0x3104728` | `0x31085A8` | `str w2,[x0,#0x43c]`, x0 = `0x4C2FAD8` | `ldr w2,[x1,#0x1e4]`, x1 = `0x4C3B088` → `0x4C3B26C` = current+0x74 |
| `0x3104C40` | `0x3108AA8` | то же | то же |

Контекст 5.33 (второй писатель, `0x3104C34..0x3104C40`):

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

**Д:** других записей в `0x4C2FF14` (в т.ч. через `0x4C2FAD8+0x43C`) в блоках 0–2 нет.
Блок 0 и блок 2 прямых записей в `state_params` вообще не делают.
**Д:** прямых записей в `pending+0x74` (`0x4C3B104`) и в `current+0x74` (`0x4C3B26C`) нет — только
через `memcpy` целого блока.

### 2.3. Чем заполняется pending (К)

`0x3101504` (5.33 block1) — «сборка params»:

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

`0x14C6384` — **геттер записи** (block 0, new):

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

**К:** `pending_params` (0x168 байт) заполняется как «запись id=0x4C» через этот геттер;
значит и поле `+0x74` (флаг) — часть этой записи, а не вычисляется в кадровом пути.
**Г:** кто и когда пишет саму запись id=0x4C (сеттер/приём UI- или PTP-команды) — в этой задаче
не установлено: сеттер живёт в блоке 2/low-level (резолвер `0x5460C`), либо запись приходит
из другого сервиса.

### 2.4. Про словарь UI_SETP — не сходится (Д)

Нумерация UI_SETP в блоке 0 (строки `UI_SETP_*` с `0x1654ED0`, номер = индекс−1) даёт для `id=0x4C`:

```
id=0x4b → UI_SETP_BT_SHOOTINGGRIP_DEVICE_ADDRESS_14   (индекс 76)
id=0x4c → UI_SETP_BT_SHOOTINGGRIP_DEVICE_ADDRESS_15   (индекс 77)
id=0x4d → UI_SETP_BT_SHOOTINGGRIP_DEVICE_ADDRESS_16   (индекс 78)
```

То есть **id геттера `0x14C6384` — это не номер UI_SETP**: 0x4C там попадает в блок Bluetooth-строк.
Сопоставление «id 0x4C → настройка UI_SETP» **неверно** и вести по нему поиск режима нельзя.

## 4. Что делать дальше (кратко)

1. **Сеттер записи 0x4C**: найти в блоке 2 функцию, парную геттеру `0x14C6384` (рядом `0x14C6434`,
   `0x14C9564`), и её вызовы с id=0x4C — там будет источник значения поля +0x74.
2. **Unicorn**: поставить watchpoint на `0x4C3B104` (pending+0x74) и на `0x4C3B26C` при обработке
   UI-команды/смены режима — какой код/команда пишет 1.
3. По MOVDC: раз таблица не используется ThreadX-приложением, остаются только внешние владельцы
   (boot ROM/SCM/Linux) — ветка H.
