# G2: образ Cortex-M4 в update.dat X-H2 5.33 — найден, разобран, связи с MOVDC нет

Дата: 2026-11-16. Воркер DeepSeek Harness (G2), папка `G2_образ_M4/`.
Все выводы получены чтением DAT (`translate XOR 0xFF`) и распакованных блоков; ничего не изменялось,
камера не использовалась. Уровни: **Д** — доказано байтами/дизассемблером; **К** — сильный кандидат;
**Г** — гипотеза.

---

## 0. Краткий ответ

1. Образ Cortex-M4 **подтверждён** и лежит не в FFLZ-блоках, а в «сыром» префиксе DAT:
   `DAT[0x1C0274 : 0x1C0274+0x31A80]` (X-H2 5.33), слинкован от **0** (SRAM 0xFA200000 = адрес 0 ядра),
   `SP=0x00000A00`, `reset=0x00000A01`. Присутствует в X-H2S 7.31 (0x22900) и X-T5 4.32 (0x32470)
   по тому же смещению — проверено на их DAT (§2).
2. Это **ThreadX**-прошивка из трёх потоков (`System Timer Thread`, `idle`, `comm`) с таблицей из 25
   команд/событий, обслуживающая mailbox, general DMA, flash-DMA, GPIO/GPIO3, ADC, capture0.
   Все 179 IRQ-векторов указывают на общий `b .` — периферийных прерываний у ядра нет, работа опросом (**Д**).
3. **MOVDC (0xFF970000 и алиас 0x5F970000) в образе M4 не упоминается ни разу**; значения 0x10030001
   нет ни в образе, ни вообще в DAT на 4-байтном выравнивании (**Д**). MOVDC описан в таблице
   дескрипторов **A53** (блок 1, VA 0x385E170) вместе с регистром тактирования 0xFF90C300 (**Д**).
4. Флаг MOVDC (`params.current+0x74`, глоб. `0x4c2ff14`) и задание съёмки `[0x4daa6e8]` M4 писать
   не может: в образе нет ни одного адреса DRAM A53 (0 совпадений 0x4C2FF14/0x4DAA6E8/страниц),
   а его собственный SRAM для него — адрес 0 (**Д**). Канал — только mailbox `0x5F90E100`
   (= A53 `0xFF90E100`) (**Д**), но обратной стороны (чтения mailbox) в A53-блоках 0–2 нет (§5).

## 1. Где образ и как он выглядит

### 1.1. Расположение (X-H2 5.33, `FIRMWARE/ver new/FWUP0028 (2).DAT`)

| Параметр | Значение |
|---|---|
| Смещение в DAT | `0x1C0274` (в «префиксе», до первого FFLZ @ 0x300274) |
| Длина | `0x31A80` = 203 392 байт |
| sha256 | `85d29ade613aa01cc5b9518218fbdd74d7976ed69130ad679f5cd88339506b9e` |
| Регион «flash 0x1C0000» | 0x274 байта перед образом (`0x1C0000..0x1C0274`) — **нули** |
| `word0` = SP | `0x00000A00` |
| `word1` = reset | `0x00000A01` (Thumb-бит) |

`0x31A80` — длина ровно до выравнивания: после `0x1F1CF4` идут нули/выравнивание,
а срез именно `0x31A80` заканчивается восемью нулевыми байтами (проверено, `24_сверка_моделей.py`).

### 1.2. Векторная таблица (первые 0x800 байт образа)

512 слов; ненулевых 190. Системные векторы:

| # | Вектор | Адрес | Что там |
|---|---|---|---|
| 0 | SP | `0x00000A00` | стек растёт вниз от 0xA00 |
| 1 | Reset | `0x00000A01` | `push {r7,lr}; bl 0xA14; bl 0x2E54; bl 0xA78` |
| 2 | NMI | `0x000018DD` | `b .` (вечный цикл) |
| 3 | HardFault | `0x00000A35` | `tst lr,#4; mrseq r0,msp; mrsne r0,psp; …` → сохраняет фрейм и уходит в `b .` |
| 4–6 | MemManage/BusFault/UsageFault | `0x000018AB` | `b .` |
| 11 | SVC | `0x000018B3` | читает регистр, маска, `bl 0x1E0DC` |
| 12 | DebugMon | `0x000018E1` | заглушка |
| 14 | PendSV | `0x00002133` | переключение контекста: `mrs ip,psp; stmdb ip!,{r4-r11}; str lr,[ip,#-4]!` … |
| 15 | SysTick | `0x000018D1` | `push {lr}; bl 0x27B0; pop; bx lr` |
| 16…511 | IRQ 0…495 | `0x000018B7` (все 179 ненулевых) | `b .` — **ни одного реального обработчика прерывания** |

Слова 7–10 и 13 — нули (резервы ARMv7-M), т.е. раскладка стандартная. **Д.** Таблица ARMv7-M;
ядро не пользуется NVIC — вся периферия опрашивается.

Reset-код подтверждает Cortex-M: в `0xA18` загружается литерал `0xE000ED14` (SCB->CCR),
пишется `0x210`, затем в `0xE000ED24` (SCB->SHCSR) пишется 0.

### 1.3. Плотность кода (после исправления метрики)

Линейный свип Thumb (с ресинхронизацией): **71 967 инструкций**, покрытие `202 438` из `203 392` байт.

| Метрика | Значение в образе | «Шум» в DAT (сырой хвост / блок 0) | Случайные данные |
|---|---|---|---|
| `bl` (0xF0..,0xD0/0xF0..) | 3 243 = **3.19 %** полуслов | 0.26 % / 0.81 % | ≈0.39 % |
| `bx lr` (0x4770) | 289 = **0.28 %** | 0.0024 % / 0.002 % | ≈0.0015 % |
| `push {..,lr}` (0xB5xx) | 472 = 0.46 % | 0.23 % / 0.03 % | ≈0.39 % |
| `ldr rN,[pc,#..]` | 4.63 % | 2–5 % | ≈3.1 % |

`bl` в образе в 8 раз выше случайного уровня, `bx lr` — в ~190 раз; вместе с плотным кодом
это однозначно код, а не данные. **Самопроверка детекторов** (`13_итоги_и_самопроверка.py`):
на 20 синтетических образах ARMv7-M (SP + 16 векторов + Thumb-код, вставленных в случайный буфер
со случайным смещением) таблица векторов найдена 20/20, Thumb-код — 20/20.

Это типичный профиль скомпилированного ARMv7-M (ARMCC: почти все константы — литеральные пулы;
пар `movw/movt` в образе **0**).

## 2. Почему прошлый отрицательный результат был ошибочным (важно для методики)

Мой предыдущий вывод «Thumb-кода и таблицы векторов в DAT нет» — артефакт трёх проверок:

1. **Требование «8–16 нечётных векторов подряд»** не выполняется на реальной таблице: в ней есть
   нулевые резервы (слова 7–9, 12) и 179 *одинаковых* IRQ-векторов, поэтому подряд идёт 3–5 нечётных слов.
2. **Проверка SP** отбрасывала `0xA00`: я ожидал SP у верха SRAM (`0xFA200000..0xFA260000` или
   on-chip SRAM ≥ 0x1000), а здесь стек в *начале* образа — образ слинкован от 0 и растёт вверх,
   стек — вниз от 0xA00.
3. **Метрика плотности Thumb была сломана** приоритетом операторов в numpy-выражении
   (`hi & 0xD0 == 0xD0` разбирается как `hi & (0xD0 == 0xD0)`), из-за чего `bl` = 0 во всех окнах,
   и «отсутствие bl» я принял за признак данных. После исправления (`(hi & 0xD0) == 0xD0`) картина
   стала нормальной.

Сигнал был на виду: окна `0x1C0000..0x1F0000` показывали `bx lr` 20–57 на 16 КиБ и `push_lr` 1.6 %
(в 4 раза выше шума) — я списал это на данные. Образ лежит в «префиксе» DAT, который я считал
только загрузчиком + таблицами.

**Рабочий рецепт поиска такого образа в следующий раз** (проверен: `26_проверка_рецепта.py`
даёт **ровно одно** совпадение на весь DAT 5.33 — `0x1C0274`). Не требовать длинных серий
нечётных слов; проверять раскладку ARMv7-M на выровненном слове `w0`:

* `w0` чётное, `0x400 ≤ w0 < 0x100000` (SP в начале образа, стек растёт вниз);
* `w1 == (w0|1)` и `w1 < 0x100000` (reset с Thumb-битом);
* `w2..w6` (NMI, HardFault, MemManage, BusFault, UsageFault) — нечётные, `> 0`, `< 0x100000`;
* `w7 = w8 = w9 = w10 = 0` и `w13 = 0` — четыре резервных слова и резерв перед PendSV;
* `w11` (SVCall), `w14` (PendSV), `w15` (SysTick) — нечётные, `> 0`, `< 0x100000`.

Для X-H2 5.33 это `DAT[0x1C0274] = {0xA00, 0xA01, 0x18DD, 0xA35, 0x18AB, 0x18AB, 0x18AB, 0,0,0,0,
0x18B3, 0x18E1, 0, 0x2133, 0x18D1}`; то же смещение в X-H2S и X-T5.

Отдельно: **три первые проверки не спасают**, а именно «SP в 0xFA200000..0xFA260000» — здесь
SP вообще не адрес SRAM A53, а смещение внутри образа (0xA00).

## 3. Модель памяти образа M4

* **Код/данные ядра — адреса 0…~0x100000**: переменные вроде `0x00034088`, `0x000F51F4`,
  векторная таблица по 0, код с 0xA00. Соответствует SRAM 1 МиБ по 0xFA200000 при отображении
  **core4: address 0 → physical 0xFA200000** (fujimod `catalog/soc/xp5/soc.json`, `mappings[0]`) — **Д**.
* **Периферия ядра — 0x5Fxxxxxx = A53 0xFFxxxxxx − 0xA0000000**. Реальные страницы из литералов образа:

| Алиас M4 | A53 | Блок по fujimod | Обращений |
|---|---|---|---|
| `0x5F90E000` | `0xFF90E000` | **mailbox** (`0xFF90E100`) | 11 |
| `0x5F930000` | `0xFF930000` | **general DMA** | 27 |
| `0x5F939000` | `0xFF939000` | **flash-DMA** | 11 |
| `0x5F907000` | `0xFF907000` | GPIO | 16 |
| `0x5F90B000` | `0xFF90B000` | GPIO3 | 18 |
| `0x5F908000`, `0x5F909000` | `0xFF908000`, `0xFF909000` | в карте fujimod нет | 15 / 14 |
| `0x5F928000` | `0xFF928000` | capture0 | 4 |
| `0x5F906000` | `0xFF906000` | ADC | 2 |
| `0x5F90C700` | `0xFF90C700` | clock-gates | 1 |
| **`0x5F970000` (MOVDC)** | `0xFF970000` | MOVDC | **0** |

Mailbox-литералы в образе: `0x5F90E100`, `0x5F90E10C`, `0x5F90E114`, `0x5F90E120`.

## 4. MOVDC: M4 его не программирует

**Д.** В образе:
* 0 слов в диапазоне `0x5F970000..0x5F973FFF` (любое выравнивание);
* 0 слов `0xFF970000`, `0xFF9700D8`, `0x5F9700D8`;
* 0 вхождений `0x10030001` — и не только в образе: **во всём DAT 5.33 на 4-байтном выравнивании
  этого значения нет** (`18_константы_и_запуск.py`). 0x10030000 есть только в Linux-хвосте
  (`0x3C42718`, `0x3C42994`) и в блоке 2 (`0xD43898`) — это не MOVDC-контекст.

**Д. Где MOVDC на самом деле.** Блок 1 (X-H2 5.33), таблица дескрипторов регистров с VA `0x385E170`:
записи по 24 байта `{start, end, clock_gate, 1, 1, count}`:

```
0xFF970000 0xFF970114 0xFF90C300 1 1 0x4      ; MOVDC0
0xFF971000 0xFF971114 0xFF90C300 1 1 0x8      ; MOVDC1
0xFF972000 0xFF972114 0xFF90C300 1 1 0x10     ; MOVDC2
0xFF973000 0xFF973040 0xFF90C300 1 1 0x20     ; movdc-reset
0xFF974000 0xFF974314 0xFF90C300 1 1 0x40     ; preview
0xFF974400 0xFF9744BC 0xFF90C300 1 1 0x40
0xFF974500 0xFF974508 0xFF90C300 1 1 0x8
0xFF977000 0xFF97700C 0xFF90C310 1 1 0x20000  ; paf
```

То есть MOVDC — периферия **A53-домена**, доступ идёт через таблицу (поэтому ADRP на 0xFF970000
и нет — адреса берутся из таблицы). **Г:** значение `0x10030001` собирается кодом A53 по битам
(в DAT его нет как 32-битного слова).

**Вывод.** Гипотеза «аппаратный MOVDC программирует M4» — **опровергнута**: MOVDC в образе M4
не упоминается вообще. Флаг MOVDC формируется/применяется на A53 (это согласуется с
`A_LCD_MOVDC/отчёт.md`: две apply-функции в блоках 0–2, значение приходит извне).

## 5. Канал M4 ↔ A53 и почему флаг/задание не от M4

**Д.** В образе M4:
* 0 вхождений `0x4C2FF14` (флаг MOVDC) и адресов его страницы;
* 0 вхождений `0x4DAA6E8` (`[0x4daa6e8]`, задание съёмки);
* 0 вхождений `0xFA200000` (свой SRAM ядро видит как 0, а не как физический адрес; слова,
  случайно попадающие в диапазон 0xFA2xxxxx, — это байты Thumb-инструкций `bl`, например
  `0xFA24F002` по смещению 0xA08, а не адреса).

**Д.** В A53-прошивке (префикс-загрузчик, блоки 0–2):
* 0 настоящих ссылок на mailbox `0xFF90E100..0xFF90E13F` (два «попадания» в блоке 2 —
  случайные байты внутри энтропийных данных: `0xFF90E950`, `0xFF90EE6B`);
* 0 настоящих ссылок на companion-SRAM `0xFA200000..0xFA2FFFFF` (частые совпадения — Unicode
  `U+FA20/U+FA30` в таблицах глифов и байты в данных).

Следствия:
* Прямая запись флага MOVDC или задания из M4 **невозможна** — он не адресует DRAM A53 (**Д**).
* Единственный физический канал — mailbox (`0x5F90E100` у M4). Но **читающей стороны в блоках 0–2
  нет**; значит либо mailbox использует другой мастер (boot ROM/Linux через `uio_pdrv_genirq` —
  в bootargs Linux есть `uio_pdrv_genirq`), либо A53↔M4 обмен идёт в другом окне, которого мы
  не нашли (**К/Г**).

Итог по звеньям: **MOVDC — нет (M4 не причастен, Д); флаг MOVDC — M4 его не пишет (Д),
формируется на A53 (Д по отсутствию путей у M4); задание `[0x4daa6e8]` — M4 его не формирует (Д),
источник остаётся внешним по отношению к блокам 0–2.**

## 6. Что M4 реально делает

### 6.1. RTOS и потоки (**Д**)

Строки в образе (смещения от начала образа):

```
0x2DDE0  "uiTSK"     0x2DDE8  "uiSYSM"   0x2DDF0  "uiSYSQ"   0x2DDF8  "uiSYST"
0x2DE00  "System Timer Thread"   0x2DE13  "idle"   0x2DE18  "comm"
```

`System Timer Thread` — штатное имя системного таймер-потока **ThreadX**; строки ThreadX/FreeRTOS
в других местах образа не встречаются (образ собран без отладочных имён). Потоки: `idle`, `comm`,
плюс системный таймер.

### 6.2. Таблица команд/событий (**К**) — образ 0x2DE24, 25 записей по 12 байт `{id, handler, aux}`

| id | handler | aux | id | handler | aux | id | handler | aux |
|---|---|---|---|---|---|---|---|---|
| 0x11A | 0x47A1 | 0x47D9 | 0x80 | 0x4475 | 0x44D9 | 0x185 | 0x4E31 | — |
| 0x29 | 0x40D9 | — | 0x83 | 0x4501 | — | 0x186 | 0x4E79 | — |
| 0x2A | 0x41DD | — | 0x86 | 0x4529 | — | 0x187 | 0x4F11 | — |
| 0x2B | 0x4289 | — | 0x87 | 0x4565 | — | 0x188 | 0x508D | — |
| 0x122 | 0x47F1 | — | 0x181 | 0x4B6D | — | 0x189 | 0x51D1 | — |
| 0x123 | 0x48F1 | — | 0x182 | 0x4BF1 | — | 0xA8 | 0x4591 | — |
| 0x125 | 0x4A91 | — | 0x183 | 0x4CD5 | — | 0xA9 | 0x4641 | 0x46C1 |
| | | | 0x184 | 0x4D31 | — | 0xB1 | 0x46F5 | — |
| | | | | | | 0xB2 | 0x4745 | — |
| | | | | | | 0xD0 | 0x4771 | — |

Обработчики — обычные функции с разбором полей команды (`ldrh r2,[r0,#2]`, `ubfx r3,r3,#0x10,#2`,
`tst.w r3,#0x1E00000`, `tbb [pc,r3]` — таблицы переходов по подтипу).

### 6.3. Mailbox-цикл (**К**)

* `0x2FA4`: `ldr r3,[0x5F90E10C]` (чтение регистра канала), `mov r1,#8; str r1,[0x5F90E120]`
  (запись 8 в регистр управления), затем ветвление по значению: `0x10` → `bl 0x2495C(1, 0x20000)`,
  `0xFF` → `bl 0x2471C` и `str 1,[r3+4]`.
* `0x3168`: цикл приёма — сообщение читается в буфер на стеке (`add.w r1,r7,#0x1C`; `bl 0x248BC`),
  при `r0 == -0x32` повтор (`bl 0x24908`), затем проверка бита `0x20000` в слове сообщения
  (`tst.w r3,#0x20000`), снятие бита и цепочка вызовов `0x3318 → 0x1E0D0 → 0x1C7E0 → 0x1D874 →
  0x597C → 0x2FF0`.
* `0x2F60`: ставит бит 1 в `[0x000F51F4 + 0x2C]` (переменная в RAM ядра), затем `bl 0x231B8`.

### 6.4. DMA и flash-DMA (**К**)

`0x1F580`: выбор канала (`cmp r0,#0xF`), база `0x5F930000`, шаг канала `0x1000`
(`lsr r5,r0,#1; lsl r5,r5,#0xC`), работа с регистрами `+0x28/+0x30/+0x50`;
в `0x1F5A8` к адресу применяется `orr r1,r0,#0x10000000` (бит 28 — атрибут/направление).
Второй блок литературы — `0x5F939000` (flash-DMA): `0x1FB74..0x1FEF8`, регистры `+0x00/+0x04/+0x08/
+0x10/+0x14/+0x18/+0x1C/+0x20`.

### 6.5. Оценка роли

Совокупность (ThreadX + mailbox + DMA/flash-DMA + GPIO/GPIO3 + ADC + capture0 + clock-gate,
отсутствие прерываний и отсутствие MOVDC/DRAM) даёт картину **служебного/хаус-кипинг ядра**:
опрос mailbox, разбор команд, пересылки DMA/flash-DMA, служебные GPIO/ADC. Это согласуется с
картой fujimod (core4 = cortex-m4, companion-SRAM 1 МиБ, mailbox, clock 600 МГц) — **К**.

## 7. Сверка с сообществом (fujimod, только чтение)

* `catalog/soc/xp5/soc.json`: `processors` — core0..core3 `cortex-a53`, **core4 `cortex-m4`**;
  `memory_regions.companion-sram` base `0xFA200000` size 1 МиБ; `hardware.companion`
  `{processor_id: core4, clock_id: companion (600 МГц), vector_base: 0, mailbox_block_id: mailbox}`
  с каналами mailbox `request 55, control 58, reply 141, status 142, fault 143`;
  блок `mailbox` = `0xFF90E100`; **`reset: {"release": null}`** — механизм выпуска M4 сообществу
  неизвестен.
* `mappings[0]`: `core4: address 0 → physical 0xFA200000` — ровно наш вывод «образ слинкован от 0».
* Наш DAT подтверждает: по 0x1C0274 лежит образ с `SP/reset` в 0..0x100000, т.е. в модели
  «адрес 0 = SRAM».
* Тот факт, что сообщество тоже не нашло код запуска M4 (`release: null`), — **К** в пользу того,
  что запуск делает boot ROM/SCM, а не A53-прошивка.

| RTOS = ThreadX, потоки `System Timer Thread`, `idle`, `comm` | **Д** |
| M4 адресует периферию по алиасу 0x5Fxxxxxx (=A53 0xFFxxxxxx − 0xA0000000) | **Д** |
| M4 **не** трогает MOVDC (0x5F970000/0xFF970000) и не содержит 0x10030001 | **Д** |
| MOVDC описан таблицей дескрипторов в блоке 1 (0xFF970000/1000/2000/3000/4000/4400/4500/7000 + clock 0xFF90C300) | **Д** |
| M4 не может писать флаг 0x4C2FF14 и задание 0x4DAA6E8 (нет адресов DRAM A53) | **Д** |
| Канал M4↔A53 — mailbox 0x5F90E100; читающей стороны в блоках 0–2 нет | **Д** (отсутствие) |
| Таблица 25 команд {id,handler} — диспетчер сообщений mailbox | **К** |
| M4 обслуживает DMA 0xFF930000 и flash-DMA 0xFF939000 (пересылки) | **К** |
| M4 — служебное ядро (GPIO/ADC/DMA/mailbox), MOVDC не его | **К** |
| Значение 0x10030001 собирается кодом A53 по битам | **Г** |
| Флаг MOVDC/задание формируются на A53, M4 участвует только косвенно (если участвует) | **Г** |
| Запуск M4 — boot ROM/SCM (а не A53-прошивка), ср. `reset.release: null` у fujimod | **К** |

---

## 9. Что осталось (следующие шаги)

1. **Обратная сторона mailbox**: найти в A53-прошивке (или в Linux-хвосте) код, читающий/пишущий
   `0xFF90E1xx`. В блоках 0–2 его нет; кандидаты — префикс-загрузчик (проверено: 0), Linux (block3/хвост),
   либо mailbox вообще не используется A53 (тогда M4 общается с другим мастером).
2. **`0x10030001`**: искать в A53 коде последовательность `movz/movk`/`orr` сборки значения для
   регистра `MOVDC+0xD8` — статически это отдельная задача (в DAT значения нет).
3. **Таблица 25 команд**: сопоставить id (0x29/0x2A/0x2B/0x80/0x83/0x86/0x87/0xA8/0xA9/0xB1/0xB2/0xD0/
   0x11A/0x122/0x123/0x125/0x181..0x189) с событиями/свойствами A53 (у нас уже есть семейства
   событий 0x34B..0x361 → id 0x2AC..0x2C0, свойство 0x2B9 и т.п.) — возможно, это общий словарь.
4. **Проверка на живом ядре**: образ слинкован от 0 и SP=0xA00 — стоит подтвердить, что SRAM
   отображается в 0 (fujimod так и моделирует, `mappings[0]`).
