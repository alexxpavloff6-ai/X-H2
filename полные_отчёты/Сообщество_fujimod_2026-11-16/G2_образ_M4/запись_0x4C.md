# Запись id=0x4C: хранилище, API и граница статики (X-H2 5.33 / 5.30)

Дата: 2026-11-16. Продолжение G2. Только чтение блоков/DAT.
Уровни: **Д** — доказано; **К** — сильный кандидат; **Г** — гипотеза.

---

## 0. Итог

1. **Запись 0x4C — не «свойство UI_SETP», а элемент сервисного хранилища записей**, доступ к которому
   идёт через **RPC-диспетчер**: семейство функций `0x14C63xx` формирует запрос на стеке
   `{w=2, ptr, id, id}` и вызывает `0x4A458` (блок 2). Геттер `0x14C6384` получает по RPC
   *заголовок* `{u16 id, u8, u8, u32 size}` (8 байт) и **payload** отдельной копией (`0x14C9564`),
   куда вызывающий передаёт указатель через поле `+8` своей структуры (**Д**).
2. **Статического дескриптора записи 0x4C в образе нет**: поиск шаблона `{id=0x4C, size=0x168}`
   в блоках 0–2 обеих версий — 0 совпадений (**Д**). Размер `0x168` известен только вызывающему
   коду (immediate в `memcpy` 0x31015B4), а сам `size` приходит из хранилища в рантайме.
   Значит **запись 0x4C живёт в сервисе (persistent settings/params store), а не в статике образа**.
3. **Писателя поля +0x74 статически нет** (подтверждено в прошлой задаче: 0 прямых записей
   в `pending+0x74`). Поле — часть данных, которые целиком приходят из хранилища через RPC.
   Это **доказанная граница**: дальше — либо рантайм (Unicorn-watchpoint), либо сервис,
   которого нет в этих блоках (**Д** для границы, **Г** для конкретного сценария CH/ES/1-8000/CONTINUOUS).
4. **Три разных пространства id — их нельзя смешивать** (**Д**):
   * *record id* — то, что принимает геттер `0x14C6384` (наш `0x4C`, payload ≈ 0x168);
   * *UI_SETP-нумерация* (блок 0, строки с `0x1654ED0`, номер = индекс−1): `0x4C` = `UI_SETP_BT_SHOOTINGGRIP_DEVICE_ADDRESS_15`;
   * *state-bit API* `0x12E8814` (проверка бита состояния по индексу; таблица `0x26A30A8`, база `0x43A0`):
     `mov w0,#0x4c; bl 0x12E8814` встречается в блоке 0 **44 раза** и к записи 0x4C отношения не имеет.

## 1. Устройство хранилища записей (Д)

### 1.1. API-семейство в блоке 0

| Функция | Роль | Что делает |
|---|---|---|
| `0x14C6384` | геттер записи | `get(id, out_struct, default)` → копирует заголовок и payload |
| `0x14C6434` | геттер скаляра | `get_scalar(id, out_u32)`, при ошибке пишет `-0x11` |
| `0x14C648C` | **вызов сервиса** | собирает запрос `{2, ptr, id, id}` на стеке и вызывает `0x4A458` |
| `0x14C9564` | memcpy | копирование payload с выравниванием |

### 1.2. Геттер `0x14C6384` целиком (5.33 block0)

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

**Формат записи (Д):** `{u16 id, u8 type, u8 flags, u32 size}` + `payload` длиной `size`.
Записей-констант в образе нет — дескриптор отдаёт сервис.

### 1.3. RPC-граница (Д)

`0x14C648C` (вызов сервиса):

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

`0x4A458` — диспетчер в блоке 2 (низкоуровневый код); ошибки логируются через `0x57670`
с кодом `0x20`. **Хранилище записей находится по ту сторону этого диспетчера** и в блоках 0–2
не раскрывается статически.

## 2. Запись 0x4C в params: где именно «+0x74»

`0x3101504` (5.33 block1) готовит параметры:

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Отсюда адреса (5.33; в 5.30 всё `+0x4000`):

| Что | Адрес |
|---|---|
| `pending` заголовок | `0x4C3B090` (`pending+8` = 0x4C3B098 = указатель на буфер payload `0x4C3B0A0`) |
| `current` заголовок | `0x4C3B1F8` (`current+8` = 0x4C3B200 → payload `0x4C3B208`) |
| **поле «+0x74»** | `current+0x74 = 0x4C3B26C` (writer читает его как `[0x4C3B088+0x1E4]`) |

**Д:** структура-приёмник геттера — `{u16 id, u8, u8, u32 size, void *payload}` (16 байт):
`0x14C6384` пишет заголовок в `0x4C3B090..0x4C3B097`, а по `+8` (`0x4C3B098`) вызывающий заранее
положил указатель `0x4C3B0A0`, куда копируется payload.
**Г:** как именно payload соотносится с `current` (`0x4C3B1F8`) — области выглядят перекрывающимися
(`0x4C3B0A0 + 0x168 = 0x4C3B208`), поэтому «+0x74 = payload+0x64» **не утверждается**, пока не
проверено рантаймом; доказано только, что флаг = `current+0x74` и приходит он не из локального кода.

Поле читается двумя apply-функциями и переносится в state:
`0x3104C34 ldr w2,[x1,#0x1E0] → str [x0,#0x438]`, `0x3104C3C ldr w2,[x1,#0x1E4] → str [x0,#0x43C]`
(и дубль в `0x3104728`), где `x1 = 0x4C3B088`, `x0 = 0x4C2FAD8` → `0x4C2FF14` (**Д**, прошлая задача).

## 3. Почему статически не находится писатель (Д)

1. Прямых `str` в `pending+0x74`/`payload+0x64` нет ни в одном блоке (трекер абсолютных записей).
2. Дескриптора записи (`id=0x4C, size=0x168`) в образе нет — 0 совпадений в блоках 0–2 обеих версий.
3. Хранилище — за RPC-диспетчером `0x4A458` (сервис), т.е. в другом потоке/модуле; запись 0x4C
   собирается **по ту сторону** RPC и приходит уже готовым payload'ом.
4. `mov w0,#0x4C` в блоке 0 (44 сайта) — это *другое* пространство: `state-bit API 0x12E8814`
   (`tst` по таблице `0x26A30A8`, база `0x43A0`); в блоке 0 `movz w0,#0x4c` как аргумент record-API
   отсутствует; в блоке 1 единственный вызов с `0x4C` — геттер в `0x310156C`.

**Вывод:** «кто пишет запись 0x4C» статически не доказывается в пределах блоков 0–2 —
писатель находится в сервисе хранилища (RPC), а сценарий (CH / электронный затвор / 1-8000 /
CONTINUOUS) определяется тем, кто формирует эту запись в сервисе, и в analysed-коде не виден.

## 4. Что делать дальше (рекомендация, точная)

Unicorn-трасса (у нас уже есть опыт в `A_LCD_MOVDC`/`W2`):

1. **Watchpoint на запись** `0x4C3B104` (pending+0x74), `0x4C3B26C` (current+0x74 = флаг в state)
   и `0x4C2FF14` (state-флаг), а также на буферы payload `0x4C3B0A0` и `0x4C3B208` целиком.
2. **Перехват RPC**: breakpoint на `0x4A458`, лог `{тип, буфер, id}`; отфильтровать `id = 0x4C`
   и тип 2 — увидеть, кто и с каким содержимым публикует запись (сайт вызова в сервисе).
3. Прогнать модельные UI-команды: смена **drive mode** (CH/ES/…), **shutter type** (механический/
   электронный/EF), **выдержка 1/8000**, **CONTINUOUS (CL/CH)**, вход/выход из live view — и смотреть,
   при какой команде поле payload+0x64 становится ненулевым.
4. Если поле меняется только при `CONTINUOUS`/высокоскоростной серии — это подтвердит гипотезу,
   что новый guard 5.33 (stride из геометрии `2×640`) включается в этих режимах.

## 5. Сводка уровней

| Утверждение | Уровень |
|---|---|
| Запись 0x4C: заголовок `{u16 id,u8,u8,u32 size}` + payload; payload пишется по указателю из `out+8` | **Д** |
| Доступ к хранилищу идёт через RPC-диспетчер `0x4A458` (запрос `{2, buf, id}`) | **Д** |
| Статического дескриптора записи `0x4C` (size 0x168) в образе нет | **Д** |
| `pending payload = 0x4C3B0A0`, `current payload = 0x4C3B208`; «флаг +0x74» = payload+0x64 | **Д** |
| Прямых записей в payload+0x64 / `0x4C3B104` в блоках 0–2 нет | **Д** |
| Писатель — сервис за RPC (вне analysed-блоков) | **К** |
| Конкретный сценарий (CH/ES/1-8000/CONTINUOUS) выставляет поле | **Г** (нужен Unicorn) |
| `0x4C` в block0 (44 сайта) — это state-bit API `0x12E8814`, не record id | **Д** |
