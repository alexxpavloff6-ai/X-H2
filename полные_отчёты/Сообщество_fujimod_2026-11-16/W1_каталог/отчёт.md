## 0. Резюме

1. **Это те же прошивки.** SHA-256 наших DAT совпадают с `update.sha256` в каталоге: X-H2 5.30 `be47168c…`, X-H2S 7.30 `87c566c1…`,
   X-T5 4.31 `790d6dee…`. Значит все их числа можно сверять с нашими блоками напрямую, и я это сделал.
2. **Наш декодер DAT = их декодер.** `flash.update_image` = «DAT с offset 628, XOR 0xFF»; их контрольный чанк флеша
   (offset `0x60000`, 32 КиБ) и «configuration» (`0xC0000`, 814 080 Б) побайтово совпали с нашим `(DAT[628:] ^ 0xFF)`.
3. **Блок 0 — это модуль настроек.** `settings.source.address` = база нашего b0 (`0x1101000` для X-H2/X-T5, `0x1421000` для X-H2S),
   размер = размер b0, и **sha256 совпал с нашим b0**. Блок 1 (`0x29AE000`+`0xECC000` и т.д.) — ровно `bulk.window` у X-H2 и X-T5.
4. **Главный подарок — словарь `UI_SETP`: имя → числовой ID** для всех трёх прошивок (3435 / 3398 / 3536 имён). Набор fujimod —
   строгое подмножество имён, найденных нами в DAT (0 имён «только у них»), а порядок адресов наших строк монотонен по их ID
   (3433/3434, 3396/3397, 3534/3535) — то есть **ID = индекс в таблице имён в .rodata блока 0**. Наши частные ID подтвердились:
   FILM_SIM 1678 (X-H2) / 1699 (X-T5), STILLCOLOR 1715 / 1714 / 1742, GRAIN 262, **PERFORMANCE 1466** (X-H2/H2S) / 1426 (X-T5).
5. **Свойство `0x2B9` из отчёта E получило имя:** `UI_SETP_NETMASK_SETTING_MANUAL_1OCTET_8` (ID 697) — дословно совпало с их же
   строкой лога. Более того, всё семейство событий `0x34B…0x361` → ID `0x2AC…0x2C0` — это октеты IP-адреса и маски. Наш вывод E
   («это октет, не режим съёмки») подтверждён независимо.
6. **MOVDC — это аппаратный блок.** В карте XP5 три экземпляра `movdc0/1/2` по `0xFF970000/0xFF971000/0xFF972000` (+ reset
   `0xFF973000`), в эмуляторе — «MOVDC output DMA» (packed422). Это объясняет, почему мы не нашли потребителя дескриптора
   `{height,width,stride}` в блоках 0–2: потребитель — DMA по MMIO (уровень К, см. §2 S1).
7. **Переписать прошивку они не умеют — они грузят код в RAM.** В каталоге нет ни одного факта о записи во флеш; зато есть
   `bulk.upload` (штатный приём буфера в RAM: `0x38F04F0`, куски по 64 КиБ, выравнивание 32) и `restart` (перезагрузка по USB через
   консольный callback). Наш вывод «изменённый DAT камера не примет» ничем не опровергнут.
8. **Для XP5 у них нет восстановления.** `recovery/processors.json` покрывает xp4/exr/exrpro/xpp, но не xp5; green-led не содержит
   X-H2/X-H2S/X-T5; generation пишет «no service-workflow locator for X-Processor 5» и «XP5 has no card mechanism».
9. **Новых версий у них нет.** `firmware-versions.generated.json` (57 релизов) заканчивается на 5.30 / 7.30 / 4.31
   (внутренние 3.51 / 3.64 / 2.14); 5.33 / 7.31 / 4.32 не упоминаются ни в файлах, ни в истории коммитов.
10. **У них есть слой, которого у нас не было:** карта MMIO XP5 (72 блока, GICv3, 4×A53 + сопроцессор Cortex-M4 с mailbox),
    JEDEC/модели NOR-чипов, именованные ID органов управления (сканер + 264 debug-команды), резервирования DRAM и полный словарь
    имён свойств. Взамен у нас есть то, чего нет у них: перечисления `MODE_RECORD`/`MODE_CONTINUOUS`/`DRIVEMODE_BKUP`,
    пространство `KEY_*`/ID > `UI_SETP_MAX`, разбор патчей 5.33/7.31/4.32.

## 1. Что в fujimod есть по теме

### 1.1 Как устроен каталог

`catalog/README.md:7-20` — четыре слоя, у каждого факта один владелец: `soc/<id>/` (карта SoC), `bodies/<id>/` (железо тела),
`firmware/<тело>/<версия>/` (идентичность прошивки + «generated facts»), `../configurations/emulator/<id>/` (конфигурация запуска).
`catalog/README.md:22-34` — `firmware-versions.generated.json` сопоставляет публичную версию, внутреннюю (BCD) и SHA-256 обновления;
bulk-профили ключуются релизом. `catalog/README.md:36-47` — тело может содержать только `controls.json` (мануал), а необязательный
блок `boot` описывает комбинации `sd` / `firmware_update` / `service`.
`catalog/README.md:61-68` — схемы и TypeScript/Python-типы генерируются из Rust-структур (doc-комментарии становятся описаниями),
CI проверяет схемы и валидность документов; `:78-79` — модули `exr2/xp4/xp5` остаются в корне крейтов.

Крейты `catalog*` — это **валидаторы и загрузчики**, а не извлекатели: они описывают формат (serde-структуры → схемы) и проверяют
инварианты (`crates/catalog/src/*.rs`, `crates/catalog-schemas/src/lib.rs:100-300`). Публичный извлекатель для XP5 в репозитории один —
`crates/corpus/src/locators/flash.rs` (см. 1.3); остальные факты для наших камер публиковались внешним конвейером (коммиты
«Publish …», журнал — `catalog/generation.generated.json`).

### 1.3 Как это извлечено из DAT (код, сигнатуры, адреса)

**(а) Чтение флеша — единственный публичный XP5-локатор.** `crates/corpus/src/locators/flash.rs:227-333`:
- `flash_read` ищется по наличию в рутине `str x0,[sp,#0x10]; str x1,[sp,#0x18]; str w2,[sp,#0x20]; str w3,[sp,#0x24]; ret`
  (`:255-265`); сначала берётся рутина, уже названная `flash_read` в их индексе, иначе — по сигнатуре (`:266-270`);
- окно флеша — 3-инструкционная рутина `mov x1,#0xf0000000; add x0,x0,x1; ret` (`:272-282`);
- «read request» обязан содержать `mov x0,#0xf8000000`, `mov w0,#0x7ffffff`, `movk w0,#0x7766,lsl#16`, `mov w0,#0x6555`,
  а вызываемый диспетчер — маску `#0x3f` (`:283-310`);
- дальше по вызовам находятся DMA-читатель, 16-инструкционная функция обслуживания кэша (`orr x0,x0,x1` / `mov w0,#0`) и выбор банка
  (`:311-333`); JEDEC-идентичность берётся из таблицы поддерживаемых чипов в самой прошивке (`:406-485`); окно жёстко
  `0xf0000000`/`0x8000000`, `update_image = {dat_offset: image_origin, xor: 255}`, `control` = 32 КиБ по `control_offset` (`:494`).

**Проверено на наших DAT** (`s7_сигнатуры_flash.py`): X-H2S 7.30 b0 — `flash_read` @`0x16A4B50` действительно `stp/mov/str…/ret` и
вызывает request @`0x16A48A4`, в котором есть все четыре маркера (`#0xf8000000`, `#0x7ffffff`, `#0x7766`, `#0x6555`), диспетчер
@`0x16A41BC` содержит `ands …, #0x3f`; window-рутина найдена по адресу **`0x16A4CB0`**, у X-T5 — **`0x1385148`**. Адреса в
`flash.generated.json` совпали с нашими один в один.

**(б) Настройки.** `settings.generated.json` = «Located settings bank and named settings for one firmware». `source` — method-4
кодированный раздел установленного образа флеша; для наших камер это **целый блок 0** (X-H2S: `address 0x1421000`, `size 12015376`,
`sha256 a32a90b7…`; X-T5: `0x1101000`, `11743456`, `fd5f8992…`). `configuration` — окно образа, которое штатный инициализатор
копирует в стёртое хранилище конфигурации (`flash_offset 0xC0000`, `bytes 814080`). При этом `defaults: null`, `sections: []`,
`settings: {}` — т.е. **список настроек в этом файле пуст**, он даёт только расположение банка. Локатор банка в публичный
репозиторий не входит (в `crates/` есть только валидатор `crates/catalog-settings/src/lib.rs`).

**(в) Имена UI.** `ui-setting-names`/`ui-scene-names` — «records each firmware's stock setting-name table … and their IDs».
Коммит **3e8d8926** «Publish stock setting names per firmware in the catalog» (Jake Teton-Landis, 2026-11-05); коммит **413be4a9** —
«scene names … located by running the firmware's own scene-name function» (Co-Authored-By: Claude Opus 5.5). Механизм: перебор
ID 0…`UI_SETP_MAX` и вызов штатной функции имени; пустые слоты не публикуются (отсюда 35 «дыр» у X-H2S и X-T5). Наши проверки
(§2 U2) показывают, что ID = порядок строк в .rodata блока 0, поэтому таблицу можно собрать и статически — без запуска кода
камеры/эмулятора.

**(г) `state`.** «Safely readable regions captured as camera state»; порядок обхода, регистры с побочными эффектами исключены.
У наших камер регион один и тот же: `dram` 0..размер тела и `boot-rom` `0xFF800000` +256 КиБ `constant:true`. При этом
`generation` пишет `xp5: no established safely readable boot ROM extent` — то есть boot-rom объявлен по карте SoC, а не снят.

**(д) `flash`.** «Stock flash-read contract»: устройство (`serial-nor`, JEDEC, модель), окно CPU `0xF0000000`/128 МиБ, `e1_window`
то же, `update_image`, `reader` (`flash_read`, alignment 64), `transport: xp5-cmd-callback`, диапазоны кода, `state_checks`
(живые предусловия: «flash driver initialized», `0x2371880` = `0x77666555` для X-H2S) и `control` — начальное чтение из образа
обновления (сверено, см. F4).

**(е) `memory-reservations`.** «Located fixed DRAM reservations»: `main_heap`, `font_library`, `language_fonts`; `locator_failures`
перечисляет несработавшие локаторы (у X-H2S пусто).

**(ж) `restart`.** «The stock power-off request with a wake deadline»: power-off ставит будильник power-controller и режет питание,
будильник снова включает камеру. Для X-H2S: `internal_version 3.64`, консольный callback в слоте `0x236F460`, `request 135`,
stub в неиспользуемой исполняемой области `0x210000` (64 Б), `ready_words`, трансляция указателей, `power_off` (`0x31A05D8`,
power_cut `0x169FFD0`), будильник 37/38 с, `boot_flag` `0x2882C9C` бит 5. Коммиты **807d74f3** (документ), **b8681802** (boot flag,
PR #295), описание PR #289 (тело X-H2S, Azoof Ahmed, 2026-11-13/14).

**(з) `bulk`.** «Located bulk-read mechanism and capture scopes». `source.mechanism: pattern_zero_base` — штатная диагностическая
подготовка указывает 32-битный источник на зарегистрированную диагностическую царапину, смещения заворачиваются от её базы
(схема `bulk.generated.schema.json`, oneOf[2]). У X-H2: `registered_buffer 0x38F04F0`, `source_state 0x3F3E038`,
`configuration_pointer 0x20C1458`, `system_mode_address 0x2730270`, окно = блок 1. У X-H2S окно — вся RAM `0x4000…0x80000000`,
scopes `quick` (69 189 632 Б от `0x4000`) и `full`. `upload` — «Located stock E0 upload destination»: `pointer`, `capacity_address`,
`piece_bytes 65536`, `address_alignment 32`, и проверки кода (`bulk_upload_command/data/complete/setup/dispatch/le32`);
`bulk_upload_le32` у X-H2 и X-H2S имеет **одинаковый** SHA-256 — хороший пример их кросс-модельной проверки.

**(и) `control-ids`.** «Generated firmware input facts, separate from the body's declarations»: `scanner` (base, count, stride 40,
lookup), `event_translation` (stride 12, physical_key → event), `debug_keys` (264 именованных команд), `inputs` (X-H2S 94, X-T5 120:
33/47 привязаны к органу, остальные `unclaimed`), `undelivered_rows`, `interfaces`.

**(к) `progress`.** Матрица «что снято»: треки `static` / `emulator` / `camera` / `fujimod` / `sd`, стадии с `pass/stale/not-run/
inapplicable`. Для X-T5: `facts 17/18`, статические стадии `bulk-source`, `flash-reader`, `state-regions`, `restart-facts`,
`card-files`, `controls`, `settings-layout` — **stale**; в треке `camera` пройдена только идентификация по FF80, а `camera-mods
(FujiMod runs from RAM)` — `not-run`.

### 1.5 `generation.generated.json` — журнал прогона генератора

По каждому `firmware_id` перечислены таблицы со статусом `available/unavailable` и причинами (`locator` + `reason`). Для наших
камер (строки 4600 / 4718 / 8093) это самый честный источник «чего у них нет»:

- `xh2-530`: доступны только `bulk`, `ui_setting_names`, `versions`; `controls/flash/restart/settings/state/progress/first-start/
  service/card-files` — unavailable с конкретными ошибками (см. 1.2).
- `xh2s-730`: доступны `bulk, controls, restart, settings, ui_setting_names, versions`; `flash` в журнале помечен unavailable
  («mapped loader missing»), хотя `flash.generated.json` опубликован отдельным коммитом 0a0b750d — т.е. журнал и публикация
  расходятся (см. §2 V5/примечание).
- `xt5-431`: доступны `bulk, controls, settings, ui_setting_names, versions`; `flash` — `publication_error: empty state capture`,
  `restart` — нужен запущенный экземпляр (arena, translation root, cache-ready words, UI cell).

### 1.6 `soc/xp5/soc.json` — карта X-Processor 5

- Процессоры: `core0..core3` Cortex-A53 + **`core4` Cortex-M4** («companion», 600 МГц, mailbox `0xFF90E100` с регистрами
  request 55 / control 58 / reply 141 / status 142 / fault 143; `companion-sram` `0xFA200000`, 1 МиБ; три mapping окна M4).
- GICv3: distributor `0xFA000000`, redistributor `0xFA080000`, stride `0x20000`, 512 линий; физ. таймер IRQ 30, вирт. 27.
- DRAM: `0..body_dram` (размер — свойство тела). SRAM: companion `0xFA200000`, boot `0xFF800000` (256 КиБ).
- 72 блока MMIO, в т.ч.: `flash-aperture 0xF0000000` (128 МиБ), `flash 0xFF90A000`, `flash-dma 0xFF939000`,
  `clock-gates 0xFF90C000`, `power-gates 0xFF90D000`, `clock-banks 0xFFA00000`, `dma 0xFF930000`,
  `renderer 0xFF93C000`, `sensor 0xFF948000`, `receiver0/1 0xFF940000/0xFF941000`, `phy 0xFF944000`, `input 0xFF946000`,
  `input-reset 0xFF950000`, **`movdc0/1/2 0xFF970000/0xFF971000/0xFF972000` + `movdc-reset 0xFF973000`**,
  `preview 0xFF974000`, `paf 0xFF976000`, `lz 0xFF980000`, `resize 0xFF982000`, `display0 0xFF990000`, `display1 0xFF9A0000`,
  `statistics 0xFF800000` (60 224 Б), `rifp 0xFFD02000`, `gpio 0xFF907000`, `gpio3 0xFF90B000`, `pin-control 0xFF904000`,
  `temperature 0xFF905000`, `adc 0xFF906000`, `timer/extended 0xFF908000/0xFF909000`, `i2c1 0xFF925000`, SPI0/3/4/5/8/9,
  `capture0/1 0xFF928000/0xFF929000`, `output-link 0xFF9A1000`, `pixel-pll0..3 0xFFA11..0xFFA14`, `mailbox 0xFF90E100`,
  `dma-routes 0xFF90E500`, `dma-address-high 0xFF90E748`, `reset-handshake 0xFF91C000`.
- Профиль `hardware.profiles.xp5`: 103 «окна» с поведением (timer, flash-storage, display-output-link, imaging-*, panel-pll,
  `movdc`, `interlace…`), плюс записываемые «configuration group» регистры `0xFAE00020…` (write-only).

**Как это ложится на наши адреса.** `0x4C2FF14` / `0x4C33F14` (флаг MOVDC), `0x4DAA6E8` (задание съёмки), `0x27008000` (блоб
параметров), кольцо видео `0x3C999000/0x40999000/0x44999000` — всё это внутри DRAM (база 0), т.е. **не MMIO**; их карта SoC
ничего о DRAM-раскладке не говорит (кроме размера тела). Зато MMIO-карта даёт то, чего у нас не было: имена и адреса блоков,
которые могут быть «внешними» потребителями (MOVDC, statistics, PAF, preview, resize, lz, display, ISP-приёмники).

### 1.7 `CONTROL_MECHANISMS.md`

Это обзор **механики** относительных дисков/качалок: 49 тел, 108 органов, страницы мануалов, классификация «dial / rocker»,
проверка связей GPIO/энкодеров. Для наших тел: X-H2 — 3 диска (`front_command_dial`, `rear_command_dial`,
`diopter_adjustment_control`), X-H2S — те же 3, X-T5 — те же 3; у всех **«No located connection»**
(`catalog/CONTROL_MECHANISMS.md:75-80,131-133`). Про меню, настройки и свойства в документе нет ничего — к нашей «системе свойств»
и пути «меню → настройка → код» он не добавляет; добавляет только: (а) какие органы физически вращаются/качаются,
(б) страницы мануала, (в) что электрическая реализация у X-H2/X-H2S/X-T5 у них не локализована.

## 3. Новое, чего у нас не было

1. **Полный именованный словарь `UI_SETP` для трёх камер** (3435 / 3398 / 3536 имён) и правило «ID = порядок строк в .rodata b0».
   Это позволяет подписать *любой* вызов `property_getter/setter` с ID ≤ `UI_SETP_MAX` (у нас в отчётах E/D это были «свойство 0x2B9»,
   «свойство 0x876» без имён).
2. **`UI_SETP` ID — это и есть ID свойства в диспетчере блока 0** (по крайней мере для 0x2B9: имя + ID + строка лога совпали).
   Отсюда: семейство `0x2AC…0x2C0` = октеты IP/маски, а не «режимы».
3. **Метаданные свойств:** вид (`REC/PLAY/MENU/PCSH/PEER/OTHER`), направление (`SYSTEM/UI_VALUE/REC_INPUT/PCSH/BACKUP`) и операции
   `VAL_MAX`, `VAL_PREV_GET`, `VAL_BACKUP_GET`, `VAL_IGNORE_SET` — готовая модель «как свойство читается/пишется/сохраняется».
4. **Карта MMIO X-Processor 5**: 72 блока, GICv3, 4×A53 + **Cortex-M4 companion** с mailbox (`0xFF90E100`, IRQ 55/58/141/142/143)
   и тремя отображениями; блоки MOVDC, statistics, PAF, preview, resize, lz, display0/1, ISP-приёмники, PLL, GPIO/I2C/SPI.
5. **MOVDC — аппаратный output DMA** (packed422), три экземпляра; это правдоподобный потребитель дескриптора `{height,width,stride}`
   из нашей правки A.
6. **Размеры DRAM:** X-H2S 2 ГиБ, X-T5 1.5 ГиБ — и то, что у X-T5 он взят из Linux device tree (блок 3), а не из кода.
7. **JEDEC/модели NOR-чипов** (`0x2C5B1B`/MT35XU01GBBA, `0x20BB20`/MT25QU512ABB) и контракт чтения флеша по `xp5-cmd-callback`.
8. **`bulk.upload`** — штатное E0-назначение для загрузки кода в RAM (указатель, ёмкость, куски 64 КиБ, выравнивание 32) с
   проверками кода; `bulk`-окна и scopes (`quick`/`full`), probes и `mapped_probe`.
9. **`restart`** как штатный механизм: консольный callback в слоте, request 135, stub в свободной исполняемой области,
   будильник power-controller, boot flag; `internal_version` 3.64.
10. **Резервирования DRAM** (`main_heap`, `font_library`, `language_fonts`) — важное для модов «не занять чужую память».
11. **Слой органов управления:** таблица сканера (stride 40), перевод `physical_key → event` (stride 12), 264 debug-команды,
    94/120 входов; у X-H2S одна недоставленная строка (`undelivered_rows`).
12. **Матрица зрелости** (`progress`) и **журнал генератора** (`generation`) — можно точно сказать, какие их факты «stale»
    и что ещё не проверено на камере (для X-T5: почти всё, кроме идентификации по FF80).
13. **Ограничения их охвата:** нет XP5-recovery, нет service/card-files/first-start для XP5, нет enum'ов, нет пространства `KEY_*`,
    нет новых версий 5.33/7.31/4.32.

   X-T5 `0x60000000`) по нашему коду.
9. **Проверить резервирования** `main_heap 44 866 640` / `font_library 663 347 200` / `language_fonts 16 121 856` (X-H2S):
   наши глобалы `0x4C2FF14`, `0x4DAA6E8`, блоб `0x27008000` в них не попадают, но проверить, что наши буферы (кольцо видео
   `0x3C999000…`) не пересекаются с `font_library`/`main_heap` — важно для любого мода.
10. **`0xFF800000`:** выяснить, boot ROM это или `statistics` (у них противоречие) — посмотреть, что читает/пишет наш код по
    `0xFF800000` и есть ли там imaging-статистика.
11. **Сверить `flash_read`-путь с нашими исследованиями USB:** у них `transport: xp5-cmd-callback` (команда через callback),
    `state_checks` «flash driver initialized» = `0x77666555`. Найти этот маркер (`0x77666555`) в наших блоках и связать с
    нашим USB- bulk (какие команды реально шлёт камера).
12. **Обновить наш отчёт E и D именами свойств** и зафиксировать, что `0x2B9` — октет маски, а не режим; в `F` — что
    `MODE_RECORD_HDR` = 0x2C и свойство `0x876` = `UI_SETP_DRV_MENU_HDR` (для X-H2).

## 5. Как воспроизвести и что лежит в папке

Все скрипты — только чтение; запуск обычным `python`. Пишут только в эту папку.

| файл | что делает |
|---|---|
| `s1_soc_карта.py` → `s1_soc_карта.txt` | сводка `soc/xp5/soc.json`: регионы, 72 блока MMIO, профиль окон, M4-mailbox |
| `s2_control_ids.py` | структура `control-ids.generated.json` для X-H2S/X-T5 |
| `s3_сверка_имён.py` → `s3_сверка_имён.json` | сверка словарей `UI_SETP`/`UILIB` fujimod с именами из наших DAT (таблицы совпадений) |
| `s4_порядок_id.py` | монотонность адресов наших строк по ID fujimod, дыры ID, имена сверх словаря |
| `s5_сверка_фактов.py` → `s5_сверка_фактов.json` | identity DAT, `settings.source` vs наш b0, `bulk.window` vs b1, контрольный чанк флеша, `code_checks` restart |
| `s6_схемы_описания.py` | вытаскивает описания полей из схем каталога (смысл каждого файла) |
| `s7_сигнатуры_flash.py` | проверяет сигнатуры XP5-flash-локатора на наших блоках (дизассемблер) |
| `s8_config_progress.py` | `settings.configuration` vs наш образ флеша; разбор `progress/xt5/4.31` |
| `s9_различия_моделей.py` | различия наборов имён и органов, покрытие XP5 в `firmware-versions`, recovery |
| `s10_сопоставление.py` → `сопоставление.json` | машиночитаемая таблица §2 (26 записей) |

Ключевые результаты, на которые опирается отчёт: `s3_сверка_имён.json`, `s5_сверка_фактов.json`, `сопоставление.json`.
