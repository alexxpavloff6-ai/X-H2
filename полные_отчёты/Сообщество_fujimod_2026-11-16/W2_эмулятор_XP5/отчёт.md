## 0. Главное в десяти пунктах

1. **XP5 у них — это SoC-модель**: 4× Cortex-A53 (`core0..3`) + 1× Cortex-M4 (`core4`, «companion»), GICv3 на 512 линий,
   `MIDR_EL1 = 0x410fd034` (A53 r0p4), тикающая база 1 ГГц. `catalog/soc/xp5/soc.json:6–47, 978–1013`.
2. **Прошивка грузится из DAT**: NOR-апертура `0xF0000000` (128 МиБ), `dat_origin = 0x274`, `xor = 0xFF`; в RAM — два
   сжатых раздела (`method4`/LZ, страница 0x4000) и один сырой loader. Для X-T5 4.31: блок 0 → `0x1101000`,
   блок 1 → `0x28EB000`, loader → `0x40000`; вход в `EL1t` по `0x5847C`.
   `crates/emulator-xp5-bringup/data/xt5-431/streams.json:4–32`, `.../manifest.toml:1–31, 157–256`.
3. **Наши блоки совпали побайтово.** SHA-256 наших `blocks/X-T5_4.31_b0` и `b1` равны `stream-00300274`/`stream-00820274` из их
   раскладки; DAT X-T5 4.31 (`790d6dee…`), X-H2S 7.30 (`87c566c1…`) и X100VI 1.31 (`0d48d2ae…`) совпали с их каталогом по
   размеру и SHA. **51 из 51** их `code_checks` (17 X-T5 + 17 X-H2 + 17 X-H2S) совпал с байтами наших блоков.
   См. §5, `сверка_вывод.txt`.
4. **«Две ОС» подтверждается и уточняется.** RTOS (ThreadX) живёт в нижних 1 ГиБ (`0x0..0x4000_0000`), Linux — с
   `0x40000000` (X-T5: `mem=256M` по их DTB; X100VI: 366 МиБ; X-E5: 366 МиБ), выше — общие арены
   `AMP 0x56E00000`, `rpmsg 0x66D00000`, `ISGC 0x66E00000` (X-E5 DTB) и «virtio/IPC/shared arenas» (X100VI).
   То есть межОСный обмен у них — **shared memory + rpmsg/virtio**, а не только регистровый mailbox.
   `catalog/bodies/xt5/body.json:73–82`, `.../x100vi/body.json:323–327`, `configurations/emulator/xe5-112/run.json:11–14`.
5. **Межпроцессорный обмен A53↔M4** — регистровый mailbox `0xFF90E100`: 8 слов payload (`+0x00..0x1C`) и cause-регистр
   `+0x20` (W1C); биты cause 0/3 → INTID 55/58 в M4, биты 4/5/6 → INTID 141/142/143 в A53. Payload — «opaque transport»,
   команд не разбирают. `crates/emulator-xp5-io/src/mailbox.rs:1–4, 70–120`, `catalog/soc/xp5/soc.json:1001–1013`.
6. **MOVDC у них — packed422 output DMA**, а не «LCD-модуль»: регистры `+0x18` (size: `w` биты 0..10, `h` 16..26),
   `+0xc0/+0xc4` (адрес, 3+32 бита), `+0xd0` (**stride**), `+0xe0/+0xe4` (cause/W1C), `+0xe8` (маска), `+0xf0` (mode=0xB),
   `+0xd8` (=0x10030001), выход — только packed 4:2:2. Наши «stride = 2 × 640 = 1280» — это ровно 640 пикселей × 2 байта
   в строке, т.е. кадр 640×480 YUV422. Уровень нашей гипотезы «кадр детекции/АФ» повышается до **К**.
   `crates/emulator-xp5-imaging/src/imaging_work.rs:1–3, 106–127`.
7. **Ничего из «наших уникальных» тем у них нет**: поиском по всему клону (rs/json/toml/md) не найдено
   `pm_dec` (0), `CSDROB` (0), `0x4daa6e8` (0), `155bde0` (0), `0x19155` (0), `MODE_RECORD` (0), `lens_id`/`lensId` (0),
   `0x411` (1 совпадение, и то в SDHCI-тесте). Это и есть «границы общего знания» по нашим вопросам.
8. **До экрана съёмки XP5 не доходит**: у X-T5 4.31 и X100VI 1.31 в их каталоге `rec`, `menu`, `stock` — `not-run`
   (`catalog/progress/xt5/4.31/progress.generated.json:204–229`, `.../x100vi/1.31/...`), тогда как у эталонного X70
   `rec=pass, menu=pass`. Модель есть, загрузка «в приложение» есть, REC — нет.
9. **AF не эмулируется**: блок `PAF` (`0xFF976000`) — только завершение сброса/готовность (`+0x00` бит 16), в комментарии
   прямо: «PAF reset completion … **not a phase-detection algorithm**». `crates/emulator-xp5-imaging/src/imaging_paf.rs:1–2`.
   Фокус и диафрагма — счёт импульсов + датчик home (для встроенного объектива X100VI) или шаговые моторы с объявленной
   механикой (для сменного X-mount).
10. **Boost/Performance не эмулируются**: есть только имена/ID настроек (`UI_SETP_PERFORMANCE = 1466`,
    `UI_SETP_FUNC_PERFORMANCE = 1470`, `UI_SETP_LCD_CUSTOM_BOOST = 2048` в X-H2 5.30), ни частот, ни ветвей кода.
    `catalog/firmware/xh2/5.30/ui-setting-names.generated.json:2591–2595`.

## 1. Что в fujimod есть по теме

### 1.1 Как устроен эмулятор (чтобы понимать вес их утверждений)

- Это Rust-воркспейс (~120 crates), два движка: **Unicorn** (Cortex-R5F/AArch64) и **Hypervisor.framework** (AArch64).
  У XP5 в профиле `engines: ["unicorn", "hypervisor"]`, шина 1 ГГц тиков. `catalog/soc/xp5/soc.json:1694–1702`.
- Запуск «строгий» (`Mode::Strict`): любое неописанное MMIO-обращение **останавливает** прогон; есть режим `Discovery`,
  который затеняет и записывает обращения. `crates/emulator-xp5-bringup/src/run.rs:183–187, 366–401`.
- Модель собирается из «окон» устройств (kind → конструктор), список kind'ов — `crates/emulator-xp5-board/src/board/mod.rs:557–638`
  и `catalog/soc/xp5/soc.json:1026–1693` (профиль `xp5`).
- Важная оговорка про охват: в CRATES.md сказано «**The extension links no XP5 model**» — XP5 не входит в Python-расширение,
  т.е. гоняется только нативным CLI. `crates/emulator/CRATES.md:410–415`.
- README эмулятора при этом всё ещё пишет «catalog boot currently supports X70 / x70-110»
  (`crates/emulator/README.md:3–5`), но код CLI уже разводит `RunInputs::Xp5` в отдельный путь
  (`crates/emulator-cli/src/bin/fujimod-emulator.rs:277–285`). Т.е. README отстал от кода — это стоит учитывать,
  если кто-то будет читать только README.

### 1.3 Цепочка загрузки XP5 в их понимании

```
boot ROM (64 КиБ @ 0xFFF00000, EL3, MMU off, MPIDR 0..3)       rom_start.rs:18–34
   └─ карта SD / внутренний NOR → stage-one «marble_init.bin» (setup DRAM)
        └─ loader: сырой образ, грузится в RAM (X-T5 0x40000, X100VI 0x81000)
             └─ EL1t hand-off (X-T5 0x5847C, X100VI 0x9920C)
                  └─ «приложение»/RTOS: разделы из DAT (settings/код, приложение)
                       └─ Linux-образ в каверне 0x40000000 (в эмуляторе не исполняется) + shared arenas
```

- ROM: 64 КиБ по `0xFFF00000`, SHA-256 зафиксирован (`41d68e8c…`), запуск EL3, `PSTATE 0x3CD`, страпы `0xFF90E000`
  (биты 2:1 = 00 → SD, бит 0 — direct flash / page cache). `crates/emulator-xp5-bringup/src/rom_start.rs:18–40`, `rom-start.toml`.
- Файлы SD-boot для XP5: `marble_init.bin` + `ffboot.bin`; `ffboot.bin` — «всё, что устанавливает обновление, распакованное
  с наложенными оверлеями». `crates/recovery/README.md:34–42, 125–145`.
- Второе ядро и далее отпускаются записью `0xF0F0F0F0`: X-T5 `0x5EAEC/0x5EAF0/0x5EAF4`, X100VI `0x9FB2C/0x9FB30/0x9FB34`
  (`manifest.toml:184–244`, `x100vi…/manifest.toml:190–241`).
- `VBAR_EL1` = `0x59800` (X-T5) / `0x9A800` (X100VI), `SCTLR_EL1 = 0x30D00800`, `CPACR_EL1 = 0x300000`,
  `ICC_PMR_EL1 = 0xFF`, обе группы EL1 включены. `catalog/firmware/xt5/4.31/firmware.json:21–105`.
- RAM: X-T5 — 0…1 ГиБ + 1…1.5 ГиБ (Linux+арены) + M-core SRAM `0xFA200000` (1 МиБ);
  X100VI — 0…1 ГиБ, 1 ГиБ…1.625 ГиБ, DDR PHY RAM `0xFB000000`/`0xFB400000` по 0x1A0000, M-core SRAM, boot SRAM
  `0xFF800000` (256 КиБ). `xt5-431/manifest.toml:8–24`, `x100vi-131/manifest.toml:8–50`.

## 2. Ответы на «Что выяснить»

### 2.1 Пункт 1. Как запускают прошивку XP5

**Загрузка из DAT.** DAT открывается как «инвертированный» (`invert()` = XOR 0xFF) и режется по объявленной раскладке;
сжатые разделы — собственный LZ «method4» (заголовок: unpacked, packed, pages, page_size=0x4000, method=4), сырые — как есть.
`crates/firmware/src/lib.rs:96–131, 276–307`; `crates/emulator-xp5-bringup/src/firmware.rs:52–78, 82–108, 110–131`.

**Что и куда грузится (X-T5 4.31)** — `data/xt5-431/streams.json`:

| Раздел | Смещение в DAT | Адрес в RAM | Размер | Кодировка |
|---|---|---|---|---|
| `stream-00300274` | `0x300274` | `0x01101000` | 11 743 456 | method4 |
| `stream-00820274` | `0x820274` | `0x028EB000` | 15 446 016 | method4 |
| `loader-00060274` | `0x060274` | `0x00040000` | 123 520 | raw |

**X100VI 1.31**: три сжатых раздела (`0x1402BC→0x881000`, `0x9C02BC→0x11C1000`, `0x10E02BC→0x2B8F000`), loader
(`0xC02BC→0x81000`) и `boot-setup` (`0xABC→0xFF800000`, 73 728 Б, первые слова — `b +0x50; nop; adrp/br`).
Плюс один «ленивый» оверлей в `verification` (`0x1A202BC`, 15 278 080 Б), который декодируется и хэшируется, но **не грузится**.
`data/x100vi-131/streams.json:4–54`.

**Сверка с нами.** Наши блоки X-T5 4.31 b0/b1 — те же байты (SHA совпал), а loader `0x60274` — это **четвёртый FFLZ-контейнер**,
которого в нашем `blocks/index.json` нет (наш распаковщик искал только контейнеры с `usize>0x10000` и `packed<=usize`, а loader
записан «сырым» блоком с заголовком `{0, 0, base, 0, size}`). Проверено: при инверсии DAT по `0x60274` лежат слова
`0, 0, 0x40000, 0, 0x1E280` — т.е. `base=0x40000, size=0x1E280`, что совпадает с их адресом и размером (§5, п.4).

**Вывод по нашей схеме «две ОС, четыре FFLZ-блока».**
- «Четыре FFLZ-блока» — это свойство **контейнера обновления** (наш счёт), а не загрузки. У fujimod в загрузке X-T5
  участвуют **три** образа: settings/код, приложение, loader. Наши блоки 2 (`0xF20274`) и 3 (`0x24A0274`) в их раскладке
  отсутствуют — вероятно, это ресурсные/оверлейные банки, читаемые позже (у X100VI аналог отнесён в `verification`). **К**.
- «Две ОС» — **подтверждается**: RTOS в нижнем ГиБ, Linux выше `0x40000000`, обмен через shared arenas/virtio/rpmsg
  (§0.4). Но у них это «память + DTB», а не исполнение Linux: Linux-образ они не грузят и не запускают.
- Ядер: **5** (4×A53 + M4), а не «два процессора». Два *мира* (RTOS и Linux) делят 4 A53.

**Межпроцессорный обмен.** Два независимых канала:
1. **A53 ↔ M4**: mailbox-регистры (`0xFF90E100`), 8 слов payload + cause W1C, INTID 55/58 → M4 и 141/142/143 → A53.
   Пейлоад не интерпретируется. `crates/emulator-xp5-io/src/mailbox.rs`.
2. **RTOS ↔ Linux**: общие арены. Для X-E5 вендорский DTB прямо называет `AMP 0x56E00000`, `rpmsg 0x66D00000`,
   `ISGC 0x66E00000`; для X100VI — «virtio/IPC/shared arenas» до `0x68000000`; для X-T5 — Linux 256 МиБ +
   арены `0x50000000+0xFF00000` и `0x5FF00000+0x100000`. `configurations/emulator/xe5-112/run.json:11–14`,
   `x100vi-131/manifest.toml:12–16`, `xt5-431/manifest.toml:12–20`.

> Для нашего вопроса «кто формирует задание съёмки `[0x4daa6e8]` — другое ядро?» это даёт **направление**, но не ответ:
> у fujimod нет ни `0x4daa6e8`, ни разбора rpmsg-команд. Канал «другая ОС» существует и назван (`rpmsg`), но какая
> структура едет по нему — не их знание. Уровень: **Г** (моя интерпретация), проверять у нас.

### 2.2 Пункт 2. Карта периферии и сопоставление с нашими находками

Карта — §1.4. По каждому нашему пункту:

**(а) Модуль MOVDC и stride дескриптора 640×480 — САМОЕ СИЛЬНОЕ СОВПАДЕНИЕ.**
У них MOVDC = «packed422 output DMA»: регистр размера `+0x18` упакован как `(h<<16)|w` (по 11 бит), адрес `+0xC0/+0xC4`,
**stride `+0xD0`**, режим `+0xF0 = 0xB`, обязательный `+0xD8 = 0x10030001`; выход — только packed 4:2:2; программный
ring не поддерживается; «второй запрограммированный адрес остаётся непрозрачным». `crates/emulator-xp5-imaging/src/imaging_work.rs:1–3, 106–127`.
Статическая опора — X-T5 `0x144BE74 / 0x144CACC / 0x144D118`, IRQ 171/172/173, reset-бит 0 общий с `0xFF973000`.

Наше: дескриптор `{height, width, stride}`, при `flag≠0` stride берётся из геометрии `2 × 640 = 1280`
(`Сравнение_версий_2026-11-16/A_LCD_MOVDC/отчёт.md:33–48`). Для packed422 кадр шириной 640 пикселей — это ровно
`640 × 2 = 1280` байт в строке. **Наше «2×640» перестаёт быть странностью и становится байтами-на-строку YUV422.**
Плюс их «packed422» объясняет, почему stride вообще связан с шириной, а не с произвольным выравниванием.

**(б) Кольцевой буфер H.265 `pm_dec` (3×64 МиБ, базы `0x3C999000/0x40999000/0x44999000`).** Не найдено. В XP5-крейтах
нет ни видео, ни кодеков: `grep` по `emulator-xp5-*` для `movie|video|codec|encoder|ProRes|H.26` — 0 совпадений.
H.264-модели есть только для старых процессоров (`emulator-exr2-isp-output/src/avc.rs`, `emulator-xpp/src/h264.rs`),
JPEG — только X-Processor Pro/4 (`crates/emulator-ip/src/jpeg.rs:1–3`). Наш H.265-разбор остаётся уникальным; **границы их знания**.

**(в) Блок OFFSET / уровень чёрного (CSDROB).** Не найдено (`CSDROB` — 0, `0x19155` — 0). У них уровень чёрного —
это **данные тела/RAW**, а не ISP-блок: `black` приходит из FujiIFD-тега `0xf00a` (36 int32, у X70 все равны) или
объявляется калибровкой тела; для X30 упомянуто «still black 0x400». `crates/emulator-image-processing/src/scene/raf.rs:100–252`,
`.../image-processing/src/raw.rs:42–44`. Т.е. **наш CSDROB-блок у них не покрыт**; их подход — читать уровень из RAF/калибровки.

**(г) Заглушки `0x155bde0/0x155bde8` в блоке 0 — подменяются ли при загрузке?** Прямого ответа нет (0 совпадений), но
есть **аналогичный механизм**, который стоит примерить: в XP5-эмуляторе есть (1) `bringup-stub` — скриптовые ответы
регистров, «scripted answers, not a model» (`data/rom-start.toml:14–46`), (2) `--emulator-patch` — патч RAM **одного прогона**
с проверкой ожидаемых байтов (`src/emulator_patch.rs:1–6, 99–125`) и (3) загрузчик модов: мод кладётся в RAM до старта,
хук-слова вставляются, когда «UILIB-ready» флаг прошивки примет объявленное значение (`src/mod_loader.rs:1–6`).
Т.е. сообщество решает такие заглушки **не перепаковкой DAT, а патчем RAM на старте** — это подтверждает нашу **Г**
«подменяются при загрузке», но про конкретные `0x155bde0/8` у них знания нет.

**(д) Задание съёмки `[0x4daa6e8]` «извне».** У них нет. Есть только канал (mailbox/rpmsg, §2.1) и общий принцип
«job приходит из другой ОС». Проверять у нас.

**(е) Дисплей/EVF/LCD.** У них: два LCDC-банка `0xFF990000/0xFF9A0000` (4 picture-группы + 2 OSD-плоскости,
Q12-сэмплирование, кроп в полупикселях, `YyCbCr`, stride `+0x14` 20 бит) — `framebuffer-xp5/src/lib.rs:10–224`;
и две панели на SSP5 как **write-only** командные регистры: LCD — клиент 4 (select GPIO 12.8, 8 бит, mode 0),
EVF — клиент 9 (select GPIO 12.10, mode 2) и клиент 8 (16-битное чтение) — `xt5-431/manifest.d/43-panel-serial.toml:1–40`.
Ключевая оговорка: «**XP5 native converted plane encoding is unresolved**» — нативный формат сконвертированных плоскостей
они не знают и подставляют собственный «emulator codec» header, который физический декодер отвергает
(`framebuffer-xp5/src/lib.rs:122–124, 230–243`). Это хорошая граница: **LCD-контроллер описан, а формат кадров
после конвертера — нет.**

**(ж) Сенсор.** `0xFF948000`, модель отдаёт RAW14-LE16 «рампу»; приёмники `0xFF940000/0xFF941000`, PHY `0xFF944000`,
input `0xFF946000`; период кадра — **функциональный 1 Гц** (чтобы не морить stock-IRQ164), не измерение.
`x100vi-131/manifest.d/50-imaging.toml:1–36`.

**(з) Кодеки.** См. (б): для XP5 нет ни JPEG, ни H.264/H.265/ProRes. Есть отдельный JPEG-блок только для XPP/XP4.

**(и) SD.** Два экземпляра SDHCI (X-T5 `0xFF9B0000` и `0xFF9B4000`, у каждого port0 UHS-I SDH30 `+0x0000`,
`+0x1E0/+0x1E4` — селекторы, `+0x2000` — UHS-II PHY, `+0x2200` — UHS-II SDHCI 4); драйвер сначала пробует port1.
IRQ 262. `xt5-431/manifest.d/25-sd.toml:1–70`, `rom-start.toml:74–80`.

**(к) USB.** В карте SoC USB-контроллера **нет**; есть только защёлка `usb-connection-status` (`0xFF90E300`, бит 0),
чей переход постит событие `0x3047`, а читается через `0xFFC0C70C`. `xt5-431/manifest.d/60-mcore.toml:65–71`.
Работа с USB (FF80, App80) у них — отдельный слой (`crates/usb`, `usb-app80`), не часть XP5-модели.

### 2.3 Пункт 3. Объектив

**Протокол X-mount у них разобран достаточно детально** (но это сменный объектив, не наш `0x411`):

- Байтовый SPI, **mode 3**, 8-битные кадры, 4-байтовые пакеты: `payload16 | family9 | ack | checksum5`, LSB=0;
  контрольная сумма — по битам 27/22/17/12/7 плюс бит 6. `crates/emulator-parts-lens/src/x_mount_link.rs:16–71`.
- Семейства: `0xFF` sync, `0x18` link parameters, `0x14` **identification** (128-байтная запись), `0x20` status,
  `0x30` aperture ring, `0x32` focus ring, `0x26` detail status, `0xC0` read catalog (блоки по 2048 Б),
  `0x80` control20 (запись защёлкивается по sync). `x_mount_link.rs:16–25, 105–124, 247–300`.
- Неизвестные команды **отвергаются**; «fixed replies» подставляют объявленные ответы; операции считаются по sync.
- Механика: независимые моторы фокуса и диафрагмы, **микрошаги** (5 периодов ramp, стадии), квадратурный энкодер
  (`steps_per_phase`), home-vane, пределы хода — всё **объявленные механические входы**, не измерения.
  `crates/emulator-parts-lens/src/lens/mechanics.rs:1–3, 43–60`.
- `identification` — **внешние 128 байт**; таблицы «ID → модель» нет, `0x411` в клоне отсутствует (1 совпадение, нерелевантное).
  `x_mount_link.rs:109–110`.

Для **встроенного** объектива X100VI у них другой канал (не X-mount): SPI4 — фокус, SPI5 — диафрагма; команда — слово
`0x2Cxx` в регистр `+8`: бит 11 enable, бит 10 направление, биты 0..9 — счётчик импульсов; по завершении пачки — IRQ 127
(фокус) / 125 (диафрагма), home-датчик — GPIO0.8. `crates/emulator-xp5-imaging/src/imaging_focus.rs:69–133`,
`.../imaging_iris.rs:45–95`, `x100vi-131/manifest.d/50-imaging.toml:111–130`.

**MF/LINEAR не найдено** (`LINEAR`/`focus ring` — только как поле `focus_ring` в протоколе). Наш вывод про
`0x411`/228/280 остаётся нашим.

### 2.4 Пункт 4. Автофокус, live view, Boost/Performance

- **AF**: не эмулируется. `PAF` — только reset-готовность (`+0x00` бит 16, `+0x300/+0x308`), «not a phase-detection algorithm».
  `imaging_paf.rs:1–2`. AF-алгоритм, зоны, tracking, глаз/лицо — отсутствуют; мод-«walkthrough af» в их прогрессе — `not-run`.
- **Live view**: у XP5 — «функциональные» источники кадра: приёмники (RAW14-LE16 рампа), `preview`, `movdc`
  (`source_luma`, период кадра), `statistics` (Y0/Y1/Cb/Cr), `rifp` (command image). Т.е. **данные синтетические**,
  частота — по объявленному `frame_period_us` (обычно 1 Гц в манифесте), а не камерная. Реальный ISP-конвейер
  у них есть только для EXR II (X70): там же измерена стоимость live view (0.93 CPU-с на 1 с гостя, статистика 90 мс/кадр).
  `crates/emulator-imaging/src/LIVE_VIEW.md:1–8`.
- **Boost/Performance**: только имена/ID (`UI_SETP_PERFORMANCE 1466`, `_AC 1467`, `_LEVER 1468`, `_MODE 1469`,
  `FUNC_PERFORMANCE 1470`, `PERFORMANCE_SET 6`, `DOTLCD_PERFORMANCE_MODE 2775`, `LCD_CUSTOM_BOOST 2048` —
  X-H2 5.30; аналоги в X-H2S/X-T5). Ни частот, ни ветвей, ни отличий Boost/Normal/Economy.
  `catalog/firmware/xh2/5.30/ui-setting-names.generated.json:1039, 1745, 2135, 2591–2595`.
- **Что реально «эмулируют» про частоты**: тики шины 1 ГГц, PLL/делители панелей (panel-pll), «17 банков» тактирования,
  `commit_ticks=1000` у memory-configuration, «1 мкс» латентность сенсорных команд. Это темп **эмулятора**, а не камеры.

### 2.5 Пункт 5. Что у них «не работает»/заглушено и почему

1. **XP5 не доходит до REC/меню** — `progress.generated.json` X-T5 4.31: `rec=not-run`, `menu=not-run`,
   `stock=not-run`, все `stock/*` (`focus`, `lens`, `film-simulations`, `record-picture`, `record-movie`, `sd`) — `not-run`;
   камера-трек — только `camera-identity=pass`. У X70 для контраста `rec=pass, menu=pass`.
   `catalog/progress/xt5/4.31/progress.generated.json:204–244, 246–350, 1186–1220`.
2. **Строгий режим = граница знания.** Любое неописанное обращение останавливает прогон, «frontier» пишется в отчёт;
   discovery-режим затеняет и логирует. `run.rs:183–187, 366–401`.
3. **DDR-контроллер — скриптовая заглушка**: «They are scripted answers, not a model: the register behavior is unknown».
   `data/rom-start.toml:14–46`. DDR PHY — просто RAM на 4 МиБ регистрового файла (`rom-start.toml:48–59`).
4. **Reset/memory-конфигурация** — «completes immediately as a functional session assumption; physical reset timing
   and effects are unmodeled», «commit … 1000-tick functional latency», «Write-only … reads and physical side effects
   remain unmodeled». `catalog/soc/xp5/soc.json:1029–1033`.
5. **PAF, AF, фокус-алгоритм** — только импульсы/готовность (§2.4).
6. **Формат плоскостей дисплея** — «unresolved», подменяется эмуляторным кодеком (§2.2е).
7. **MOVDC**: реализован единственный наблюдённый режим (`+0xF0=0xB`, packed422), второй адрес — непрозрачен,
   «no software ring access». `imaging_work.rs:1–3, 111–119`.
8. **Mailbox**: «no deadlines, memory writes, command handlers or firmware execution state» — payload непрозрачен.
   `mailbox.rs:1–4`.
9. **Сцены XP5**: статистические сцены не поддерживаются, только кадры/command images с `luma`;
   `apply_run_scene` отвергает остальное. `crates/emulator-xp5-board/src/boot.rs:341–378`.
10. **Кодеки/USB/JPEG на XP5** отсутствуют (§2.2б, к).
11. **XP5 в Python-расширение не входит**: «The extension links no XP5 model». `CRATES.md:412`.

   `ISGC 0x66E00000` (X-E5 DTB), «virtio/IPC» у X100VI; DTB X-T5 SHA `9cb8691a…`, `mem=256M`.
8. **Адреса загрузки**: ROM 0xFFF00000 (64 КиБ, SHA), boot SRAM 0xFF800000 (256 КиБ), companion SRAM 0xFA200000 (1 МиБ),
   loader X-T5 0x40000 / X100VI 0x81000, hand-off 0x5847C / 0x9920C, release `0xF0F0F0F0` (0x5EAEC / 0x9FB2C).
9. **DDR**: контроллеры `0xFAF00000..0xFAF30000` (опрос `+0x7800`, код результата `+0x784`), PHY `0xFB000000`/`0xFB400000`
   по 4 МиБ регистрового файла, таблицы в flash `0xF0012510`, `0xF0011E00/0xF0012090/0xF00124E0`.
   `rom-start.toml:14–59`; `crates/recovery/README.md:134–145`.
10. **Питание/клавиши**: power-controller на SPI8 (select GPIO 15.15), регистры 0x00/0x10, RTC-секунды, страпы
    `0xFF90E000`; клавиши — лестницы на ADC 1/2/14 и регистры 52/53 power-controller.
    `30-power-input.toml:1–70`; `catalog/bodies/xt5/hardware` (bus_drain).
11. **I2C-цели**: fuel gauge `0x36`, TMD2772-подобный датчик глаза `0x39`, retained-регистры `0x66/0x68`; IRQ 289.
12. **SD**: два UHS-II слота, port0 UHS-I + port1 UHS-II, PHY на `+0x2000`, IRQ 262.
13. **Их каталог статики по нашим камерам**: `catalog/firmware/xh2/5.30/*` (UI-имена, bulk-окно, `configuration_pointer`),
    `xh2s/7.30/*` (NOR, обновление, память, настройки, restart). Это готовый кросс-чек для W1/W3.
14. **Их «философия» изменения прошивки**: всё делается в RAM одного прогона (патчи, моды, SD-boot), DAT не перепаковывается
    «на камеру» — `mod_loader.rs`, `emulator_patch.rs`, `crates/recovery/README.md`.
15. **X-T5 b0 = settings bank** и **X-T5 b1 = bulk window**: функциональное назначение наших блоков 0/1 для X-T5.

## 5. Как сверял (и что это доказывает)

Сценарий: `сверка_с_fujimod.py` (в этой папке, только чтение). Полный лог: `сверка_вывод.txt`.
Он сверяет три вещи: (1) идентичность DAT, (2) наши распакованные блоки против их `streams.json`, (3) их `code_checks`
из `bulk.generated.json` против байтов наших блоков.

Результаты:

1. **DAT**: X-T5 4.31 `109 365 284` / `790d6dee…` == их `xt5-431`; X-H2S 7.30 `110 302 568` / `87c566c1…` == их `xh2s-730`;
   X100VI 1.31 `109 251 576` / `0d48d2ae…` == их `x100vi-131`. Размер и SHA совпали полностью.
2. **Блоки**: SHA наших `X-T5_4.31_b0` и `b1` равны `stream-00300274` (11 743 456) и `stream-00820274` (15 446 016);
   адреса совпали (`0x1101000`, `0x28EB000`). Значит **наш распаковщик и их декодер дают одни и те же байты**.
3. **Их code-checks**: 17/17 (X-T5 4.31), 17/17 (X-H2 5.30), 17/17 (X-H2S 7.30) — все совпали по SHA с нашими блоками,
   включая адреса вида `0x2C020A0`, `0x14F63A4`, `0x2CC1CB0`, `0x2FD9AC8`.
4. **Сырые разделы**: `boot-setup` X100VI (`DAT 0xABC`, 73 728 Б) и `loader` (`DAT 0xC02BC`, 123 584 Б) воспроизводятся
   инверсией DAT и совпадают по SHA с их раскладкой; заголовок loader'а — `{0, 0, base, 0, size}`.
5. **Заголовки method4** по всем их смещениям валидны (page_size 0x4000, method 4, pages = ceil(packed/0x4000));
   по `0x60274` (X-T5) и `0xC02BC` (X100VI) заголовка сжатия нет — это действительно сырые образы.
6. **Наш указатель** `0x20c1458` (X-H2 5.30) == их `configuration_pointer`; наш блок 1 X-H2 (0x29AE000, 15 515 648) == их bulk-window.

Границы этой сверки: она доказывает, что **их адреса/размеры/хэши относятся к тем же байтам, что у нас**, но не доказывает
их интерпретации (что MOVDC — packed422, что payload mailbox значит X и т.п.). Интерпретации помечены в таблице отдельно.

## 6. Что стоит проверить у нас дальше (конкретные шаги)

1. **MOVDC-регистры в наших прошивках.** Найти в блоках 1/2 X-H2 5.33 и X-T5 4.32 записи `0x10030001` в `base+0xD8`,
   `0xB` в `+0xF0`, `stride` в `+0xD0` и `size` в `+0x18` для баз `0xFF970000/FF971000/FF972000`. Если найдутся —
   мы получаем имена полей для нашей «структуры дескриптора» `{h,w,stride}` и подтверждаем packed422 прямо по коду.
2. **Проверить, что геометрия 640 относится к 640-пиксельному кадру, а не к 640-байтовой строке.** В нашей MOVDC-функции
   сравнить `+0x18`-эквивалент (поле геометрии) с шириной в регистре размера: если код пишет `(h<<16)|w` — гипотеза
   «packed422 640×480» становится **Д**.
3. **Искать в наших DAT канал «другая ОС»:** строки/литералы `rpmsg`, `virtio`, `AMP`, `ISGC`, адреса `0x56E00000`,
   `0x66D00000`, `0x66E00000`, `0x5FF00000`, `0x50000000`; и обращения к `0xFF90E100` (mailbox) в блоках 1/2.
   Это прямой путь к ответу «кто пишет `[0x4daa6e8]`».
4. **Проверить boot ROM-окно:** у X-H2S/X-T5 в их `state.generated.json` регион `boot-rom` — `0xFFC00000`, 256 КиБ;
   у X100VI ROM — `0xFFF00000`, 64 КиБ. У нас искать в блоках `adrp` на `0xFFC00000` и `0xFFF00000`,
   а также `boot-sram 0xFF800000`.
5. **Сверить наши UI_SETP-таблицы с их `ui-setting-names.generated.json`** (X-H2 5.30, X-H2S 7.30, X-T5 4.31):
   у них name→ID, у нас строки меню; пересечение даст отсутствующие у нас имена (и наоборот). Особенно
   `UI_SETP_PERFORMANCE*` (1466–1470) и `UI_SETP_LCD_CUSTOM_BOOST` (2048/2047/2121) — это вход в пункт «Boost».
6. **Проверить SPI5-панели:** в наших блоках искать клиентов SSP5 (LCD select GPIO 12.8 «times-2» register encoding,
   EVF select 12.10, строка `EvfSd_NG`). Если совпадёт — получим подтверждение, что наш «дисплей» и их «панели» —
   один и тот же физический канал, и наши находки по LCD можно привязать к LCDC-банкам 0xFF990000/0xFF9A0000.
7. **Проверить USB-защёлку** `0xFF90E300` / событие `0x3047` в наших прошивках — может дать нам недостающий флаг
   подключения USB (полезно для W3/PTP).
8. **Проверить `movdc-reset`/`input-reset` handshake** (reset-бит 0, `+0x24 == 0x10001` у resize) в наших блоках —
   это даст нам модель инициализации imaging-блока, которой у нас нет.
9. **Не переносить их «settings bank»-вывод на X-H2 без проверки:** у X-H2S/X-T5 блок 0 — settings (подтверждено SHA),
   у X-H2 5.30 их `settings.generated.json` нет; проверить, что наш X-H2 b0 тоже банк настроек (по строкам/таблицам).
10. **H.265/CSDROB оставить нашими** — у сообщества этого нет; но их `LIVE_VIEW`/`PERFORMANCE` полезны как методика
    (как измерять «3× камеры») для наших будущих физических тестов.
