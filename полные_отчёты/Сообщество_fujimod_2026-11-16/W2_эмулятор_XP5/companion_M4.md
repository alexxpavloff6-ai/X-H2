# Companion Cortex-M4 на XP5: откуда берётся код и как его найти в наших DAT

Дополнение к `отчёт.md` (W2). Источники: клон fujimod `c61fa145` (только чтение) + наши DAT.
Проверочный сценарий: `companion_M4.py` (только чтение), его лог — `companion_M4_вывод.txt`.
Уровни: **Д** — доказано кодом/данными и проверено на наших байтах; **К** — сильный кандидат; **Г** — гипотеза.

---

## 0. Ответ в двух строках

**Образ M4 лежит в нашем DAT X-H2 (FWUP0028) по смещению `0x1C0274`** (flash `0x1C0000`), длина **`0x31A80`** (203 392 Б),
**raw, без сжатия**, грузится A53-кодом в **SRAM `0xFA200000`** (M4 видит её как локальный `0`), BSS `0x19340` зануляется там же.
Это **не FFLZ-контейнер** и не «пятый блок»: запись о нём — **id=3** в таблице компонентных дескрипторов по flash `0x1A0000`
(DAT `0x1A0274`), а копирует его A53-функция X-H2 `0x13FB120`/`0x13FB194`; «спуск» M4 — **бит 21 регистра `0xFF90C928`**.

У X-T5 4.31/4.32 и X-H2S 7.30/7.31 — тот же `0x1C0000`, но другие размеры (`0x32470` и `0x22900` соответственно).

Геттер (X-H2 `0x14E1BB0`, X-T5 `0x14D9AB8`, X-H2S `0x1801758`):

## 3. Формат образа: это действительно ARMv7-M (Cortex-M4)

Образ X-H2 (`DAT 0x1C0274`, 0x31A80 Б) начинается с векторной таблицы:

```
00000a00 00000a01 000018dd 00000a35 000018ab 000018ab 000018ab 00000000
00000000 00000000 00000000 000018b3 000018e1 00000000 00002133 000018d1
```

| Вектор | Значение | Смысл |
|---|---|---|
| 0 | `0x00000A00` | начальный **SP** (стек в локальной SRAM) |
| 1 | `0x00000A01` | **Reset** → код по локальному `0xA00` (Thumb-бит) |
| 2 | `0x000018DD` | NMI |
| 3 | `0x00000A35` | HardFault |
| 4–6 | `0x000018AB` | MemManage/BusFault/UsageFault |
| 7–10 | 0 | резерв (архитектурно) |
| 11 | `0x000018B3` | SVCall |
| 12 | `0x000018E1` | DebugMon |
| 13 | 0 | резерв |
| 14 | `0x00002133` | PendSV |
| 15 | `0x000018D1` | SysTick |
| 16…194 | `0x000018B7` ×179 | IRQ0..178 → обработчик по умолчанию |
| далее | 0 | конец таблицы |

Подтверждения (дизассемблер Thumb, `companion_M4_вывод.txt`, §4):
- reset `0xA00`: `push {r7,lr}; bl 0xA14; bl 0x2E54; bl 0xA78; pop {pc}` — настоящий Thumb-код;
- `0xA14`: `ldr r3,[pc,#0x14]` → литерал **`0xE000ED14`** (ARMv7-M **CCR**), пишет `0x210`, затем `[r3+0x10]` = **`0xE000ED24`**
  (SHCSR) = 0 — типичная инициализация ядра Cortex-M;
- NMI-заглушка `0x18DC`: `b .` (вечный цикл) — как и положено в bare-metal образе;
- в образе есть литералы **`0x5F90E100`** (×2) и **`0x5F90E120`** (×3) — это локальные адреса mailbox и его cause-регистра
  (локальный = физический + `0x60000000` по модулю 2³²: `0xFF90E100 + 0x60000000 = 0x1_5F90E100 → 0x5F90E100`). **Д**

**Карта памяти M4** (по `soc.json` + литералам образа):

- локальный `0x00000000..0x000FFFFF` — **SRAM** (физически `0xFA200000`, 1 МиБ): код, данные, стек, векторы (`vector_base = 0`);
- локальные `0x5F000000..0x5FFFFFFF` — **алиас периферии** `0xFF000000..0xFFFFFFFF` (mailbox `0x5F90E100`, SPI `0x5F911000`, input-capture `0x5F928000`, SD `0x5F9B0000`);
- `0x60000000..0x6FFFFFFF` — **алиас DRAM** `0x00000000..0x0FFFFFFF`; конкретные окна объявлены в `companion-map-1`
  (`0x68473000 → 0x08473000`, 0x57D000) и `companion-map-2` (`0x6263D000 → 0x0263D000`, 0x41000);
- своего flash у M4 **нет** — образ всегда копируется A53 в SRAM. Локальный `0` и есть SRAM.

BSS: `0x19340` байт сразу после образа (`0xFA200000 + 0x31A80 .. + 0x4ADC0`), зануляется `memset` в той же функции. **Д**

## 4. Цепочка запуска (X-H2 5.30) — кто, когда и чем «спускает» M4

*(листинг инструкций не публикуется — фрагмент кода Fujifilm; воспроизводится сценариями этой папки)*

Разбор release-хелпера (`0x13AD514` + таблицы):
- `0x18F4688 + 8*idx` — адреса регистров: `idx 0..17 → 0xFF90C900, 0xFF90C904, … 0xFF90C944`; **`idx 0xA → 0xFF90C928`**;
- `0x18F47D0 + 4*idx` — разрешённые маски: `idx 0xA → 0x00A00000` (биты 21 и 23);
- запись `(0xa, 0x200000, 1)` = установить **бит 21** в `0xFF90C928` (блок `clock-gates` `0xFF90C000` по `soc.json`). **Д**

Тот же шаблон в других моделях (**Д** по коду):
| модель | чтение clock 0xA | копия M4 | release |
|---|---|---|---|
| X-H2 5.30 | `bl 0x13AD588` @`0x13FB190` | `0x13FB194` (memcpy `0x14D2534`) | `bl 0x13AD514` @`0x13FB2DC` |
| X-H2 5.33 | то же (адреса сдвинуты: `0x13F21C4` — `mov x0,#0xF0000000`) | — | — |
| X-T5 4.31 | `bl 0x13AB948` @`0x13F7B00` | `0x13F7B58` (memcpy `0x14CA42C`) | `bl 0x13AB8D4` @`0x13F7C84` |
| X-H2S 7.30 | `bl 0x16CAF00` @`0x17176D8` | `0x171778C` (memcpy `0x17F20C8`) | тот же шаблон после mailbox-инициализации |

**Инициатор mailbox — A53.** Перед «спуском» M4 она обнуляет все 8 слов payload и пишет `0x7F` в cause (`+0x20`) —
по модели fujimod это W1C, т.е. сброс битов 0..6. После этого M4 стартует и уже сам пишет в `+0x10/+0x14/+0x18`
(reply/status/fault → INTID 141/142/143), а A53 шлёт request/control (`+0x00/+0x0C` → INTID 55/58). **Д** для
последовательности, **К** для семантики битов.

## 5. Есть ли образ внутри DAT, или это отдельный раздел NOR?

**Внутри DAT, но вне FFLZ-блоков.** Раскладка flash (X-H2, по нашей таблице и fujimod):

| flash | DAT | что |
|---|---|---|
| `0x00000`… | `0x00274`… | заголовок обновления / setup-конверт |
| `0x60000` | `0x60274` | loader (id=0), 0x1E340 → RAM `0x40000` |
| **`0x1C0000`** | **`0x1C0274`** | **образ Cortex-M4 (id=3) + BSS `0x19340`** |
| `0x22C0000` | `0x22C0274` | служебная секция 0x20000 (id=7) |
| `0x24A0000` | `0x24A0274` | наш блок 3 → RAM `0x580000` (id=1) |
| `0x2940000` | `0x2940274` | секция id=2 |
| `0x300000` | `0x300274` | наш блок 0 (id=4) → `0x1101000` |
| `0x840000` | `0x840274` | наш блок 1 (id=5) → `0x29AE000` |
| `0xF40000` | `0xF40274` | наш блок 2 (id=6) |
| `0x3C40000` | `0x3C40274` | оверлей/языковой банк (id=10) |

Почему мы его раньше не нашли: наш распаковщик искал **FFLZ-контейнеры** по шагу 0x1000 от `0x274`, а образ M4 —
**сырой** (`fsz == size`, флаги 0), лежит до блока 0 и не имеет FFLZ-заголовка. Байтовая сигнатура векторов
(`00 0a 00 00 01 0a 00 00 dd 18 00 00 35 0a 00 00 …`) в четырёх FFLZ-блоках **отсутствует** (проверено поиском). **Д**

Связь с «boot ROM / отдельным разделом NOR»: в DAT его **нет** в boot ROM (boot ROM — это 64 КиБ по `0xFFF00000`,
в обновление не входит; `crates/emulator-xp5-bringup/src/rom_start.rs:18–34`). Образ M4 — обычная секция обновления,
адресуемая таблицей компонентов, поэтому при обновлении прошивки она обновляется вместе с ней.

## 6. Что искать в нашем DAT X-H2 (FWUP0028) — конкретные адреса и сигнатуры

> DAT читается **инвертированным** (XOR 0xFF): `flash_offset = DAT_offset − 0x274`. Проверено по `control`-хэшу fujimod
> для flash `0x60000` (`3867c1a8…` для X-T5 и `886e711e…` для X-H2S). **Д**

| Что | Где искать | Значение / сигнатура |
|---|---|---|
| **Образ M4** | **DAT `0x1C0274`**, длина `0x31A80` | `00 0a 00 00 01 0a 00 00 dd 18 00 00 35 0a 00 00 ab 18 00 00 ab 18 00 00 ab 18 00 00` |
| SHA образа (контроль) | те же байты | `85d29ade613aa01c…` (X-H2 5.30 и 5.33 — одинаковы) |
| **Дескриптор M4** | **DAT `0x1A0484`** (flash `0x1A0000`, запись idx 7, шаг 0x40) | `id=3`; `+0x10 size=0x31A80`; `+0x20 bss=0x19340`; `+0x28 flash=0x1C0000`; `+0x30 fsz=0x31A80` |
| Указатель на таблицу | DAT `0x1A0274` | u64 `0x10C0050` (X-H2/X-T5) или `0x13E0050` (X-H2S) |
| Терминатор таблицы | DAT `0x1A0504` | `ff ff ff ff` |
| **A53-копировщик** | блок 0 X-H2 5.30: **VA `0x13FB194`** (функция `0x13FB120`) | `ldr x1,[x19,#0x28]; ldr w2,[x19,#0x18]; mov x0,#0xF0000000; add x1,x1,x0; mov x0,#0xFA200000; bl memcpy` |
| Геттер дескриптора | X-H2 `0x14E1BB0`; X-T5 `0x14D9AB8`; X-H2S `0x1801758` | `mov w2,w0; adrp x0,#0x10C0000; ldr x0,[x0]; ldr w1,[x0]; … add 0x40` |
| **Release M4** | X-H2 VA `0x13FB2D0`; X-T5 `0x13F7C78` | `mov w0,#0xA; mov w1,#0x200000; mov w2,#1` → **бит 21 `0xFF90C928`** |
| Таблица адресов release | X-H2 VA `0x18F4688` (18 u64) | `0xFF90C900 + 4*i`; маска `0x18F47D0` = `0x00A00000` для idx 0xA |
| Guard «уже запущен» | X-H2 `0x13FB14C` | `tbz w0,#21, <копировать>` |
| Mailbox (в образе M4) | внутри образа, смещения `0x32DC`/`0x36E4` (X-H2) | литералы `00 e1 90 5f` (`0x5F90E100`) и `20 e1 90 5f` (`0x5F90E120`) |
| BSS M4 | сразу за образом | `0xFA200000 + 0x31A80`, длина `0x19340` (зануляется, в DAT этих байт нет) |

Готовые проверки (одной командой):

```python
from pathlib import Path; import hashlib, struct
d = bytes(b ^ 0xFF for b in Path(r'<корень проекта>\FIRMWARE\ver 5.30\FWUP0028.DAT').read_bytes())
img = d[0x1C0274:0x1C0274+0x31A80]
print(hashlib.sha256(img).hexdigest())              # 85d29ade613aa01c…
print(img[:16].hex())                               # 000a0000010a0000dd180000350a0000
w = struct.unpack_from('<8I', d, 0x1A0484)          # дескриптор: id=3, …
```

Ожидаемые значения для остальных моделей: X-T5 4.31/4.32 — `0x32470`, SHA `5854107f8c951c2b…`;
X-H2S 7.30/7.31 — `0x22900`, SHA `85476217f55a6774…`. Если у нас в DAT по `0x1C0274` не сходится —
значит версия не из этого ряда (или файл другой модели).

## 7. Границы: чего мы всё ещё не знаем

1. **X100VI** использует **другую** таблицу: по flash `0x40000`/`0x40800` (DAT `0x6402BC`/`0x1202BC`, VA `0x40000`/`0x40800`),
   строки иной раскладки (`{size, …, id, …, address}`); указателя `0x10C0050` там нет, запись `id=3` в setup-области
   не находится. fujimod говорит, что A53 `0x14D3F14` копирует «section5» — но конкретное flash-смещение и размер
   для X100VI им не зафиксированы. **Открытый пункт** (наши X-H2/X-H2S/X-T5 закрыты).
2. **BSS-регион `0x19340`** в DAT отсутствует (его зануляет код) — в образе его нет; кто и что туда пишет до старта M4,
   не проверено (**Г**).
3. **Второй `memcpy` 0x6000** (X-H2: dest `*(0x1C51DB8)+0x4E0C`) — что копируется (калибровка? общая структура M4?)
   не установлено; у X-T5 размер `0x6000`, сдвиг `+0x4E94`, у X-H2S `+0x310` (**Г**).
4. **Семантика cause-битов** mailbox (0x7F при init, 0x1/0x20 в модели fujimod) — модель трактует их как W1C,
   но реальный смысл каждого бита не доказан (**К/Г**).
5. **Почему размеры образа различаются** (X-H2 0x31A80, X-T5 0x32470, X-H2S 0x22900) при одинаковом flash-адресе —
   разные сборки под разные наборы периферии; проверять по строкам/таблицам внутри образов (**К**).
6. **Пины 9.8/9.9** (`0x1382EE8`) перед копированием — вероятно, питание/сброс домена M4, но это не доказано (**К**).
