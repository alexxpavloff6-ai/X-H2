# W2: контур управления съёмкой `reccont` X-H2 5.30

## Краткие выводы

1. Задача с меткой `reccont` регистрирует запись хранилища `0x03`: 48 элементов по `0x50` байт, полезная часть до `0x48`. В блоках 0–1 найдены 47 прямых публикаций: 4 в блоке 0 и 43 в блоке 1 (**Д**).
2. Цикл `0x2D67134` получает запись `0x03` через `0x14CF354` с индексом `-1`. При успешном чтении он сначала проверяет текущее состояние в `0x2E00D18`; затем на части путей копирует полезную часть и передаёт событие в `0x2D9A060` и `0x2D5B36C` (**Д**).
3. События `0x0204`, `0x0205`, `0x0206` – пакеты разного размера: соответственно 12 байт из трёх слов, 4 байта из одного слова и 44 байта с несколькими полями. Они подтверждают передачу данных в `reccont`, но не называют эти данные «спуском», «началом/концом экспозиции» или «готовым кадром» (**Д** для состава, **Г** для названий).
4. `0x1212–0x1214` – три пустых сообщения без данных, их публикует блок 0. Их семантика в коде не подписана. Отдельные события `0x1220–0x1222` имеют по 16 байт и переводят внутреннее поле состояния в значения 3/2/4 (**Д** для передачи и записи состояния).
5. Обработчик `0x2D5B36C` не пишет файл и не вызывает по прямой ветке `MOVDC`. Он вызывает три группы процедур состояния и в них разбирает несколько кодов `0x0200–0x022E`; конкретные физические операции по кодам из этих переходов не выводятся (**Д** для ветвления, **Г** для прикладного толкования).
6. В просмотренном цикле и его трёх основных обработчиках не нашёл прямых чтений `UI_SETP_CONTINUOUS` (`0x858`), выходов `DOTLCD_CONTINUOUS` (`0xACE/0xACF`), типа/фактического затвора или выдержки. Это отдельные настройки и структуры съёмки; их прямую связь с событиями `0x03` статический разбор не устанавливает (**Д** отрицательное для просмотренных функций).
7. `MODE_RECORD` (`0x1141EE0`) и RECF-поле `[ctx+0x3978]` относятся к другому уровню подготовки изображения. В имеющихся источниках `0x3978` копируется в RECF-контекст из задания; прямой путь от этой копии к циклу `reccont` не доказан (**Д/К**, см. границу ниже).
8. Установить полную последовательность «нажатие спуска → экспозиция → создание кадра → серия/HDR/видео → файл» по этим событиям нельзя. Связь с кодировщиками RAW/JPEG, файловой подсистемой и публикацией `0x4C` не прослежена; требуется динамическая трасса сообщений с одновременной регистрацией состояния съёмки (**Г**, открытая граница).

## Область и способ

Разбирались только блоки X-H2 5.30 из `fwcommon.load('X-H2','old',0/1)` и ранее подготовленный прямой каталог записи `0x03` в `Записи_2026-11-18\U2_каталог_записей`. Адреса ниже – адреса выполнения для 5.30. Камера и резервные копии камеры не использовались. Скрипт `analyze_reccont.py` перечитывает прямые записи каталога, извлекает константные коды событий из функций-отправителей и формирует `результат.json` только в этой папке.

Обозначения: **Д** – непосредственно видно в коде/данных; **К** – сильная, но неполная связь; **Г** – предположение либо неразрешённый вопрос.

## Схема очереди и обработчиков

```text
отправитель в блоке 0 или 1
  → 0x14CF124(id=3, заголовок {код:u16, состояние:u8, тип:u8, длина:u32, указатель})
  → хранилище записей в сервисном модуле
  → 0x2D67134: 0x14CF354(id=3, out, index=-1)
      ├─ ненулевой результат → 0x2D5B36C → повтор чтения
      └─ запись прочитана → 0x2E00D18 (проверка/сопоставление с текущим состоянием)
           ├─ вернул 1 → повтор чтения
           └─ иначе → копия заголовка и данных → 0x2D9A060 → 0x2D5B36C → повтор чтения
```

### Цикл `0x2D67134`

- В начале вызывает `0x2D66F54`, затем использует буферы вокруг `0x3BC2B48` и `0x3BC2B58`.
- В `0x2D6718C–0x2D67198` читает очередь `0x03`: `w0=3`, `x1=0x3BC2B48`, `w2=-1`; далее по `w0` выбирает ветку ошибки/ожидания или обработки сообщения.
- При обычном сообщении заголовок содержит код в первых двух байтах, длину по `+4`, указатель на полезные данные по `+8`. Цикл копирует до `0x10` байт заголовка и полезную часть по длине, вызывает `0x2E00D18`, затем на ветке обработки – `0x2D9A060` и `0x2D5B36C`.
- Это цикл маршрутизации и обновления состояния. В нём нет явного файлового вызова или записи кадра на карту (**Д**).

### Что делают три обработчика

| Функция | Наблюдаемое действие | Что из этого следует |
|---|---|---|
| `0x2E00D18` | Читает текущее скалярное состояние через `0x14CF404`; для части значений пишет диагностические данные; вызывает `0x2E2704C`, затем условно `0x2E20AD8` и `0x2E24520`. Возвращаемое значение `1` пропускает следующую ветку обработки. | Это фильтр/согласование состояния перед обработкой. По нему не определяется начало экспозиции или запись файла (**Д** механика, **Г** назначение). |
| `0x2D9A060` | Для кодов `0x1228` и `0x1229` проверяет биты глобальной маски и записывает результат `0/1/2/3` в поле сообщения `+0x18`. Для остальных кодов сразу возвращает. | Это небольшое преобразование метаданных отдельных событий, а не общий обработчик всех событий `0x03`. Прямые публикации `0x1228/0x1229` среди 47 найденных вызовов не выявлены. |
| `0x2D5B36C` | Последовательно вызывает `0x2D5AE4C`, `0x2D5B290`, `0x2D5AE68`; сохраняет результат средней функции и возвращает его после обновляющих вызовов. | Функция применяет событие к нескольким внутренним состояниям/подсистемам `reccont`. Имена физических операций отсутствуют (**Д** для вызовов). |

`0x2D5B290` читает текущий код события из общего сообщения. Для `0x0200` дополнительно проверяет слово `[указатель+0x1FC]`: в поле состояния `0x3E29FC0` записывает `0` или `1`. Для `0x1221`, `0x1220`, `0x1222` записывает соответственно `2`, `3`, `4`; для прочих кодов – `5`. Затем вызывает `0x2D5AD60(4)`. Это доказанные числовые переходы, но назначение самого поля состояния не установлено.

`0x2D5B398` – отдельный обработчик с собственными прямыми вызывающими; он не входит в цепочку прямых вызовов `0x2D67134`. В нём есть ветвления по `0x0200`, `0x0201`, `0x020B`, `0x0203–0x0209`, `0x0214`, `0x021F`, `0x0226`, `0x022A`, `0x022B`, `0x022D` и `0x1130`. В ветках записываются числовые состояния в `0x3E29FC2` и вызывается `0x2D5AD60(5)`; отдельные коды дополнительно зависят от глобального значения или поля полезной части. Это не даёт достаточного основания называть каждый переход спуском, экспозицией, серией или видео.

## Отправители и состав сообщений

В записи каталога перечислены все 47 прямых отправителей `0x03`. Среди 43 сайтов блока 1 коды встречаются так:

- `0x0200–0x020E` (кроме отсутствующих `0x0210`), `0x0211–0x0216`, `0x021F`, `0x0220–0x022E` – в основном по одному отправителю; `0x020D` публикуют три функции.
- `0x1212`, `0x1213`, `0x1214` – по одному отправителю в блоке 0, без полезных данных.
- `0x1220`, `0x1221`, `0x1222` – по одному отправителю в блоке 1, по 16 байт каждый.
- Ещё один отправитель блока 0 – общая функция `0x14E614C`, которая получает код события аргументом и размер/указатель на данные. Она не зашивает один код константой.

Примеры структуры, прямо читаемой в кодировщиках:

| Код | Отправитель | Что копируется в полезную часть | Уровень |
|---|---:|---|---|
| `0x0204` | `0x2D3808C` | три слова из входной структуры (`+0`, `+4`, `+8`), длина `0x0C` | **Д** |
| `0x0205` | `0x2D380E8` | одно слово из входа, длина `4` | **Д** |
| `0x0206` | `0x2D38134` | слова из полей `+0…+0x28`, включая байт `+0x1C`, длина `0x2C` | **Д** |
| `0x1212–0x1214` | блок 0, `0x14E619C`, `0x14E6098`, `0x14E60DC` | нулевая длина и нулевой указатель | **Д** |
| `0x1220–0x1222` | `0x2D5A34C`, `0x2D5A39C`, `0x2D5A3E8` | 16 байт: аргументы соответствующих обёрток | **Д** |

Сами значения `0x0204/205/206` — номера событий, а не документированные названия операций. В частности, размер пакета и соседство кодов не доказывают «спуск затвора», начало/конец экспозиции или завершённую запись файла. Эти названия оставлены открытыми (**Г**), как и отдельная привязка к одиночной съёмке, серии, брекетингу, HDR и видео.

## Настройки съёмки, MODE_RECORD и граница RECF

- В ранее разобранном меню `UI_SETP_CONTINUOUS` (`0x858`) хранится выбор включения серийного режима; текущий фактический выход серии отражён отдельно в `DOTLCD_CONTINUOUS` (`0xACE/0xACF`). Значения CH/CL и меню/фактический выход нельзя отождествлять.
- Выбор типа затвора `UI_SETP_SHUTTER_TYPE` (`0x827`) отделён от фактического типа затвора в съёмочной структуре (`+0x19AC`); фактическая выдержка также идёт отдельным полем `+0x1994`. Синхронизатор переносит значения из структуры в выходные настройки, но это не доказывает чтение этих полей очередью `reccont`.
- `MODE_RECORD` разрешается таблицей `0x1141EE0`; известные коды P/S/A/M — `0x21–0x24`, HDR — `0x2C`. RECF-контекст `[ctx+0x3978]` читается в функциях подготовки изображения и по одному из найденных путей копируется из поля задания. Ни `0x1141EE0`, ни прямое чтение `[ctx+0x3978]` не стоят в видимом основном цикле `0x2D67134` и его обработчиках `0x2D9A060`, `0x2D5B36C`, `0x2E00D18`.
- Поэтому в этой работе нет подтверждённой ветки вида «если CH – повторить захват», «если HDR – сделать несколько экспозиций» или «если видео – перейти к записи потока». Номер `0x020C` из серии событий не связан доказательством с `MODE_RECORD_HDR=0x2C`.
- В общем каталоге есть отдельные публикации записи `0x4C`, а код MOVDC читает эту запись для переноса LCD-флага. Прямого вызова публикации `0x4C` из `reccont` либо доказанной связи события `0x03` с файловыми писателями не найдено. Поиск задач `recbjpeg`, `recblsraw`, `recbmedia` и `filecont1` также не дал сквозной трассы «событие 0x03 → файл».

## Что это даёт для будущих доработок прошивки

`0x03` – подходящая точка для наблюдения за управляющими сообщениями съёмки, но не готовая карта жизненного цикла. Для расшифровки события следует одновременно фиксировать код и все байты полезной части, время, режим записи, `UI_SETP_CONTINUOUS`, фактический затвор, выдержку и появления файлов/записей `0x4C`. Сопоставление по нескольким состояниям (одиночный кадр, CH/CL, брекетинг, HDR, видео) позволит различить команды и подтверждения. До такой трассы менять обработчики по предположительному смыслу кода события рискованно.
