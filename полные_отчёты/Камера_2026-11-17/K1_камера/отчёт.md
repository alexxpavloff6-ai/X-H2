# K1: read-only снимки свойств X-H2 и BACKUP настроек

Дата исследования: 17.11.2026. Камера: Fujifilm X-H2, прошивка 5.30, USB `VID_04CB&PID_02F2`.

## 1. Правила и границы

Выполнены требования `../КОНТЕКСТ.md`: никаких программных изменений настроек, RESTORE, сервисного режима, вендорских операций, записи объектов или прошивки. Настройки между снимками меняет только владелец руками. Инструмент создаёт новую папку снимка и отказывается работать, если она уже существует; файлы открываются в режиме exclusive-create.

В коде `xh2_snapshot.py` активный белый список по умолчанию состоит только из `0x1001`, `0x1014`, `0x1015`. Операции `0x1008/0x1009` добавляются лишь флагом `--backup` после отдельного одобрения координатора и только с параметром handle `0`. Других PTP-операций в коде нет; отрицательные проверки подтвердили отказ до `SendCommand` для `0x1016`, неодобренного BACKUP и ненулевого handle.

## 2. Операции чтения свойств

| Операция | Параметры | Направление данных | Назначение и обоснование |
|---|---|---|---|
| `0x1001 GetDeviceInfo` | нет | камера → ПК | Стандартное чтение DeviceInfo: операции, свойства, форматы, модель, прошивка. Использовалось в прежних read-only логах. |
| `0x1014 GetDevicePropDesc` | один `uint32`, содержащий код свойства | камера → ПК | Стандартное чтение DevicePropDesc: тип, Get/Set, default/current, range/enum. Не содержит data phase ПК → камера. |
| `0x1015 GetDevicePropValue` | один `uint32`, содержащий код свойства | камера → ПК | Стандартное чтение текущего значения. Не содержит data phase ПК → камера. |

## 3. BACKUP: точная последовательность экспорта

Опубликованный отчёт [`Внешние_инструменты/Отчёт.md`](https://github.com/alexxpavloff6-ai/X-H2/blob/main/полные_отчёты/Внешние_инструменты/Отчёт.md) называет полную резервную копию функцией fujicli, но не раскрывает протокол. Точная последовательность восстановлена по исходникам fujicli:

1. `0x1008 GetObjectInfo`, единственный параметр `ObjectHandle = 0x00000000`, данные **камера → ПК**. Возвращает PTP ObjectInfo, в том числе `ObjectFormat` и `CompressedSize`.
2. Проверка в новом инструменте: `ObjectFormat == 0x5000` (`FujiBackup`), размер больше нуля и не превышает предохранительный предел 256 MiB.
3. `0x1009 GetObject`, единственный параметр `ObjectHandle = 0x00000000`, данные **камера → ПК**. Возвращает сам непрозрачный BACKUP-блоб, который сохраняется без интерпретации и модификации.

Источники:

- [`CameraBackupManager::export_backup`](https://github.com/karaolidis/fujicli/blob/main/crates/fujicore/src/features/backup/manager.rs): `ptp.read(GetObjectInfo, [0])`, затем `ptp.read(GetObject, [0])`;
- [`Ptp::read`](https://github.com/karaolidis/fujicli/blob/main/crates/fujicore/src/ptp/mod.rs): явно описан как операция, чья data phase идёт **from the camera**;
- [`CommandCode`](https://github.com/karaolidis/fujicli/blob/main/crates/fujicore/src/ptp/container.rs): `GetObjectInfo=0x1008`, `GetObject=0x1009`;
- [`ObjectFormat`](https://github.com/karaolidis/fujicli/blob/main/crates/fujicore/src/ptp/structs.rs): `FujiBackup=0x5000`; ObjectInfo содержит `compressed_size`.

**Размер и формат:** заранее фиксированный размер для X-H2 источники не дают. Его надо брать из ObjectInfo и фактической data phase. Полезная нагрузка — opaque byte stream с форматом объекта `0x5000`; утверждать внутренний формат, сжатие или наличие записи `0x4C` по этим источникам нельзя. Фактические размер, SHA-256 и ObjectInfo будут записаны после одобренного чтения.

**Ограничение доказательства:** fujicli содержит комментарий `Naively assuming that all cameras backup/restore in the same way`; опубликованный отчёт указывает, что X-H2 в fujicli лишь опознаётся, а функции не включены. Поэтому это документированный read-direction путь на поддерживаемых fujicli камерах, но не гарантия применимости/отсутствия внутренних transient-действий на X-H2. Первый вызов требует отдельного `ask`; при ошибке или неожиданном ObjectInfo повторных попыток нет.

`rawji` реализует чтение/запись профиля RAW CONV и скачивание результата, но не whole-camera BACKUP. `fujinx` сохраняет рецепты слотов как файлы. Клон fujimod `crates/usb/PROTOCOL.md` описывает отдельный сервисный ff80-протокол, а не PTP BACKUP; поиск по `backup` в `crates/usb` и `crates/catalog-service` не дал PTP-последовательности. Этот сервисный канал здесь запрещён и не используется.

## 4. RESTORE и другие запрещённые операции

| Операции | Что делают | Почему не используются |
|---|---|---|
| `0x100C SendObjectInfo (params 0,0)` с ObjectInfo `format=0x5000`, затем `0x100D SendObject (handle 0)` с блобом | `import_backup` в fujicli: загрузка и восстановление настроек | Это RESTORE и data phase ПК → камера; категорически запрещено. |
| `0x1016 SetDevicePropValue` | Запись любого свойства; `D18C` переключает слот, `D185` задаёт профиль, `D183` запускает проявку | Даже «backup C1–C7» сторонних recipe-инструментов может писать `D18C`; здесь запрещено. |
| `0x900C/0x900D` | Fuji SendObjectInfo/SendObject, загрузка RAF | Запись в камеру, вендорские операции. |
| `0x100B DeleteObject`, `0x100F Format`, `0x100E InitiateCapture` | Удаление, форматирование, съёмка | Изменяют состояние/данные. |
| `0x1017 ResetDevicePropValue`, любые `0x9xxx`, сервисный ff80 | Сброс свойства или не доказанное чтение | Нет разрешения и достаточного доказательства «только чтение». |
| `0x1007 GetObjectHandles`, `0x100A GetThumb`, прочие стандартные чтения | Могли бы читать объекты | Не нужны для BACKUP по fujicli и не входят в одобренный белый список K1, поэтому не отправляются. |

## 5. Инструмент и формат снимков

`xh2_snapshot.py LABEL OUTPUT_ROOT [--backup]`:

- находит ровно одну X-H2 `VID_04CB&PID_02F2`, после DeviceInfo проверяет модель `X-H2` и прошивку `5.30`;
- сохраняет `device_info.bin`, разобранный DeviceInfo и WPD-сведения;
- для каждого объявленного свойства вызывает `0x1014` и `0x1015`, сохраняя response, параметры, исходные байты в hex, SHA-256 и декодирование, если тип доступен;
- при одобренном BACKUP сохраняет `backup_object_info.bin` и `backup.bin`, размер и SHA-256;
- пишет `snapshot.json`, человекочитаемый `run.log` и машинный `operations.jsonl`; последний журналирует каждый WPD `SendCommand` (`EXEC_READ`, каждый `READ_DATA`, `END_DATA_TRANSFER`) и каждую PTP-операцию до отправки;
- не использует WPD vendor-opcode/vendor-description запросы и не перечисляет объекты: для задачи это лишние обращения к устройству.

`diff_snapshots.py SNAPSHOTS_ROOT OUTPUT` сравнивает значения свойств и байты BACKUP попарно. Для сценария 02 выделяет два класса: **strict** (02 отличается от 01, а все контроли 03–07 равны 01) и **scenario_only** (значение/байт 02 не встречается ни в одном контроле). Отдельно показывает шум `01_база ↔ 07_база_повтор`; отсутствующие данные не считаются совпадением.

### 7.3 Гипотеза «перезапуск питания» — подтверждена снимком 07C

Процедура владельца (сообщена координатору): для 01–06 — каждый раз ВЫКЛЮЧЕНИЕ камеры, отключение кабеля, включение, смена меню, ВЫКЛЮЧЕНИЕ, подключение кабеля, ВКЛЮЧЕНИЕ; для 07/07B — без перезапуска (только отключил кабель, сменил меню, подключил). Для 07C — выключил и включил с подключённым кабелем, **без съёмки и без нажатий**.

| Снимок | Перезапуск | Съёмка | `0x1A8` | `0x1D8` | `0x18C` | `0x681` | `0xF6BC` |
|---|---|---|---|---|---|---|---|
| `06_DISP_OFF` | да | да | 1 | 1 | 800000 | 69 | 21851 |
| `07_база_повтор` | нет | нет | 1 (stale) | 1 (stale) | 800000 (stale) | 69 (stale) | 21851 |
| `07B_база_повтор` | нет | полунажатие | 1 (stale) | 1 (stale) | 800000 (stale) | 69 (stale) | 21851 |
| `07C_база_повтор` | **да** | **нет** | **3** | **3** | **2500** | **0** | **23126** |

Вывод: output-поля `0x1A8` (фактический затвор), `0x1D8` (DOTLCD_SHUTTERTYPE), `0x18C` (SHUTERSPEED_OUTPUT) и служебное `0xF6BC` обновляются при **выключении/включении питания** (запись банка настроек при выключении либо пересчёт при загрузке), а не при спуске затвора: в 07C они обновились без единого кадра и без нажатий. Версия «только при полном спуске» не подтвердилась (07C без нажатий); полунажатие (07B) тоже не обновляет. Display-индекс `0x681` (DOTLCD_SHUTTERSPEED) при загрузке сбрасывается в 0 (в 01 после съёмки был 40) — заполняется в процессе работы камеры. `0x1D8`, ранее считавшийся «зеркалом меню», ведёт себя как output-поле режима съёмки (в 07B меню EF=3, `0x1D8`=1).

Практическое правило для следующих снимков: после смены конфигурации владелец должен **перезапустить питание камеры** (как в 01–06) перед подключением и снимком; иначе output-поля блоба отстают от меню и не пригодны для проверки фактического затвора/выдержки. Меню-поля (`0x63A`, `0x5B2`, `0x4F8`, `0x68C`, `0x29B`) обновляются без перезапуска.

### 7.4 Классификация runtime/контекстных полей (Г)

- **FRONT_CMD_ASSIGN** (`UI_SETP_FRONT_CMD_ASSIGN`): 1154 во всех снимках 01–05 и 07–07C, **20 только в 06**. Владелец передний диск не трогал (подтверждено координатором) — это не настройка, а контекстное состояние UI: в 06 кабель подключён из меню НАСТРОЙКА (диск = навигация по вкладкам), на экране съёмки = выдержка. Согласуется с изменением позиций меню в 06. Класс: **Г — runtime/контекстное состояние UI**.
- Позиции меню (`STILL_MENU_POS_TAB/ITEM`, `SETUP_MENU_POS_ITEM_1/2`, `SETUP_COMM_MENU_POS_ITEM`) и `SETTING_CHKSUM` — служебная зона `0xC0–0xE5`, не учитывать (как в ПЕРЕДАЧА).
- Display-состояние: `DOTLCD_SHUTTERSPEED` (`0x681`), `DOTLCD_FLASHTTLMODE`, `DOTLCD_RECOORMODE`, `DOTLCD_EXPOSUREMETER_OUTPUT`, `DOTLCD_UNKNOWNSTATUS_OUTPUT` — различаются в повторной базе 01↔07C, класс Г.
- **`0xF6BC` — «не установлено», не счётчик спусков**: не менялся без перезапуска (06=07=07B=21851) и вырос на 1275 (21851→23126) при перезапуске **без съёмки** (07C). Монотонный рост в 01–06 объясняется перезапусками питания, а не кадрами. Привязка к UI_SETP не доказана.
- `0xF724` — volatile-метаданные (вне первой контрольной суммы), не учитывать.
- **Поле file `0x673` (u8)**, именуемое декодером `UI_SETP_DOTLCD_EXTFLASHEMITTESTPERMIT`: значения по серии 01/02/02B/03/04_MS/04_MS_CH/02C/05/06/07/07B/07C = 0/1/0/1/0/1/0/1/0/0/0/0 — следует за конфигурацией, не guard-маркер; причина не установлена (нужны flash-контроли). 3. **Границы вывода**: наблюдения владельца при 1/8000 (`02C`) и 1/16000 (`02B`) в этой сессии не собирались — видимость на этих выдержках остаётся непроверенной; переносить вывод «линий нет» на них нельзя. Исходная гипотеза «дефект должен воспроизводиться в 02B/02C» визуально не подтверждена и не опровергнута данной серией.
4. **Достоверность**: все снимки серии валидны по конфигурации, кроме `08` (EF вместо ES — сохранён как доказательство, наблюдение при 1/500 помечено EF). Output-поля обновлены: владелец перезапускал питание после каждой смены; `0xF6BC` рос на каждом переходе (23126→24560→24973→25318→26016→26329) — индикатор перезапуска/служебное («не установлено», не счётчик спусков).
5. **Необъяснённые байты** diff серии — runtime/служебные: блок пути кадра `0x84F–0x86B` (ASCII-путь появляется/очищается; триггер не установлен, вероятно связан с просмотром), служебный хвост `0xF6C0–0xF6C5`, `0xF728–0xF729`; сценарных полей не касаются, привязка не установлена.
