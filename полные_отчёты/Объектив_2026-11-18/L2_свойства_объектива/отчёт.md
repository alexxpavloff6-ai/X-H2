# L2 — свойства объектива 0x1DB2…0x1DC2

## Краткие выводы

1. Свойства читаются через общий байтовый массив, выбранный глобальным указателем. Геттер принимает номер свойства; u16-геттер объединяет байты с соседних адресов младший байт первым (**Д**).
2. В X-H2 5.30 `0x1DB2…0x1DB7` — свойства u8, а `0x1DB8`, `0x1DBA`, `0x1DBC`, `0x1DBE`, `0x1DC0`, `0x1DC2` — свойства u16. Нечётные адреса между u16-ключами — второй байт значения, а не отдельные ключи (**Д**).
3. Эти пары подставляются в описание операций объектива по классу запроса. Пара `0x1DB3/0x1DBA` использовалась MF-ветвью, а `0x1DB2/0x1DB8` — резервными/прочими ветвями (**Д**).
4. Для `0x1DB3` и `0x1DBA` кодового писателя не обнаружено; кто наполняет активный массив свойств и как значения попадают из объектива, не установлено (**Д** для отрицательного поиска в блоках; **Г** для источника).
5. В ветвях lenscom (`0x13EB4DC`, переключатель `0x13EBB88`) прямой записи этих свойств или таблицы соответствия кодов `0x18D9–0x1944` номерам свойств не найдено. Поток разбирает сообщения и передаёт события обработчикам; возможный косвенный обратный вызов остаётся за границей (**Д/Г**).
6. В X-H2 5.33 `0x1DB3` и `0x1DBA` больше не читаются. Для MF с идентификатор объектива `0x411` код задаёт шаг `0x8C` и значение `0xE4`; прочим объективам — шаг `0x80` и значение `0` (**Д**).
7. Изменение относится к MF-операциям `0x1E/0x20` диспетчера `0x2CEB0E4`; оно не доказывает изменение алгоритма автофокуса или пользовательской настройки угла кольца (**Д**).

## Хранилище и доступ

В X-H2 5.30 байтовый доступ выполняет `0x149AE2C`: через служебную функцию `0x149ADA0` выполняются диапазонные ветви и обращение к глобальному параметру; затем байт читается из массива по базе, загруженной из `0x20C1458`, со смещением, равным ID. Обёртка `0x149B0CC` использует этот путь как u8-геттер. Обёртка `0x149B18C` вызывает сборщик двух соседних байтов `0x149B0E0`; младший байт берётся первым. В 5.33 соответствующие обёртки диспетчера — `0x14920FC` и `0x14921BC`.

Глобальная переменная `0x20C1458` содержит указатель на активный массив, а не сами данные. Статический разбор здесь не выявил, кто устанавливает указатель и какой внешний загрузчик наполняет массив.

Это отдельная операция чтения, не запись свойства.

## Lenscom и предполагаемый писатель

Поток `lenscom` получает запись `0x88` через `0x14CF354`, определяет класс по коду события и направляет сообщения в таблицу ветвления `0x1912414`. Известные коды `0x18D9–0x1944` — коды сообщений протокола. По доступным ветвям данные распаковываются и передаются функции-обработчику/функции обратного вызова. Прямой вызов геттеров семейства 0x1DB2–0x1DC2 в обработчике/переключателе не обнаружен, и явного вызова сеттера свойств не установлено.

Поэтому назначить конкретные коды lenscom отдельным свойствам нельзя: найденная схема не показывает ни ID свойства в событии, ни прямую запись в массив. Вполне возможно, что обратный вызов из контекста записи передаёт данные дальше, однако его фактическая цель в данной цепи не доказана. Для `0x1DB3/0x1DBA` более ранний поиск по блокам также не нашёл кодового писателя; значения описаны как приходящие извне, но маршрут их загрузки остаётся открытым.

## Что изменилось в 5.33

В 5.30 MF-операции `0x1E/0x20` брали пару `0x1DB3` (u8) и `0x1DBA` (u16), затем помещали `2 × 0x1DB3` в `out+0x50`, а `0x1DBA` — в `out+0xA0`. Если значения были неподходящими, эта ветвь могла сформировать нулевые параметры; фактические значения на конкретном объективе неизвестны.

В X-H2 5.33 оба чтения удалены. При идентификатор объектива `0x411` ветвь выдаёт `out+0x50 = 0x118` (из шага `0x8C`) и `out+0xA0 = 0xE4`. Для остальных объективов соответствующая MF-ветвь использует `out+0x50 = 0x100` и `out+0xA0 = 0`. Тем самым прошивка перестала полагаться на старые два значения именно в этой операции и задала параметры явным образом для XF30mm Macro (сопоставление ID модели подтверждено материалами сравнения версий, не строковым именем внутри прошивки).

В X-T5 реализация отличается: в её MF-ветви используются свойства `0x2059/0x205A` и `0x205C/0x205E`. Это поведение другой модели; переносить его на X-H2 нельзя.

Правка затрагивает разбор MF-операций объективного диспетчера `0x2CEB0E4`, а не выбор режима фокусировки AF-S/AF-C как таковой. Связь с последующим транспортом до мотора не прослежена. Параметры похожи на коэффициенты пересчёта движения кольца, однако физический смысл конкретных величин без дальнейшего потребителя остаётся вероятным толкованием (**К**).

## Схема потока

```text
Объектив / внешний источник данных (точный загрузчик не найден)
        ? запись в активный массив свойств
        ↓
общий массив по базе из 0x20C1458 → геттеры по ID 0x1DBx
        ↓
диспетчер 0x2CEB0E4
  5.30: MF 0x1E/0x20 → 0x1DB3 + 0x1DBA → out+0x50 / out+0xA0
  5.33: lens 0x411 → константы 0x8C / 0xE4; прочие → 0x80 / 0
        ↓
описатель/состояние операции; физическая команда мотору не установлена

Отдельная ветвь: lenscom 0x13EB4DC → код 0x18D9–0x1944 → обработчик/callback.
Прямого перехода из неё в писатель массива 0x1DBx не найдено.
```

## Доказательность и границы

- **Д** — непосредственные вызовы геттеров и инструкции диспетчера в блоках X-H2 5.30/5.33; идентификаторы, типы и формирование выходных полей.
- **К** — трактовка пары как коэффициентов/опорных параметров пересчёта движения кольца, согласующаяся с тем, как поля преобразуются.
- **Г** — источник фактических значений и косвенный callback lenscom; конечная доставка команды на мотор.

Отрицательный вывод ограничен проверенными блоками и прямыми/видимыми путями. Он не исключает косвенный вызов, другой блок прошивки или данные, сформированные вне исследованного кода.

## Что это даёт для будущих доработок прошивки

Для правки MF X-H2 точка, где 5.33 обошла старые данные, — ветвь диспетчера `0x2CEB0E4`: там формируются `out+0x50` и `out+0xA0`. Изменение обработчика lenscom само по себе пока нельзя считать способом менять свойства `0x1DBx`: доказанной связи с писателем нет. Чтобы менять данные свойств, сначала нужно найти установку указателя `0x20C1458`, запись в активный массив и цель обратных вызовов lenscom; физический эффект правки затем требует отдельного прослеживания downstream-потребителя.
