# Четыре камеры: запись представления MODE в виртуальный буфер

## Результат

Развита проверка читателя MODE для [X-H2S/X-T5](../X-H2S_X-T5/Отчёт.md) и [X-H2/X100VI](../X-H2_X100VI/Отчёт.md): теперь исполнение в Unicorn продолжается не только до входа оригинальной функции записи двух байтов, но и **через неё до возврата читателя**. Подготовка сохранённого MODE и последующий читатель запускаются отдельно в одной VM; память с результатом сохранителя не переписывается, однако штатный вызов читателя на камере не показан.

| Модель | Вход UI | Сохранённый MODE | Результат перевода перед функцией записи | Байты виртуального буфера после выполнения |
|---|---:|---:|---:|---|
| X-H2 | 14 | 13 | 11 | `0b 00` |
| X-H2 | 0 | 0 | 1 | `01 00` |
| X-H2S | 14 | 13 | 11 | `0b 00` |
| X-H2S | 0 | 0 | 1 | `01 00` |
| X-T5 | 14 | 13 | 11 | `0b 00` |
| X-T5 | 0 | 0 | 1 | `01 00` |
| X100VI | 14 | 13 | 11 | `0b 00` |
| X100VI | 0 | 0 | 1 | `01 00` |

Согласно словарю, UI 14 — Classic Chrome. Здесь `11` — другое внутреннее представление, а не цветовой коэффициент, не доказанное поле кадра и не значение JPEG/RAF MakerNote. Назначение этого буфера и то, попадает ли он в файл, не установлены. Результат не описывает полный рецепт и не позволяет судить о внешнем виде фотографии.

## Как поставлен опыт

Используются оригинальные инструкции и карты X-H2 5.30, X-H2S 7.30, X-T5 4.31 и X100VI 1.31 из предыдущих исследований. Исходный DAT каждой модели сверяется по SHA-256 до и после. Сначала исходная ветвь выбора с искусственными входами UI `14` либо `0` и нулевыми флагами записывает MODE: у X-H2S/X-T5 старое слово `0xffffffff`, у X-H2/X100VI — 0 при новом 14 и 14 при новом 0. Затем исследователь отдельно запускает читатель с искусственным объектом `0x60000000`, не меняя MODE в VM. Исходный преобразователь передаёт число оригинальной функции двухбайтовой записи.

Для проверки доступности буфера вызов отдельной функции заменён синтетическим возвратом; её реальное содержимое и допустимость записи **не исполнялись и не подтверждены**. При возврате 0 реальный writer пишет два байта в виртуальный буфер и увеличивает синтетический счётчик с 0 до 2. Если принудительно вернуть 1, начальные байты `aa bb` и счётчик 0 остаются неизменными. Это отрицательный контроль проверенной ветви, не доказательство защиты реальной камеры.

| Модель | Перехваченная функция | Адрес виртуального буфера при счётчике 0 |
|---|---:|---:|
| X-H2 | `0x2bf66d0` | `0x26be0c4` |
| X-H2S | `0x2f0eca8` | `0x29d9e9c` |
| X-T5 | `0x2b369f0` | `0x25fa75c` |
| X100VI | `0x2df31d0` | `0x284170c` |

Адреса — модельные, не смещения DAT и не наблюдаемые адреса памяти включённой камеры. До эксперимента буфер заполнен `aa bb`. Два байта и позиция подтверждены исполнением исходных команд writer с указанным искусственным окружением, но файл, носитель, ISP и камера не задействованы. Сохранённое значение не передано в setter структуры кадра; этот мост остаётся открытым.

## Воспроизведение

```text
python -X utf8 Анализ_прошивки/Связь_MODE_кадра/Проверка_записи/проверить_запись.py
```

Сценарий использует существующие локальные зависимости и помощники предыдущих опытов, перезаписывает только собственный [результаты.json](результаты.json), DAT только читает. Выполнены 12 случаев: по два разных входа и одному отрицательному контролю для каждой из четырёх камер; все сравнения в данном запуске выполнены.
