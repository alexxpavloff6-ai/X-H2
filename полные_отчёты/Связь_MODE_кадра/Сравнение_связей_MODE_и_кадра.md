# Продолжение: куда передаётся настройка имитации плёнки

## Основной вывод

Для каждой из четырёх камер выполнено продолжение исследования **собственного** машинного кода, а не перенос адресов с X-H2. Найдены два разных участка:

1. **Новый потребитель сохранённого MODE:** исходный код читает сохранённую настройку, переводит её в другое внутреннее представление и записывает два байта в виртуальный буфер. При заданных условиях Classic Chrome даёт `MODE=13`, представление `11`, байты `0b 00`. Назначение буфера пока не установлено.
2. **Вход в структуру кадра:** найден исходный вызывающий код перед setter и исполнена его часть с искусственно заданным значением. Этот участок работает с другим источником данных. Для X-H2/X100VI исполнение дошло до фактической записи в **виртуальное** поле кадра; X-H2S/X-T5 — до входа setter, до самой записи.

**Между этими двумя участками полного моста пока нет.** Нельзя заявлять, что запись в найденный двухбайтовый буфер создаёт кадр или что значение исходного MODE штатно дошло до setter. В опыте с setter его источник заполнялся исследователем.

## Что означают числа

Словарь каждой из исследованных прошивок связывает UI-код 14 с базовой имитацией Classic Chrome. Проверенные значения относятся к внутренним форматам:

```text
выбор UI 14 → сохранённое MODE 13
                   │
                   ├─ отдельно вызванный оригинальный читатель
                   │        → представление 11 → байты 0b 00 в виртуальном буфере
                   │
                   └─ ? неизвестный штатный мост ? → источник setter кадра
                                                        ↓
                                  эксперимент: синтетические 13 или 0 → setter
```

Стрелки от исследовательского опыта показывают отдельные вызовы в одной VM; **это не непрерывная съёмка**. Физическая кнопка, реальные камера/объектив, аппаратный ISP и готовый файл не участвовали. `11` не доказано как тег MakerNote или цветовой коэффициент; Classic Chrome также не равен полному пользовательскому рецепту. JPEG владельца обработаны Lightroom и здесь не используются как внутрикамерный эталон.

## Сопоставление одинаковых опытов

| | X-H2 5.30 | X-H2S 7.30 | X-T5 4.31 | X100VI 1.31 |
|---|---|---|---|---|
| Собственная ячейка сохранённого MODE, модельный адрес | `0x02680414` | `0x0299c40c` | `0x025bcccc` | `0x027f7a54` |
| Синтетический UI 14 → сохранённое MODE | `13` | `13` | `13` | `13` |
| Отдельный оригинальный читатель → представление | `11` | `11` | `11` | `11` |

| Контроль UI 0 → MODE → представление → байты | `0 → 1 → 01 00` | `0 → 1 → 01 00` | `0 → 1 → 01 00` | `0 → 1 → 01 00` |
| Адрес начала setter кадра | `0x01562e18` | `0x018827c8` | `0x01559350` | `0x0162a450` |
| Поле внутри структуры | `+0xc0` | `+0xc0` | `+0xc0` | `+0xd0` |
| Где экспериментально наблюдался синтетический вход | В поле кадра записано 13 | На входе setter 13 или 0; запись setter не исполнялась | На входе setter 13 или 0; запись setter не исполнялась | В поле кадра записано 13 |
| Незакрытый источник | `0x04d1fbc8 + 4×index` | `0x04c935c8 + 4×index` | `sp+0x68` или `0x04ba6948 + 4×index` | `0x052b6bb8 + 4×index` или отдельный вычислитель |

Адреса и структуры выше — **условные модельные адреса распакованных образов**, не смещения DAT и не показания памяти работающей камеры. `index` в опытных ветвях ограничивается до младшего байта. Происхождение данных массива или альтернативного вычислителя из сохранённого MODE не доказано. Подробности различаются: у X100VI условие выбора альтернативного массива в опыте не исполнялось — исследователь начал после этой развилки; у X-T5 подготовка `sp+0x68` изучена статически, а при вызове setter буфер вручную заполнен, сам предшествующий вычислитель не исполнялся.

## Что действительно исполнено

### Сохранитель → отдельный читатель → запись

Для каждой модели оригинальная ветвь получает искусственные UI и старое значение, выполняет конвертер и записывает MODE в виртуальную память. Затем исследователь **отдельно** вызывает оригинальный читатель в той же памяти: MODE не переносится вручную. Читатель и writer исполняются до возврата. Проверка доступности записи заменена искусственным возвратом:

- возврат 0: UI 14 даёт `0b 00`, UI 0 даёт `01 00`, виртуальный счётчик увеличивается на два;
- возврат 1: предварительные байты `aa bb` и счётчик остаются без изменения.

Это 12 выполненных случаев — по три для каждой модели; неподменённый код проверки доступа, реальное выполнение камеры и значение буфера вне VM не установлены. [Сценарий, входы, адреса и результаты](Проверка_записи/Отчёт.md).

### Источник → обёртка → setter

Для X-H2 и X100VI искусственная запись 13 в индексированный массив приводит к прохождению оригинальной обёртки и записи 13 в виртуальное поле кадра. Искусственный специальный handle `0xffff0000` выбирает положительную проверку; при `0xffffffff` setter не вызывается и контрольное поле остаётся неизменным. Переходы, формула адреса и начальные значения — [в отчёте двух моделей](X-H2_X100VI/Отчёт.md).

Для X-H2S искусственное значение подано в массив, для X-T5 — на стек; оригинальные инструкции и проверка обёртки доведены до входа setter, но сам setter в этих опытах ещё не исполнялся. Проверены значения 13 и 0 и отрицательная ветвь по handle. Подробности и подтверждения — [в отчёте X-H2S/X-T5](X-H2S_X-T5/Отчёт.md). Начальный handle и объекты заданы исследователем, их тип и условия штатной съёмки не доказаны.

## Что исследовать следующим

- Найти реальные записи в индексированные массивы и происхождение слова X-T5 на стеке и вычислителя X100VI.
- Проследить, поступает ли к этим источникам сохранённый MODE; поиск прямых ARM64-ссылок не покрывает все косвенные адреса и функции.
- Замкнуть только доказанные границы между состоянием и кадром, не заменяя отсутствующий переход вручную; затем изучать взаимодействие с остальными параметрами рецепта и аппаратной обработкой.
- Для вывода о фотографии нужны дальнейшие наблюдения на реальных камерах и контролируемые прямые камерные изображения; одна запись в виртуальной памяти не является обработкой пикселя.

Дополнительно для X100VI выполнен отдельный [опыт диспетчера восстановления](../Исследование_блоков/X100VI_диспетчер/Отчёт.md): исходный отправитель и приёмник соединены искусственной очередью, а другой обработчик отдельно использовал полученное значение в расчёте адреса. Реальный вывод панелей не доказан.
