# X-H2S 7.30 и X-T5 4.31: читатели MODE и вызов setter кадра

## Итог и границы

Найдена и **исполнена новая связь от сохранённого MODE к другому потребителю**: исходная функция читает ячейку, проверяет возможность перевода представления 3→4 и передаёт результат в функцию записи двух байтов. Для Classic Chrome это **11**, а не 13. Эта функция записи и вызывающий её диспетчер не отождествлены с наполнением структуры кадра. **Мост из сохранённого MODE к setter кадра не доказан** ни у одной модели. У обеих найдены непосредственный вызывающий setter код и его источник; у X-T5 прослежена дополнительная подготовка. Не установлено, каким путём сохранённое слово влияет на эти источники.

Данные — собственные распакованные блоки обеих прошивок; адреса — виртуальная карта этих блоков, а не смещения в DAT. Исполняются оригинальные ARM64-инструкции в Unicorn с искусственной памятью и явно заданными регистрами; это не запуск камеры. Отдельные эксперименты с setter используют **вручную заданный синтетический источник**, они не подтверждают штатную передачу MODE. Никаких выводов о готовых снимках, фактическом событии съёмки или JPEG нет.

## Воспроизведение и входы

Из корня проекта: `python Анализ_прошивки/Связь_MODE_кадра/X-H2S_X-T5/исследовать.py`. Требуются имеющиеся в `Анализ_прошивки/инструменты` Unicorn и Capstone, существующий `анализ_файла.py` и оба DAT. Скрипт только читает DAT, проверяет SHA-256 и записывает рядом `результаты.json`: SHA и размеры распакованных блоков, байты и инструкции двух исследованных фрагментов, границы и результаты экспериментов. Хэши входов:

* X-H2S `FWUP0027.DAT`: `87c566c1ff6343e4c7463a4ef968183f41d1f24cc63d610433d3a387b13f731b`. Блоки: `0x40000`, `0x1421000` (DAT `0x300274`), `0x2cca000` (DAT `0x840274`).
* X-T5 `FWUP0030.DAT`: `790d6deecf26766188b0e506e40645e6b816addfeba39a52334349405421724e`. Блоки: `0x40000`, `0x1101000` (DAT `0x300274`), `0x28eb000` (DAT `0x820274`).

Память VM вне загруженных блоков изначально нулевая. Для сохранителя UI-слово — 14 из словаря Classic Chrome или 0 для контрольной имитации; сравниваемое старое слово и ячейка состояния искусственно равны `0xffffffff`, флаг ошибки — 0. Происхождение этих глобалов в работающей камере не установлено. Исполнение начинается до сравнения и непрерывно проходит оригинальный конвертер и сохранитель до указанной границы. Затем регистры и стек сбрасываются, но память с результатом сохранителя **не переписывается**; читатель запускается отдельно с `x0=0x60000000` (искусственный объект назначения) и останавливается при входе в его функцию записи. Это последовательные отдельные запуски на одной памяти, не доказательство вызова читателя камерой после сохранителя.

| Модель | Сравнение → граница | UI-слово / старое слово | MODE | Читатель → граница записи | `w1` на границе, UI 14 / UI 0 |
|---|---|---|---|---|---|
| X-H2S | `0x164b194 → 0x164b62c` | `0x236e100 / 0x236bc70` | `0x299c40c` | `0x2f1328c → 0x2f1111c` | 11 / 1 |
| X-T5 | `0x132a978 → 0x132ae4c` | `0x2003300 / 0x2001080` | `0x25bcccc` | `0x2b3b53c → 0x2b38e3c` | 11 / 1 |

В обоих случаях состояние для UI 14 равно 13, для UI 0 равно 0, флаг ошибки равен 0. 0 — отрицательный контроль против фиксированного результата 11; не тест невозможности перевода. Входы 14 и 0, а также таблица конвертера задокументированы в соответствующих отчётах `Сквозной_цвет`.

## Что читает MODE

* X-H2S `0x2f132a4: adrp x0, #0x299c000; 0x2f132a8: ldr w1, [x0, #0x40c]`; `w0=0x68d`, `w2=3`, `w3=4`, вызов проверки `0x1455944`. При ненулевом результате повторное чтение `0x2f132d8..dc`, вызов преобразователя `0x1455930` по `0x2f132e4`, затем `mov w1,w0; mov x0,x19; bl 0x2f1111c` (`0x2f132e8..f0`). При нулевом результате передаётся константа 1 (`0x2f132b8..c0`). Вызывающий код `0x2f29380` передаёт адрес `sp+0x38`.
* X-T5 соответствующие инструкции `0x2b3b554..558`, параметр `0x6a3`, проверка `0x113595c`, повторное чтение `0x2b3b588..58c`, преобразователь `0x1135948` по `0x2b3b594`, далее вызов `0x2b38e3c` по `0x2b3b5a0`. Ветка нулевой проверки передаёт 1 по `0x2b3b568..570`. Вызывающий код `0x2b52784` передаёт `sp+0x38`.

Назначение функции записи установлено статически: X-H2S `0x2f1112c` ограничивает значение до 16 бит, `0x2f11134` вызывает проверку длины, а `0x2f1113c..174` дважды увеличивает счётчик `[x19]` и пишет младший, затем старший байт в глобальный буфер с базой `0x29d9e9c`. X-T5 `0x2b38e4c..94` делает то же для базы `0x25fa75c`. Поскольку эксперимент останавливается **до входа** в эти функции, сами записи не исполнялись; их назначение не следует путать с записью в кадр. Результат 11 — представление 4, полученное оригинальной функцией для 13, а не значение кадра.

Прямые ссылки на ту же ячейку найдены также в X-H2S `0x2fae838`, `0x2fae90c`, `0x2fae92c`, `0x2fb7abc` и X-T5 `0x2bd8758`, `0x2bd882c`, `0x2bd884c`, `0x2be17d0`: там сравнения либо преобразования с другими идентификаторами. Это не установленные вызовы setter. Поиск адресных ссылок выполнялся по ARM64 `adrp` к странице и 32-битному непосредственному `ldr/str` с нужным смещением в следующих 11 инструкциях: он не исключает косвенный доступ, другой способ формирования адреса или непрямые вызовы.

## Кто вызывает setter кадра

**X-H2S.** Единственный найденный прямой `bl` в распакованных блоках: `0x1874448 → 0x18827c8`. Обёртка начинается `0x18743dc` и вызывается по `0x32d2538`. Вызов получает `w0=w19` (контекст/handle), `w1=w20` (индекс кадра), `w2` из `0x32d2520..252c`: `adrp x0, #0x4c92000; add x0,x0,#0xaf8; add x0,x0,w20,uxtb #2; ldr w2,[x0,#0xad0]`, то есть массив `0x4c935c8 + 4*(w20 & 255)`. Сама обёртка вызывает проверку `0x1880f04` с типом `0xa`; при нуле возвращается без setter. Иначе `0x1884698` даёт индекс структуры, адрес кадра вычисляется как `0x25ba3d0 + 0x2748*index + 0x3e0 + 0xe8*frame_index`, а `w2` передаётся как `w1` setter. Сам setter пишет `[x0,#0xc0]`. Запись нуля в первый элемент массива наблюдается статически по `0x32c98b4`; происхождение остальных значений и связь массива с сохранённым MODE не установлены.

**X-T5.** Единственный найденный прямой `bl` setter: `0x154a6c4 → 0x1559350`; обёртка `0x154a658`, вызов `0x2ef90b4`. Аналогичная проверка `0x1557af8` с типом `0xa`; адрес кадра `0x2222248 + 0x2778*index + 0x3e0 + 0xf8*frame_index`; setter пишет `[x0,#0xc0]`. Непосредственный вход `w2` по `0x2ef90a0` загружается из `sp+0x68`, если результат `0x1542ca4` не равен 12. Если равен 12, ветка `0x2ef9228..238` заменяет его на элемент `0x4ba6948 + 4*(w20 & 255)`; нулевая инициализация первого элемента видна по `0x2eefd08`.

В обычной ветке массив из шести слов на `sp+0x68` подготавливается оригинальным вызовом `0x2ef9094 → 0x2f54574` с `w0=w19`, `w1=2`, `x2=sp+0x68`. Функция заполняет локальный семисловный блок результатами нескольких getter, включая `0x1543640 → 0x1558550`, читающий поле `+0x108` выбранной структуры. По `0x2f54670` вызывается `0x2eb2cfc`: исходный первый элемент проходит через `0x2eb2b54`; если он не `0xff`, сохраняется напрямую, иначе в зависимости от условий используются второй элемент или таблица/дополнительное отображение. Полученный первый элемент по `0x2f54674..78` записывается в начало выходного блока, т.е. затем в `sp+0x68`. Связь этого поля `+0x108`, параметров таблицы либо альтернативного массива с сохранителем MODE не найдена. Этот маршрут установлен статически, а не исполнен от сохранителя.

## Отдельный эксперимент caller → setter

Сценарий запускает X-H2S с `0x32d2520`, индексом `w20=0` и искусственным словом 13 либо 0 в элементе `0x4c935c8`. Для X-T5 запуск с `0x2ef90a0`, искусственный `w0=0` выбирает обычную ветку, а 13 либо 0 заранее положено в `sp+0x68`: предшествующий `0x2f54574` **не исполняется**. Это модельные значения для проверки передачи, не установленные камерой значения. В обоих случаях `w19=0xffff0000` — искусственный специальный handle, который исходная проверка принимает; нулевая модельная глобальная таблица выбирает индекс 0. Остановка на первой инструкции setter, до его записи: X-H2S `x0=0x25ba7b0`, X-T5 `x0=0x2222628`, `w1` равен заданным 13 или 0. Контроль `w19=0xffffffff` доходит до инструкции после вызова обёртки (`0x32d253c` / `0x2ef90b8`) без достижения setter для обоих значений. Эти наблюдения не показывают реальный handle, подготовку данных или фактическую запись кадра.

Прямые вызовы искались по всем распакованным блокам декодированием ARM64 `BL` и сравнением адреса цели. Косвенные вызовы и другие способы обращения не исключены. Следующий конкретный незакрытый разрыв: производитель `0x4c935c8` и источников X-T5 `sp+0x68` / `0x4ba6948`, включая структуру `+0x108`, должен быть связан с ячейкой сохранителя доказуемым потоком данных; нынешние независимые эксперименты не связывают их.
