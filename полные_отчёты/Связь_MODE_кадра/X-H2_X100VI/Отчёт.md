# X-H2 5.30 и X100VI 1.31: от сохранённого MODE к полю кадра

## Итог и граница

Найден новый, более длинный участок **перед setter кадра**: исходный код читает индексированное слово, передаёт его третьим аргументом обёртке, а та при положительном результате проверки вызывает setter. Для обеих камер этот участок исполнен оригинальными инструкциями на искусственной памяти с положительным и отрицательным контролем. Также для обеих камер отдельно исполнены исходные сохранение MODE и его последующее чтение с преобразованием в той же виртуальной памяти, без ручного переноса сохранённого значения.

**Мост целиком не доказан.** Источник индексированного слова перед setter не связан найденной цепью инструкций с сохранённой глобальной ячейкой. В X100VI есть ещё альтернативный путь через результат отдельного вычислителя. В опыте с setter значение 13 специально записано в индексированный массив исследователем. Это проверка участка от массива до поля кадра, а не передача штатного сохранённого MODE. Оба запуска фрагмента чтения MODE начинаются отдельно от сохранителя; это не непрерывная трасса всей камеры. Образы, RAM и регистры Unicorn не являются наблюдением действующей камеры. Снимки не исследовались и о готовых фотографиях выводов нет.

## Источники и воспроизведение

Из корня проекта: `python -X utf8 Анализ_прошивки/Связь_MODE_кадра/X-H2_X100VI/исследовать.py`. Используются локальные Capstone, Unicorn и `анализ_файла.py`; `результаты.json` содержит инструкции с байтами, адреса, входы и результаты. DAT читаются и сверяются по SHA-256 до и после:

* X-H2 `FIRMWARE/ver 5.30/FWUP0028.DAT`: `be47168cb075ef726e67cb4bb08175a896047a3b0de2bcb6e65333b22cfcb203`; FFLZ с `0x300274`, `0x840274`, модельные базы `0x01101000`, `0x029ae000`.
* X100VI `Firmware на прочиеFuji/FPUPDATE.DAT`: `0d48d2ae26ac7ebab9b0e4cac56324807ec1ea8ae30df06b0b9e79066dc0a14a`; FFLZ с `0x9c02bc`, `0x10e02bc`, базы `0x011c1000`, `0x02b8f000`. Второй блок записывается поверх первого при перекрытии. Статический поиск использует ту же карту с приоритетом второго блока. Адреса — модельные, не смещения DAT и не измеренные адреса работающей камеры.

## Читатели сохранённого состояния

| | X-H2 | X100VI |
|---|---|---|
| сохранитель | `0x012eefc0` | `0x013d2040` |
| ячейка | `0x02680414` | `0x027f7a54` |
| сравнение, изменение | `0x0132d138` → `0x0132d5e0` | `0x01411a3c` → `0x01411fb4` |
| отдельный читатель | `0x02bfacf8` → `0x02bfad10` | `0x02df7cb0` → `0x02df7cc8` |
| другая ветвь читателя | `0x02bfaccc` | `0x02df7c84` |
| чтение для условных сравнений/конвертации | `0x02c96ad8`, `0x02c96bac`, `0x02c96bcc`, `0x02c9f9dc` | `0x02e9a6bc`, `0x02e9a790`, `0x02e9a7b0`, `0x02ea37c4` |

Например, X-H2 `0x02bfad00: adrp x0, #0x2680000`, `0x02bfad04: ldr w1, [x0, #0x414]`, затем `0x02bfad08: mov w0, #0x68e` и вызов `0x01135930`. Аналог X100VI: `0x02df7cb8: adrp x0, #0x27f7000`, `0x02df7cbc: ldr w1, [x0, #0xa54]`, `0x02df7cc0: mov w0, #0x6dc`, вызов `0x011f5a34`. В этой ветви задаются представления 3→4. Возвращённое значение передаётся функции `0x02bf8b44` / `0x02df56d4` инструкциями вызова `0x02bfad18` / `0x02df7cd0`. Статически эта функция маскирует `w1` до 16 бит и, если проверка размера возвращает 0, двумя `strb` записывает младший и старший байты (`0x02bf8b80`, `0x02bf8b9c` / `0x02df5710`, `0x02df572c`), увеличивая счётчик; это **другой** получатель, не setter кадра. Его назначение и связь с кадром не установлены. Запись байтов в данном опыте не исполнялась: граница — вход этой функции.

Опыт: два сравниваемых слова искусственные `14` и `0`, начальное сохранённое значение 0, флаги обнулены (полные адреса в JSON). После исходного участка сохранено 13. Исследователь отдельно запускает читатель в **той же** памяти: `w0=11`; затем устанавливает синтетический указатель получателя `x19=0x70001000` и продолжает оригинальные инструкции до входа функции записи, где `w1=11`. Значение 13 не копируется им вручную. Дополнительный опыт с искусственными словами `0` и `14` даёт MODE 0 и `w1=1`. При `14 == 14` первый запуск останавливается сразу за сравнением (`0x0132d150` / `0x01411a54`), сохранённое 0 не меняется; отдельный читатель даёт `w1=1`. Контроль доказывает отсутствие записи только до указанной границы, не за пределами всей процедуры. В предшествующей ветви читателя с тем же чтением проверяется результат другого вызова; при нуле вызывается та же функция записи с аргументом 1 — это статический вывод, не выполненный здесь путь.

Поиск читателей охватывает непосредственную последовательность соседних `ADRP` и `LDR/STR` с тем же базовым регистром и точным смещением. Поиск прямых вызовов рассматривает выровненные 32-битные кодировки ARM64 `BL` в двух распакованных областях. Индиректные вызовы, иное вычисление адреса, таблицы указателей и нераспакованные области им не исключаются; найденные совпадения сами по себе не гарантируют достижимость.

## Кто вызывает setter кадра и с какими структурами

| | X-H2 | X100VI |
|---|---|---|
| setter и поле | `0x01562e18`, `frame+0xc0` | `0x0162a450`, `frame+0xd0` |
| прямой вызов setter | `0x01554ad4` | `0x0161adc8` |
| начало обёртки | `0x01554a68` | `0x0161ad5c` |
| прямой вызов обёртки | `0x02fbcccc` | `0x031db0b8` |
| проверка обёртки `(w0, 10)` | `0x01561554` | `0x01628b0c` |
| базовый адрес массива записей кадра | `0x0229e3a0` | `0x0230fa78` |
| вычисленный указатель записи | `base + frame_index*0x2748 + 0x3e0 + slot*0xe8` | `base + frame_index*0x2e20 + 0x408 + slot*0x108` |

Обёртка сохраняет входные `w0`, `w1`, `w2` в `w20`, `w19`, `w21`; вызывает проверку с константой `10`, при нулевом результате возвращается без setter; при ненулевом получает индекс кадра от `0x01564ce8` / `0x0162c5a0`, вычисляет адрес записи и передаёт в setter прежний `w2`. Конкретные блоки и байты сохранены в JSON. Не следует считать `w0`/`w1` известными именами объектов: их семантика не доказана.

У X-H2 инструкции `0x02fbccb4..0x02fbccc0` читают `w2` из `0x04d1fbc8 + (w20 & 255)*4`; после `mov w1,w20`, `mov w0,w19` вызывается обёртка. У X100VI при результате `0x016133a8 == 12` переход `0x031db22c..0x031db23c` читает `0x052b6bb8 + (w20 & 255)*4` и переходит к вызову обёртки. При результате, отличном от 12, `0x031db0a4` вместо этого загружает `w2` из `[sp+0x68]`: туда перед вызовом `0x03237e78(w19, 2, sp+0x68)` указана выходная структура. Внутри `0x03237e78` эта структура сначала обнуляется, вызываются дополнительные функции, затем вычислитель `0x0319324c`, и `0x03237f78..0x03237f7c` копирует его выходное слово в первый элемент структуры. Связь этого вычислителя с сохранённым MODE отдельно не доказана. В опыте альтернативная проверка `==12` не исполнялась: входной PC установлен прямо на её ветвь.

## Исполнение массива до кадра

Оба прогона начинаются не с физического события, а с `0x02fbccb4` / `0x031db22c`, и заканчиваются до следующего соседнего setter на `0x02fbccd0` / `0x031db0bc`. Искусственно заданы: массив по указанному адресу `13`, индекс `w20=0`, начальное поле `0xaabbccdd`, стек `0x7000f000`, значение индекса кадра по умолчанию 0 (`0x02271500` / `0x022c5768`). Другие байты берутся из соответствующих распакованных образов либо нулевой выделенной виртуальной памяти. Исследователь не устанавливает `w2` для setter: он загружается исходным кодом из искусственного массива и передаётся через реальные вызовы.

При `w19=0xffff0000` проверка использует специальную ненулевую ветвь, индексатор выбирает искусственный индекс по умолчанию, вызываются обёртка и setter, поле `0x0229e840` / `0x0230ff50` становится 13. При `w19=0xffffffff` проверка возвращает ноль, setter не посещается и поле остаётся `0xaabbccdd`. Это отрицательный контроль именно условия обёртки и границы текущего запуска, а не утверждение, что эти значения представляют обычные дескрипторы камеры.

## Конкретный незакрытый разрыв

Не установлено, кто штатно заполняет `0x04d1fbc8 + index*4` и `0x052b6bb8 + index*4`, и получает ли этот источник значение из `0x02680414` / `0x027f7a54`. Равно не установлено, поступает ли сохранённое значение в вычислитель `0x0319324c` альтернативной ветви X100VI. Следующий исследовательский шаг — проследить записи массивов и входы вычислителя через косвенные адреса, не подменяя их содержимое как доказанный канал. Положительный опыт с искусственным массивом и чтение состояния не соединяют эти два края.
