# Каталог записей X-H2 5.30 — регистрации, публикации и читатели

## Основные выводы

1. Хранилище записей динамическое: сервисный модуль не содержит готового перечня ID. Клиенты регистрируют объекты через `0x14CEDAC`, а сервис индексирует их в таблице `0x630170 + 8×(ID−1)`.
2. В блоках 0–1 найдено 98 прямых вызовов регистрации: 83 различных постоянных ID и 15 вызовов с вычисляемым ID. Для 83 постоянных ID восстановлены параметры дескриптора и сопоставлены прямые вызовы записи/чтения.
3. Регистрация передаёт пару `{число элементов, размер элемента}`. `0x14CF124` ограничивает длину публикации значением размером элемента за вычетом 8 байт; код выделяет `число элементов × (округлённый размер элемента + 8)` байт.
4. Для `0x4C` регистрация задаёт 48 элементов размером элемента `0x160`, максимум данных записи — `0x158`. Это совпадает с полным пакетом построителя `0x311B6B8`; поле LCD-флага находится в `пакет+0x64`.
5. По `0x4C` найдено 86 прямых вызовов публикации в блоке 1 и одно чтение: `0x31053F8`, функция `0x3105390`. Далее данные применяются в коде MOVDC.
6. Записей с постоянными ID и прямыми вызовами API, но без найденной регистрации с постоянным ID: 8 для записи и 1 для чтения. Они могут регистрироваться через динамические аргументы; эти совпадения не следует считать доказанным несоответствием.
7. `0x14CF45C` — подписка с обратным вызовом. Найдено 11 вызовов: постоянные ID `0x3E8` (2 раза), `0x6` и `0x1E`; остальные 7 используют ID, не восстановленный как константа. Ни один из трёх постоянных ID подписки не совпал с постоянными ID регистрации.
8. По заданным настройкам фокуса прямой путь через публикацию/чтение записей не обнаружен. Путь `TARGET_*` заканчивается локальными полями состояния и журналированием; скрытый путь через динамический ID или непрозрачное поле не исключён.
9. Для большинства записей код устанавливает размер и адреса вызовов, но не смысловую подсистему: одних ID и функций регистрации недостаточно для присвоения имени. Полные функции, вызовы и дескрипторы приведены в JSON.

## Объём и способ проверки

Сопоставлены прямые вызовы четырёх API в блоках 0–2, регистрации через `0x14CEDAC` в блоках 0–1, аргументы дескрипторов и постоянные ID прямых публикаций/чтений. Для RPC `0x14CF45C` отдельно разобраны ID, вызывающая функция и обратный вызов. Сервисная сторона взята из U1: резолвер `0x5460C`, основной обработчик `0x54354`, вторичный маршрут `0x546C8`, таблица записей `0x630170`. Камера не использовалась.

В поле регистрации первый элемент дескриптора читается как число элементов, второй — как размер элемента. Это подтверждается инструкциями `0x14CEDAC`, которые сохраняют размер элемента и вычисляют объём выделения. `0x14CF124` загружает этот размер и сравнивает размер публикуемых данных с размером элемента за вычетом 8 байт. Поэтому ниже показаны обе величины: размер зарегистрированного элемента и доступный размер данных. Для слотов короче 8 байт поле максимального размера данных оставлено неустановленным из-за поведения вычитания в коде.

Прямой писатель/читатель в таблице означает ближайшую функцию, которая вызывает соответствующий API. В JSON для каждой записи сохранены все адреса вызовов и функций; счётчики в отчётной таблице нужны для обзора. Назначение записи отдельной подсистеме помечено только там, где оно подтверждено цепочкой данных.

## Настройки фокуса

Проверены `FOCUS_MODE 0x8C0`, `FOCUS 0x6FB`, `DETECT_SUBJECT 0x620`, `FACEDETECT 0x618`, `EYE_AF 0x61C`, `AFC_SET_CALL 0x70D`, `TARGET_* 0x710–0x723`, `PRE_AF 0x1E2`, `Performance 0x5BA–0x5BE`.

У функций чтения AF-C `0x1338C70/0x1338C9C/0x1338CC8` и обработчиков `0x12F0BD4/0x12F0C6C/0x12F0D04` прямых вызовов `0x14CF124` или `0x14CF354` нет. Обработчики обновляют локальные значения `0x2680474/0x2680478/0x268047C` и могут отправлять уведомления в журнал. В списке регистраций и RPC-подписок совпадения с этими функциями/ID не установлены. Это доказывает отсутствие прямого пути в просмотренном коде, но не исключает непрозрачное поле записи или динамический ID вне сопоставленного вызова.

## Подтверждённая цепочка `0x4C`

```text
Съёмочный контекст и оценщик LCD
  → построитель полного пакета 0x311B6B8
  → публикация 0x14CF124(ID=0x4C, размер данных 0x158)
  → объект записи в динамической таблице сервиса 0x630170
  → чтение 0x31053F8 → 0x14CF354
  → обработчик MOVDC → состояние LCD-защиты
```

Дескриптор регистрации `0x311B7C4` вызывает `0x14CEDAC` с ID `0x4C`, числом элементов `0x30` и размером элемента `0x160`. `0x14CEDAC` передаёт ID и описание в `0x4BC90`; при отсутствии объекта `0x4BC90` вызывает `0x4BBD4`, который записывает указатель в `0x630170 + 8×(ID−1)`. Предел данных `0x160−8=0x158` совпадает с размером полного пакета в `0x311B6B8`; это подтверждает согласованность регистрации и публикации. Поле `пакет+0x64` переносит флаг LCD, а чтение выполняется внутри цикла обработки записи `0x3105390`.

## Неустановленные связи и ограничения

- 15 регистраций имеют вычисляемый ID. Их аргументы и дескрипторы перечислены в `registered_records.json`, но поиск по коду не свёл все ID к значениям.
- Среди прямых публикаций с константным ID есть восемь ID без найденной константной регистрации; одно чтение также не сопоставлено с регистрацией. Возможная причина — динамический ID, другой путь инициализации или непросмотренная косвенная регистрация.
- Подсистемы для остальных записей не назначались по одному лишь диапазону адресов, похожим размерам или соседству вызова. Нужна дальнейшая трассировка полей и потребителей; списки функций уже сохранены для выбора следующих кандидатов.
- ID RPC `0x3E8`, `0x6`, `0x1E` не совпали с постоянными регистрациями. Подписка не означает автоматически, что обратный вызов читает тот же объект через `0x14CF354`; это отдельный механизм уведомлений.

## Что это даёт для будущих доработок прошивки

1. Для каждой постоянной записи можно менять или проверять дескриптор на основании пары «число элементов — размер элемента», а допустимый размер публикации сверять с ограничением размером элемента за вычетом 8 байт.
2. Для `0x4C` теперь разделены три размера: зарегистрированный элемент `0x160`, максимальные данные `0x158` и выделение массива `0x4380` байт при 48 элементах. Подменять один размер другим нельзя.
3. Чтобы определить назначение неизвестной записи, начинайте с соответствующих адресов писателей/читателей из JSON и прослеживайте формирование и использование полей; таблица регистрации сама по себе семантику не задаёт.
4. Для AF дальнейший поиск по коду стоит продолжить по динамическим регистрациям/ID и за границей блоков, поскольку доказанной прямой связи с текущими AF-C обработчиками нет.
