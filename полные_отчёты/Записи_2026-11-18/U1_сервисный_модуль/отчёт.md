# U1. Сервисный модуль и хранилище записей X-H2 5.30

## Краткие выводы

1. Сервисный модуль – участок DAT `0x60274..0x7E5B4`, загруженный по VA `0x40000`; размер участка `0x1E340`, вход `0x58420` (**Д**, метаданные заголовка и код входа).
2. Вход `0x58420` выполняет начальную настройку исключений и процессорных режимов, затем передаёт управление через `0x5B308`/`0x45728`. Это загрузчик и инфраструктурный модуль, а не часть блока настроек UI (**Д**).
3. В участке найдено 476 адресов стандартного пролога `stp x29,x30,[sp,#-N]!`. Это число уверенно распознаваемых начал функций, но не точный общий счёт: функции без такого пролога и совпадения в данных этим подсчётом не исключены (**Д** для подсчёта шаблона, К для полного числа функций).
4. `0x5460C` проверяет диапазон ID `1..0x7FFE`, затем ищет запись в таблице указателей `0x630170 + 8*(id−1)`. Число активных элементов читается из поля около `0x5E2F8`; таблица и её элементы – данные памяти во время работы, а не встроенный список ID (**Д**).
5. Код описывает несколько раздельных хранилищ: записи, скалярные значения, объекты/очереди обмена и кольцевой журнал. У них отдельные таблицы и резолверы; смешивать их ID и размеры нельзя (**Д**).
6. Для записи `0x4C` внешний построитель передаёт пакет размером `0x158`; поле LCD-защиты лежит в пакете по `+0x64`. Это подтверждает размер конкретного пакета, но не раскрывает полный перечень дескрипторов и не доказывает, что `0x158` – объявленный размер записи во всех контекстах (**Д`/`К`, см. ограничения ниже).
7. Подписки/уведомления поддерживаются: обработчик `0x54354` связывает объект записи с двусвязным списком ожидания и запускает задачу ожидания; при изменении он использует callback/публикацию. Это механизм времени выполнения, а не простое чтение статической ячейки (**Д** для механизма списка и запуска, К для полной семантики публикации).
8. В журнале `0x57670` записи кладутся в кольцевую область с шагом `0x10`; при заполнении индекс циклически обновляется. Прямой связи этой функции с банком настроек `0x12768` не найдено (**Д** для кольцевой структуры, Д для отсутствия прямой ссылки в проверенном модуле).
9. По статическому коду модуля не восстановить конечную таблицу всех ID и размеров: они регистрируются в динамической памяти другими участками прошивки. Для связи с резервной копией DOTLCD требуется проследить внешнего писателя/читателя или проверить фактический цикл выключения; вывод из одного загрузчика не устанавливает этот путь (**Д** о динамическом источнике таблицы, Г о связи с резервной копией).

## Метод и границы

Использованы только DAT 5.30 и распакованные блоки прошивки, уже находящиеся в рабочей папке. Сырые блоки и резервные копии не изменялись; камеру не подключал. Для VA загрузчика использована уже проверенная привязка: смещение DAT `0x60274` соответствует VA `0x40000`, размер `0x1E340`. Анализ выполнен штатными помощниками `q3common.py` и `fwcommon.py`; воспроизводимый файл исследования – `analyze_u1.py`, выдержки – `дизассемблирование.txt`.

Уровни: **Д** – прямо следует из кода/таблиц; **К** – сильное, но неполное толкование; **Г** – гипотеза, для которой нужна внешняя проверка.

## Карта узлов

| VA | Назначение | Что подтверждено |
|---:|---|---|
| `0x58420` | Вход загрузчика | Настраивает векторы исключений EL1–EL3, переключает стек/режим и переходит в стартовую последовательность (**Д**). |
| `0x4A458`, `0x4A588`, `0x4A684`, `0x4A780` | Входы диспетчеризации/обработки запросов | Синхронизация через общий замок, проверка структуры и передача разным обработчикам. В `0x4A458` принимается структура с полями `type` по `+0`, указателем по `+0x10`, и двумя значениями по `+0x18/+0x20`; проверяются `type & ~7 == 0` и согласованность двух значений. Реализация для разных групп уходит в `0x4B9B0`, `0x4BBD4`, `0x4BDAC`, `0x4C090` (**Д** для проверок/переходов, К для названий операций). |
| `0x5460C` | Резолвер записи по ID | Проверяет допустимый диапазон, количество и наличие дескриптора; вызывает основной путь `0x54354` (**Д**). |
| `0x54354` | Основной путь записи/чтения/подписки | Находит объект записи в `0x630170[id−1]`; обрабатывает ожидающие запросы и связанный список, завершает ожидания при публикации (**Д** для таблицы и очереди). |
| `0x546C8` | Вторичный маршрут записи | Работает с той же таблицей указателей, проверяет состояние объекта, связывает запрос/контекст ожидания и запускает обработчик (**Д**). |
| `0x50D94` | Скалярный резолвер | Отдельная таблица `0x630940`; возвращает два поля скалярного объекта. Это не таблица записей (**Д**). |
| `0x50E64` | Второй скалярный/массивный маршрут | Использует другую таблицу `0x970910`; передаёт структуру с размером и указателем на массив (**Д**). |
| `0x57670` | Журнал | Формирует запись журнала и помещает её в кольцевую область, размер шага записи `0x10`; индекс ограничен ёмкостью и заворачивается (**Д**). |

Счётчик `0x5E2F8` и таблица `0x630170` используются как изменяемое состояние: в исходном участке нет последовательности готовых пар `ID → размер`. Статические функции регистрации принимают ID и описание от вызывающей подсистемы, выделяют/сохраняют объект и записывают указатель в таблицу. Следовательно, фактический набор зависит от последовательности инициализации клиентов и не может быть выведен только из бинарного участка загрузчика (**Д**).

## Типы запросов и диспетчеризация

Обработчики около `0x4A458` проверяют младшие три бита поля `type`: значения вне `0..7` отклоняются. В показанном коде это битовое поле/флаги, а не законченный `switch` с понятными именами восьми команд. Для `0x4A458` указатель `+0x10` обязателен; поля `+0x18` и `+0x20` проходят парную проверку границ; затем структура передаётся обработчику после получения замка (**Д**). Поэтому именовать значения 0–7 как отдельные команды без анализа каждого вызывающего кода нельзя.

Внешняя RPC-обёртка `0x14CF45C` из блока 0 действительно заполняет тип `2`, кладёт адрес функции обратного вызова и ID, затем вызывает `0x4A458`; среди проверенных вызовов это путь подписки/уведомления, не синхронное изменение значения (**Д**, согласуется с 11 вызовами обёртки и их аргументами в ранее подготовленной разведке Q3). Остальные маршруты `0x4A588/0x4A684/0x4A780` используют разные таблицы/обработчики и не должны автоматически считаться типами записи.

## Дескрипторы и известные ID

### Что хранится

Резолвер `0x5460C` использует ID как индекс в таблице указателей: `descriptor = *(0x630170 + 8*(id−1))`. Рядом проверяется максимальный зарегистрированный индекс из `0x5E2F8`. Для скалярных объектов применяются другие таблицы (`0x630940`, `0x970910`). Само содержимое дескриптора не является плоской статической записью в DAT: указатели и объекты создаются при регистрации.

### Восстановленный список

| ID | Известный размер/описание | Основание и уровень |
|---:|---|---|
| `0x4C` | Пакет записи: `0x158` байт; поле LCD-защиты находится в `+0x64`. Полный размер/флаги динамического дескриптора отдельно не восстановлены. | Построитель `0x311B6B8/0x311B788` в блоке 1, вызов API записи `0x14CF124`; **Д** для пакета/смещения, **К** для тождества пакета и полного размера записи. |

Это не полный реестр ID. В загрузчике нет статических ID-записей, а регистрации вызываются из других подсистем с параметрами, сформированными во время запуска. Чтобы получить полный список всех фактически активных записей и их размеров, нужно собрать все места регистрации API по блокам 0–1, восстановить потоки аргументов каждого места и сопоставить выделенный размер с ID; для окончательной проверки нужен дамп таблицы `0x630170` вместе с объектами в рабочем состоянии. Текущий анализ не выдаёт этот результат за завершённый.

Операции записи и чтения проходят через резолвер и объект дескриптора. Объекты умеют держать контексты ожидания в связном списке; при публикации/изменении сервис будит ожидающий поток или вызывает зарегистрированный обратный вызов (**Д** для связанного списка и постановки задачи, К для универсальности поведения во всех видах записей). Подписка отдельным RPC-путём подтверждена для ID `0x3E8`, `6`, `0x1E` и других ID из 11 вызовов `0x14CF45C`; `0x4C` среди этих подписок не найден (**Д** по проверенным вызовам).

## Сохранение во флеш-память и связь с банком `0x12768`

В изученном участке загрузчика не найдено прямой ссылки на `0x12768` и не найден явный вызов функции, которая записывает сервисную таблицу в банк настроек. Резолверы работают с таблицами указателей и объектами, выделяемыми во время исполнения; журнал тоже ведётся в кольцевой оперативной области. Это указывает на механизм обмена данными в памяти, но не доказывает, что отдельные клиенты никогда не сохраняют собственные значения во флеш-память (**Д** для проверенного участка, К для вывода о назначении хранилища).

Связь между `DOTLCD_*`, записью `0x4C`, моментом выключения и резервной копией пока не установлена этим исследованием. Известный путь `0x4C` переносит LCD-флаг внутри пакета, но это само по себе не является записью во флеш-память. Наблюдение «значение появляется в резервной копии после выключения» требует отдельного поиска по вызывающему модулю сохранения/энергосбережения и сопоставления с фактической копией; текущая статическая проверка не даёт основания приписывать это сервису записей (**Г** для возможной связи).

## Что это даёт для будущих доработок прошивки

1. Для изменения обмена между подсистемами сначала надо найти регистрацию нужного ID у клиента, а затем проверить дескриптор и читателей; поиск только в загрузчике не раскрывает активный список.
2. Изменение `0x4A458` влияет на общий путь запросов и синхронизацию. Перед изменением важно определить тип и структуру запроса у конкретного вызывающего кода; тип `2` уже используется как путь обратного вызова.
3. Для изменения LCD-флага подтверждён пакет `0x4C` и смещение `+0x64`; изменение этой записи не доказывает сохранение настройки. Путь во флеш-память/резервную копию следует искать отдельно в модуле выключения или сохранения пользовательских настроек.
4. Не заменять динамическую таблицу `0x630170` догадочным жёстким перечнем. Для каталога всех записей нужен охват клиентских регистраций и, если доступно, снимок таблицы из памяти камеры; камеру в этой задаче не использовал.
